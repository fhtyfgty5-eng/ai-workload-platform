# ADR-0003：控制面运行期故障采用安全退出

- 状态：已批准，待实现验证
- 日期：2026-08-21
- 适用范围：模块 2 单控制面协调者的运行期数据库与 Advisory Lock 故障

## 背景

模块 2 使用 PostgreSQL Advisory Lock 保证同一数据库在同一时刻只有一个控制面实例负责恢复和执行 Run。Advisory Lock 绑定数据库会话：连接断开时 PostgreSQL 会自动释放锁。

如果旧进程失去数据库连接，它当前无法确认锁是否仍由自己持有。此时新进程可能已经连接数据库并取得锁。若旧进程仍继续接收请求或启动外部任务，就可能出现两个协调者同时工作。仅在启动时取得一次锁，不能覆盖这一运行期故障。

另一个边界是，数据库故障、进程关闭与用户取消不是同一件事。基础设施故障不应把 Run 写成 `canceled`；数据库最后一次成功提交的非终态状态必须保留，以便新进程恢复。

## 决策

模块 2 的控制面采用 fail-stop 策略：持锁专用连接周期性检查数据库可用性和锁所有权。一旦检查失败，或受监督的 `Engine.Execute/Resume` 返回系统错误，进程立即进入不可就绪状态，中断本机执行，停止 HTTP 服务并以错误退出。

原进程不尝试重新连接数据库或重新取得丢失的 Advisory Lock。数据库恢复后，通过人工、进程管理器、Docker 或未来 Kubernetes 启动一个新进程。新进程重新执行迁移检查、取得锁、扫描 PostgreSQL 中的非终态 Run，并按至少执行一次语义恢复。

安全退出只中断本机 Executor 和等待，不写入用户取消。显式取消仍由取消 API 持久化 `cancel_requested_at`，并由 Engine 收敛到 `canceled`。

进程收到正常退出信号时也会中断本机执行，但这种清理不报告为运行期故障；重启后仍从 PostgreSQL 的最后一次成功提交状态恢复。

## 原因

- 失去持锁连接后，旧进程已经没有可靠证据证明自己仍是唯一协调者；
- 在同一进程重新取得锁会掩盖一段所有权不明的时间，期间可能已有新协调者接管；
- PostgreSQL 是模块 2 的事实状态来源，停止旧进程再从已提交状态恢复，语义最清楚；
- 模块 2 是单实例阶段，安全优先于故障期间的无感可用性；
- 该策略便于通过停库、重启和恢复实验验证，也能与未来 Docker/Kubernetes 的进程重启机制衔接。

## 未选择方案

### 同一进程自动重连并重新加锁

优点是数据库短暂恢复后服务可以自行继续。未选择它，因为旧进程无法证明断连期间没有其他实例取得锁；重新加锁前后的活动任务所有权也需要额外 fencing 机制，模块 2 尚未具备这一能力。

### 只把 `ready` 设为 false，进程继续存活

优点是保留诊断入口。未选择它，因为正在运行的 Engine 和 Executor 仍可能继续产生外部副作用，且部署系统可能不会重启一个仍然存活的进程。

### 连续多次失败后再退出

优点是可以容忍偶发探测错误。未选择它，因为一次连接错误已经意味着会话锁可能释放；在没有租约或 fencing token 的前提下继续执行会扩大双协调者风险。

### 立即把活动 Run 标记为 canceled

优点是数据库状态看起来快速收敛。未选择它，因为基础设施中断不是用户意图，而且故障发生时数据库可能不可写。Run 应保留最后一次成功提交的非终态状态，由新进程把遗留的 running Attempt 识别为 interrupted 后恢复。

## 结果与代价

- 单实例阶段发生数据库或锁故障时会有一段服务不可用时间；
- 没有外部进程管理器时，需要人工重启控制面；
- 运行期 Context 中断和业务取消必须在 Engine 内部分开；
- 所有异步 Execute/Resume 错误必须被监督，不能丢弃；
- 启动恢复必须异步接管，不能等待每个 Run 执行到终态；
- 周期检查存在最长一个检查周期的发现窗口，本决策不提供严格 fencing 或多实例高可用承诺；
- 至少执行一次恢复可能重复外部副作用，任务仍需使用幂等接口或业务去重。

## 验证

本决策至少通过以下证据验证：

1. 单元测试证明锁检查或 Engine 系统错误会令 `ready=false`，取消其他本机执行并只报告一次致命错误；
2. Engine 测试证明父 Context 中断不写 `canceled`，显式 `Engine.Cancel` 仍写业务取消；
3. PostgreSQL 集成测试证明专用连接持锁检查、第二实例拒绝和锁失效检测；
4. 进程测试证明致命错误会停止 HTTP 服务并错误退出；
5. 用户手动停止 PostgreSQL，观察旧进程安全退出，再恢复数据库并重启验证非终态 Run 恢复。
