# ADR-0002：产品定位与模块路线调整

- 状态：已批准，包含 2026-08-14 后续补充决策
- 日期：2026-08-14
- 替代范围：部分替代 ADR-0001 的产品表述和原 10 模块路线，不否定可靠工作流内核主线

## 背景

模块 0 完成后，项目已经说明了工作流、DAG、状态机和可靠执行的基础概念。模块 1 的设计进一步确认，可靠性、恢复语义和性能基准必须先在单机内核中验证。

重新审视原路线时发现三个问题：

- “面向 AI 与数据任务”覆盖面过宽，外部读者难以判断项目究竟提供什么产品；
- 原模块 2 直接进入自然语言生成工作流，但控制面 API、持久化数据库和 Agent 的运行边界尚未建立；
- 容器、Kubernetes、Agent 适配、案例和产品化相距较远，容易形成多个功能都有但缺少完整证据链的展示项目。

项目还需要同时满足系统学习、求职作品和未来 GitHub 开源三个目标，因此路线必须优先形成一个可以运行、测试、复现故障并解释架构取舍的成熟最小产品。

## 决策

项目定位调整为：

> 面向 Agent 与确定性程序任务的可靠运行时和调度平台。

“确定性程序任务”是指在相同输入和环境下，主要执行路径与结果可以由程序规则明确判断的任务，例如数据清洗、索引构建和批量计算。Agent 任务会调用模型和工具，结果、耗时与失败方式具有更强的不确定性。平台不负责替代这些任务的业务逻辑，而是统一管理它们的依赖、状态、重试、恢复、权限和执行证据。

项目路线调整为 8 个模块，编号为模块 0 至模块 7：

1. 项目定义与文档基线；
2. 单机可靠工作流内核；
3. 控制面 API 与持久化存储；
4. Agent Runtime、模型与工具执行；
5. 多 Worker、租约、心跳与故障恢复；
6. 可观测性、故障注入与性能验证；
7. 受限执行环境与 Kubernetes；
8. 真实场景、最小控制台与开源发布。

Agent Runtime 是 Agent Runtime Environment 的简称，中文可称为“Agent 运行时环境”。它负责为 Agent 准备模型、工具、上下文、权限、预算和取消信号，并把执行过程转换为平台可以持久化和审计的结构化事件。普通程序执行器与 Agent Runtime 共用工作流可靠性内核，但不强行使用相同的内部实现。

自然语言生成工作流草稿不再是独立的早期模块，但确定为模块 3 的必做最小产品演示能力。它必须建立在结构化工作流提交、校验、执行和审计边界之上，不能提前改变模块 1 和模块 2 的依赖顺序，也不能绕过用户确认直接执行。

## 原因

- 单机内核、持久化控制面、Agent 执行和多节点恢复之间的依赖顺序更清楚；
- 控制面 API 和数据库不再隐藏在“产品化”阶段，能够尽早形成可使用的服务边界；
- Agent 不只是一个模型接口适配器，而是具有工具、权限、预算、取消和审计边界的运行对象；
- 性能基准从模块 1 开始建立，可观测性模块负责形成系统化证据而不是第一次关注性能；
- 容器隔离与 Kubernetes 放在同一阶段，减少两次基础设施迁移；
- 最终通过真实场景、快速开始、控制台和公开材料验证产品价值，而不是依赖功能清单宣称优势。
- 自然语言到结构化工作流的演示能让用户直观看到 Agent Runtime、校验器和可靠内核如何协作，但演示必须以可验证的结构化结果为终点，不能以模型输出“看起来合理”为验收标准。

## 未选择方案

### 保留原 10 个模块

优点是文档改动少。未选择它，因为自然语言能力早于运行基础，控制面和数据库缺少独立验收点，容器与 Kubernetes 又被拆得过远。

### 压缩为 6 个大模块

优点是路线看起来更短。未选择它，因为单个模块会同时包含多个可独立失败的系统，难以进行 TDD、用户审核、学习复盘和清晰提交。

### 只做通用工作流引擎

优点是范围更小。未选择它，因为无法验证 Agent 权限、工具调用、预算和人工介入等项目希望学习的 AI Infra 问题，也难以体现与现有通用调度项目的方向差异。

### 只做 Agent 编排框架

优点是更贴近当前 AI 热点。未选择它，因为项目的主要技术价值来自可靠执行、持久化和故障恢复；只强调 Agent 编排容易弱化分布式系统深度，并与现有模型 SDK 或图编排框架直接重叠。

## 代价

- 项目仍然跨越工作流、分布式系统、Agent、容器和 Kubernetes，必须严格控制每个模块范围；
- Agent Runtime 会引入模型供应商差异、工具安全和成本管理，需要 Mock 与人工触发的真实模型测试分离；
- 控制面和持久化提前后，需要更早设计 API 兼容性、事务和幂等边界；
- 8 个模块并不保证形成市场优势，差异化仍要通过真实使用、故障报告和性能数据验证；
- 路线调整会使早期文档和 Git 历史保留旧表述，需要通过 ADR 和文档导航解释演进过程。

## 不变边界

- 模块 0 仍然完成；
- 模块 1 的任务标识、DAG 编译、状态机、重试、取消、恢复、文件存储和性能验证设计保持不变；
- 不自研大模型、数据库、容器运行时或 Kubernetes；
- 不承诺安全执行任意恶意代码；
- 不为了覆盖简历关键词提前引入消息队列、缓存或协调服务；
- 未经用户审核，不自动提交 Git、创建 Pull Request 或公开仓库。

## 后续验证

每个实现模块至少提供：

- 一个可运行入口；
- 自动化测试；
- 至少一个失败或恢复场景；
- 与该模块风险相匹配的性能或资源数据；
- 架构取舍和未选择方案；
- 可从 README 或示例目录复现的使用方法。

如果真实场景不能证明 Agent 与普通程序共用可靠执行内核带来实际价值，应重新评估产品定位，而不是继续增加功能。

## 后续补充决策（2026-08-14）

用户确认自然语言转工作流对于产品演示和理解项目价值很重要，因此将其从“可选能力”调整为模块 3 的必做最小能力。

模块 3 至少需要完成以下流程：

```text
自然语言目标
  -> Agent 生成结构化工作流草稿
  -> 标记用户事实、Agent 假设和待确认问题
  -> 依赖、参数、权限和资源校验
  -> 用户修改并确认
  -> 提交给可靠工作流内核执行
```

自动化测试使用 Mock Model（模拟模型，用固定结果模拟模型响应），不访问外部网络。演示可以人工触发一个合法模型适配器，但必须设置预算、低并发和明确的用户确认步骤。草稿生成失败、校验失败、用户拒绝和模型超时都必须有可解释结果。

这项调整增加的是模块 3 的产品展示和输入路径，不改变模块 1 的可靠性边界，也不把自然语言生成误认为完整的 Agent 产品或安全策略。
