# 项目本地运行、演示与换电脑手册

本文是 AI Workload Platform 的项目级运行入口，目标是在一台新的 Mac mini M4 上，从零准备环境、拉取代码、启动当前完整系统，并完成一次可重复演示。项目后续增加 Agent Runtime、自然语言工作流、多 Worker、可观测性、受限任务执行和控制台后，本文会同步更新，不会停留在模块 2。

当前已验证范围：

| 项目 | 当前状态 |
| --- | --- |
| 目标电脑 | Mac mini M4，Apple Silicon ARM64 |
| 最新已验证模块 | 模块 7 自然语言 Draft、浏览器控制台、Workflow/Run 闭环与开源治理 |
| 当前推荐演示 | 浏览器完成草稿生成、服务端校验、人工确认、Run 启动和 Task/Event 观测；模块 6 受限执行仍作为独立路径 |
| 尚未包含 | 真实 Agent 任务执行环境、生产级多租户沙箱、长期观测后台；模块 6 的部分资源和网络实验仍未完成 |
| 最后验证日期 | 2026-08-26 浏览器闭环、Go/前端测试、文档和安全检查通过 |

Mac mini M4 使用 Apple Silicon，即 ARM64 指令架构；本文的 Docker Desktop 安装流程已经在同架构的 macOS 上实际验证。后续章节凡是标记“当前”的内容，描述的是上表所列最新模块，而不是项目最终能力。

代码、迁移脚本、`compose.yaml` 和示例来自 Git。数据库内容、Token、密码和日志属于本机数据，不提交到仓库。

## 如何使用本文

本文保留为项目唯一的完整运行入口，不要求先阅读其他部署文档。当前有两条演示路径：产品闭环展示自然语言草稿如何经过确认进入可靠工作流，模块 6 沙箱闭环展示固定 Action 如何在 Docker 或 Kubernetes 的受限环境中执行。当前自然语言草稿不会自动改写为 `executor=container`，因此两条路径需要分别运行。

| 目的 | 阅读顺序 |
| --- | --- |
| 新电脑首次安装 | 第 2 至 8 节完成工具、项目、数据库和配置准备，再按第 9、10 节启动和演示 |
| 已安装环境的日常启动 | 第 6 节启动 PostgreSQL，第 7 节加载配置，第 9 节启动控制面和 Worker |
| 完整产品闭环演示 | 第 9 节准备四个终端，再执行第 10 节；需要故障证据时继续执行第 10.4 节 |
| 模块 6 Docker 沙箱演示 | 第 9 节启动基础服务，再执行第 12.1、12.2 节 |
| 模块 6 Kubernetes 补充演示 | 安装 kind/kubectl 后执行第 12.3 节；Worker 路径为可选项 |
| Worker 故障接管演示 | 先完成第 9 节和第 10.3 节，再执行第 10.4 节 |
| 查看指标、Trace 和实验 | 先完成第 9 节，再阅读第 11、12 节 |
| 排查本机问题 | 先查看第 15 节，再回到对应安装或启动章节 |

第 2 至 8 节多数操作只需在新电脑首次准备时执行。`cp .env.example .env.local`、安装软件和生成 Token 不属于每次启动步骤；日常启动不要覆盖已经配置好的 `.env.local`。

## 1. 当前已验证的运行架构

模块 7 完成后的运行关系如下：

```text
macOS
  |-- Agent CLI、Runtime、Mock Model 和只读任务目录：本机进程
  |-- Go 控制面、Dispatch Coordinator、Metrics 和告警规则：本机进程
  |-- workload-worker：本机独立进程，可选择 mock、docker 或 kubernetes 执行器
  |-- workload CLI：本机进程
  |-- React/Vite 控制台：本机开发服务器，通过代理访问控制面
`-- Docker Desktop 的 Linux 虚拟机
        |-- PostgreSQL 16：Docker 容器
        |     `-- 数据：Docker 数据卷
        `-- 模块 6 可选：Docker Engine 受限任务容器，或 kind 集群中的 Job/Pod
```

Docker Compose 当前只负责提供 PostgreSQL 开发数据库。它不负责运行 Go 控制面或 Worker，也不表示工作流任务已经容器化或进入安全沙箱。

Trace stdout 导出和 Webhook 接收器都属于可选本地进程，不由 Docker Compose 启动。当前没有 Prometheus、Grafana、Jaeger 或 Tempo 服务；`/metrics` 和 stdout Span 是应用侧观测出口，不是完整监控后台。模块 6 的任务容器也不由 Docker Compose 启动，而是由 Worker 通过 Docker Engine API 或 Kubernetes API 按 Attempt 创建。

**Mock Executor（模拟执行器）** 是用确定结果代替真实业务动作的测试执行器。它现在运行在独立 Worker 进程中。当前演示会完整推进工作流状态，但不会真的清洗文档、调用模型或执行定义中的命令。

## 2. 检查电脑架构和基础工具

打开 macOS 的“终端”应用，运行：

```bash
# 查看当前 Mac 的 CPU 指令架构；Mac mini M4 应输出 arm64。
uname -m

# 确认 Git 已经安装，并查看当前版本。

```

Mac mini M4 的 `uname -m` 应输出 `arm64`。首次运行 `git` 时，如果系统提示安装 Command Line Tools，按提示完成安装后重新执行。**Command Line Tools** 是 Apple 提供的一组命令行开发工具，其中包含 Git 和编译所需的基础工具。

## 3. 安装 Homebrew、Go 和 jq

**Homebrew** 是 macOS 上常用的软件包管理器，可以用命令安装和升级开发工具。先检查是否已经安装：

```bash
# 检查 Homebrew 是否已经安装；能输出版本号就不需要重复安装。
brew --version
```

若命令不存在，先核对 [Homebrew 官方安装页](https://brew.sh/) 的当前说明，再执行其官方安装命令：

```bash
# 从 Homebrew 官方地址下载安装脚本，并交给 Bash 执行。
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

安装程序可能要求输入当前 macOS 管理员账户的登录密码；终端输入密码时不会显示字符或星号，这是正常行为。Apple Silicon Mac 默认把 Homebrew 安装到 `/opt/homebrew`。安装器结束时会显示 **Next steps**，按提示把 Homebrew 加入 Shell 环境；默认使用 zsh 的新电脑通常执行：

```bash
# 把 Homebrew 的环境初始化命令写入 zsh 登录配置；这一行通常只执行一次。
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile

# 让当前终端立即加载 Homebrew 环境，不必关闭后重新打开终端。
eval "$(/opt/homebrew/bin/brew shellenv)"

# 确认当前终端已经可以找到 Homebrew。
brew --version
```

第一行只需执行一次；它让以后新开的终端也能找到 `brew`。第二行让当前终端立即生效。如果安装器给出的路径或命令与这里不同，以安装器的 **Next steps** 为准。

安装 Go：

```bash
# 安装 Go；HOMEBREW_NO_AUTO_UPDATE=1 表示本次安装前不自动更新 Homebrew 仓库。
HOMEBREW_NO_AUTO_UPDATE=1 brew install go

# 确认 Go 已经安装，并检查版本和 darwin/arm64 架构信息。
go version
```

项目当前使用 Go 1.26 或兼容版本。Mac mini M4 上的输出应包含 `darwin/arm64`。如果仓库以后调整 Go 版本要求，以根目录 `go.mod` 和 `README.md` 为准。

安装并验证 `jq`：

```bash
# 安装 jq；演示流程使用它查看 JSON 并提取草稿哈希。
HOMEBREW_NO_AUTO_UPDATE=1 brew install jq

# 确认 jq 已经安装并输出版本号。
jq --version
```

**jq** 是在命令行读取、筛选和格式化 JSON 的工具。模块 3 的草稿查看、内容哈希提取和模块 4 的完整演示都会使用它，因此它是演示工具而不是可选依赖。

## 4. 安装 Docker Desktop

**Docker Desktop** 在 macOS 上提供 Docker 命令行客户端、Docker Engine、Docker Compose、Linux 虚拟机和 Dashboard。当前项目需要它来运行 PostgreSQL 容器。

### 4.1 已验证的 Homebrew 安装方式

先单独下载并校验安装包，再执行安装。这样网络中断时更容易重试：

```bash
# 单独下载并校验 Docker Desktop 安装包；下载中断时可以重新执行。
HOMEBREW_NO_AUTO_UPDATE=1 brew fetch --cask --retry docker-desktop

# 使用已经下载的安装包，把 Docker Desktop 安装到 Applications。
HOMEBREW_NO_AUTO_UPDATE=1 brew install --cask docker-desktop

# 启动 Docker Desktop；首次启动需要在界面中完成许可和系统授权。
open -a Docker
```

安装过程中出现 `Password:` 时，输入当前 macOS 管理员账户的登录密码。终端不会回显密码，输入后按回车即可。

如果 Homebrew 提示其他第三方 Tap 不受信任，但最后显示 `docker-desktop was successfully installed!`，说明这些警告没有阻止 Docker Desktop 安装。不要为了安装 Docker 而直接信任无关的整个 Tap，也不要关闭 Homebrew 的 Tap 信任检查。

首次启动 Docker Desktop 时，按界面完成许可确认和必要的系统授权，等待菜单栏 Docker 图标显示 Engine 已经运行。Docker 账号登录可以跳过：当前项目使用公开 PostgreSQL 镜像，登录不是本地运行的前置条件。

### 4.2 官方安装包备用方式

如果 Homebrew 下载持续失败，从 [Docker Desktop for Mac 官方安装页](https://docs.docker.com/desktop/setup/install/mac-install/) 下载 Apple Silicon 版本，打开 DMG 并把 Docker 拖入 Applications，然后启动 Docker。不要下载 Intel 芯片版本。

### 4.3 验证客户端、Engine 和 Compose

Docker Desktop 完全启动后运行：

```bash
# 同时检查 Docker 命令行客户端和 Docker Engine；输出中应同时有 Client 和 Server。
docker version

# 检查 Docker Compose 是否可用并查看版本。
docker compose version
```

`docker version` 应同时显示 Client 和 Server。只有 Client 通常表示命令已经安装，但 Docker Desktop 或 Engine 尚未启动。Apple Silicon Mac 上常见的架构信息是：

```text
Client OS/Arch: darwin/arm64
Server OS/Arch: linux/arm64
```

客户端运行在 macOS，服务端运行在 Docker Desktop 的 Linux 虚拟机中，所以两者的操作系统不同是正常现象。`docker compose version` 有版本输出，表示 Compose 可用；文档不要求固定的 Docker Desktop 小版本。

### 4.4 模块 6 的 kind 和 kubectl

`kubectl` 是 Kubernetes 的命令行客户端，`kind` 用 Docker 容器创建本地 Kubernetes 集群。模块 6 的 Docker 路径不依赖它；只有要验证 Kubernetes Job/Pod 时才安装：

```bash
# 安装 Kubernetes 命令行客户端和本地 kind 集群工具；只执行一次。
HOMEBREW_NO_AUTO_UPDATE=1 brew install kubectl kind

# 确认两个命令已经安装。
kubectl version --client
kind version
```

如果 Homebrew 下载 kind 或 Kubernetes 节点镜像失败，先处理网络或镜像源问题；不要把“命令已安装”误认为“集群已经创建”。

## 6. 启动 PostgreSQL

确保 Docker Desktop 已启动，然后运行：

```bash
# 根据 compose.yaml 在后台创建或启动 PostgreSQL 服务。
docker compose up -d postgres

# 查看 Compose 服务状态；等待 postgres 的健康状态变为 healthy。
docker compose ps
```

`docker compose up` 会读取仓库的 `compose.yaml`；`-d` 表示在后台运行；`postgres` 是 Compose 服务名。第一次运行时，Docker 会下载公开的 `postgres:16.10-bookworm` 镜像并创建容器和数据卷，不需要登录 Docker 账号。

等待 `docker compose ps` 中 PostgreSQL 状态变为 `healthy`。当前端口映射为本机 `127.0.0.1:5432` 到容器 `5432`，数据库默认只接受本机连接。

查看启动日志：

```bash
# 查看 PostgreSQL 最近 100 行日志，用于确认数据库已经可以接受连接。
docker compose logs --tail=100 postgres
```

日志出现 `database system is ready to accept connections` 表示 PostgreSQL 已经可以连接。

## 7. 创建本机配置和 Token

从公开模板创建不会提交的本地配置：

```bash
# 从公开模板创建本机配置；-n 会在文件已存在时拒绝覆盖。
cp -n .env.example .env.local
```

如果 `.env.local` 已经存在，`cp -n` 会保留原文件。不要为了重新运行文档而删除或覆盖其中已经生成的 Token。

生成三个彼此不同的随机 Token：

```bash
# 生成第一个 64 位十六进制随机字符串，填写为 WORKLOAD_VIEWER_TOKEN。
openssl rand -hex 32

# 再生成一个不同的随机字符串，填写为 WORKLOAD_OPERATOR_TOKEN。
openssl rand -hex 32

# 第三次生成独立字符串，填写为 WORKLOAD_WORKER_BOOTSTRAP_TOKEN。
openssl rand -hex 32
```

把三次输出分别填入 `.env.local` 的 `WORKLOAD_VIEWER_TOKEN`、`WORKLOAD_OPERATOR_TOKEN` 和 `WORKLOAD_WORKER_BOOTSTRAP_TOKEN`。viewer 只能查询，operator 可以创建和取消，bootstrap Token 只允许 Worker 注册；三者不能相同。每台新电脑都必须重新生成这三个 Token，Git 只保存不可用占位值。`DATABASE_URL` 中的开发数据库密码与 `compose.yaml` 一致，只用于绑定在本机回环地址的开发环境，不能照搬到公开或生产部署。

可以使用任意文本编辑器打开 `.env.local`。除了上面三个 Token，默认离线演示直接保留模板中的 `DATABASE_URL`、`WORKLOAD_HTTP_ADDR`、Worker 参数和空的 `WORKLOAD_MODEL_*`；不要把 Token 粘贴到命令行参数、截图或 Git 文件中。真实模型不是默认演示的前置条件，只有准备好个人服务地址和 API Key 时才填写对应变量。

项目不会自动读取 `.env.local`。在当前终端加载配置：

```bash
# 让随后读取的变量自动导出给当前终端启动的子进程。
set -a

# 在当前终端读取 .env.local；该操作不会影响其他终端窗口。
source .env.local

# 关闭变量自动导出，避免后续普通 Shell 变量都被自动导出。
set +a
```

`set -a` 会把随后读取的变量自动导出给子进程；`source` 在当前 Shell 中执行文件；`set +a` 关闭自动导出。每个新终端窗口都需要重新执行这三行。

## 8. 执行数据库迁移

```bash
# 把尚未执行的数据库迁移按顺序应用到本地 PostgreSQL。
go run ./cmd/workload-server migrate up
```

**数据库迁移（Database Migration）** 是按版本修改数据库表、索引和约束的 SQL。项目使用显式迁移命令，服务启动时只检查结构是否完整，不会自动修改数据库。新电脑或新数据卷第一次运行时必须执行；重复执行已应用的迁移应保持安全。

## 9. 启动和检查控制面

从本节开始会同时使用多个终端。各终端职责固定如下：

| 终端 | 职责 | 是否持续占用 |
| --- | --- | --- |
| A | 运行 `workload-server` 控制面 | 是 |
| B | 执行健康检查、CLI 和查询命令 | 否 |
| C | 运行第一个 `workload-worker` | 是 |
| D | 运行第二个 `workload-worker` | 是 |

每个终端都必须进入项目根目录。环境变量只在当前终端及其子进程中有效，不会自动从另一个终端同步。

把运行控制面的终端称为**终端 A**。在终端 A 已经进入项目根目录并加载 `.env.local` 后运行：

```bash
# 启动控制面服务；命令会持续占用终端 A，演示期间不要关闭。
go run ./cmd/workload-server
```

看到 `workload server ready` 后保持该进程运行。另开一个终端作为**终端 B**，进入同一个项目根目录并检查：

```bash
# 检查服务进程是否存活；成功时返回 {"status":"live"}。
curl -fsS http://127.0.0.1:8080/health/live

# 检查数据库、迁移、协调锁和后台分发循环是否已经就绪。
curl -fsS http://127.0.0.1:8080/health/ready
```

`live` 只表示进程存活；`ready` 还要求数据库和迁移可用、进程持有 PostgreSQL Advisory Lock，并且后台分发与回收循环已经启动。初次扫描在后台进行，因此 `ready` 不表示所有 `ready` Task 已经创建 Dispatch，也不表示已经存在可用 Worker。第二个控制面实例会因 Advisory Lock 已被占用而退出，这是当前单协调器边界，不是高可用机制。

### 9.1 准备操作终端

终端 B 的健康检查不需要认证，但后续 Worker 查询和控制面 CLI 都需要 Token。在执行任何认证请求前，先在终端 B 加载配置并选择 operator Token：

```bash
# 把 .env.local 中的配置导出给终端 B 后续启动的 CLI 和 curl。
set -a
source .env.local
set +a

# 控制面 CLI 统一读取 WORKLOAD_TOKEN；这里选择拥有写权限的 operator Token。
export WORKLOAD_TOKEN="$WORKLOAD_OPERATOR_TOKEN"

# 只检查服务地址和 Token 是否已加载，不打印凭据内容。
test -n "$WORKLOAD_SERVER_URL" && echo 'WORKLOAD_SERVER_URL 已加载' || echo 'WORKLOAD_SERVER_URL 未加载，请停止并检查配置'
test -n "$WORKLOAD_TOKEN" && echo 'WORKLOAD_TOKEN 已加载' || echo 'WORKLOAD_TOKEN 未加载，请停止并检查配置'
```

只有最后两行都显示“已加载”时才继续。关闭终端 B 或重新打开窗口后，需要重新执行本小节。

### 9.2 启动两个独立 Worker

网络控制面不再执行任务。把运行第一个 Worker 的终端称为**终端 C**，进入项目根目录并加载本机配置，然后覆盖该进程的显示名称和并发槽位：

```bash

set -a
source .env.local
set +a

# 为第一个 Worker 设置唯一显示名称，并允许同时执行两个 Mock 任务。
export WORKLOAD_WORKER_NAME='worker-a'
export WORKLOAD_WORKER_CONCURRENCY='2'

# 启动第一个独立 Worker；命令会持续占用终端 C。
go run ./cmd/workload-worker
```

另开**终端 D**，同样进入项目根目录、加载 `.env.local`，再启动名称不同的第二个 Worker：

```bash
# 在终端 D 单独加载配置；环境变量不会从终端 C 自动同步。
set -a
source .env.local
set +a

# 为第二个 Worker 设置不同名称和两个并发槽位。
export WORKLOAD_WORKER_NAME='worker-b'
export WORKLOAD_WORKER_CONCURRENCY='2'

# 启动第二个独立 Worker；命令会持续占用终端 D。
go run ./cmd/workload-worker
```

两个进程启动后，在已经配置 `WORKLOAD_TOKEN` 的终端 B 查询 Worker 摘要：

```bash
# 查询已注册 Worker、会话状态和活动租约数；响应不会返回任何令牌。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workers"
```

预期能看到 `worker-a` 和 `worker-b`，状态为 `active`。同名进程再次启动会创建新会话，不会覆盖旧会话；正常退出时，有活动租约的 Worker 会先进入 `draining`，完成已有任务后进入 `stopped`，没有活动租约则直接进入 `stopped`。未正常退出且超过离线阈值的旧会话会显示 `offline`。

## 10. 完整演示项目：文档处理与摘要工作流

本节是一条从用户目标到可靠执行结果的完整演示主线。它使用“读取文章、清洗内容、生成摘要”作为公开示例，把 Agent 的自然语言规划、人工确认、可靠工作流、多 Worker 执行和运行观测串成一个可重复项目。默认使用 Mock Model 和 Mock Executor，因此不需要购买模型服务，也不会执行本机命令或访问外部业务系统。

### 10.0 演示项目说明

**项目目标：** 证明平台能够把一句自然语言目标转换为经过校验的结构化 Workflow，在用户确认后创建不可变版本并启动 Run；执行过程中由独立 Worker 领取任务，控制面和 PostgreSQL 保存状态，浏览器展示任务和事件结果。

**示例输入：**

> 先读取 article.md，再清洗内容，最后生成摘要。

这句话会生成三个有依赖关系的任务：`read -> clean -> summarize`。后一个任务只有在前一个任务成功后才会进入可执行状态。Mock Executor 返回确定的模拟结果，所以“成功”表示平台的调度、状态保存和页面展示链路成功，不表示真的读取或修改了 `article.md`。

**参与组件：**

| 组件 | 在演示中的职责 |
| --- | --- |
| React/Vite 控制台 | 输入自然语言目标，展示 Draft，提交校验和确认请求，显示 Run、Task 和 Event |
| Go 控制面 | 校验 Draft，创建不可变 Workflow，持久化 Run 状态，生成 Dispatch 并提供查询 API |
| PostgreSQL | 保存 Workflow、Run、Task、Attempt、Event、Worker 会话和租约等业务事实 |
| 两个 Worker | 注册能力、领取 Dispatch、执行 Mock Action、发送心跳并提交结果 |
| Mock Model | 用固定响应模拟模型规划和只读工具调用 |
| Mock Executor | 用确定结果模拟任务执行，不执行 Action 中的本机命令 |

**终端安排：**

| 终端 | 运行内容 | 演示期间是否保持运行 |
| --- | --- | --- |
| A | `workload-server` 控制面 | 是 |
| B | 健康检查、浏览器前置检查、CLI 和 API 查询 | 否 |
| C | 第一个 `workload-worker` | 是 |
| D | 第二个 `workload-worker` | 是 |
| 浏览器 | Vite 控制台 | 是 |

**完整执行顺序：**

1. 按第 2 至 8 节准备 Go、Node.js、Docker Desktop、PostgreSQL、`.env.local` 和三个不同的 Token。
2. 按第 9 节启动 PostgreSQL、迁移、控制面和两个 Worker，确认 `/health/ready` 返回 `{"status":"ready"}`，两个 Worker 都是 `active`。
3. 按第 18.1 节启动 Vite，在浏览器打开终端输出的地址，选择 `operator` 并输入本机 operator Token。
4. 在控制台输入示例目标，点击“生成草稿”和“校验草稿”，检查三个任务、依赖、事实、假设、问题、校验结果和内容哈希。
5. 点击“确认并启动运行”。控制台先确认 Draft，再创建 Workflow 版本并启动 Run；同名 Workflow 已存在时会创建新的不可变版本。
6. 在 Run 详情页等待 `succeeded`，确认三个 Task 成功、事件时间线出现分发/领取/完成事件；需要查看 Attempt 历史时使用控制面 Task 详情 API。
7. 如果要展示分布式执行，再按第 10.3 节运行四路并行 DAG；如果要展示故障恢复，再按第 10.4 节强杀持租约 Worker，等待第二个 Worker 接管。
8. 演示结束按第 14 节停止服务；保留数据库数据可复用下一次演示，确认不再需要时再清理数据卷。

**成功判据：**

- Draft 状态经过校验后才允许确认，存在阻塞错误或未解决问题时确认按钮不可用；
- Workflow 创建成功后版本不可变，重复请求不会静默覆盖定义；
- Run、Task、Attempt 和 Event 的最终状态来自控制面和 PostgreSQL，而不是浏览器内存；
- 至少一个 Worker 领取并完成任务，控制面本身不执行网络 Run；
- 浏览器关闭后，已提交的 Run 仍可通过服务端查询；
- Mock 演示不会调用真实模型、执行任意 Shell、访问外部网络或改变宿主机文件。

第 10.1 节至第 10.6 节分别给出 CLI Draft 文件检查、控制面提交、多 Worker 并行、Worker 故障接管、协调锁检查和可选真实模型验证。10.1、10.2 是浏览器闭环之外的 CLI 等价路径，便于单独检查中间文件；它们与第 18.2 节的浏览器操作使用同一套后端能力，不是互相独立的产品。

### 10.1 CLI 生成、校验与确认（可选路径）

这一阶段只需要 Go，不需要启动 Docker、PostgreSQL 或控制面。它用于单独检查 Draft JSON 的生成、校验和哈希确认，不是浏览器产品闭环的必经步骤；浏览器操作见第 18.2 节。**Mock Model（模拟模型）** 用固定响应复现模型与工具调用协议，因此不消耗模型额度，也不把网络波动混入演示。

先创建 Git 已忽略的本地演示目录：

```bash
# 创建模块 3 演示文件目录；.workload 已被 Git 忽略，不会提交生成结果。
mkdir -p .workload/agent-demo
```

从自然语言目标生成草稿：

```bash
# 使用离线 Mock Model 生成结构化草稿，并把完整审核对象写入本地文件。
go run ./cmd/workload agent draft \
  '先读取 article.md，再清洗内容，最后生成摘要' \
  --model mock \
  --output .workload/agent-demo/draft.json

# 查看草稿中的定义、事实、假设、待确认问题和只读工具调用记录。
jq '.' .workload/agent-demo/draft.json
```

`Fact（事实）` 在这里表示直接来自用户输入的陈述，并不表示平台已经访问外部系统核实。`Assumption（假设）` 是模型为补齐输入而推断的内容。`Question（待确认问题）` 是必须解决后才能确认的缺失信息。

校验草稿：

```bash
# 校验 Action、Input 参数、权限、任务超时、Agent Workflow 并发和 DAG，并输出新的已校验草稿。
go run ./cmd/workload agent validate \
  .workload/agent-demo/draft.json \
  --output .workload/agent-demo/validated.json

# 查看 errors、warnings、needs_confirmation 状态和确认所需的 content_hash。
jq '{status,content_hash,validation,facts,assumptions,questions,tool_calls}' \
  .workload/agent-demo/validated.json
```

`content_hash` 是对用户实际审核内容计算的 SHA-256 哈希。SHA-256 是一种摘要算法：输入变化时摘要也会变化。这里用它检测“审核后、确认前”草稿是否被修改，不用于隐藏草稿内容。

确认并输出最终 WorkflowDefinition：

```bash
# 用 jq 从已校验草稿读取哈希，保存到当前终端变量。
DRAFT_HASH="$(jq -r '.content_hash' .workload/agent-demo/validated.json)"

# 确认当前文件仍与审核时一致，并只输出最终结构化 WorkflowDefinition。
go run ./cmd/workload agent confirm \
  .workload/agent-demo/validated.json \
  --hash "$DRAFT_HASH" \
  --output .workload/agent-demo/workflow.json

# 查看最终定义；此时尚未创建控制面资源，也没有启动 Run。
jq '.' .workload/agent-demo/workflow.json
```

预期最终定义包含 `read -> clean -> summarize` 三个任务。校验警告提示存在 Agent 假设，但用户显式确认后可以输出定义；如果存在未解决问题、校验错误或哈希不匹配，`confirm` 会拒绝。

### 10.2 CLI 确认结果提交给控制面（可选路径）

如果选择上一节的 CLI 路径，继续使用已经按照第 9.1 节加载配置的终端 B。浏览器闭环不需要执行本节，因为控制台会在确认后自动调用相同的创建和启动 API。先重新检查当前窗口仍然具有所需变量：

```bash
# 检查服务地址是否已加载；应输出 WORKLOAD_SERVER_URL 已加载。
test -n "$WORKLOAD_SERVER_URL" && echo 'WORKLOAD_SERVER_URL 已加载' || echo 'WORKLOAD_SERVER_URL 未加载，请停止并检查配置'

# 检查 CLI Token 是否已加载，但不输出 Token；应输出 WORKLOAD_TOKEN 已加载。
test -n "$WORKLOAD_TOKEN" && echo 'WORKLOAD_TOKEN 已加载' || echo 'WORKLOAD_TOKEN 未加载，请停止并检查配置'
```

只有两行都显示“已加载”时才继续。如果变量为空，回到第 9.1 节重新加载，不要只重试业务命令。否则 CLI 会在发送 HTTP 请求之前报告 `WORKLOAD_SERVER_URL and WORKLOAD_TOKEN are required`；该错误不会创建 Workflow，也不会修改数据库。

先查询 `agent-document-pipeline` 是否已经存在：

```bash
# 只查询 Workflow 是否存在，并输出 HTTP 状态码；这条命令不会创建或修改数据。
curl -sS -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workflows/agent-document-pipeline"
```

返回 `200` 表示 Workflow 已存在，直接复用 version 1，不再执行创建命令。返回 `404` 才执行一次初始化创建：

```bash
# 仅当上一条查询返回 404 时，才提交刚刚确认的最终定义。
go run ./cmd/workload workflow create .workload/agent-demo/workflow.json \
  --idempotency-key 'manual-workflow-agent-document-pipeline-v1'
```

创建命令使用稳定的幂等 Key。同一调用者使用相同 Key 和相同定义重试时会返回第一次创建的资源；不能每次为同一个 Workflow ID 换新 Key，否则数据库已有该 Workflow 时会返回 `409 workflow_exists`。查询返回 `401`、`500`、`503` 或其他状态时，应先检查 Token、服务日志和 `ready`，不能把它当作“不存在”继续创建。

Workflow 准备好后，为本次演示生成新的后缀并启动一次 Run：

```bash
# 生成精确到秒的后缀，让本次 Run 使用新的幂等 Key。
DEMO_SUFFIX="$(date +%Y%m%d%H%M%S)"

# 启动 agent-document-pipeline v1，并把 CLI 返回的 JSON 保存到当前终端变量。
START_OUTPUT="$(go run ./cmd/workload run start agent-document-pipeline --version 1 --idempotency-key "manual-agent-run-$DEMO_SUFFIX")"

# 打印启动结果，便于人工确认其中的 run_id 和初始状态。
printf '%s\n' "$START_OUTPUT"

# 从启动结果中提取 run_id，保存为后续查询使用的当前终端变量。
DEMO_RUN_ID="$(printf '%s\n' "$START_OUTPUT" | sed -nE 's/.*"run_id":"([^"]+)".*/\1/p')"
```

确认上一组命令已经提取出 `DEMO_RUN_ID`，再查询：

```bash
# 通过 CLI 查询本次 Run 的整体状态。
go run ./cmd/workload run status "$DEMO_RUN_ID"

# 通过 API 查询该 Run 下全部任务的状态和执行次数。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "http://127.0.0.1:8080/api/v1/runs/$DEMO_RUN_ID/tasks"
```

Run 最终应进入 `succeeded`，三个任务均成功。Workflow 初始化重试要复用原来的稳定幂等 Key；想创建新的 Run 时才换一个 Key。网络控制面只创建 Dispatch 和推进状态，安全 Mock Executor 运行在终端 C、D 的独立 Worker 中；它只返回模拟结果，不会执行定义中的 Action、调用模型或访问外部服务。

### 10.3 两个 Worker 并行执行

终端 C、D 的两个 Worker 保持运行。在终端 B 先查询模块 4 示例 Workflow 是否存在：

```bash
# 只查询模块 4 并行示例是否存在；返回 200 表示可以直接复用 version 1。
curl -sS -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workflows/module4-parallel-demo"
```

只在返回 `404` 时初始化 Workflow；返回其他状态时先排查认证或服务状态：

```bash
# 仅在查询返回 404 时创建模块 4 并行示例的不可变 version 1。
go run ./cmd/workload workflow create examples/module4-parallel-workflow.json \
  --idempotency-key 'manual-workflow-module4-parallel-demo-v1'
```

为本次演示创建新 Run，并保存 Run ID：

```bash
# 生成本次演示专用幂等 Key 后缀。
PARALLEL_SUFFIX="$(date +%Y%m%d%H%M%S)"

# 启动包含四个并行上游任务和一个 merge 下游任务的 Run。
PARALLEL_OUTPUT="$(go run ./cmd/workload run start module4-parallel-demo --version 1 \
```

### 10.4 强杀 Worker、租约回收与第二 Worker 接管

这个实验需要让 Worker A 执行足够长，才能在租约有效期间强制终止进程。先在终端 C、D 对当前 Worker 按 `Ctrl+C`，等待它们完成 drain 并退出。然后在终端 C 构建独立二进制，并以 20 秒 Mock 延迟启动 Worker A；PID 写入 Git 已忽略的 `.workload` 目录，便于从另一个终端精确强杀目标进程：

```bash
# 构建可精确定位 PID 的本地 Worker 二进制。
mkdir -p .workload/bin
go build -o .workload/bin/workload-worker ./cmd/workload-worker

# 加载配置，并让 Worker A 的 Mock 任务持续 20 秒。
set -a
source .env.local
set +a
export WORKLOAD_WORKER_NAME='worker-crash-a'
export WORKLOAD_WORKER_CONCURRENCY='1'
export WORKLOAD_MOCK_EXECUTION_DELAY='20s'

# 后台启动 Worker A，保存准确 PID，再让终端等待该进程。
.workload/bin/workload-worker &
WORKER_A_PID=$!
printf '%s\n' "$WORKER_A_PID" > .workload/worker-crash-a.pid
wait "$WORKER_A_PID"
```

在终端 D 启动无延迟的接管 Worker B：

```bash
# 加载相同服务和 bootstrap Token，但使用不同 Worker 名称。
set -a
source .env.local
set +a
export WORKLOAD_WORKER_NAME='worker-recovery-b'
export WORKLOAD_WORKER_CONCURRENCY='1'
export WORKLOAD_MOCK_EXECUTION_DELAY='0s'

# 启动等待接管任务的 Worker B。
go run ./cmd/workload-worker
```

在终端 B 创建新的并行示例 Run，并等待 Worker A 出现活动租约：

```bash
# 创建本次故障实验的 Run，并提取 Run ID。
RECOVERY_SUFFIX="$(date +%Y%m%d%H%M%S)"
RECOVERY_OUTPUT="$(go run ./cmd/workload run start module4-parallel-demo --version 1 \
  --idempotency-key "worker-recovery-run-$RECOVERY_SUFFIX")"
printf '%s\n' "$RECOVERY_OUTPUT"
RECOVERY_RUN_ID="$(printf '%s\n' "$RECOVERY_OUTPUT" | sed -nE 's/.*"run_id":"([^"]+)".*/\1/p')"

# 查询 Worker 摘要；重复执行，直到 worker-crash-a 的 active_leases 大于 0。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workers"
```

确认 Worker A 已持有租约后，在终端 B 强制终止它。`SIGKILL` 不会执行 drain，才能模拟进程崩溃：

```bash
# 读取终端 C 保存的准确 PID，先显示目标，再发送不可捕获的 SIGKILL。
WORKER_A_PID="$(cat .workload/worker-crash-a.pid)"
printf '即将强制终止 worker-crash-a，PID=<%s>\n' "$WORKER_A_PID"
kill -9 "$WORKER_A_PID"
```

默认租约为 15 秒，控制面每秒扫描一次。等待租约过期并由 Worker B 接管后查询结果：

```bash
# 重复查询，直到 Run 最终进入 succeeded。
go run ./cmd/workload run status "$RECOVERY_RUN_ID"

# 查看全部 Task，找到包含 interrupted 和后续 succeeded Attempt 的任务。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/runs/$RECOVERY_RUN_ID/tasks"

# 再查询 Worker 会话，确认旧 Worker 最终为 offline，新 Worker 保持 active。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workers"
```

至少一个被 Worker A 领取的 Task 应出现 Attempt 1 `interrupted`、Attempt 2 `succeeded`，Run 最终为 `succeeded`。旧租约在回收后提交会得到 `409 lease_lost`；自动化测试会保存并重放旧令牌验证这一点，人工演示不把租约明文写入终端或文件。

### 10.5 单实例协调锁检查与历史恢复证据

模块 4 之后，网络 Run 的任务只由独立 Worker 执行。模块 2 曾使用控制面内 Mock Executor 完成数据库中断恢复实验，但依赖 `workload-server` 中 `WORKLOAD_MOCK_EXECUTION_DELAY` 的旧命令已经失效，不应再作为当前演示执行。历史环境、步骤和结果保存在[模块 2 验证报告](../实验/模块2验证报告.md)；当前故障演示使用上一节的 Worker 强杀与租约接管。

Advisory Lock 单实例检查仍然有效。先保持终端 A 的控制面运行，再另开一个**终端 E**进入项目根目录，加载配置并尝试启动第二个控制面：

```bash
# 让 .env.local 中的变量导出给即将启动的第二个控制面进程。
set -a

# 在终端 E 单独读取配置；环境变量不会从终端 A 或 B 自动同步过来。
source .env.local

# 关闭变量自动导出。
set +a

# 尝试启动第二个控制面；预期因协调锁已被终端 A 中的实例持有而失败退出。
go run ./cmd/workload-server
```

因为第一个控制面已经持有 PostgreSQL Advisory Lock，第二个进程应报告锁已被占用并以非零状态退出。这证明当前是单协调者设计，不表示已经具备高可用。

### 10.6 可选的真实模型人工验证

**Model Adapter（模型适配器）** 把平台统一的 `ModelRequest` 和 `ModelResponse` 转换成模型服务的 HTTP JSON。当前实现不绑定供应商 SDK；服务必须支持 Chat Completions 风格的 `model`、`messages`、`tools` 和 JSON Schema `response_format`。工具调用后的下一轮会发送 assistant `tool_calls` 历史和带 `tool_call_id` 的 `role=tool` 结果消息。

真实模型不是默认演示前置条件。只有准备好合法服务地址、模型名和个人 API Key 时才配置。把下面三项填写到本机 `.env.local`，不要把真实值写进 `.env.example`、命令历史、截图或 Git：

```dotenv
WORKLOAD_MODEL_ENDPOINT=https://合法供应商提供的完整接口地址
WORKLOAD_MODEL_NAME=供应商模型标识
WORKLOAD_MODEL_API_KEY=只保存在本机的API-Key
```

远程服务地址必须使用 `https://`。`http://` 只允许 `localhost`、`127.0.0.1` 或 `::1` 等本机回环地址，供本地模型和自动化测试使用；适配器不会自动跟随 HTTP 重定向，避免 Bearer API Key 被转发到其他地址。

每台新电脑都需要重新创建 `.env.local` 并填入自己的合法配置。Git 只保存空占位和变量名称，不会同步凭证。加载配置后人工运行：

```bash
# 把 .env.local 的可选模型配置导出给当前终端启动的 CLI。
set -a
source .env.local
set +a

# 只检查三个变量是否非空，不打印 API Key 或完整服务地址。
test -n "$WORKLOAD_MODEL_ENDPOINT" && \
test -n "$WORKLOAD_MODEL_NAME" && \
test -n "$WORKLOAD_MODEL_API_KEY" && \
echo '真实模型配置已加载' || echo '真实模型配置不完整，请停止'

# 显式选择 http 模型适配器；不写 --model http 时仍使用离线 Mock Model。
go run ./cmd/workload agent draft \
  '先读取 article.md，再清洗内容，最后生成摘要' \
  --model http \
  --output .workload/agent-demo/real-model-draft.json
```

CLI 不会记录 API Key，也不会把供应商类型写入公开 Agent 接口。真实调用仍受 4 轮模型、8 次工具、64 KiB 响应、30 秒 Runtime 总时限和 5 秒工具单次时限约束。供应商是否支持这里使用的 Chat Completions 工具消息与 JSON Schema 结构化输出，需要在实际选定供应商后单独验证；模块 3 的默认自动化测试只使用本地 HTTP 模拟服务。

## 11. 查看模块 5 观测数据

模块 5 的日志、指标和调用链都是诊断数据，不会代替 PostgreSQL 中的 Workflow、Task、Attempt、Dispatch 和租约状态。

### 11.1 查看 Prometheus 指标

先在执行查询的终端加载本地环境变量，确保地址和 viewer Token 可用：

```bash
set -a
source .env.local
set +a
export WORKLOAD_SERVER_URL="http://127.0.0.1:8080"
```

然后读取只读指标入口。服务端要求 viewer 或 operator Token；返回内容中不会使用 RunID、TaskKey、WorkerID 或 DispatchID 作为标签：

```bash
curl -fsS -H "Authorization: Bearer $WORKLOAD_VIEWER_TOKEN" \
  "$WORKLOAD_SERVER_URL/metrics"
```

Prometheus 文本中，名称以 `_total` 结尾的通常是累计计数器，Gauge 表示当前值，Histogram 会产生 `_bucket`、`_sum` 和 `_count` 三类序列。`workload_db_pool_wait_seconds_total` 只累加相邻 pgx 连接池快照的等待时长增量，不会把累计值重复相加。当前项目只提供标准文本出口，不要求安装 Prometheus 或 Grafana。

### 11.2 输出本地调用链

控制面和独立 Worker 默认都关闭 Trace 导出。`off` 使用不采样 Provider，不创建可记录 Span；`stdout` 只用于本地人工检查。

在控制面终端设置以下变量并重启 `workload-server`，Span 元数据会写入该终端：

```bash
export WORKLOAD_TRACING_MODE=stdout
export WORKLOAD_TRACING_SERVICE_NAME=workload-server
go run ./cmd/workload-server
```

Worker 不读取控制面的 `WORKLOAD_TRACING_MODE`，而是使用专用变量，避免同一份 `.env.local` 让所有进程意外同时输出大量 Span。在每个 Worker 终端设置以下变量并重启 `workload-worker`：

```bash
export WORKLOAD_WORKER_TRACING_MODE=stdout
export WORKLOAD_WORKER_TRACING_SERVICE_NAME=workload-worker
go run ./cmd/workload-worker
```

输出只包含 Trace ID、Span ID、操作名和状态，不包含 Token、完整任务输入或结果。Worker Client 发出的 HTTP Trace Context 会传播到控制面，使同一次 Claim、Heartbeat 或 Complete 请求的客户端和服务端 Span 保持父子关系。Run 创建和稍后异步执行之间没有持久化 Trace Context，不能声称整条 Run 自动属于一条 Trace。演示结束后把两种 tracing mode 都恢复为 `off`，避免终端输出影响性能观察。

### 11.3 本地 Webhook 告警

只有配置 `WORKLOAD_ALERT_WEBHOOK_URL` 时才启动告警采集和发送。URL 必须是没有内嵌用户名或密码的 HTTP(S) 地址；空值表示关闭通知。Webhook 只接收告警名称、状态、摘要、时间、规则版本和有限标签；标签仅允许固定的 `component`、`severity` 键和值，任意业务 ID 或凭据会被过滤。超时、网络错误和 5xx 使用有限重试，4xx 不重试。

换电脑时不需要迁移旧 Webhook 配置。根据新电脑上的本地接收器重新填写 `.env.local`，不要把真实通知地址提交到 Git。

### 11.4 观测故障排查

- `/metrics` 返回 `401`：当前终端没有加载 viewer/operator Token，或请求使用了 Worker Token；
- `/metrics` 返回 `404`：当前启动的服务没有启用模块 5 Metrics 组件，检查是否运行了最新代码；
- 控制面没有 Span 输出：确认 `WORKLOAD_TRACING_MODE=stdout` 并重启服务；
- Worker 没有 Span 输出：确认 `WORKLOAD_WORKER_TRACING_MODE=stdout` 并重启对应 Worker；
- Webhook 没有通知：确认 URL、接收器进程和告警持续时间，单次短暂抖动不会立即触发；
- Webhook 变慢：通知使用有界异步队列，不应阻塞工作流状态和租约；日志会记录通知失败或队列已满；
- 指标中找不到单个 Run：这是低基数设计，单 Run 使用状态 API、日志和 Trace 查询。

### 11.5 运行模块 5 实验脚本

以下命令都在仓库根目录执行。先加载 `.env.local`，再把 `DATABASE_URL` 映射为测试夹具使用的 `TEST_DATABASE_URL`；测试会创建并清理隔离数据库，不会复用业务数据库中的表。

运行单 Worker、单 Run、1,000 任务的关闭观测基线，并把完整输出保存到临时证据目录：

```bash
set -a
source .env.local
set +a
export TEST_DATABASE_URL="$DATABASE_URL"
scripts/run-module5-benchmark.sh --workers 1 --runs 1 --observability off --output-dir /tmp/ai-workload-module5-evidence
```

`--workers` 只能是 `1`、`4` 或 `16`，`--runs` 只能是 `1` 或 `8`，`--observability` 支持 `off`、`logs`、`logs_metrics` 和 `logs_metrics_tracing`。脚本默认先预热 1 轮，再正式运行 5 轮；`--iterations 1` 只用于快速检查脚本，不作为正式结论。脚本会记录 Go、操作系统、CPU、Compose 镜像和基准原始输出。

模块 5 已在 Mac mini M4 上完成 1/4/16 Worker、1/8 Run 和四种观测配置共 24 个组合的正式五轮对照。汇总、离群值和结论见[模块 5 验证报告](../实验/模块5验证报告.md)；临时原始输出不会随 Git 克隆到新电脑，换电脑后如需重新取证，应使用本节脚本生成新的本机结果。

运行一个故障场景并保存原始输出：

```bash
scripts/run-module5-faults.sh --scenario worker-kill --output-dir /tmp/ai-workload-module5-evidence
```

`worker-kill` 会启动两个测试子 Worker，真正强杀第一个进程，并验证第二个进程接管；测试结束会清理子进程。`pool-exhaustion` 使用真实 pgx 单连接池。`claim-delay`、`complete-error`、`heartbeat-error`、`coordinator-lock` 和 `postgres-unavailable` 使用构造函数传入的一次性故障计划；其中 `postgres-unavailable` 不会停止共享 Docker PostgreSQL，只验证 Repository 调用方遇到一次错误后的恢复边界。`lease-expiry` 使用真实租约过期和迟到结果请求。

脚本不会停止、重启或删除 Docker 容器，也不会复用现有业务表；测试夹具会创建并清理隔离数据库。物理停止 PostgreSQL、网络分区和数据库崩溃恢复不在该脚本的已验证范围内。

## 12. 模块 6 受限执行演示

模块 6 的任务容器不是 `docker compose up` 自动启动的服务。它由 Worker 在领取到 `executor=container` 的 Attempt 后，通过 Docker Engine API 或 Kubernetes API 按需创建；PostgreSQL 仍然保存 Run、Attempt、Dispatch 和租约事实。

### 12.1 构建并验证固定动作镜像

在项目根目录运行：

```bash
# 编译 Linux ARM64 的固定动作二进制，构建本地 workload-action 镜像，并运行一次受限动作。
bash scripts/run-module6-docker.sh
```

脚本不会拉取基础镜像，也不会执行用户传入的 Shell。它使用仓库内固定的 `document.normalize` 动作，并设置非 root、只读根文件系统、无网络、无提权、删除 capability、CPU/内存/PID 和临时存储上限。输出最后的镜像 ID 用于验证当前构建结果。

### 12.2 让 Docker Worker 执行容器任务

先按照第 9 节启动 PostgreSQL、控制面和迁移。第 9.2 节启动的 Mock Worker 可以继续运行，但它只会领取 `executor=mock` 的任务，不会领取模块 6 的 container 任务。另开一个 Worker 终端，加载配置并明确选择 Docker 运行时：

```bash
# 加载本机配置；环境变量只对当前终端生效。
set -a
source .env.local
set +a

# 选择 Docker 执行器和仓库内固定动作镜像；不要改成任意镜像或命令。
export WORKLOAD_WORKER_RUNTIME=docker
export WORKLOAD_WORKER_ACTION_IMAGE=workload-action:local
export WORKLOAD_WORKER_NAME=worker-docker

# 启动能够创建受限 Docker 容器的 Worker；它会注册 mock 和 container 两种能力。
go run ./cmd/workload-worker
```

保持这个 Worker 终端运行，在操作终端先构建镜像，再创建并启动模块 6 示例 Workflow：

```bash
# 确保本机固定动作镜像已经存在；重复执行是幂等的本地构建操作。
bash scripts/run-module6-docker.sh

# 让控制面编译并保存带 container Executor 的 Workflow v1；幂等 Key 使用本次演示的固定值。
export WORKLOAD_TOKEN="$WORKLOAD_OPERATOR_TOKEN"
go run ./cmd/workload workflow create examples/module6-container-workflow.json --idempotency-key module6-container-workflow-v1

# 为本次演示生成新的 Run 幂等 Key；同一个固定 Key 重复执行只会返回旧 Run。
MODULE6_SUFFIX="$(date +%Y%m%d%H%M%S)"

# 创建一次新的 Run，并把返回的 JSON 保存到当前终端变量。
MODULE6_OUTPUT="$(go run ./cmd/workload run start module6-container-demo --version 1 \
  --idempotency-key "module6-container-run-$MODULE6_SUFFIX")"
printf '%s\n' "$MODULE6_OUTPUT"

# 提取后续查询使用的 Run ID；没有提取到 ID 时立即停止，避免查询空路径。
MODULE6_RUN_ID="$(printf '%s\n' "$MODULE6_OUTPUT" | jq -r '.run_id // empty')"
test -n "$MODULE6_RUN_ID" || { echo '未能提取 MODULE6_RUN_ID，请检查启动命令输出' >&2; exit 1; }
```

使用刚刚提取的 Run ID 查询 Run 和任务详情：

```bash
# 查询模块 6 Run 的整体状态；重复执行直到状态为 succeeded。
go run ./cmd/workload run status "$MODULE6_RUN_ID"

# 查询两个 container Task 的状态、Attempt 和结构化输出。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/runs/$MODULE6_RUN_ID/tasks"

# 查询执行器 Worker，确认 worker-docker 处于 active 且声明了 container 能力。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workers"
```

预期 `normalize` 和 `summarize` 都为 `succeeded`，任务结果来自固定动作镜像。若任务保持 `ready` 或 `queued`，先确认 `worker-docker` 已注册为 `active`、终端加载了相同的 `.env.local`、镜像标签为 `workload-action:local`，并且 `WORKLOAD_WORKER_RUNTIME=docker`。第 9 节的 Mock Worker 不会执行这些 container Task。

## 13. Docker Dashboard 导览

Docker Desktop 不同版本的布局可能略有差异，但核心对象不变。

### 13.1 Containers

打开 **Containers**，可以看到以当前项目目录命名的 Compose 项目，以及其中的 `postgres` 容器。重点检查：

对应命令：

```bash
# 列出 Docker Desktop 管理的全部数据卷。
docker volume ls

# 显示当前 compose.yaml 声明的数据卷名称，便于和 Dashboard 对照。
docker compose config --volumes
```

停止或删除 PostgreSQL 容器通常不会删除这个数据卷，所以重新创建容器后原来的本地数据库仍在。删除数据卷会删除本机 PostgreSQL 数据，项目代码无法从 Git 恢复这些数据。

下面的命令会删除 Compose 容器及其数据卷，属于重置本地开发数据库的破坏性操作，本文只说明含义，不把它作为日常步骤：

```bash
# 删除当前 Compose 项目的容器、网络和数据卷；会永久清除本地 PostgreSQL 数据。
docker compose down --volumes
```

只有明确不需要本机测试数据、并准备重新执行迁移时才使用。执行前先用 `pwd` 确认位于正确项目目录。

### 13.4 Builds

**Builds** 展示根据 Dockerfile 构建自有镜像的记录。控制面和 Worker 仍是本机 Go 进程，但模块 6 已有 `deploy/module6-action/Dockerfile`；运行 `bash scripts/run-module6-docker.sh` 后，可以在 Images 看到 `workload-action:local`，Builds 中也可能出现对应构建记录。没有构建记录不影响 PostgreSQL Compose 服务运行。

## 14. 停止和下次恢复

正常停止时，先在 Worker 终端按 `Ctrl+C`。Worker 会先发送 drain 停止领取新任务，在关闭期限内继续心跳和完成已有租约，再次发送 drain 进入 `stopped`。然后在控制面终端按 `Ctrl+C`。只有故障实验才使用 `kill -9`，日常停止不要强杀。

只停止 PostgreSQL、保留数据库内容：

```bash
# 停止 PostgreSQL 容器，但保留容器、数据卷和数据库内容。
docker compose stop postgres
```

下次开发时先启动 Docker Desktop，然后在项目目录运行：

```bash
# 根据 compose.yaml 重新启动已有 PostgreSQL，缺少容器时会自动创建。
docker compose up -d postgres

# 查看服务状态，等待 postgres 变为 healthy。
docker compose ps
```

接着加载 `.env.local` 并重新启动控制面，再分别启动至少一个独立 Worker。正常停止和启动不需要重新执行迁移；只有代码引入新迁移、使用了新的数据卷，或迁移检查提示版本不完整时才执行 `migrate up`。

## 15. 常见故障排查

### 15.1 Docker Desktop 下载被重置

先重试单独下载：

```bash
# 重试下载并校验 Docker Desktop 安装包，不执行安装。
HOMEBREW_NO_AUTO_UPDATE=1 brew fetch --cask --retry docker-desktop
```

下载完成后再运行安装命令。若仍持续失败，使用 Docker 官方 Apple Silicon 安装包。`curl: (35) Recv failure: Connection reset by peer` 通常是下载连接中断，不代表 macOS 密码或 Docker 账号错误。

### 15.2 找不到 Docker 应用或只有 Client

```bash
# 尝试启动已经安装的 Docker Desktop 应用。
open -a Docker

# 检查客户端能否连接 Engine；应同时输出 Client 和 Server。
docker version
```

如果 `open` 提示找不到应用，Docker Desktop 尚未成功安装。如果 `docker version` 只有 Client 或提示无法连接 daemon，等待 Docker Desktop 完全启动；仍失败时从 Dashboard 的 Troubleshoot 查看 Engine 状态。

### 15.3 PostgreSQL 容器不健康

```bash
# 查看 PostgreSQL 容器是否正在运行以及健康检查结果。
docker compose ps

# 查看最近 200 行 PostgreSQL 日志，用于定位启动或初始化失败原因。
docker compose logs --tail=200 postgres
```

先根据日志判断是初始化、权限还是数据库启动问题。不要在没有确认数据价值前删除 Volume。

### 15.4 本机 5432 端口已被占用

```bash
# 查出当前正在监听本机 5432 TCP 端口的进程；该命令只读取信息，不会终止进程。
lsof -nP -iTCP:5432 -sTCP:LISTEN
```

常见原因是本机已安装 PostgreSQL，或另一个容器占用端口。先确认进程归属，再选择停止冲突服务；不要直接终止不认识的公司或系统进程。若要修改 Compose 端口，还必须同步修改 `.env.local` 的 `DATABASE_URL`。

### 15.5 控制面无法连接数据库

依次检查：

```bash
# 检查 PostgreSQL 容器是否运行且健康。
docker compose ps

# 只检查 DATABASE_URL 是否已加载，不打印其中可能包含的数据库密码。
test -n "$DATABASE_URL" && echo 'DATABASE_URL 已加载' || echo 'DATABASE_URL 未加载'

# 在配置和数据库正常后重试迁移，以获得具体连接或结构错误。
go run ./cmd/workload-server migrate up
```

确认当前终端已经加载 `.env.local`，PostgreSQL 为 `healthy`，URL 的主机、端口、数据库名和账号与 `compose.yaml` 一致。不要在截图或公开日志中展示真实生产密码和 Token。

### 15.6 匿名拉取失败

当前公开 PostgreSQL 镜像不要求登录。若错误明确表示 Docker Hub 匿名额度受限，可以登录个人 Docker 账号；若错误是连接重置、DNS 或超时，应先处理网络问题，登录通常无效。

### 15.7 Run 一直停在 ready 或 queued

先确认至少一个兼容 Worker 已注册且处于 `active`：

```bash
# 查询 Worker 会话和活动租约数；需要 viewer 或 operator Token。
curl -fsS -H "Authorization: Bearer $WORKLOAD_TOKEN" \
  "$WORKLOAD_SERVER_URL/api/v1/workers"
```

没有 Worker 时，Task 会保持 `ready`；有 pending Dispatch 但 Worker 没有继续领取时，Task 可能显示 `queued`。检查 Worker 终端是否报配置、认证、协议或网络错误，并确认每个 Worker 都加载了 `WORKLOAD_SERVER_URL`、`WORKLOAD_WORKER_BOOTSTRAP_TOKEN` 和唯一名称。旧会话为 `offline` 不代表新进程会自动复用它；运行中的 Worker 收到永久会话或协议错误会退出，重新启动后才会注册新会话。

## 16. 换电脑检查清单

1. 确认新电脑是 Apple Silicon，并安装 Command Line Tools、Homebrew、符合项目要求的 Go、Node.js 24 LTS、npm 和 `jq`；
2. 安装并启动 Docker Desktop，确认 `docker version` 同时有 Client 和 Server；
3. 确认 `docker compose version` 可用，Docker 登录可以跳过；
4. 配置个人 GitHub SSH Key 或使用 HTTPS 克隆仓库；
5. 进入项目目录后执行 `go mod download`，提前下载并校验 Go 依赖；
6. 执行 `docker compose up -d postgres`，等待数据库 `healthy`；
7. 从 `.env.example` 创建 `.env.local`，在新电脑重新生成 viewer、operator 和 Worker bootstrap 三个不同的 Token；
8. 加载配置，执行 `go run ./cmd/workload-server migrate up`；
9. 启动控制面并检查 `live`、`ready`；
10. 在两个终端分别启动名称不同的 `workload-worker`，查询 Worker 列表确认均为 `active`；
11. 按“当前推荐演示”先完成自然语言草稿、校验和确认，再把最终定义提交控制面并启动 Run；
12. 运行多 Worker 并行示例，并至少练习一次强杀 Worker、租约回收和第二 Worker 接管；
13. 需要真实模型人工验证时，在本机 `.env.local` 重新配置三个 `WORKLOAD_MODEL_*` 变量；不需要真实模型时保持为空；
14. 查询 `/metrics`，需要展示调用链时分别为控制面和 Worker 临时开启 stdout Trace；
15. 需要验证代码时运行 `go test ./...`；真实 PostgreSQL 测试额外设置 `TEST_DATABASE_URL`。

来自 Git 的内容包括代码、迁移、Compose 配置、环境变量模板和示例。不会来自 Git 的内容包括 Docker 镜像缓存、容器、数据卷、数据库内容、`.env.local`、Token、密码和日志。

模块 6 当前改动若仍处于本机未提交状态，新电脑从 GitHub 克隆后不会包含这些改动；必须先由作者提交并推送，再按本文复现模块 6。kind 集群和 Docker 镜像也不会随 Git 仓库同步，需要在新电脑重新创建或构建。

不要复制公司配置、Token、密码或业务数据到个人电脑和公开仓库。需要迁移个人测试数据时，使用 PostgreSQL 官方备份与恢复工具，并确认其中不含公司信息；如果只是为了重复演示，推荐在新电脑重新创建干净的本地数据库和演示数据。

## 17. 演示前检查

当前推荐演示以“自然语言草稿、可靠多 Worker 执行、故障接管和观测证据”形成一条产品闭环。不需要逐个演示历史模块；模块 5 的 24 组性能矩阵适合说明设计判断，不适合现场完整重跑。正式展示前至少完整走通一次下面的链路：

```text
输入自然语言目标
  -> Mock Model 调用只读任务目录
  -> 生成并查看事实、假设和待确认问题
  -> 校验参数、权限、任务超时、Agent Workflow 并发和 DAG
  -> 使用内容哈希确认草稿
  -> 输出最终 WorkflowDefinition
  -> 启动 Docker Desktop
  -> 启动并确认 PostgreSQL healthy
  -> 加载 .env.local
  -> 检查或执行数据库迁移
  -> 启动 workload-server
  -> 检查 live 和 ready
  -> 启动两个独立 Worker 并查询会话
  -> 创建 Workflow
  -> 启动 Run
  -> 查询 Run 和三个任务成功
  -> 查询 /metrics，确认队列、Worker、租约和协议操作指标
  -> 运行四路并行 DAG
  -> 强杀持租约 Worker
  -> 观察 interrupted Attempt、第二 Worker 接管和最终 succeeded
  -> 需要时开启 stdout Trace，解释单次 Worker HTTP 请求的父子 Span
```

不要只确认服务能启动。演示前还要确认终端字体和窗口大小便于观看、命令中没有真实密钥、幂等 Key 不会与上一次演示冲突，并准备解释 Mock Model、HTTP 模型适配器和 Mock Executor 分别模拟什么、为什么草稿不能直接执行，以及租约为什么只能拒绝旧结果而不能撤销外部副作用。

当前默认产品演示优先展示浏览器中的“自然语言生成结构化工作流草稿、校验、用户确认、Run 启动和执行观测”闭环；需要突出可靠性时，再补充多 Worker 故障接管和指标观察；Docker/Kubernetes 更适合作为专项技术演示，展示固定 Action、资源边界、部署清单和故障实验，不需要逐个演示所有历史模块。

## 18. 模块 7 浏览器控制台

### 18.1 前端依赖和开发服务器

以下命令都在项目根目录的 `web/` 中执行。`npm ci` 按 lockfile 安装与仓库一致的依赖；`npm test` 运行前端自动化测试；`npm run typecheck` 检查 TypeScript 类型；`npm run build` 生成本地生产构建；`npm run dev` 启动开发服务器和 `/api`、`/health`、`/metrics` 代理。

```bash
cd web
npm ci
npm test -- --run
npm run typecheck
npm run build
npm run dev
```

Vite 默认监听 `127.0.0.1:5173`；端口被占用时会选择下一个端口，以终端输出为准。代理目标默认是 `http://127.0.0.1:8080`，可通过 `VITE_API_PROXY_TARGET` 覆盖地址，但不要在该变量中放 Token。

### 18.2 浏览器闭环

先按本文前面的顺序启动 PostgreSQL、迁移、控制面和至少一个 Worker，再在浏览器打开 Vite 地址。

1. 登录页选择 `operator`，输入本机 `.env.local` 中的 operator Token；Token 只保存在当前标签页 `sessionStorage`。
2. 点击“创建草稿”，输入“先读取 article.md，再清洗内容，最后生成摘要”。
3. 点击“生成草稿”和“校验草稿”，检查任务依赖、事实、假设、问题、校验结果与内容哈希。
4. 点击“确认并启动运行”。控制台先确认 Draft，再创建 Workflow 版本并启动 Run；同名 Workflow 已存在时会创建新的不可变版本。
5. 在 Run 详情页等待 `succeeded`，检查三个 Task 和事件时间线；需要查看 Attempt 历史时调用控制面 Task 详情 API；在 Workers 和 Observability 页面检查 Worker 会话和低基数指标。

控制台只调用查询、Draft、Workflow 和 Run API，不直接连接 PostgreSQL、Docker Engine、Kubernetes 或 Worker 内部协议。关闭标签页会清除 Token 和未提交草稿；刷新页面或控制面重启后，当前标签页的草稿仍需重新服务端校验。

### 18.3 前端常见错误

- `npm ci` 失败：确认 Node.js 主版本至少为 24，删除未完成的 `node_modules` 后重试；不要改用 `npm install` 生成未审查的 lockfile。
- Vite 页面能打开但 API 请求失败：确认控制面监听 `127.0.0.1:8080`，并检查 Vite 启动日志中的代理目标。
- 401：Token 为空、过期或不是当前控制面的 Token；重新从 `.env.local` 读取并输入。
- 403：当前角色是 viewer；切换为 operator 只能在本地授权范围内进行。
- Run 停在 `ready` 或 `queued`：查询 Workers，确认至少一个兼容 Worker 为 `active`，并检查 Worker 的 bootstrap Token、服务地址和唯一名称。
- 页面显示错误后不会自动重放写请求；先确认服务端是否已经创建 Workflow 或 Run，再决定是否重新点击。
