# 产品说明

## 1. 这是一个什么产品

AI Workload Platform 是本项目正在从零开发的产品名称，不是一个准备科普的通用行业术语。

项目定位是：

> 面向 Agent 与确定性程序任务的可靠运行时和调度平台。

平台接收由多个任务组成的工作流，按照依赖关系调度任务，并负责保存状态、处理失败、控制执行权限和记录过程。它既可以运行数据清洗、索引构建等普通程序，也可以运行会调用模型和工具的 Agent，但不会替代任务自身的业务逻辑。

Agent 是能够围绕目标调用模型、工具或外部服务，并根据执行结果决定后续动作的软件组件。确定性程序任务则主要按照预先编写的程序规则执行。二者的内部行为不同，但都需要面对超时、失败、取消、重复执行和进程重启，因此可以共用可靠工作流内核。

## 2. 项目解决什么问题

很多后台工作不是一次请求就能完成，而是由多个有先后关系的步骤组成。

以 AI 文档处理为例：

```text
读取新文档
  -> 清洗内容
  -> 切分段落
  -> 生成向量
  -> 更新搜索索引
  -> 执行质量评测
  -> 评测通过后发布
```

以游戏活动结算为例：

```text
关闭活动入口
  -> 等待进行中的战斗结束
  -> 计算最终排名
  -> 保存排名快照
  -> 分批发放奖励
  -> 核对发放结果
```

如果只使用脚本、定时器和人工操作，会逐渐出现这些问题：

- 前一步尚未完成，后一步已经开始；
- 运行机器宕机后，不知道任务执行到了哪里；
- 重新运行导致重复写数据或重复发奖励；
- 多台机器同时执行同一个任务；
- 日志散落在不同机器，无法快速定位问题；
- 每个业务团队重复实现重试、超时和告警；
- AI 生成的代码获得了过多文件或网络权限；
- 长时间任务需要用户持续盯着某个终端窗口。

本项目提供统一的工作流运行与调度能力，负责保存执行状态、检查依赖、分配任务、处理失败和记录整个过程。

## 3. 使用与不使用的区别

### 3.1 不使用统一平台

团队通常采用：

- Linux cron；
- 业务服务内的定时器；
- 人工执行脚本；
- 自己实现 Redis 锁；
- 失败后人工查看日志并重新运行；
- 在每个项目里分别实现重试和状态记录。

这种方式适合任务很少、失败影响不大的情况。

### 3.2 使用统一平台

用户定义任务步骤和依赖关系，平台负责：

- 判断任务何时可以执行；
- 选择执行节点；
- 保存任务状态；
- 在失败后按规则重试；
- 节点宕机后重新分配任务；
- 限制任务使用的资源和权限；
- 记录输入、输出、日志和执行时间；
- 提供人工审批、取消、回放和恢复能力。

## 4. 是否必须使用多个 Agent

不是。

平台支持三种执行方式：

1. 单 Agent：适合修改一个明确功能或完成一项独立分析；
2. 多 Agent：适合可并行、需要不同专业能力或需要独立审查的任务；
3. 普通程序任务：适合数据清洗、索引构建、批量计算等确定性工作。

多个 Agent 并不是越多越好。并行执行会引入协调、上下文传递、修改冲突和模型成本。平台需要根据依赖关系和成本限制选择合适的执行方式。

### 4.1 Agent Runtime 的作用

Agent Runtime 是 Agent Runtime Environment 的简称，中文可称为“Agent 运行时环境”。它负责向 Agent 提供模型、工具、上下文、权限、预算、超时和取消信号，并把模型调用、工具调用、人工审批和最终结果记录为可审计事件。

工作流内核回答“哪个任务现在可以执行、失败后如何恢复”；Agent Runtime 回答“一个 Agent 任务在什么能力和限制下执行”。二者分离后，工作流内核不绑定某家模型，普通程序任务也不必承担 Agent 特有的复杂度。

## 5. 工作流是否需要用户定义

需要。平台不能自动知道企业内部的业务规则。

用户可以通过配置、SDK 或图形界面定义步骤。模块 3 将提供自然语言生成工作流草稿的产品入口，但草稿必须经过：

- 依赖校验；
- 参数校验；
- 权限校验；
- 资源校验；
- 用户确认。

AI 可以帮助发现明显遗漏，但不能读取用户没有提供的业务事实，也不能替用户承担最终验收责任。

### 5.1 自然语言生成工作流草稿

用户可以用自然语言描述目标，例如：

> 每天凌晨处理当天新增文档，生成向量并更新索引；如果质量评测低于阈值，不要发布，并通知负责人。

系统可以让 Agent 生成一份结构化工作流草稿，但草稿不能直接执行。系统必须依次完成：

1. **依赖校验**：确认所有前置任务存在，且依赖关系没有循环；
2. **参数校验**：确认任务参数类型、必填字段和取值范围正确；
3. **权限校验**：确认每个任务能够访问的文件、网络、数据库和工具符合策略；
4. **资源校验**：确认 CPU、内存、磁盘、并发数和预计运行时间有可用配额；
5. **用户确认**：展示任务步骤、输入输出、权限、资源和风险，用户确认后才创建正式运行。

系统需要明确区分以下三种信息：

- 用户明确提供的事实；
- Agent 根据已有信息推导出的假设；
- Agent 无法确认、必须向用户追问的信息。

当关键条件缺失时，Agent 应先提问，而不是自行猜测。用户确认后的工作流应保留原始描述、草稿版本、修改记录和最终配置，便于后续追溯。

自然语言生成是模块 3 的必做产品演示能力，但不是可靠内核的前置条件。项目会先在模块 1 和模块 2 建立结构化工作流的提交、校验、执行和审计边界，再在模块 3 接入草稿生成，避免生成效果掩盖内核正确性问题。自动化测试使用 Mock Model，真实模型只用于人工触发的低并发演示。

## 6. 目标用户

首批希望验证的用户包括：

- 有数据处理和模型评测任务的 AI 团队；
- 需要批量推理和索引更新的搜索团队；
- 需要可靠执行后台任务的互联网业务团队；
- 需要限制 Agent 权限和资源的 Agent 产品团队；
- 需要统一管理脚本和定时任务的小型技术团队。

项目当前不会假设所有团队都需要一套新平台。首批验证重点是：现有脚本、定时任务或 Agent 原型已经出现恢复、审计、权限和重复建设问题，但引入大型平台成本又过高的团队。

## 7. 适用和不适用场景

适合：

- 任务包含多个步骤；
- 任务可能运行几分钟到几小时；
- 失败后需要恢复；
- 任务需要跨机器或跨服务执行；
- 任务需要统一审计、监控和资源限制；
- 任务数量较多，需要排队和限流。

不适合：

- 简单的一次性脚本；
- 游戏帧循环；
- 战斗中的毫秒级定时器；
- 对网络延迟极其敏感的在线请求；
- 失败后人工重跑即可、没有数据风险的任务。

## 8. 与现有产品的关系

本项目处在多个成熟产品覆盖范围的交叉位置：

| 产品类别 | 代表产品 | 主要优势 | 本项目不重复追求的方向 |
| --- | --- | --- | --- |
| 数据工作流 | Airflow、Dagster、Prefect | 数据管道、定时调度和生态集成 | 不以替代完整数据平台生态为目标 |
| 可靠执行 | Temporal | 持久化执行、恢复语义和多语言 SDK | 不承诺短期达到其生产成熟度和生态规模 |
| Kubernetes 工作流 | Argo Workflows | 以容器和 Kubernetes 为中心的执行 | 前期不要求用户先拥有 Kubernetes |
| Agent 编排 | LangGraph | Agent 状态图和模型应用开发 | 不把模型调用框架作为工作流可靠性的全部 |
| Agent 可观测性 | LangSmith、Langfuse | 模型调用追踪、评测和分析 | 不只观察模型调用，还管理普通任务和系统恢复 |
| 定时任务平台 | XXL-JOB | 易于接入的分布式任务调度 | 不把定时触发作为唯一执行模型 |

这些产品的存在说明需求真实，也意味着本项目不能靠功能名称形成优势。实际选型时，如果现有产品已经低成本满足需求，就不应为了使用本项目而迁移。

当前待验证的差异化假设是：

- 同一套可靠内核同时支持确定性程序任务和结果更不确定的 Agent 任务；
- Agent Runtime 内置工具权限、预算、人工审批、取消和执行审计；
- 使用任务回放、故障注入和恢复报告解释系统行为；
- 提供受限执行和资源控制，同时明确不把容器等同于绝对安全沙箱；
- 保持可私有部署和对小型团队友好的安装体验。

这些是假设，不是已经实现的功能或经过市场证明的优势。项目必须用代码、测试、故障实验、性能数据和真实试用逐项验证；无法验证的内容不能写入 README 或简历作为既成事实。

## 9. 项目价值

确定性较高的价值：

- 学习分布式系统、容错、容器和可观测性；
- 形成可验证的个人系统项目；
- 为 AI 后端、数据平台、Agent Infra 和分布式后端岗位提供面试案例；
- 将当前工作中的时间轮、Kafka、状态恢复等经验抽象为通用能力。

需要验证的价值：

- 是否有团队愿意真实使用；
- 是否比现有产品更容易部署和使用；
- 是否能够形成活跃开源项目；
- 是否具有托管服务或企业私有化的付费空间。
