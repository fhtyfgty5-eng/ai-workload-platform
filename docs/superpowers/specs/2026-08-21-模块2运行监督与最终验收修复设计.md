# 模块 2 运行监督与最终验收修复设计

## 1. 背景与目标

模块 2 已经实现控制面 HTTP API、PostgreSQL 持久化、身份权限、Go SDK、CLI、恢复协调器和本地开发文档。全仓测试、竞态检测、静态检查和文档验证均曾通过，但最终审查发现：现有测试没有覆盖运行期数据库断开、异步执行错误、长时间恢复、OpenAPI 完整性和数据库版本前向不兼容等关键路径。

本轮目标不是增加新的产品功能，而是修复这些会影响可靠性或公开契约的缺陷，使模块 2 的实现、设计文档、学习文章和人工演示保持一致。只有自动验证和用户手动演示均通过后，模块 2 才能标记完成、提交和发布文章。

## 2. 已确认决策

### 2.1 运行期故障采用安全退出

控制面持续检查 PostgreSQL 和持有 Advisory Lock 的专用连接。一旦检查失败，旧进程无法证明自己仍是唯一协调者，必须执行 fail-stop（检测到无法安全继续的故障后主动停止）：

1. 立即令 `ready=false`，拒绝新的业务请求；
2. 中断本机正在执行或恢复的 Run，但不把它们记为用户取消；
3. 停止 HTTP 服务；
4. 释放本机资源并以非零状态退出；
5. 不在同一进程重新连接数据库或重新取得锁；
6. PostgreSQL 恢复后，由新进程取得锁、扫描非终态 Run 并按至少执行一次语义恢复。

该决策的原因和代价记录在 [`ADR-0003`](../../决策/ADR-0003-控制面运行期故障采用安全退出.md)。

### 2.2 不把基础设施中断写成业务取消

当前 Engine 把父 `context.Context` 的取消和用户调用 `Engine.Cancel` 视为同一件事，都会把 Run 推进到 `canceled`。这不适用于控制面安全退出：数据库连接或协调锁失效不是用户取消，数据库中的 Run 应保留为最后一次成功提交的非终态，以便重启恢复。

Engine 必须区分两种信号：

- **业务取消**：用户通过 API 请求取消，先持久化 `cancel_requested_at`，再通知 Engine；Run 最终进入 `canceled`。
- **执行中断**：进程关闭、协调锁失效或监督器停止，只取消当前进程内的 Executor 和等待；不新增业务取消记录，不强行写终态，Engine 返回可被监督器观察的错误。

这是对模块 1 Engine 运行控制语义的必要修正，不改变 DAG、状态机、重试上限和至少执行一次恢复规则。模块 1 本地 CLI 收到退出信号时，如需表达用户主动取消，必须显式调用 `Engine.Cancel`，不能继续依赖父 Context 的隐式含义。

## 3. 问题清单与完成条件

| 问题 | 当前风险 | 完成条件 |
|---|---|---|
| Advisory Lock 仅在启动时取得 | 连接断开后旧实例仍可能接收请求，新实例同时取得锁 | 周期性检查专用连接和锁所有权，失败后安全退出 |
| 异步 `Execute` 错误被丢弃 | Run 可能永久停在非终态，进程仍报告 ready | 所有 `Execute/Resume` 结果都由监督器接收，非空错误触发安全退出 |
| 启动恢复同步执行到终态 | 长任务或远期重试阻塞 HTTP 启动，查询和取消不可用 | 启动阶段只完成锁定、扫描、加载和任务接管，恢复在后台受监督运行 |
| OpenAPI 仅做字符串检查 | 方法、状态码和 Schema 漂移无法被发现 | OpenAPI 升级到 3.1.0，补全 DTO，并用 YAML 结构化契约测试校验 |
| 迁移检查只验证已知版本存在 | 旧程序可能连接含未知新版本的数据库 | 服务启动要求数据库版本集合与内置版本集合精确一致 |
| Run 列表缺少条件过滤 | 与已批准的模块 2 设计不一致 | 支持 `workflow_id` 和 `status` 过滤，非法状态返回 400 |
| 列表使用 offset 游标 | 并发插入时可能重复或遗漏 | Workflow、Version 和 Run 列表改用稳定键集游标 |
| 业务日志字段不足 | 难以按 Workflow、Run 或 Task 定位问题 | 在相关生命周期日志中记录结构化业务标识且不泄露凭据 |
| 模块 2 基础计数没有明确消费方 | 为完成清单而临时增加接口会制造无用契约 | 模块 2 只保留日志和健康检查，指标统一在模块 5 设计 |

## 4. 运行监督器设计

### 4.1 职责边界

`internal/runtime.Coordinator` 从“启动恢复辅助器”升级为单进程运行监督器，负责：

- 取得并持有 PostgreSQL Advisory Lock；
- 启动前列出并加载所有非终态 Run；
- 异步提交新 Run 的 `Execute` 和已有 Run 的 `Resume`；
- 观察每个 Engine 调用的返回错误；
- 周期性检查数据库连接和锁所有权；
- 对首次致命错误执行一次安全退出；
- 提供线程安全的就绪状态和只读致命错误通知。

它不负责 DAG 调度、任务状态转换、数据库事务、HTTP 错误映射或业务取消。

### 4.2 关键接口

接口名称可在实施时遵循现有 Go 命名习惯微调，但语义固定如下：

```go
type Lock interface {
    Check(context.Context) error
    Close() error
}

type RunEngine interface {
    Execute(context.Context, workflow.RunID) (workflow.WorkflowRun, error)
    Resume(context.Context, workflow.RunID) (workflow.WorkflowRun, error)
}

// CoordinatorAPI 展示具体 Coordinator 对外提供的运行监督能力。
type CoordinatorAPI interface {
    // Ready 返回当前进程是否仍具备接收业务流量的条件。
    Ready() bool
    // Enqueue 在 Run 已持久化后把新 Run 交给受监督的 Execute。
    Enqueue(workflow.RunID)
    // Errors 只报告本进程的首个致命错误，供进程生命周期管理器退出。
    Errors() <-chan error
}
```

Coordinator 内部为全部 Engine 调用创建统一的运行期 Context。正常进程关闭或安全退出会取消该 Context，使活动 Executor、超时等待和重试等待停止。Engine 必须把这种中断与业务 `Cancel` 分开。

### 4.3 启动数据流

```text
读取并校验配置
  -> 连接 PostgreSQL
  -> 精确检查迁移版本
  -> 在专用连接取得 Advisory Lock
  -> 列出全部非终态 RunID
  -> 逐个 Load，确认数据库记录可读取
  -> 将每个 Run 交给受监督的后台 Resume
  -> 启动锁健康检查
  -> ready=true
  -> HTTP 开始监听
```

“恢复完成”在这里表示非终态 Run 已被当前协调者接管，不表示所有 Run 已经执行到终态。`Resume` 的深层快照校验或执行错误在后台返回后仍属于致命系统错误，会触发安全退出。

若取得锁、列举 Run 或加载任一 Run 失败，启动立即失败，`ready` 始终为 false，HTTP 不监听。启动阶段已经创建的后台任务必须统一中断并等待退出，不能留下游离 goroutine。

### 4.4 新 Run 数据流

```text
HTTP 启动 Run
  -> 在事务中创建 pending Run 和幂等记录
  -> 事务提交成功
  -> Coordinator.Enqueue(RunID)
  -> 后台 Engine.Execute
  -> nil：业务运行已经正常收敛到终态
  -> 非 nil：监督器触发安全退出
```

如果 Run 已提交而进程在入队前退出，该 Run 仍保留为 `pending`，下次启动扫描会恢复它。幂等重放不得创建第二个 Run。

### 4.5 锁健康检查

Advisory Lock 必须一直绑定在取得锁的同一条 PostgreSQL 专用连接上。`Check` 在该连接上使用带超时的查询同时确认：

- 连接仍可用；
- 当前 PostgreSQL backend 仍持有约定的 Advisory Lock。

生产默认每秒检查一次，单次检查超时一秒；测试通过可替换时钟或间隔避免真实等待。一次检查失败即表示当前进程无法证明所有权，不在原进程重试或重新加锁。

该轮询会留下最长约一个检查周期的故障发现窗口，因此模块 2 不能宣称具备严格的分布式 fencing（栅栏）或多实例高可用。模块 4 将通过 Worker 租约、心跳和必要的 fencing token 处理更强的分布式所有权问题。

### 4.6 致命错误和关闭顺序

监督器通过一次性门闩只处理首个致命错误：

1. 原子地将 `ready` 设为 false；
2. 保存并发送首个错误，后续错误只作为附加日志；
3. 取消统一运行期 Context，中断本机 Engine 调用；
4. 主进程收到错误后使用有上限的 Context 关闭 HTTP 服务；
5. 等待受监督 goroutine 退出；
6. 关闭锁连接和 Repository；
7. 返回原始致命错误，使进程非零退出。

收到 `SIGINT` 或 `SIGTERM` 属于正常关闭：同样先 `ready=false` 并中断本机执行，但不制造致命错误，进程正常退出。HTTP 优雅关闭最长等待五秒，避免无界阻塞。

Coordinator 进入正常关闭或已经处理首个致命错误后，其他 Engine 调用因统一 Context 中断而返回的 `context.Canceled` 只用于完成清理，不能反过来把正常关闭改成错误退出。

## 5. Engine 中断语义

Engine 活动表不再只保存一个无法区分来源的 `context.CancelFunc`，而是保存每个 Run 的运行控制信息。控制信息至少能表达：

- 停止当前 Run 的进程内执行；
- 停止原因是否为显式业务取消。

行为规则：

| 触发来源 | 是否停止 Executor | 是否写 `canceled` | 返回结果 |
|---|---:|---:|---|
| API 已持久化取消后调用 `Engine.Cancel` | 是 | 是 | 取消流程正常收敛 |
| 模块 1 直接调用 `Engine.Cancel` | 是 | 是 | 保持原有显式取消能力 |
| Execute/Resume 父 Context 取消 | 是 | 否 | 返回 `context.Canceled` 或可判定的中断错误 |
| Executor 主动返回 `ResultCanceled` | 是 | 是 | 保持现有业务语义 |
| 数据库保存失败 | 是 | 否 | 返回原始系统错误 |

基础设施中断发生时，最后一次已经成功提交的状态仍是事实来源。可能存在持久化为 `running` 的 Attempt；新进程 `Resume` 会把该 Attempt 记为 `interrupted`，再根据剩余重试次数恢复或失败。这仍是至少执行一次而不是恰好一次。

## 6. OpenAPI 3.1 契约

### 6.1 文档完整性

`api/openapi.yaml` 升级为 `openapi: 3.1.0`，补全：

- Workflow 摘要和分页响应；
- Workflow Version 摘要和分页响应；
- Run 摘要和分页响应；
- 取消响应；
- Task、Attempt、StateEvent 和统一错误响应；
- 每个已实现操作的成功状态、常见错误状态和 JSON Schema；
- Run 列表的 `workflow_id`、`status`、`cursor`、`limit` 查询参数；
- 健康检查路径和响应 Schema。

Schema 必须匹配 Go 实际 JSON 字段、必填规则、`omitempty` 和枚举值，不把未来字段写成已经支持。

### 6.2 结构化契约测试

测试引入轻量的 `gopkg.in/yaml.v3`，把 OpenAPI 解析为结构化数据，不再只查找字符串。类型化测试表逐项声明当前实现的：

- path；
- HTTP method；
- 成功状态码；
- 成功响应引用的 Schema；
- 必需参数和请求体；
- 公共错误响应。

测试还要遍历所有公开操作，确保响应有描述，JSON 响应有 Schema，`$ref` 指向已存在的组件，并拒绝文档中存在实现未注册的方法。该测试用于防止契约漂移，不替代 HTTP 行为测试。

## 7. 列表过滤与稳定游标

### 7.1 Run 过滤

`GET /api/v1/runs` 增加两个可选条件：

- `workflow_id`：只返回指定 Workflow 的 Run；
- `status`：只返回指定合法 Workflow 状态的 Run。

两个条件可以同时使用。空值视为未指定；未知状态返回 `400 invalid_request`。过滤条件必须参与 Repository 查询，不能先读取整页再在内存过滤。

### 7.2 键集游标

键集分页使用上一页最后一条记录的稳定排序键继续查询，不使用“跳过 N 条”的 offset：

| 列表 | 排序键 | 下一页条件 |
|---|---|---|
| Workflow | `workflow_id` | `workflow_id > last_id` |
| Version | `version` | `version > last_version`，并固定 WorkflowID |
| Run | `(created_at, run_id)` | 元组大于上一页最后一条，过滤条件保持不变 |
| Task | `task_index` | `task_index > last_index`，并固定 RunID |
| Event | `sequence` | `sequence > last_sequence`，保持现有方式 |

Run 游标使用 URL 安全 Base64 编码的版本化 JSON，包含 `created_at` 和 `run_id`。服务端把它视为不可信输入，严格解码和校验；客户端只负责原样回传。游标不携带 Token、密码或业务输入。

每个游标只在相同资源和相同过滤条件下使用。为防止误用，Run 游标还包含过滤条件的摘要；不匹配时返回 400。键集分页保证在并发插入下不因行位移产生 offset 式重复或遗漏，但它不是跨多次请求的数据库快照，新插入且排序在游标之前的数据不会回到已经翻过的页面。

## 8. 数据库迁移兼容性

内置迁移文件名解析为有序且不重复的版本集合。数据库中的 `schema_migrations` 必须满足：

- 服务启动的 `CheckMigrations`：数据库集合与内置集合精确相等；
- `migrate up`：数据库已有版本必须是当前内置版本的合法前缀，随后只按顺序应用缺失迁移；
- 数据库出现内置代码未知的任意版本，包括未知更高版本时，旧程序拒绝启动和迁移；
- 数据库缺少已知版本、版本顺序损坏或迁移表不可读时，返回包含版本信息但不泄露连接凭据的错误。

真实 PostgreSQL 集成测试至少覆盖空库迁移、完整版本通过、缺失版本拒绝和未知版本拒绝。测试插入的异常版本必须在测试隔离数据库或可回滚边界内清理。

## 9. 结构化日志与指标边界

模块 2 保留 `slog` 结构化日志。相关事件按可获得的信息记录：

- Workflow 创建和版本创建：`workflow_id`、`workflow_version`；
- Run 创建、入队、恢复、完成和系统错误：`workflow_id`、`workflow_version`、`run_id`；
- Mock Executor 的 Attempt：`workflow_id`、`run_id`、`task_key`、`attempt_number`；
- HTTP：`request_id`、method、规范化 path、status、`error_code`；
- 监督器故障：错误类别和关闭阶段。

不得记录 Bearer Token、Authorization 请求头、数据库 URL、密码、完整请求体或可能包含敏感输出的 Executor 结果。日志测试检查关键字段存在，并检查凭据不出现。

模块 2 不新增 `/metrics`，也不为没有明确消费方的计数设计临时进程内接口。请求、错误、Run 终态和恢复数量等指标连同 Prometheus/OpenTelemetry 统一在模块 5 设计。模块 2 设计文档中原“基础计数”要求同步改为这一边界。

## 10. 可复现的 Mock 延迟

当前默认 Mock Executor 立即返回成功，无法稳定制造“Attempt 正在执行时数据库断开”的人工演示条件。控制面增加仅作用于 Mock Executor 的可选延迟配置 `WORKLOAD_MOCK_EXECUTION_DELAY`：

- 默认值为 `0s`，现有普通演示仍立即完成；
- 使用 Go duration 格式，例如 `30s`；
- 只等待后返回固定成功结果，不解释 `Action`，不运行 Shell，不访问外部网络；
- 等待必须响应 Context 中断；
- 最大值为五分钟，负数、无法解析或超过上限时启动失败；
- `.env.example` 和本地部署文档明确标注它只用于演示和测试。

故障演示使用至少两次最大尝试次数的 Workflow，并把延迟设为 `30s`。第一次 Attempt 进入 `running` 后停止 PostgreSQL；重启恢复时，该 Attempt 被标记为 `interrupted`，剩余尝试继续执行。这样可以稳定观察安全退出和至少执行一次恢复，而不把生产不需要的测试端点加入 HTTP API。

## 11. 测试策略

实施遵循 TDD：先增加能够稳定复现缺陷的失败测试，再实现最小修复，最后全量回归。

### 11.1 单元测试

- Coordinator 启动只等待恢复任务被接管，不等待 Run 终态；
- 新 Run 的 `Execute` 和恢复 Run 的 `Resume` 错误都会被观察；
- 首个错误令 `ready=false`，只发布一次致命错误并取消其他运行；
- Lock 检查失败触发安全退出，同进程不重新加锁；
- 正常关闭不报告致命错误；
- Engine 显式取消写入 `canceled`，父 Context 中断不写业务取消；
- Run 过滤解析、非法状态、游标往返、游标篡改和过滤条件不匹配；
- OpenAPI 结构化契约测试；
- 迁移版本集合比较。
- Mock 延迟默认关闭、边界校验和 Context 中断。

### 11.2 PostgreSQL 集成测试

- 专用连接仍持有 Advisory Lock 时检查成功；
- 第二个 Repository 无法取得相同锁；
- 锁连接失效或锁所有权不存在时检查失败；
- 未知迁移版本和缺失迁移版本被拒绝；
- Workflow、Version、Run 键集分页在页间插入数据时不重复；
- Run 按 WorkflowID、Status 和组合条件过滤。

### 11.3 进程与端到端测试

- 长时间 `waiting_retry` 的恢复不阻塞 HTTP 查询和取消；
- 已提交但尚未入队的 pending Run 能在重启后恢复；
- 模拟 Engine 系统错误时服务先失去就绪状态，再停止 HTTP 并返回非零错误；
- 停止 PostgreSQL 后锁健康检查失败，活动 Run 不被错误写成用户取消；
- PostgreSQL 恢复并重启服务后，非终态 Run 被重新扫描；
- 日志包含必要业务字段且不包含 Token 或数据库密码。

若真实进程测试无法稳定控制 Docker 时序，自动测试使用可控假实现覆盖状态机，真实 PostgreSQL 覆盖锁和迁移；Docker 停库场景保留为必须通过的用户手动演示。不能用不稳定的 `sleep` 代替可观察条件轮询。

### 11.4 全量验证

至少执行：

## 13. 用户手动演示门

自动验证通过后，由用户在本机亲自执行并观察：

1. 启动 Docker Desktop 和 PostgreSQL；
2. 执行迁移并启动第一个控制面；
3. 创建 Workflow、启动 Run，查询三个任务成功；
4. 启动第二个控制面，确认 Advisory Lock 拒绝第二个协调者；
5. 使用 `WORKLOAD_MOCK_EXECUTION_DELAY=30s` 启动一个可观察的非终态 Run，再执行 `docker compose stop postgres`；
6. 确认原控制面先变为不可用，随后安全退出，Run 没有被误记为用户取消；
7. 恢复 PostgreSQL 并重启控制面；
8. 检查 `live`、`ready`、已有 Run 和恢复结果；
9. 检查日志中没有 Token、密码或 Authorization 内容。

演示所需的完整命令和预期输出在自动验证完成后提供。只有用户明确回复演示通过，才能执行以下动作：

- 将模块 2 状态改为完成；
- 给出可提交结论和中文 commit 描述；
- 由用户手动提交。

发布模块 2 学习文章是另一个独立人工门。代码和实验事实核对后，还必须单独审核文章的标题与开头、章节顺序、术语一致性、逻辑跳跃、表达清晰度、重复或过度解释以及结尾边界。问题修正并重新检查后，才能提供 250 字以内摘要及文章标签；只有用户最终阅读确认后，由用户手动发布。

本节是模块 2 完成时的一次人工验收，不是要求该演示步骤在所有未来版本中永久保持不变。后续模块可以扩展或替代早期入口，但必须由自动化回归保护仍然属于当前产品契约的能力。最新主线持续维护一套随产品演进的完整演示；历史模块演示需要重现时，以对应完成提交和当时的验证报告为准。最终面试主要展示完整产品正常路径和少量高价值故障场景，不按模块顺序逐一演示。

## 15. 不在本轮范围内

- 同一进程自动重新取得丢失的 Advisory Lock；
- 多控制面实例高可用、主从切换或跨节点任务租约；
- 恰好一次执行保证；
- Redis、Kafka 或外部任务队列；
- Prometheus、OpenTelemetry、指标面板和告警系统；
- MySQL 存储实现；
- 真实模型、Agent Runtime、任意 Shell 执行或任务容器隔离；
- 自动提交 Git、推送、创建 PR 或自动发布博客。

## 16. 最终验收标准

以下条件必须全部满足：

1. 五项最终审查阻塞问题均有失败测试和实现修复；
2. Engine 能区分业务取消与基础设施中断；
3. 运行期数据库或锁失效会令服务安全退出，不在原进程重新加锁；
4. 启动恢复不被长任务和远期重试阻塞；
5. OpenAPI 3.1 与 HTTP 实现通过结构化契约测试；
6. 数据库未知或缺失迁移版本被拒绝；
7. Run 过滤和稳定键集游标通过单元及 PostgreSQL 集成测试；
8. 结构化日志可定位关键资源且不泄露凭据；
9. 全量自动验证通过；
10. 文档和学习文章只描述实际完成并验证的能力；
11. 用户按步骤完成手动演示并明确确认通过；
12. 在用户手动提交前，不标记模块完成，也不给出“可以提交”的结论。
