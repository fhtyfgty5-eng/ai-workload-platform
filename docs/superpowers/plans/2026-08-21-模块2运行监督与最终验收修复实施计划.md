```go
var errBusinessCancel = errors.New("workflow business cancellation requested")

type activeRunControl struct {
	stop context.CancelCauseFunc
}

func (e *Engine) stoppedRunResult(
	ctx context.Context,
	runCtx context.Context,
	snapshot RunSnapshot,
) (WorkflowRun, error) {
	cause := context.Cause(runCtx)
	if errors.Is(cause, errBusinessCancel) {
		return e.finalizeCancellation(context.WithoutCancel(ctx), snapshot)
	}
	if cause == nil {
		cause = context.Canceled
	}
	return WorkflowRun{}, cause
}
```

`registerActiveRun` 使用 `context.WithCancelCause`；活动 `Engine.Cancel` 调用 `control.stop(errBusinessCancel)`；父 Context 取消沿用 `context.Cause`。`executeSnapshot` 中所有原来因 `runCtx.Err()` 调用 `finalizeCancellation` 的分支改为调用 `stoppedRunResult`。Executor 主动返回 `ResultCanceled` 时先使用业务原因停止，再收敛业务取消。

- [ ] **步骤 3：实现监督器状态和首次致命错误门闩**

Coordinator 内部至少包含：

```go
type Coordinator struct {
	store   RecoveryStore
	engine  RunEngine
	acquire LockAcquirer
	options CoordinatorOptions

	mu      sync.RWMutex
	ready   bool
	closing bool
	lock    Lock
	cancel  context.CancelFunc
	errors  chan error
	fatal   sync.Once
	wg      sync.WaitGroup
}
```

`Start` 的顺序是取得锁、列举全部 ID、逐个 Load、建立内部 Context、设为 ready、异步调用 Resume、启动锁检查。`run` 包装 Execute/Resume 并把非 nil 系统错误交给：

```go
func (c *Coordinator) fail(err error) {
	c.fatal.Do(func() {
		c.mu.Lock()
		c.ready = false
		c.mu.Unlock()
		c.cancel()
		c.errors <- err
	})
}
```

若 Coordinator 已进入正常关闭，或统一 Context 已因首个故障取消，其他 Run 返回的 `context.Canceled` 只完成清理，不再次报告致命错误。

- [ ] **步骤 4：实现 Enqueue、健康循环和有界 Close**

`Enqueue` 只在 Coordinator ready 且未 closing 时启动受 `WaitGroup` 跟踪的 Execute；若已关闭，Run 保持已提交的 pending 状态，供下次启动扫描。健康循环使用 ticker，每次检查创建带 `LockCheckTimeout` 的 Context；任何失败调用 `fail`，不调用 `acquire`。

`Close(ctx)` 必须先令 ready=false、标记正常关闭、取消统一 Context，再等待 `WaitGroup`；等待超时返回 `ctx.Err()`，最后关闭锁。重复 Close 保持幂等。

- [ ] **步骤 3：在持锁专用连接确认连接和锁所有权**

`advisoryLock` 保存 `*pgxpool.Conn`。`Check` 在这条连接上执行：

```sql
SELECT EXISTS (
    SELECT 1
    FROM pg_locks
    WHERE locktype = 'advisory'
      AND pid = pg_backend_pid()
      AND classid::bigint = (($1::bigint >> 32) & 4294967295)
      AND objid::bigint = ($1::bigint & 4294967295)
)
```

查询错误直接返回包装错误；结果为 false 返回 `ErrCoordinatorLockLost`。不得使用 `pg_try_advisory_lock` 做检查，因为会增加同一会话的可重入锁计数。

- [ ] **步骤 4：实现精确迁移集合检查**

```go
func validateMigrationSet(embedded, applied []int64) error {
	if !slices.Equal(embedded, applied) {
		return fmt.Errorf("database migrations %v do not match embedded migrations %v", applied, embedded)
	}
	return nil
}

func validateMigrationPrefix(embedded, applied []int64) error {
	if len(applied) > len(embedded) || !slices.Equal(embedded[:len(applied)], applied) {
		return fmt.Errorf("database migrations %v are not a valid prefix of embedded migrations %v", applied, embedded)
	}
	return nil
}
```

`CheckMigrations` 使用精确集合；`Migrate` 先验证合法前缀，再按顺序应用缺失版本，最后再次精确检查。

```sql
-- Workflow
WHERE id > $1 ORDER BY id LIMIT $2

-- Version
WHERE workflow_id = $1 AND version > $2 ORDER BY version LIMIT $3

-- Run
WHERE ($1 = '' OR workflow_id = $1)
  AND ($2 = '' OR status = $2)
  AND ($3::timestamptz IS NULL OR (created_at, run_id) > ($3, $4))
```
