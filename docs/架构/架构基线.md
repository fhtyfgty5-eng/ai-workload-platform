# 架构基线

## 1. 文档目的

本文件描述当前已批准的高层架构、组件职责和演进顺序，不代表所有组件都需要立即实现。每个模块开始前仍须确认需求、学习必要概念、制定实施计划并经过用户审核。

项目定位是：

> 面向 Agent 与确定性程序任务的可靠运行时和调度平台。

## 2. 核心分层

```text
CLI / SDK / 控制台
        |
        v
控制面 API
        |
        v
可靠工作流内核 <-> 持久化存储
        |
        v
Worker 与任务租约
        |
        +-> 普通程序执行器
        |
        +-> Agent Runtime -> 模型 / 工具 / 人工审批

日志、指标、调用链和审计事件贯穿各层
```

分层的目的不是把项目拆成尽可能多的服务，而是明确哪些职责可以独立测试和替换。模块 1 中这些组件可以在同一进程内；只有进入控制面和多 Worker 阶段后，才建立网络边界。

## 3. 组件职责

### 3.1 可靠工作流内核

可靠工作流内核负责与执行对象无关的规则：

- 校验任务标识和依赖；
- 将 DAG 编译为适合调度的数据结构；
- 管理工作流、任务和 Attempt 状态机；
- 判断任务何时可以执行；
- 处理并发、重试、超时、取消、失败传播和恢复；
- 通过抽象接口保存运行状态和执行历史。

Attempt 表示一次具体执行尝试。一个任务可能因为临时失败、超时或进程中断产生多个 Attempt，但任务最终只有一个成功、失败或取消等终态。

内核不直接调用某家模型、不解析自然语言，也不依赖 Kubernetes。普通程序执行器、Agent Runtime 和未来的容器执行器都通过统一的执行结果边界与内核协作。

### 3.2 控制面

控制面是向用户和客户端提供稳定操作入口的服务层，负责：

- 接收和版本化工作流定义；
- 创建、查询和取消运行实例；
- 执行身份、权限、参数和配额校验；
- 协调工作流内核、持久化存储和 Worker；
- 提供审批、查询和审计 API。

控制面不直接完成业务任务。自然语言生成工作流草稿是模块 3 的必做上层产品能力，但不是控制面的基础职责；草稿只有转换为经过校验和用户确认的结构化定义后才能提交。

模块 2 的控制面接口第一阶段使用 HTTP/REST，并以 OpenAPI 描述稳定契约。gRPC、API Gateway 等内部通信或多服务入口能力只有在后续模块出现明确需求后再评审，不作为当前控制面的前置条件。

控制面当前建议使用 Go 实现，因为项目希望复用现有 Go 经验，并利用其并发、网络服务和部署能力。未选择 Java，是因为当前没有必须使用其企业生态的需求；未选择 Python，是因为核心服务更关注并发执行、类型边界和单文件部署，模型适配仍可通过协议接入 Python 生态。

### 3.3 持久化存储

持久化存储负责保存：

- 工作流定义和版本；
- WorkflowRun、TaskRun 和 Attempt；
- 状态事件、审批记录和最小结果元数据；
- Worker、租约和后续恢复所需信息。

模块 1 先定义 Store 接口并使用 JSON 文件验证恢复语义。模块 2 第一实现选择 PostgreSQL，利用事务、约束、索引和查询能力建立网络控制面的持久化边界。PostgreSQL 和 MySQL 都能满足本项目的核心需求；选择 PostgreSQL 是因为它在 `jsonb` 查询、部分索引、`RETURNING` 以及复杂状态查询方面更顺手，便于验证工作流状态和并发领取语义。MySQL 8 同样支持事务、JSON、窗口函数和 `SKIP LOCKED`，并不是能力不足，只是部分查询和约束需要采用不同设计。

项目不在第一阶段同时维护 PostgreSQL 和 MySQL 两套实现。Store 接口隔离持久化边界，SQL 尽量保持可移植；只有目标部署环境、用户需求或实验证据明确需要时，才评估 MySQL 适配。未选择在模块 1 直接使用数据库，是为了先隔离工作流正确性；未选择自研存储，因为它不属于项目目标。

消息队列、缓存和协调服务只有在数据库与多 Worker 实验暴露具体瓶颈后才评审，不能为了覆盖技术名词提前加入。

### 3.4 Worker 与任务租约

Worker 是实际领取和执行任务的节点。进入多节点阶段后，它负责：

- 注册自身能力并持续上报心跳；
- 领取与自身能力匹配的任务租约；
- 准备普通程序或 Agent 的执行环境；
- 传递超时和取消信号；
- 收集结构化结果、日志和资源使用信息；
- 在租约有效期内上报执行结果。

租约是带有效期的任务占用权。它用于处理 Worker 失联后任务需要重新分配、旧 Worker 又恢复上报的竞争情况。租约不能消除任务重复执行，因此外部副作用仍需要幂等、唯一请求 ID 或结果去重。

模块 4 第一版已经实现 Worker 通过 HTTP 主动拉取任务、PostgreSQL 持久化 Dispatch 与租约、数据库事务校验结果所有权的方案。网络控制面只创建和协调 Dispatch，不再在自身进程执行 Run；模块 1 的本地 Engine 和 FileStore 入口继续保留。Worker 注册、领取、心跳、完成和 drain 使用独立认证边界，查询接口不返回会话令牌或租约令牌。

拉取方式让 Worker 根据自身空闲容量请求任务，也不要求控制面主动连接 Worker。注册和任务完成会向 Coordinator 发送合并的唤醒提示，Worker 释放槽位也会唤醒本地领取循环；这些通知只减少延迟，丢失后仍由 PostgreSQL 和周期扫描恢复。当前不引入消息队列或 gRPC 流，因为单机基准首先暴露的是单 Run revision 串行提交与空领取竞争，而不是缺少另一套队列系统；具体接口、状态与故障语义见[模块 4 需求与设计](../计划/模块4需求与设计.md)和[模块 4 验证报告](../实验/模块4验证报告.md)。

### 3.5 普通程序执行器

普通程序执行器运行数据清洗、索引构建、批量计算或其他确定性较高的任务。它接收结构化输入、超时和取消信号，返回结果、错误分类和执行元数据。

模块 1 只提供 Mock Executor，不执行任意本机命令。真实进程和容器执行器需要在权限、环境、日志和资源边界明确后再加入。

### 3.6 Agent Runtime

Agent Runtime 是 Agent Runtime Environment 的简称，中文可称为“Agent 运行时环境”。它负责：

- 选择和调用经过配置的模型适配器；
- 向 Agent 提供明确允许的工具和上下文；
- 管理模型调用次数、Token 或费用预算；
- 处理工具调用、人工审批、超时和取消；
- 记录模型请求、工具结果、决策步骤和最终结果的审计事件；
- 把供应商错误转换为平台统一的临时失败、永久失败或限流结果。

模型是 Agent 的能力来源之一，Agent Runtime 才是平台管理的执行边界。API Key 是供应商账号凭证，不是 Agent 身份；多个逻辑 Agent 可以共享合法凭证，但必须遵守供应商速率、并发和使用条款。

普通程序执行器与 Agent Runtime 共用工作流内核的状态、重试和恢复规则，但拥有不同的配置、风险和观测数据，因此不合并成一个包含所有条件分支的实现。

### 3.7 可观测性与审计

可观测性用于回答：

- 当前有哪些任务正在运行；
- 为什么某个任务失败或等待；
- 哪个步骤最慢、消耗了多少资源；
- 一次请求经过了哪些服务和执行节点；
- 故障发生后系统是否按设计恢复；
- Agent 调用了哪些模型和工具，谁批准了敏感操作。

前期先保留结构化状态事件和稳定标识，后续逐步加入日志、指标、分布式调用链和告警。告警是在指标、状态或错误满足预设条件时产生的主动通知；项目只实现规则、抑制和可替换通知出口，不重复建设短信、邮件或即时通信服务。审计事件用于追溯重要操作，不等同于可以随意删除或采样的调试日志。

### 3.8 受限执行环境与 Kubernetes

受限执行环境负责限制任务能够使用的 CPU、内存、磁盘、运行时间和网络权限。容器提供进程与资源隔离能力，但不能被描述为可以安全运行任意恶意代码的绝对沙箱。

Kubernetes 是本项目明确要学习和使用的基础设施，但项目不实现 Kubernetes 本身。使用目标包括：

- 部署控制面、Worker 和可观测性组件；
- 为任务提供受限制的执行环境；
- 学习 Pod 生命周期、服务发现、节点选择和滚动更新；
- 验证 Pod 重启、节点失联、资源耗尽和任务重新分配。

前期使用本地进程和 Mock 验证核心正确性，后期使用本地轻量集群做集成实验，避免基础设施复杂度掩盖工作流问题。是否使用 Rust 实现受限执行组件，要在模块 6 开始前根据安全边界、学习成本和 Go 实现能力单独评审。

### 3.9 轻量 Web 控制台

模块 7 的控制台是面向用户的浏览器客户端，不是新的业务服务。它使用 React、TypeScript 和 Vite 构建，放在独立的 `web/` 目录中；开发环境可以使用 Vite 开发服务器，演示或发布时使用构建后的静态文件。

控制台通过现有版本化 HTTP API 调用控制面：

```text
浏览器 Web 控制台
  -> HTTP/JSON API
  -> Go 控制面
  -> 工作流内核、PostgreSQL、Worker 与观测组件
```

控制台负责页面布局、表单输入、状态展示、轮询、错误提示和用户确认；控制面负责认证、权限、草稿校验、状态转换、幂等、取消和业务事实。前端不得直接连接 PostgreSQL，不得根据本地状态自行推断任务可执行性，也不得绕过草稿确认提交运行。

第一版使用有限轮询刷新 Run 和 Worker 状态，不提前引入 WebSocket 或 SSE。这样可以复用现有查询 API，减少连接生命周期和部署复杂度；只有在真实演示或用户体验证据表明轮询不足时，才评估服务端推送。

控制台至少提供以下页面或视图：

- 工作流与版本列表、任务依赖和 Agent 草稿确认；
- Run 详情、Task/Attempt 状态、事件时间线和取消操作；
- Worker、租约和故障接管结果；
- 日志、指标和 Trace 的摘要或跳转入口；
- 可理解的加载、空状态、权限错误、网络错误和业务错误。

不选择 Go 模板作为第一方案，是因为项目需要证明具备现代前后端整合能力；不选择 Next.js，是因为 Go 控制面已经是唯一服务端事实源，增加第二套服务端会模糊认证、部署和状态边界。控制台不承担移动端、小程序、复杂商业后台或调度算法职责。

## 4. 数据流

### 4.1 结构化工作流

```text
用户通过 CLI / SDK / 控制台提交结构化定义
  -> 控制面完成定义、身份和配额校验
  -> 工作流内核编译 DAG 并创建运行状态
  -> 持久化存储确认状态保存成功
  -> 调度器识别可执行任务
  -> Worker 获得任务或租约
  -> 普通程序执行器或 Agent Runtime 执行
  -> Worker 上报结构化结果和执行证据
  -> 内核持久化新状态并解锁后续任务
  -> 工作流成功、失败、取消或等待人工处理
```

### 4.2 模块 3 的自然语言草稿路径

```text
用户描述目标
  -> Agent Runtime 生成结构化工作流草稿
  -> 系统标记事实、假设和待确认问题
  -> 依赖、参数、权限和资源校验
  -> 用户检查并确认
  -> 进入结构化工作流提交流程
```

草稿不能绕过结构化校验直接执行。该流程是模块 3 的必做演示能力，但不是模块 1 至模块 2 的前置条件；模块 7 再将它接入控制台。

## 5. 模块演进边界

| 模块 | 本阶段增加的架构能力 | 明确不提前实现 |
| --- | --- | --- |
| 模块 1 | 单进程内核、Mock Executor、文件 Store | 网络 API、数据库、真实模型、容器 |
| 模块 2 | HTTP/REST/OpenAPI 控制面、PostgreSQL 第一实现、最小客户端 | 多 Worker、Agent 工具执行 |
| 模块 3 | Agent Runtime、模型、工具边界和自然语言工作流草稿 | 任意代码沙箱、大规模多 Agent |
| 模块 4 | Worker、心跳、租约和重新分配 | Kubernetes 调度替代品 |
| 模块 5 | 完整观测链路、故障注入和系统基准 | 只展示仪表盘而没有恢复证据 |
| 模块 6 | Docker/Compose、容器限制和本地 Kubernetes 集成 | 绝对安全承诺、自研容器运行时 |
| 模块 7 | 真实场景、轻量 Web 控制台、SDK、CI/CD 和开源发布 | 未经验证的企业级功能清单 |

## 6. 关键架构原则

- 正确性和可恢复性优先于功能数量；
- 单 Agent 是一等能力，多 Agent 不是默认选项；
- 普通程序任务不依赖模型或 Agent 框架；
- 外部服务必须可替换、可模拟；
- 测试不得默认依赖付费 API 或外部网络；
- 状态保存成功后才能推进依赖和调度新任务；
- 至少执行一次不等于恰好执行一次，副作用必须考虑幂等和去重；
- 不把容器等同于绝对安全沙箱；
- 不在缺少真实需求时提前引入复杂中间件；
- 公共后端能力服务于产品主线，Redis、Kafka、对象存储、OAuth/OIDC、gRPC、Elasticsearch 和 API Gateway 按需求评审，不为覆盖招聘关键词提前加入；
- 文档中的规模和性能结论必须来自可复现实验；
- 每个模块必须具备明确接口、自动化测试和失败场景。
