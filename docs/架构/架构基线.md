# 架构基线

## 1. 文档目的

本文件只描述当前已批准的高层架构，不代表所有组件都需要立即实现。每个模块开始前必须先编写详细学习资料和实施计划。

## 2. 系统组成

### 2.1 控制面

控制面可以理解为总调度室，负责：

- 接收工作流定义；
- 校验任务依赖；
- 保存工作流和运行状态；
- 判断哪些任务已经可以执行；
- 把任务分配给执行节点；
- 处理重试、超时、取消和恢复；
- 提供查询、审批和审计接口。
- 将自然语言工作流草稿转换为结构化定义，并在执行前完成依赖、参数、权限和资源校验。

当前建议使用 Go 实现，原因是与用户现有经验衔接较好，并适合网络服务和并发任务管理。

### 2.2 执行节点

执行节点可以理解为实际完成工作的工人，负责：

- 接收任务；
- 准备执行环境；
- 启动普通程序或 Agent；
- 限制 CPU、内存、磁盘、时间和网络权限；
- 收集日志与任务产物；
- 上报执行结果和心跳。

受限执行节点未来可能使用 Rust 实现，用于学习系统编程和容器隔离。该选择尚未进入代码阶段，开始该模块前需要单独确认。

### 2.3 Agent 适配层

平台不能绑定某一家模型或产品。计划通过统一接口适配：

- Mock Agent；
- 支持官方 API 的云模型；
- 本地模型；
- 普通脚本或服务任务。

API Key 是供应商账号凭证，不等于 Agent 身份。多个逻辑 Agent 可以共享合法凭证，但必须遵守速率、并发和使用条款。

### 2.4 状态与事件

工作流状态需要持久化，以便服务重启后恢复。初期先定义存储接口并提供低成本实现，后续再根据一致性需求选择 PostgreSQL 等持久化系统。

消息系统、缓存和协调服务只有在需求出现后才引入，不能为了覆盖简历关键词而强行加入。

### 2.5 可观测性

可观测性用于回答：

- 当前有哪些任务正在运行；
- 为什么某个任务失败；
- 哪个步骤最慢；
- 某次执行消耗了多少资源；
- 一个请求经过了哪些服务；
- 故障发生后系统是否恢复。

后续通过日志、指标和调用链逐步实现。

### 2.6 Kubernetes 使用边界

Kubernetes 是本项目明确要学习和使用的基础设施，但本项目不实现 Kubernetes 本身。

使用 Kubernetes 的目标包括：

- 部署控制面、执行节点和可观测性组件；
- 为任务提供隔离的执行环境；
- 通过 CPU、内存和临时存储限制控制任务资源；
- 学习节点选择、Pod 生命周期、服务发现和滚动更新；
- 验证节点失联、Pod 重启和任务重新分配。

前期先使用本地进程和 Mock 执行器验证工作流正确性，避免 Kubernetes 的部署复杂度掩盖核心问题。后期使用本地轻量集群进行集成验证。项目不把 Kubernetes 当作“简历关键词”，每个使用的对象都必须对应一个实际问题和实验。

## 3. 当前逻辑数据流

```text
用户提交工作流
  -> 控制面校验定义
  -> 控制面保存运行状态
  -> 调度器识别可执行任务
  -> 执行节点领取任务
  -> 普通程序或 Agent 执行
  -> 节点上报日志与结果
  -> 控制面更新状态
  -> 解锁后续依赖任务
  -> 工作流成功、失败或等待人工处理
```

## 4. 关键架构原则

- 单 Agent 是一等能力，多 Agent 不是默认选项；
- 正确性和可恢复性优先于功能数量；
- 外部服务必须可替换、可模拟；
- 测试不得默认依赖付费 API；
- 不把容器等同于绝对安全沙箱；
- 不在缺少真实需求时提前引入复杂中间件；
- 文档中的规模和性能数据必须来自可复现实验；
- 每个模块必须具备明确接口、测试和失败场景。
