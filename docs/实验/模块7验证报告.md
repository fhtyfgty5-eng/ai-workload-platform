# 模块 7 验证报告

## 验证目标

验证从自然语言目标生成工作流草稿、服务端校验、人工确认、创建不可变 Workflow、启动 Run，并在浏览器中查看 Task、Event、Worker 和 Metrics，再通过控制面 API 查询 Attempt 的闭环。

## 环境

- macOS Apple Silicon（本次机器为 Mac mini M4）
- Go 1.26.2
- Node.js 24.13.1、npm 11.8.0
- PostgreSQL 16（Docker Compose）
- 控制面 `127.0.0.1:8080`
- Vite 控制台 `127.0.0.1:5173`
- Mock Model、Mock Executor

Token 只从本机 `.env.local` 加载并输入浏览器会话，报告不记录 Token、数据库密码、Run ID 或业务文件内容。

## 浏览器闭环

1. 启动 PostgreSQL、迁移、控制面、至少一个 Worker 和 Vite。
2. 浏览器输入 operator Token，进入“创建草稿”。
3. 输入“先读取 article.md，再清洗内容，最后生成摘要”。
4. 页面展示用户事实、Agent 假设、校验结果和三个任务：`read`、`clean`、`summarize`。
5. 点击校验，状态变为 `needs_confirmation`；确认按钮只在没有阻塞错误和未解决问题时可用。
6. 点击“确认并启动运行”，控制台创建 Workflow。若同名 Workflow 已存在，则创建新的不可变版本；若定义冲突由服务端返回的冲突仍会展示为错误。
7. 控制台启动 Run 并进入详情页。实际观察到 Run 从 `pending` 到 `succeeded`，三个 Task 均为 `succeeded`，事件时间线包含分发、领取和完成事件；Attempt 详情通过控制面 Task 查询 API 获取。
8. Runs、Workers、Observability 页面均从控制面查询；前端未调用 Worker 注册、领取、心跳、完成或 drain 接口。浏览器闭环不重复执行故障接管实验，故障接管证据由后端/API/E2E 验证报告提供。

## 失败路径

- 缺少 Worker 时，Run 会停留在 `ready` 或 `queued`，页面不伪造成功状态。
- viewer Token 只能查询，生成、确认和启动操作返回 403。
- 同名 Workflow 的定义不一致时不会静默复用，服务端冲突会显示在草稿页。
- 控制面不可用时，页面保留错误信息；写请求不会自动重试。
- 关闭标签页会清除 sessionStorage 中的 Token 和未提交草稿；刷新页面或控制面重启后，当前标签页仍可重新校验草稿。

## 限制

- 默认使用 Mock Model/Executor，不证明真实模型的理解质量，也不执行用户提供的任意命令。
- 草稿不写 PostgreSQL；浏览器关闭后草稿不可恢复。
- 本次闭环验证了本地 PostgreSQL 和 Mock Worker，没有把容器安全、Kubernetes NetworkPolicy、CPU/临时存储限制或生产容量写成已验证事实。
- 轮询使用固定间隔和 AbortController；没有引入 WebSocket 或 SSE。

## 真实模型验证状态

本报告没有执行外部真实模型调用，也不把真实模型作为模块 7的复现前置条件。仓库中的 `agent/httpmodel` 只通过本机 `httptest.Server` 验证 OpenAI-compatible HTTP 请求、工具调用消息、JSON Schema、429、非法响应和取消。未来如果进行具体供应商的人工冒烟，需要单独记录服务类型、模型名、工具调用、结构化输出、服务端校验、错误边界和脱敏性能摘要，不能把默认 Mock 闭环改写成真实模型证据。
