## 真实进程故障演示

2026-08-22 按[项目本地运行、演示与换电脑手册](../部署/本地开发与配置.md)第 10.2 节完成真实 PostgreSQL 中断与新进程恢复：

1. 使用 `WORKLOAD_MOCK_EXECUTION_DELAY=90s` 启动恢复示例，Run `3c528f0a8e2d19f0eea3894ade9bebe7` 进入 `running`；
2. 在第一次 Attempt 运行期间执行 `docker compose stop postgres`；
3. 原控制面在 Advisory Lock 健康检查中收到 PostgreSQL `SQLSTATE 57P01`，随后以非零状态退出，没有继续以协调者身份运行；
4. 恢复 PostgreSQL、清除 Mock 延迟并启动新控制面，`GET /health/ready` 返回 `{"status":"ready"}`；
5. 原 Run 最终为 `succeeded`，revision 为 7；`long-running` 任务的 Attempt 1 为 `interrupted`，Attempt 2 为 `succeeded`，任务最终为 `succeeded`；
6. 本次展示的控制面日志没有输出 Token、数据库密码或 Authorization Header。

这组结果证明：运行期数据库中断会使失去锁所有权证明的旧进程安全退出；数据库恢复后，新进程能根据已提交状态把遗留的运行中 Attempt 标记为中断，并按剩余尝试次数继续执行。它没有把基础设施中断误写成用户取消。

## 性能基线

性能基线使用 1 个任务和每轮 100 次操作运行 5 轮：Run 串行查询平均 `0.281 ms/op`，10 逻辑 CPU 并行查询的总耗时折算平均 `0.081 ms/op`，创建 pending Run 平均 `1.234 ms/op`。环境、原始结果和限制见[模块 2 控制面性能基线](模块2性能基线.md)。

## 结果边界

- Advisory Lock 是单实例执行协调，不是高可用方案；
- 自动化测试与一次真实 Docker 停库演示已覆盖当前单实例监督器的主要故障语义，但一次本机演示不能替代重复故障注入、长时间稳定性测试或多节点高可用验证；
- 当前只有本机回环 HTTP、单任务、100 次操作的窄口径基线，没有 P95/P99、饱和吞吐、跨机器数据库或后台执行竞争数据，不能据此作生产性能承诺；
- Docker Compose 只提供 PostgreSQL 开发依赖，不代表任务容器化或安全沙箱；
- Token、本地环境文件和数据库内容不进入 Git，换电脑需要重新生成本地 Token 并执行迁移。
