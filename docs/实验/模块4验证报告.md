# 模块 4 多 Worker、租约与故障恢复验证报告

## 1. 验证目标

模块 4 把网络控制面的任务执行从控制面进程拆到独立 Worker 进程。本报告验证以下结论：

- 多个 Worker 能按容量并发领取同一个有向无环图中的任务；
- Worker 失联后，已领取任务不会永久停留在运行中；
- 旧租约的迟到结果不能覆盖新 Attempt 的结果；
- 控制面重启后，Worker 会话和未过期租约仍由 PostgreSQL 事实恢复；
- 运行取消和 Worker 优雅退出不会留下新的可领取任务；
- 全局背压和跨轮 Run 基础公平性由自动化测试固定；
- 性能数据只描述当前本机和当前实现，不推导生产容量。

## 2. 环境与输入

验证环境：

- macOS 26.1；
- Apple M4，10 个逻辑 CPU，32 GiB 内存；
- Go 1.26.2；
- PostgreSQL 16，运行在 Docker Desktop；
- HTTP、Context、加密随机数和测试服务器使用 Go 标准库；
- PostgreSQL 客户端使用 pgx v5。

自动化故障测试使用独立临时数据库。Worker 进程测试会构建 `workload-worker`，启动两个真实操作系统进程，并强制终止持有租约的第一个进程。任务只执行安全 Mock Action，不访问文件、Shell、外部网络或真实模型。

性能输入是一个包含 1,000 个相互独立 Mock 任务的 Run。Workflow 并发分别设置为 1、4、16，对应相同数量的 Worker，每个 Worker 并发槽位为 1。每个任务依次经过 Dispatch 创建、领取、心跳和结果提交。为了在可接受时间内完成 15 个样本，基准使用 25 毫秒起步、500 毫秒封顶的指数退避；生产 Worker 默认值仍是 250 毫秒和 5 秒。测试连接池上限显式设为 64，避免 16 Worker 被客户端默认连接数提前限流。这些参数属于固定实验条件，不是推荐的生产配置。

## 3. 自动化验证覆盖

### 3.1 正常分发

真实 PostgreSQL 端到端测试创建一个控制面和两个 Worker，执行包含两个并行任务的工作流。测试确认：

- 两个任务都只产生一个成功 Attempt；
- Worker 摘要能够查询活动租约数；
- 查询响应不包含会话令牌、令牌摘要或租约令牌；
- Run 最终进入 `succeeded`。

### 3.2 Worker 进程崩溃

进程测试让 Worker A 领取一个长任务，然后强制结束该进程。租约过期后，控制面把 Attempt 1 记录为 `interrupted`，创建新的 Dispatch；Worker B 领取 Attempt 2 并成功完成。Run 最终进入 `succeeded`。

这个场景验证的是至少执行一次恢复：任务不会静默丢失，但 Worker A 在崩溃前已经产生的外部副作用无法由租约自动撤销。真实执行器仍必须使用幂等请求、唯一业务键或补偿逻辑。

### 3.3 迟到结果

测试保存 Worker A 的旧 DispatchID 和租约令牌，等待该租约回收并由 Worker B 创建 Attempt 2，再通过 HTTP 重放旧完成请求。控制面返回稳定错误码 `lease_lost`，Run revision 不因旧结果变化；Worker B 的当前结果可以正常提交。

### 3.4 控制面重启

测试关闭 HTTP 服务、Dispatch Coordinator 和数据库连接，再连接同一个 PostgreSQL、重新取得 Advisory Lock 并启动新控制面。Worker 使用原 WorkerID、原会话令牌和原租约令牌继续心跳和完成，不需要直接访问数据库。

### 3.5 取消、优雅退出与空闲会话

运行中取消会在事务内撤销 pending/leased Dispatch，把活动 Attempt 记为 `canceled`，后续心跳收到 `revoked`，迟到完成返回 `lease_lost`。

Worker 收到进程退出信号后先调用 drain：停止领取新任务，但在关闭期限内继续为已有租约发送心跳并提交结果；期限耗尽才取消本地执行。第一次 drain 在仍有活动租约时把会话改为 `draining`；租约完成后，Worker 再次调用 drain，把会话改为 `stopped` 并记录 `stopped_at`。没有活动租约时直接进入 `stopped`。空闲 Worker 也会发送不含租约的心跳，否则长时间没有任务时会被数据库误判为 offline。

### 3.6 背压与公平性

PostgreSQL 集成测试确认：

- `pending + leased` Dispatch 数不会超过配置的全局上限；
- 每个扫描轮次对每个 Run 最多推进一个 task index 最小的 Ready 任务；
- 全局容量为 1 时，从未分发或最久未分发的 Run 优先，不被旧大 Run 跨轮饥饿；
- 没有兼容 Worker 时任务保持或返回 `ready`，不创建 Attempt；
- 兼容 Worker 后注册后，周期扫描会重新发现任务；
- 多 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取时不会重复获得同一个 Dispatch。

## 4. 实际发现并修复的问题

### 4.1 空闲 Worker 没有心跳

最初运行时只在持有租约时发送心跳。Worker B 等待 Worker A 的租约过期期间没有任务，因此先被离线扫描标记为 offline，恢复任务无法领取。修复后，空闲 Worker 也周期发送空租约心跳。

### 4.2 优雅退出提前取消活动任务

最初活动任务 Context 直接继承进程退出 Context。收到信号后任务先被取消，随后才发送 drain，请求顺序与设计目标相反。修复后，停止领取和取消租约使用不同生命周期：先 drain 并保留心跳与完成窗口，关闭期限耗尽才取消剩余任务。

### 4.3 配置值与数据库事实不一致

控制面会把配置的心跳间隔和租约时长返回给 Worker，但 PostgreSQL 最初仍使用写死的 5 秒和 15 秒。修复后，Repository 与 Worker API 接收同一组已校验配置，数据库签发、续租和离线阈值与协议声明一致。

### 4.4 并发事务锁顺序反转

首轮 4 Worker 基准发生超时。根因是部分事务先锁 Run 再写 Dispatch，另一些事务先锁 Dispatch 再更新 Run，形成循环等待风险。修复后，完成、回收、取消和孤儿 Dispatch 清理消除了 Dispatch -> Run 的反向锁定；领取使用同一条 `FOR UPDATE OF r, d SKIP LOCKED` 语句筛选候选 Run 和 Dispatch。现有并发测试连续 20 轮通过，正式基准不再因该问题超时，但仍需在模块 5 的持续并发压测中观察 PostgreSQL 死锁和事务重试。

### 4.5 完成后没有及时触发下一轮领取

首次 1 Worker 基准超过 60 秒。继续追踪发现两条延迟链：Worker 完成结果后，Worker API 没有唤醒 Coordinator；Worker 本地释放并发槽位后，领取循环也可能仍在等待上一次轮询计时器。修复后，注册成功和完成成功会发送合并的 Coordinator 唤醒提示，活动租约结束会通知本地领取循环立即重新计算空闲槽位。对应回归测试使用 1 秒轮询下限，确认任务完成后 150 毫秒内已再次领取，而不是等待完整轮询周期。

### 4.6 本地安全期限没有先受租约过期时间约束

Worker 本地最初只按 Attempt 截止时间安排取消。如果心跳因网络或 PostgreSQL 故障无法续租，本地执行可能越过较早的租约过期时间，继续产生平台不会接受的结果。修复后，初始安全期限取 `lease_expires_at` 与 `attempt_deadline` 中较早者；合法心跳续租后更新本地计时器，但永远不越过 Attempt 截止时间。测试覆盖心跳失败时按租约期限取消，以及续租成功后延长执行窗口。

### 4.7 优雅退出没有收敛到 stopped

最初 drain API 无论活动租约数都只写 `draining`，Worker 运行循环也只调用一次。正常退出的会话因此不会写入 `stopped_at`，之后只能被离线扫描改成 `offline`。修复后，数据库在锁定 Worker 会话期间统计活动租约：有租约时进入 `draining`，没有租约时进入 `stopped`；领取事务使用同一行锁，因此不能在“判断无租约”和“写入 stopped”之间并发分配新任务。Worker 完成已有租约后发出第二次 drain，相关 PostgreSQL 状态转换测试和 Runtime 测试固定这一闭环。

### 4.8 持久化取消意图没有周期收敛

取消 API 先提交 `cancel_requested_at`，再调用分发协调器撤销租约。如果进程在两个事务之间退出，调度查询会排除该 Run，旧扫描逻辑也不会再次取消它。修复后，每次启动与周期扫描都先查找已经请求取消但尚未终止的 Run，并调用幂等取消事务完成收敛。集成测试只提交取消意图，随后直接运行恢复扫描，确认 Run、Task、Attempt 和 Dispatch 全部进入取消终态。

### 4.9 默认执行器破坏历史幂等哈希

模块 4 为省略 `executor` 的旧定义补上默认值 `mock`。如果直接对新规范化 JSON 计算哈希，同一个历史请求会因为多出字段而得到不同哈希，并被误判为幂等冲突。修复后，计算幂等哈希时把默认 `mock` 还原为空字段；省略与显式默认值语义相同，未来非默认执行器仍参与哈希。

### 4.10 Heartbeat 与 Reaper 使用了不同时间快照

受控并发测试让 Heartbeat 在租约到期前读取数据库时间并等待 Dispatch 锁，再让 Reaper 在到期后选中同一行。旧实现可能先让 Heartbeat 返回 `renewed`，随后仍按 Reaper 的旧候选结果回收。修复后，Reaper 在候选查询中同时锁 Run 和 Dispatch，跳过正在续租的行，并在结算前按 `clock_timestamp()` 和最新期限复核。

### 4.11 单轮限制不能保证跨轮公平

旧排序每轮都从最早创建的 Run 开始。全局容量为 1 时，旧大 Run 完成一个任务后会再次获得下一轮名额，新 Run 可能长期等待。修复后，从未创建 Dispatch 的 Run 优先，其余按最近一次 Dispatch 时间排序；独立索引支持该持久化排序，控制面重启后也不依赖内存游标。

### 4.12 OpenAPI 枚举与运行时不一致

任务查询已经可能返回 `queued`，OpenAPI 的 `TaskStatus` 却没有该值；完成请求文档又允许 `canceled`，而 Worker 完成实现会拒绝它。新增结构化 YAML 契约测试后，响应枚举补上 `queued`，完成结果只保留成功、临时失败和永久失败；运行取消仍由控制面取消接口负责。

### 4.13 永久 Worker 会话错误被无限忽略

Worker 原先忽略所有 Claim 和 Heartbeat 错误。会话被标记为 offline 后，服务端持续返回 `worker_session_invalid`，进程会永久空转。修复后，永久认证或协议错误会取消本地会话并让进程返回错误退出，临时网络和 5xx 仍重试；重启进程会重新注册新会话。

结果确认：4 Worker 相比 1 Worker 的平均吞吐提高约 50%，16 Worker 相比 4 Worker 只提高约 9%。16 Worker 还出现一轮 14.33 tasks/s 和 2,596 次空领取，波动明显。每次 Task 状态变化都递增同一条 Run revision，同一个 Run 的事务必须串行提交；Worker 增多还会增加领取竞争。这个设计保证 revision 和事件序号连续，是模块 4 正确性边界，但也是模块 5 必须量化和优化的瓶颈。

多进程崩溃测试使用 2 秒租约、50 毫秒心跳和 5 毫秒回收扫描周期。测试租约必须大于独立 Worker 的 1 秒本地安全余量，否则 Worker 会在领取后立即取消本地执行，测试无法验证真实的进程崩溃接管。修正参数后连续运行五轮均通过，其中一次带详细日志的运行从发送 `SIGKILL` 到 Run 成功约为 2.04 秒。这个结果验证恢复时间受租约和扫描周期控制，不代表默认配置：默认本地配置是 15 秒租约和 1 秒扫描，人工演示通常需要等待约一个租约周期再加扫描、领取和完成时间。

## 7. 当前限制

- 只有一个控制面协调者；Advisory Lock 用于拒绝第二个协调者，不提供控制面高可用。
- Worker 当前只执行安全 Mock Action，不能执行 Shell、文件、URL、容器或真实 Agent 任务。
- Worker 会话使用 Bearer Token，没有 OAuth/OIDC、mTLS、租户隔离或远程证书管理。
- PostgreSQL 同时承担状态和分发，单 Run revision 形成串行提交点。
- HTTP 拉取会产生空领取；指数退避降低压力，但增加空闲后首个任务的等待时间。
- 租约只能拒绝旧结果，不能撤销已经发生的外部副作用。
- 日志已有安全字段边界，但指标、分布式 Trace、告警和持续性能回归属于模块 5。
