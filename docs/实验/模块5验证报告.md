# 模块 5 验证报告

## 1. 验证目标与事实边界

本报告记录模块 5 的结构化日志、低基数 Prometheus 指标、OpenTelemetry 调用链、五类告警、八类故障实验和四种观测配置性能矩阵。

观测组件是诊断旁路，不是 Workflow、Run、Task、Attempt、Dispatch 或租约的业务事实来源。日志、指标、Trace 或 Webhook 失败不得改变 PostgreSQL 事务、租约所有权、结果幂等和模块 4 已有的恢复语义。

## 2. 验证环境

| 项目 | 值 |
| --- | --- |
| 日期 | 2026-08-26 |
| 主机 | Mac mini M4，Apple M4，`darwin/arm64` |
| Go | `go1.26.2 darwin/arm64` |
| PostgreSQL | Docker Compose 镜像 `postgres:16.10-bookworm` |
| Benchmark 任务 | 1,000 个无依赖 Mock 任务 |
| Worker 数 | 1、4、16 |
| Run 形态 | 1×1,000 或 8×125 |
| 观测配置 | `off`、`logs`、`logs_metrics`、`logs_metrics_tracing` |
| 轮次 | 每个组合预热 1 轮，正式 5 轮 |

测试使用本机回环网络、真实 PostgreSQL 和隔离临时数据库，不访问外部模型 API。Mock Executor 不执行 Shell、文件、URL 或真实 Agent 操作。

## 3. 观测契约验证

### 3.1 日志

- 控制面和独立 Worker 共用 `observability.NewLogger`，支持 text/json 与 debug/info/warn/error；
- HTTP、Worker API 和 Worker Runtime 记录可获得的 request_id、run_id、task_key、attempt、worker_id、dispatch_id、operation、duration_ms 和 error_code；
- 采样 Span 存在时，控制面、Worker API 和 Worker Client 日志从 Context 自动补充 trace_id、span_id；
- 成功的高频 Worker 协议操作使用 Debug，失败使用 Warn；
- 生产 Handler 过滤 Bearer Token、密码、API Key、Session Token 和 Lease Token；
- `error` 属性限制为 512 字节，UTF-8 截断不会产生无效编码；
- 日志不记录完整 Action、Input、任务结果或凭据。

### 3.2 指标

- `/metrics` 返回 Prometheus 文本且不查询业务数据库；
- HTTP 方法、路由模板、操作、状态、结果和错误码经过白名单归一化，未知值映射为 `unknown`；
- 非法 HTTP 状态码映射为 `unknown`；同一 Registry 重复构造 Metrics 时复用已注册 Collector，不触发重复注册 panic；
- run_id、task_key、attempt、worker_id、dispatch_id 和原始 URL 不作为指标标签；
- Coordinator 从 PostgreSQL 聚合队列、Worker 和活动租约快照，刷新对应 Gauge；
- `workload_db_pool_wait_seconds_total` 只累加 pgx 相邻累计快照的增量；
- Complete 和租约回收告警计数使用固定 64 个秒级桶，规则读取最近 30 秒窗口，内存不会随进程运行时间增长；
- 不提供事务外推测的 Run、Task、Attempt 和 Dispatch 生命周期 Counter。

### 3.3 Trace

- `TracingServiceName` 写入 OpenTelemetry Resource 的 `service.name`；
- `off` 使用 `NeverSample`，不创建可记录 Span；
- Worker 使用独立的 `WORKLOAD_WORKER_TRACING_MODE` 和 `WORKLOAD_WORKER_TRACING_SERVICE_NAME`；
- Worker Client 在 Claim、Heartbeat 和 Complete 请求中注入 W3C `traceparent`，控制面提取后创建子 Span；
- 成功与失败 Span 写入稳定 outcome、error_code 和 OpenTelemetry status；
- stdout 使用容量 256、最大批量 64、100 ms 批处理等待和 1 秒导出超时的 Batch Span Processor；
- 阻塞 Writer 测试证明 `Span.End` 不直接等待慢 Writer；队列满时允许丢弃，不承诺零丢失。

当前只证明单次 Worker HTTP 请求的 Client、HTTP 和 Worker API Span 父子关系。Run 创建、Coordinator 异步扫描和稍后 Worker Claim 之间没有持久化 Trace Context，不能写成整条 Run 自动属于一条 Trace。

## 4. 告警 E2E

五类规则使用真实本地 HTTP Webhook 接收器验证：

| 规则 | 触发 | 恢复 |
| --- | --- | --- |
| `queue_backlog` | 队列有任务且无可用槽位，持续 10 秒 | 队列清空或出现可用槽位，持续 5 秒 |
| `workers_offline` | 队列有任务且在线 Worker 为 0，持续 5 秒 | 至少一个 Worker 在线，持续 5 秒 |
| `lease_reclaim_errors` | 30 秒窗口内回收错误大于 0 | 连续一个窗口没有错误 |
| `complete_error_rate` | 至少 20 个样本、错误率大于 5%，持续 30 秒 | 样本仍足够且错误率低于 1% |
| `db_pool_near_exhaustion` | 使用率大于等于 80%，持续 10 秒 | 使用率低于 70%，持续 10 秒 |

每类规则持续满足后只发送一次 `firing`，恢复窗口满足后只发送一次 `resolved`，共 10 个事件；持续异常和持续恢复不会重复发送。输入缺失进入 `unknown`，只在状态变化时通知一次，不误判为恢复。

Runner 会记录 firing、resolved、unknown、notify success 和 notify error 指标。Webhook 返回 5xx 或超过客户端超时时，发送使用有限重试；4xx 不重试。Webhook 标签只接受 `component` 和 `severity` 的固定值集合，任意标签和业务 ID 会被丢弃。下一轮快照采集和调度业务路径不会等待通知完成。

## 5. 八类故障实验

八类场景均通过 `scripts/run-module5-faults.sh` 映射到独立自动化测试，并在 PostgreSQL 16 环境运行：

| 场景 | 注入方式 | 验证结果 | 证据边界 |
| --- | --- | --- | --- |
| `postgres-unavailable` | 真实 Repository 前一次性返回错误 | 下一次 Repository 调用恢复 | 不等价于网络断开或数据库进程重启 |
| `claim-delay` | Claim 前可取消延迟 | Context 到期取消，下一次 Claim 正常 | 验证客户端和包装器边界 |
| `complete-error` | Complete 一次性错误 | 相同租约和结果重试，Run 收敛为 `succeeded` | 不模拟响应提交后丢失 |
| `heartbeat-error` | Heartbeat 一次性错误 | 下一次心跳成功续租 | 不等价于长时间网络分区 |
| `coordinator-lock` | Advisory Lock 健康检查一次性错误 | 底层数据库锁仍可独立验证 | 生产控制面遇到致命锁错误会安全退出 |
| `worker-kill` | 真正强杀测试子 Worker | 第二个 Worker 约 2.05 秒接管；Attempt 为 `interrupted`、`succeeded` | 本机进程实验，不等价于整机掉电 |
| `lease-expiry` | 等待真实租约过期 | 旧 Complete 返回 `lease_lost`，新租约完成成功 | 外部副作用仍可能重复 |
| `pool-exhaustion` | 占满真实 pgx 单连接池 | 第二次获取按 Context 超时，释放后恢复 | 不代表生产数据库容量 |

`postgres-unavailable` 不停止、重启或删除共享 Docker PostgreSQL。物理停止 PostgreSQL、网络分区和数据库 crash recovery 不在模块 5 的八类自动化实验内。

## 6. 性能方法

每个组合处理相同的 1,000 个任务。单 Run 使用 1 个包含 1,000 个任务的 Run；多 Run 使用 8 个各 125 个任务的 Run。基准分别记录总耗时、tasks/s、Claim/Heartbeat/Complete P50/P95/P99、空领取次数、B/op 和 allocs/op。

基准直接调用 Repository，以便让 24 个组合保持相同业务输入，并在操作边界分别启用日志、进程内指标和 Span。它没有经过生产 HTTP 中间件、Coordinator 聚合快照或告警 Webhook，也没有采集最大队列深度、租约回收耗时、连接池峰值、进程 CPU、goroutine 和 BatchSpanProcessor 丢弃数。因此本报告不能用现有矩阵评价这些路径的独立开销。

以下表格使用五轮中位数，并保留最小至最大范围。中位数减少单个离群值对中心结果的影响，范围保留本机波动；不只使用均值，也不删除离群轮次。

## 9. 结果解释

单 Run 中，三种观测配置相对 `off` 的中位耗时差值约为 0.10%~6.39%；1 Worker 和 16 Worker 的部分轮次出现 67~77 秒的大离群值。多 Run 中，部分观测配置的中位耗时反而低于 `off` 1.43%~10.22%。这些组合按顺序而不是随机交错运行，因此数据库缓存、操作系统调度和 Go 运行时波动会进入差值。

负差值不表示日志或 Trace 能提高业务性能。当前证据只支持：应用侧日志、内存指标和写入 `io.Discard` 的批处理 Trace 开销没有稳定大到压过五轮样本波动。它不能代表真实网络 Trace 导出器、长期日志存储或生产采样策略的成本，也不能给出适用于所有输入的固定开销百分比。

Run 形态的差异更明确。关闭观测时，1、4、16 Worker 的单 Run吞吐中位数为 21.39、38.75、36.86 tasks/s，多 Run 为 28.09、133.1、164.5 tasks/s。单 Run 的全部状态提交共享一条 revision，16 Worker 继续增加并发不能绕过该串行点；8 个 Run 有独立 revision，可以并行提交。

## 10. 原始证据与复现命令

关闭观测和仅日志的原始输出保存在：

```text
/tmp/ai-workload-module5-formal
```

指标与 Trace 最终补跑输出保存在：

```text
/tmp/ai-workload-module5-final
```

原始输出包含机器、Go 版本、Compose 镜像、预热状态、五轮 Benchmark 和结束时间，不包含 Token。`/tmp` 文件属于当前电脑的临时证据，不提交 Git，也不保证换电脑后仍存在。

运行单个正式组合前，先加载本地配置并把业务数据库地址映射给隔离测试夹具：

```bash
set -a
source .env.local
set +a
export TEST_DATABASE_URL="$DATABASE_URL"
scripts/run-module5-benchmark.sh --workers 1 --runs 1 --observability off --output-dir /tmp/ai-workload-module5-evidence
```

运行八类故障中的 Worker 强杀场景：

```bash
scripts/run-module5-faults.sh --scenario worker-kill --output-dir /tmp/ai-workload-module5-evidence
```

脚本不会停止、重启或删除 Docker 容器。故障场景和完整人工操作说明以本地开发与配置手册为准。

## 11. 已知限制

- stdout Trace 导出器和测试 SpanRecorder 不代表生产采集链路；有界队列允许丢弃；
- `/metrics` 是本地只读出口，不包含长期存储和图表；
- Webhook 不保存告警状态，不接入真实邮件、短信或企业 IM；
- 低基数指标不能直接按单个 Run 聚合，单 Run 使用日志、Trace、状态 API 和数据库事件；
- `lease_reclaim_errors` 状态机已经验证，但生产 Coordinator 遇到回收数据库错误会安全退出，不能保证退出前一定发送告警；
- `postgres-unavailable` 只验证一次 Repository 错误，不覆盖网络分区、物理停库和数据库崩溃恢复；
- Benchmark 使用本机回环网络、Mock Executor 和单机 PostgreSQL，不包含真实模型延迟和跨主机网络；
- 性能矩阵直接走 Repository，不包含生产 HTTP、Coordinator 聚合查询和 Webhook，也没有最大队列、连接池峰值、CPU、goroutine 或 Span 丢弃数；
- 单 Run revision 和完整快照分配是当前实现的性能边界，结果不是生产容量或 SLA。
