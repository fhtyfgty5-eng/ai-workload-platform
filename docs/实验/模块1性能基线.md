# 模块 1：单机可靠工作流内核性能基线

## 1. 目的与结论边界

本文记录模块 1 首轮 Go Benchmark 的输入、环境、原始输出和观察结果，用于回答以下问题：

- 10,000 个任务的定义编译和恢复预处理成本是多少；
- 1,000 个 WorkflowRun 共享编译定义是否比重复编译更节省时间和分配量；
- 一次完成事件解锁大量直接下游时的成本是多少；
- JSON 快照在 100 和 10,000 个任务规模下的保存、读取成本是多少。

这些数据只代表指定机器、代码版本和输入构造下的首轮基线，不是服务等级目标，也不表示系统已经达到生产级。延迟、吞吐和内存验收阈值需要结合后续使用场景另行确认。

### 2.1 指标与术语

Go Benchmark 是 Go 标准库提供的可重复性能测量机制。输出中的三个主要指标分别是：

- `ns/op`：完成一次基准操作平均消耗的纳秒数，数值越小表示该输入下单次操作越快；
- `B/op`：完成一次基准操作产生的内存分配字节数，表示分配流量，不等于操作结束后的常驻内存；
- `allocs/op`：完成一次基准操作触发的内存分配次数。

基准名称末尾的 `-10` 表示本次 Go 进程使用的 `GOMAXPROCS` 为 10，也就是最多允许 10 个操作系统线程同时执行 Go 代码；它不是任务数或重复次数。DAG（Directed Acyclic Graph，有向无环图）表示任务依赖图中不存在沿有向边回到起点的环。

## 3. 基准输入

| 基准 | 输入和测量边界 |
| --- | --- |
| `CompileTenThousandTasks` | 10,000 个任务、9,999 条线性依赖，包含定义深拷贝、TaskKey 校验与索引、依赖编译和环检测 |
| `CompileRejectsTenThousandAndOneTasks` | 10,001 个合法形态任务，测量超过硬上限后的拒绝成本 |
| `CreateOneThousandRunsSharedDefinition` | 预先编译 100 任务线性定义，再创建 1,000 个共享同一定义指针的 RunSnapshot |
| `CreateOneThousandRunsSeparateDefinitions` | 每个 Run 都重新编译同一个 100 任务定义，并持有独立定义指针 |
| `EngineCompiledCacheHit` | 100 任务定义已经由 Engine 缓存，重复按 RunID 命中同一编译结果 |
| `DependencyUnlock` | 1 个上游和 9,999 个直接下游；不计写前快照复制，只测成功事件、状态事件记录和 9,999 条边的解锁 |
| `ResumeTenThousandTasks/WaitingDependencies` | 10,000 任务线性 DAG，无失败源；不计快照复制，只测恢复校验和依赖计数重算 |
| `ResumeTenThousandTasks/FailedAncestor` | 10,000 任务线性 DAG，首任务最终失败；不计快照复制，测失败向全部后代传播、状态事件和依赖重算 |
| `FileStoreSnapshot100Tasks` | 100 个 TaskRun 和 100 条状态事件的完整 JSON 快照，分别测 Save 和 Load |
| `FileStoreSnapshot10000Tasks` | 10,000 个 TaskRun 和 10,000 条状态事件的完整 JSON 快照，分别测 Save 和 Load |

共享与独立定义基准中的 `B/op` 是每次创建 1,000 个快照产生的总分配量，不等同于垃圾回收后的常驻堆内存。FileStore Save 包含 JSON 编码、临时文件写入、文件同步、关闭、原子替换和目录同步；Load 包含文件读取和 JSON 解码。

## 4. 运行命令

先用单次执行确认全部 Benchmark 能被发现：

```bash
go test ./workflow/... -run '^$' -bench 'Benchmark(Compile|Create|Engine|Dependency|FileStore|Resume)' -benchtime=1x -benchmem
```

再让每个基准运行约一秒并重复五轮：

```bash
go test ./workflow/... -run '^$' -bench . -benchmem -count=5
```

使用 `./workflow/...` 而不是只运行 `./workflow`，因为真实 FileStore 位于 `workflow/filestore` 子包；把 FileStore 基准放进父包会形成 Go 导入环。

## 7. 观察与瓶颈

1. 共享编译结果的方向得到数据支持。在当前输入下，创建 1,000 个共享定义的 RunSnapshot 平均约 1.376 ms、分配约 9.27 MB；每个 Run 分别编译平均约 17.662 ms、分配约 31.50 MB。后者约慢 12.84 倍，分配量约为 3.40 倍。
2. 10,000 任务线性 DAG 的完整 Compile 平均约 1.841 ms。超过上限的定义虽然约 0.261 ms 即被拒绝，但仍分配约 0.96 MB，因为当前实现先深拷贝输入再检查任务数量；这是进入不可信网络输入阶段前的优化候选，不在未确认阈值前改动模块 1 行为。
3. 无失败源的 10,000 任务恢复预处理平均约 0.117 ms、仅 3 次分配；失败祖先传播到全部后代时平均约 0.905 ms，但因记录 9,999 个任务状态事件，分配增至约 4.93 MB 和 20,020 次。算法遍历保持线性，事件对象是主要分配来源。
4. 一次成功事件解锁 9,999 个直接下游平均约 0.746 ms。约 4.76 MB 和 10,025 次分配主要来自为每个下游记录 ready 状态事件；未来如果该路径成为热点，应先分析事件存储布局，而不是取消状态审计。
5. FileStore 是当前最明显的延迟边界。100 任务 Save 已约 9.009 ms，说明文件和目录同步带来固定成本；10,000 任务 Save/Load 分别约 26.559 ms 和 29.887 ms，并产生约 14.59 MB 和 18.93 MB 分配。结果支持模块 2 转向数据库事务存储的路线，但不能仅凭本机数据决定数据库结构。
6. Engine 编译缓存命中为 0 分配，五轮约 7.38 ns/op；该微基准只测进程内互斥锁保护的 map 命中，不代表完整 Run 查询延迟。

## 8. 限制与后续阈值

- 测试只在一台 Apple M4 开发机上运行，没有跨机器、跨文件系统或持续集成环境对照；
- 没有固定 CPU 频率、隔离后台进程或清空文件系统缓存；五轮波动已经保留在原始输出中；
- FileStore 使用本机临时目录，结果受 APFS（Apple File System，苹果文件系统）、缓存和同步实现影响；
- 快照基准使用 pending TaskRun 和每任务一条合成事件，不包含大量 Attempt 历史或长结果文本；
- `B/op` 表示分配流量，不等于常驻内存，也没有测量垃圾回收暂停；
- 1,000 Run 基准测量 RunSnapshot 创建和定义共享策略，没有把 1,000 个 Run 注册为同时执行，也没有启动 1,000 个 Executor、goroutine（Go 运行时管理的轻量并发执行单元）或定时器；
- 恢复基准只测内存预处理，不包含 FileStore Load/Save 和后续 Executor 执行；这些成本已经拆分测量；
- 本轮没有并发运行多个 Benchmark，不代表 1,000 个 Run 同时执行时的调度吞吐；
- 尚未确认“可接受”的编译、恢复、快照读写和内存阈值，因此当前只保留基线与瓶颈，不设置持续集成（Continuous Integration，CI）性能门禁。

用户审核本报告后，需要确定是否以当前数据作为模块 1 的首轮验收基线，以及哪些指标应在模块 2 或模块 5 中设为回归阈值。
