# 模块 3 验证与限制

## 验证范围

模块 3 在已有可靠工作流内核和控制面之上增加：

- 统一 Model Adapter（模型适配器）接口；
- 默认离线 Mock Model；
- 人工显式启用的 OpenAI-compatible HTTP 模型适配器；
- 工具注册表和只读工作流目录查询工具；
- 自然语言目标到结构化 Workflow 草稿；
- 用户事实、Agent 假设和待确认问题；
- 参数、权限、任务超时、Agent Workflow 并发和 DAG 校验；
- 内容哈希与人工确认；
- `agent draft`、`agent validate`、`agent confirm` CLI。

本报告只记录已经运行的自动化测试、本机 Mock CLI 演示和性能基线。外部真实模型调用需要用户提供合法服务和凭证，本次没有把某个外部供应商的可用性写成已验证事实。

## 环境

- 验证日期：2026-08-22；
- macOS，Apple M4，ARM64，10 个逻辑 CPU；
- Go 1.26；
- 默认模型：不访问网络的 Mock Model；
- HTTP 适配器测试：本机 `httptest.Server`，不访问外部网络；
- API Key：自动化测试只使用测试字符串，不读取本机真实凭证。

## 自动化覆盖

模块 3 的测试覆盖：

- `TaskDefinition.Input` 的嵌套 JSON 深拷贝、64 KiB 上限、非法 Go 值和循环引用；
- Engine 把隔离后的 Input 传给 Executor，旧定义不带 Input 时保持兼容；
- 4 轮模型、8 次工具、64 KiB 响应、30 秒 Runtime 和 5 秒工具调用上限；
- API Key、Authorization、Token 和密码字段在嵌套对象、切片中的审计脱敏；
- 工具白名单、权限拒绝、未知字段和超长查询；
- 工作流目录返回只读副本，不提供文件路径、命令或 URL 输入；
- 草稿状态转换、事实/假设/问题、规范化 JSON 哈希和定义、校验结果、状态篡改检测；
- 未知 Action、必填参数、类型、枚举、权限、任务超时、Agent Workflow 并发、开放问题和 DAG 校验；
- Mock Model 的确定性工具调用与草稿输出；
- 临时模型错误只重试一次，永久错误不重试；
- Runtime 取消、工具超时、重复工具调用 ID、模型轮数和工具次数耗尽；
- 成功、失败和取消路径的模型轮数与工具调用数审计；
- 确认前再次校验和编译，确认操作不创建 Workflow 或 Run；
- HTTP 适配器的结构化请求、429 映射、非法响应、Context 取消和凭证日志边界；
- CLI 参数、严格 JSON、失败退出码、生成、校验和确认链路。

默认全仓验证命令：

```bash
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
bash scripts/test-verify-docs.sh
bash scripts/verify-docs.sh
git diff --check
```

涉及 `httptest.Server` 的测试需要允许本机回环端口。真实 PostgreSQL 集成测试需要额外设置 `TEST_DATABASE_URL`；这两个条件都不表示测试会访问公网模型。

## Mock CLI 人工演示

实际运行以下链路：

```text
自然语言目标
  -> Mock Model 请求 workflow_catalog_query
  -> 只读目录返回模板
  -> 生成三任务草稿
  -> 校验后进入 needs_confirmation
  -> 使用 content_hash 确认
  -> 输出 WorkflowDefinition
```

实际草稿包含：

- `draft_id=draft_9913729ffa0b49be6bb3121c`；
- 事实：用户要求读取 `article.md`，并按读取、清洗、摘要的顺序处理；
- 假设：清洗模式为 `standard`，摘要上限为 200 词；
- 待确认问题：空；
- 工具调用：`workflow_catalog_query`，结果为 `allowed`；
- 校验错误：0；
- 校验警告：1 个 `assumption_present`；
- 状态：`needs_confirmation`；
- 最终任务依赖：`read -> clean -> summarize`。

确认命令只输出最终 WorkflowDefinition。最终定义中的默认 `max_attempts=1` 来自模块 1 编译器的规范化结果；确认过程没有启动 Run，也没有写入 PostgreSQL。

## 安全和可靠性边界

- 模型只能提出工具调用，Runtime 只执行注册表中的工具；第一版唯一工具只读查询静态目录；
- 工具接口没有 Shell、任意文件路径、任意 URL 或数据库写操作；
- 工具白名单降低误调用风险，但不是任意恶意代码沙箱；
- 内容哈希检测审核后修改，不是数字签名，也不证明是谁进行了确认；
- 审计使用内存 Sink，进程退出后不会持久保存；模块 5 再接入完整可观测性与持久审计；
- HTTP 适配器只验证 OpenAI-compatible 合约，不保证所有供应商完全兼容；
- Mock Model 只支持固定文档处理示例，不衡量自然语言理解质量；
- 模块 3 只校验任务超时和 Agent Workflow 并发；CPU、内存和临时存储尚未进入任务定义，留到模块 6 的真实执行环境；
- 最终控制面仍使用安全 Mock Executor，Action 和 Input 会进入可靠执行链路，但不会真的读取、清洗或摘要文件；
- Agent 生成、任务执行和多 Worker 是三个不同边界。本模块完成前两个边界中的草稿生成与模型/工具协议，没有实现多 Worker 或生产任务环境。

## 外部真实模型待验证项

用户配置合法 Endpoint、Model 和 API Key 后，需要人工确认：

1. 供应商支持 Chat Completions 风格的结构化输出和工具调用；
2. 工具名称、参数 Schema 和返回结构符合供应商限制；
3. 429、5xx、超时和取消按平台错误码转换；
4. 日志和终端输出不包含 API Key；
5. 实际费用、Token 用量和响应延迟记录为供应商实验，不混入本地平台基线。

在这组人工验证完成前，只能表述为“真实模型适配器已经实现并通过本地 HTTP 合约测试”，不能表述为“某个真实模型供应商已经端到端通过”。

## 真实模型人工冒烟记录模板

这项验证需要作者在本机主动配置供应商地址、模型名和 API Key 后执行，不属于默认自动化测试，也不应放入 CI。建议只记录下面这些脱敏信息：

| 项目 | 记录内容 |
| --- | --- |
| 服务类型 | OpenAI-compatible，或供应商公开的兼容协议名称 |
| 模型名 | 模型标识，不记录 API Key |
| 调用目标 | “先读取 article.md，再清洗内容，最后生成摘要” |
| 工具调用 | 是否成功调用只读任务目录，调用次数是否在上限内 |
| 结构化输出 | 是否返回可解析的 WorkflowDraft JSON |
| 服务端校验 | 是否通过 Action、Input、依赖、超时、权限和 DAG 校验 |
| 人工确认 | 是否使用原始 `content_hash` 成功确认 |
| 错误边界 | 超时、429、5xx 或非法 JSON 的实际表现 |
| 性能与费用 | 首 token/完整响应耗时、Token 用量和费用的脱敏摘要 |

不要记录完整 Prompt、业务文件内容、Authorization 头、API Key 或包含凭证的 Endpoint 查询参数。只有在工具调用、结构化输出和服务端审核都成功后，才能把该供应商写成“完成一次人工端到端冒烟”；这仍然不等于所有场景或生产容量已经验证。
