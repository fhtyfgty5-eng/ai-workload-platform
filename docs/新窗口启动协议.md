# 新窗口启动协议

## 目的

每个新的 Codex 窗口都视为一个没有上一段对话记忆的协作者。它不能假设自己知道项目已经做了什么，也不能只阅读一个状态文件后直接修改代码。

本协议用于让新的 Codex 窗口快速恢复上下文，并在动手前接受用户确认。

## 用户启动提示词

新窗口开始时，将下面这段文字和项目路径一起发送给 Codex：

```text
这是 ai-workload-platform 项目的续接任务。

请先进入本机 ai-workload-platform 仓库根目录；不要在提示词或公开文档中写死个人绝对路径。

请先不要写代码，也不要修改文件。请按 docs/新窗口启动协议.md 执行：

1. 阅读 README.md、项目状态.md、docs/产品/产品说明.md、docs/架构/架构基线.md、docs/学习/学习资料规范.md 和 docs/计划/项目路线图.md；
2. 执行 git status --short --branch 和 git log -5 --oneline；
3. 根据项目状态中的“当前阶段、当前模块、下一步”和最近提交，判断当前实际进度；
4. 找到当前模块对应的详细计划、学习资料、代码和测试；
5. 运行当前模块已有的验证命令；
6. 检查待公开内容是否包含密钥、公司信息、业务数据、本机绝对路径或未经验证的产品声明；
7. 用中文汇报：项目目标、当前模块、已完成内容、未完成内容、发现的不一致、建议的下一步；
8. 等我确认后再开始任何实现。

学习资料要面向没有相关背景的读者，首次出现的专业名词必须解释，并说明技术选型和未选择同类方案的原因。
```

## Codex 必须阅读的文件顺序

1. `README.md`：项目入口和安全边界；
2. `项目状态.md`：当前事实、当前模块和下一步；
3. `docs/产品/产品说明.md`：产品价值、用户和使用边界；
4. `docs/架构/架构基线.md`：已批准的系统结构；
5. `docs/学习/学习资料规范.md`：学习资料的读者、结构和技术选型要求；
6. `docs/计划/项目路线图.md`：模块顺序和验收目标；
7. 当前模块的详细计划；
8. 当前模块的学习资料、代码和测试。

如果这些文件之间有冲突，以最新的用户确认和 Git 中最近的实际代码为准，并先报告冲突，不要自行选择后继续改动。

如果当前模块缺少详细计划、学习资料、代码或测试，必须在汇报中明确写出“缺失”，不能把上游概览文档或空目录当作已完成交付物。

`README.md` 是面向 GitHub 访问者的产品入口，不承担完整的 Codex 交接职责。内部续接事实以 `项目状态.md` 和本协议为准，但二者都必须与 Git、代码和测试的实际状态核对。

## 开源内容检查

仓库计划在条件成熟后公开。每次准备提交公开文档、示例、配置或日志前，至少检查：

1. 是否包含 API Key、访问令牌、私钥、密码或可用凭证；
2. 是否包含当前或过往公司的代码、内部名称、域名、业务数据、配置或未公开文档；
3. 是否包含用户名、个人绝对路径、内部网络地址或不必要的环境信息；
4. 是否把计划能力、性能目标或差异化假设写成已经实现和验证的事实；
5. 是否引用了许可证不明确、不能再分发的代码、图片、数据或其他资源；
6. 是否将 Codex 交接、用户确认、Git 操作或本机验证输出混入面向用户的产品说明和技术文章；
7. 新增依赖是否记录来源、版本、用途和许可证风险。

自动检查只能发现已知模式，不能替代人工保密和版权审查。Git 历史中的作者邮箱、本机路径或已删除秘密也不会因为修改当前文件自动消失，公开前必须单独检查完整历史。

## 博客文章恢复检查

新窗口准备处理学习文章时，必须先完成以下检查，并在修改正文前报告发现的问题：

1. 从 `docs/学习/学习资料规范.md` 和 `项目状态.md` 确认专栏定位、当前项目阶段和文章状态；
2. 判断文章类型是项目总览篇、技术学习篇还是模块实践篇，并按照对应职责检查正文；
3. 检查正文是否混入 Codex 交接、Git 操作、仓库管理、文档验收输出等仅供项目内部使用的内容；
4. 项目总览篇必须明确说明这是一个从零开发的新项目，并交代产品目标、目标用户、核心边界以及与现有产品的差异；
5. 技术学习篇必须面向没有相关背景的读者解释首次出现的专业名词，并说明相关技术在本项目中的作用、技术选型和未选择同类方案的原因；
6. 模块实践篇必须围绕已经发生且可复现的设计、实现、测试或故障实验展开，不能用文档检查结果代替业务行为验证；
7. 如果同一篇文章同时承担完整的项目介绍和详细的技术科普，或者混入项目交接记录，先报告职责冲突并建议拆分，不直接改写；
8. 不得为了突出项目介绍而删除必要的术语解释、类比、示例、失败场景或替代方案，技术学习篇应保留足够的学习深度。

专栏名称、文章发布状态、验证日期和公开地址只记录在 `项目状态.md`。可直接发布的文章正文不得包含这些内部元数据。

## 每次会话结束前必须更新的内容

在用户审核模块前，更新 `项目状态.md` 的“当前阶段”“已完成”“正在进行”“下一步”“测试状态”和“最近交接”。

每次交接至少记录：

- 日期；
- 当前分支和最近提交；
- 本次完成的工作；
- 尚未完成的工作；
- 当前阻塞或待确认问题；
- 运行过的验证命令及结果；
- 下一窗口应该先读或先做什么。

## 防止上下文漂移

- 探索性问题不会自动改变已批准范围；
- 新想法先写入“候选想法”，获得用户批准后才进入正式计划；
- 任何范围调整都要更新 `docs/决策/` 中的决策记录；
- 状态文件不能代替代码和测试检查；
- 没有用户确认，不提交 Git、不公开仓库、不部署外部服务。

## 新窗口的最小汇报格式

```text
我已阅读核心文档并检查仓库。

项目目标：
当前阶段/模块：
已完成：
未完成：
代码与文档是否一致：
验证结果：
下一步建议：

我会等待确认后再修改文件。
```
