# 维护者启动指南

## 目的

本指南帮助新的维护者在不了解仓库历史的情况下恢复上下文、验证当前状态并安全开始工作。它适用于本地开发、代码审查、缺陷修复和功能演进，不替代产品文档或部署手册。

## 先建立项目上下文

按以下顺序阅读：

1. [README](../README.md)：产品目标、快速开始、当前能力和安全边界；
2. [项目状态](../项目状态.md)：已完成交付、验证证据和明确限制；
3. [产品说明](产品/产品说明.md)：目标用户、适用场景与非目标；
4. [架构基线](架构/架构基线.md)：组件职责、数据流和模块边界；
5. [项目路线图](计划/项目路线图.md)：模块为何按当前顺序演进；
6. 当前问题对应的需求设计、实施记录、学习文章、实验报告、代码和测试。

文档描述的是已知事实和设计意图，Git 状态与测试结果才是当前代码状态的最终依据。

## 核对工作区

在仓库根目录运行：

```bash
git status --short --branch
git log -5 --oneline
bash scripts/verify-docs.sh
bash scripts/check-secrets.sh
bash scripts/check-dependency-licenses.sh
```

工作区存在未提交修改时，先阅读并保留这些修改。不要用 `git reset --hard`、`git checkout --` 或其他破坏性命令覆盖未知来源的文件。

## 找到验证入口

- 后端：`go test ./...`、`go test -race ./...`、`go vet ./...`；
- 前端：进入 `web/` 后运行 `npm test -- --run`、`npm run typecheck`、`npm run build`；
- 文档：`bash scripts/test-verify-docs.sh` 与 `bash scripts/verify-docs.sh`；
- 安全与许可证：`bash scripts/check-secrets.sh` 与 `bash scripts/check-dependency-licenses.sh`；
- Kubernetes 清单：`bash scripts/verify-k8s-manifests.sh`；
- 模块专属实验：查看 `docs/实验/` 中对应报告列出的命令和环境前提。

本地启动 PostgreSQL、控制面、Worker、控制台和完整演示的步骤见[本地开发与配置](部署/本地开发与配置.md)。默认演示使用 Mock Model/Executor，不需要真实模型 API Key。

## 维护原则

- 先用现有测试或可复现实验确认行为，再调整实现或结论；
- 保持 API、状态语义、数据库迁移和安全边界与架构文档一致；
- 新增术语时在首次出现处解释；学习文章必须说明技术选型、替代方案和证据边界；
- 不提交 Token、密码、业务数据、公司资料、个人绝对路径、容器卷或构建产物；
- 不把 Mock 测试、静态清单或单次本机数据表述为真实模型、生产容量或完整隔离证据；
- 对外部副作用继续采用至少执行一次语义，并在执行器侧实现幂等或去重；
- 修改后按风险范围运行验证，并更新相关设计、部署、学习和实验文档。

## 模块边界

模块 0 至模块 7 的当前交付已经完成。后续工作应以明确问题为起点，而不是为了技术栈关键词引入未使用的基础设施。当前最值得继续补充证据的边界是：真实模型兼容性、Kubernetes 网络实际阻断、CPU/临时存储限制、完整 Worker 租约恢复，以及生产环境下的容量与高可用设计。
