# 模块 0 文章大纲

## 使用说明

> 历史说明：本大纲记录模块 0 文章形成时的拆分思路。当前文章规则以 [`学习资料规范`](../学习资料规范.md) 为准，默认使用直接定义、数据流和最小示例，不把生活类比或面试问答作为固定章节。

模块 0 不把产品介绍和完整技术科普强行放在同一篇文章中，而是拆成一篇项目总览篇和一篇技术学习篇。两篇文章都属于草稿，先审核结构，再分别完善正文。尚未实现的能力必须写成设计目标或后续验证计划，不能写成已经完成的事实。

文章之间的关系：

```text
项目总览篇：建立产品认知
    -> 技术学习篇：解释产品赖以实现的核心技术
        -> 后续模块实践篇：记录真实代码、测试和实验
```

---

## 第一篇：项目总览篇

### 标题

`从 0 构建 AI Workload Platform（一）：为什么做、做什么、与现有产品有什么不同`

### 文章目标

让读者从文章开头就知道，作者正在从零开发一个名为 AI Workload Platform 的新项目，而不是单纯科普一个行业术语。读者读完后，应能说明产品解决什么问题、谁会使用、如何使用、与成熟产品是什么关系，以及哪些差异化方向仍待验证。

### 建议章节

1. **开篇说明正在开发什么**
   - 项目名称；
   - 要解决的问题；
   - 一句话产品定义；
   - 当前仍处于从零设计和实现阶段。

2. **现实问题：为什么需要这个项目**
   - 多步骤 AI 或数据任务的典型流程；
   - 脚本、定时任务和人工操作的局限；
   - 任务失败、重试、超时、状态丢失和资源冲突；
   - 哪些简单场景不需要这个平台。

3. **产品到底做什么**
   - 工作流定义；
   - 任务依赖；
   - 单 Agent、多 Agent 和普通程序任务；
   - 状态记录；
   - 调度、重试、取消、恢复、资源控制和审计。

4. **用户如何使用**
   - 描述任务；
   - 生成工作流草稿；
   - 校验依赖、参数、权限和资源；
   - 用户确认；
   - 执行并查看状态；
   - 处理失败或恢复任务。

5. **目标用户和典型场景**
   - AI 应用开发者；
   - 数据处理和实验流程维护者；
   - 需要可靠执行后台任务的工程团队；
   - 搜索、推荐、数据清洗和模型评估等场景。

6. **与成熟产品的关系**
   - Airflow、Prefect 等数据工作流平台；
   - Temporal 等可靠任务执行平台；
   - Argo Workflows、Kubernetes Jobs 等容器化执行方案；
   - LangGraph 等 Agent 工作流方案；
   - 比较产品定位、任务类型、可靠性能力、Agent 支持和资源控制，不使用没有证据的全面领先结论。

7. **本项目希望验证的差异化方向**
   - 普通程序任务、AI 任务和 Agent 任务是否能统一管理；
   - 自然语言生成工作流草稿后，经过校验和用户确认再执行；
   - Agent 执行是否能纳入重试、超时、取消、恢复和审计；
   - 以上是项目假设，不能提前写成已证明的市场优势。

8. **技术路线和推进顺序**
   - 先用 Go、本地进程和 Mock Agent 验证核心工作流；
   - 再考虑持久化、容器、Kubernetes 和真实模型；
   - 解释为什么不一开始引入完整基础设施。

9. **当前边界和项目状态**
   - 当前处于模块 0；
   - 尚无业务代码；
   - 已完成产品定义和技术基线；
   - 尚未证明性能、故障恢复和生产可用性。

10. **总结**
    - 再次说明产品是什么；
    - 说明与成熟产品的关系；
    - 说明当前最重要的待验证问题；
    - 引出第二篇技术学习篇。

### 正文边界

- 重点是产品认知，不展开完整的 DAG、状态机和重试实现细节；
- 不写 Codex 交接、Git、目录管理、文档验证输出或用户对话记录；
- 不把“待验证的差异化方向”写成市场优势；
- 技术名词只解释理解产品所需的最小范围，详细解释留给第二篇。

## 第二篇：技术学习篇

### 标题

`从 0 构建 AI Workload Platform（二）：工作流、DAG、状态机与可靠执行基础`

### 文章目标

让没有相关背景的读者理解工作流平台的核心技术，并知道这些技术在 AI Workload Platform 中解决什么问题。文章保留详细术语、最小示例、失败场景和替代方案，但不混入项目交接或仓库验收内容。

### 建议章节

1. **开篇说明技术与项目的关系**
   - AI Workload Platform 为什么不能只依赖一段脚本；
   - 本文解释的技术如何支撑任务依赖、状态管理和失败恢复。

2. **先看一个最小问题**
   - 以数据准备、模型调用、结果整理三个步骤为例；
   - 说明步骤之间存在依赖；
   - 说明中间失败后不能简单地从头重跑。

3. **前置知识**
   - 任务；
   - 工作流；
   - 调度器；
   - 执行节点；
   - 持久化状态。

4. **核心术语**
   - Workflow：工作流；
   - DAG（Directed Acyclic Graph，有向无环图）；
   - Dependency：任务依赖；
   - Scheduler：调度器；
   - State Machine：状态机；
   - Durable Execution：持久化执行；
   - Retry、Timeout、Cancellation、Recovery、Idempotency；
   - 首次出现时给出英文全称、中文含义和项目中的具体作用。

5. **DAG 如何表达任务依赖**
   - 使用 A -> B -> C 和并行分支示例；
   - 解释为什么必须禁止环；
   - 说明拓扑排序和依赖解锁的基本思路；
   - 说明 DAG 只描述先后关系，不等于完整的运行状态。

6. **状态机如何表达任务生命周期**
   - Pending、Ready、Running、Succeeded、Failed、Retrying、Cancelling、Cancelled、TimedOut 等状态；
   - 说明每次状态变化的触发条件；
   - 说明“取消中”和“已取消”的区别；
   - 说明非法状态转换为什么必须拒绝。

7. **DAG 与状态机如何配合**
   - DAG 决定任务什么时候具备运行条件；
   - 状态机记录任务当前处于什么阶段；
   - 调度器根据两者决定是否启动后续任务。

8. **最小执行示例**
   - 输入工作流；
   - 初始状态；
   - 任务执行；
   - 依赖解锁；
   - 失败、重试和最终状态；
   - 使用表格或代码块展示状态变化。

9. **可靠执行必须处理什么**
   - 进程崩溃；
   - 网络失败；
   - 重复提交；
   - 超时但远端实际已完成；
   - 取消请求到达太晚；
   - 状态保存成功但结果上报失败；
   - 重试非幂等操作的风险。

10. **技术选型**
    - 为什么当前控制面选择 Go；
    - 为什么先用本地进程；
    - 为什么使用 Mock Agent；
    - 为什么通过接口隔离外部模型和存储；
    - 对比 Python、Node.js、Rust、Docker、Kubernetes、真实模型和直接绑定 SDK 的方案。

11. **在项目中的组件位置**
    - 工作流定义；
    - 校验器；
    - 调度器；
    - 状态存储接口；
    - Agent 或普通程序执行器；
    - 后续的容器和节点管理。

12. **如何验证**
    - DAG 依赖解锁测试；
    - 环检测测试；
    - 重试测试；
    - 超时和取消测试；
    - 幂等测试；
    - 重启恢复测试；
    - 离线 Mock 测试；
    - 当前没有业务代码时，明确标记为后续验证计划，不伪造实验结果。

13. **常见错误和失败场景**
    - 依赖环；
    - 无限重试；
    - 只在内存保存状态；
    - 把超时当作远端未执行；
    - 把容器当成绝对安全边界；
    - 盲目使用多 Agent。

14. **进一步思考**
    - 哪些失败可以自动重试；
    - 如何判断一次执行是否真正完成；
    - 如何设计恢复后的幂等边界；
    - 多 Agent 什么时候值得增加复杂度；
    - 这些问题作为作者的后续思考，不伪装成读者已经提出的问题。

15. **总结与限制**
    - 总结 DAG、状态机和可靠执行之间的关系；
    - 说明当前内容是设计和学习基线；
    - 明确真正的状态转换、恢复和性能结论必须等待后续代码和测试。

### 正文边界

- 开头必须说明技术在 AI Workload Platform 中解决的具体问题；
- 首次出现的专业名词必须解释，并说明技术作用、选型原因和未选择同类方案的原因；
- 必须保留类比、最小示例、失败场景和替代方案，以保证学习深度；
- 当前没有业务代码和业务实验，所有验证部分只能写成验证计划；
- 不写 Codex 交接、Git、目录管理、文档验证输出或用户对话记录；
- 不写未发生的读者提问。
