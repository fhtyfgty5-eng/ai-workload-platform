## 摘要

本文面向没有工作流平台背景的读者，解释 AI（Artificial Intelligence，人工智能）与数据任务为什么需要可靠的执行平台，并用一个最小例子介绍项目后续会使用的核心概念。

读完后，读者应该能够：

- 用一个四步示例说明工作流如何执行；
- 区分不同的任务执行方式；
- 说明管理任务的部分与实际运行任务的部分有什么不同；
- 解释为什么失败后再次执行必须考虑重复结果；
- 说明当前技术选择解决了什么问题，以及何时应该换成其他方案。

本文只建立模块 0 的概念基线，不代表工作流内核已经实现，也不提供生产环境性能结论。

## 1. 本章要解决的问题

很多后台工作不是运行一次命令就结束，而是由多个有先后关系的步骤组成。例如，把新文档加入搜索系统可能需要读取、清洗、生成向量并更新索引。任何一步失败，都可能留下不完整的数据。

单个脚本可以完成正常路径，却通常不能自动回答这些问题：

- 进程崩溃后，哪些步骤已经完成；
- 同一个步骤是否会被两台机器重复执行；
- 失败后应该重试几次，重试是否会产生重复数据；
- 前置步骤没有成功时，后续步骤为什么没有启动；
- 用户取消任务时，正在运行的步骤应该怎样结束；
- 外部模型或服务暂时不可用时，整个流程怎样恢复。

本项目研究的核心不是“如何写更多脚本”，而是“如何可靠地管理不同执行单元的整个运行过程”。

## 2. 前置知识

阅读本文不要求具备任何工作流平台或基础设施背景。

只需要知道三个基础概念：

- **程序**：一组可以被计算机执行的指令；
- **进程（Process）**：程序的一次运行实例，例如同一个程序同时启动两次会产生两个进程；
- **数据库（Database）**：用于长期保存和查询结构化数据的系统，程序退出后其中的数据通常仍然存在。

分布式系统（Distributed System，分布式系统）是多个通过网络协作的计算机或进程组成的系统。网络可能延迟或中断，进程也可能独立崩溃，因此“某一步是否真正成功”比单机函数调用更难判断。本项目先从单机内核开始，后续才进入多节点阶段。

## 3. 一句话定义

工作流平台是一套保存执行状态、检查步骤依赖、安排任务运行并处理失败的系统，让由多个步骤组成的后台工作最终能够可靠完成。

## 4. 中英文术语和缩写

### 4.1 工作流、任务和依赖

- **工作流（Workflow）**：为完成一个目标而组织起来的一组任务及其关系。例如“处理文档并更新索引”是一个工作流。
- **任务（Task）**：工作流中可以单独执行和记录结果的最小步骤。例如“清洗一篇文档”是一个任务。
- **依赖（Dependency）**：一个任务开始前必须满足的条件。若“生成向量”依赖“清洗文档”，清洗成功前不能生成向量。
- **编排（Orchestration）**：根据依赖、状态和策略决定任务何时执行、在哪里执行以及失败后怎么办。

### 4.2 任务依赖图

DAG 是 Directed Acyclic Graph 的缩写，中文是**有向无环图**：

- **有向（Directed）**表示关系有方向，例如 A -> B 表示 B 依赖 A；
- **无环（Acyclic）**表示不能沿依赖关系绕一圈回到原任务。

如果 A 依赖 B，同时 B 又依赖 A，两个任务都会永远等待，因此工作流提交前必须检查依赖环。

### 4.3 不同执行方式

- **Agent（智能代理）**：根据目标和上下文选择模型、工具或操作步骤并返回结果的软件执行单元。它的输出可能受到模型、提示词和外部工具影响，不一定每次相同。
- **Mock Agent（模拟智能代理）**：不调用真实模型，而是按测试预设返回成功、失败、超时或指定结果的替代实现。Mock 的含义是“模拟真实依赖的可控对象”。
- **普通程序任务（Program Task）**：按确定代码执行的任务，例如解析文件或计算校验和。它通常比 Agent 任务更容易重复验证。

API 是 Application Programming Interface 的缩写，中文是**应用程序编程接口**，用于让不同程序按约定交换请求和结果。API Key 是接口访问凭证。Agent 不等于大模型，也不等于 API Key；多个逻辑 Agent 可以合法共享一个凭证，但仍需遵守供应商限制。

### 4.4 管理与执行职责

- **控制面（Control Plane）**：接收工作流、校验依赖、保存状态、判断可执行任务并处理重试和取消的管理部分。可以把它理解为调度室。
- **执行节点（Worker Node）**：真正启动普通程序或 Agent、收集日志并上报结果的执行部分。Worker 的中文常译为“工作节点”或“执行节点”。
- **调度器（Scheduler）**：控制面中选择“接下来运行哪个任务”的组件。

控制面决定做什么，执行节点负责实际去做。两者分开后，未来才能让多个执行节点共享同一套状态和调度规则。

### 4.5 状态保存与恢复

- **状态（State）**：任务在某一时刻所处的阶段，例如等待、可运行、运行中、成功、失败或已取消。
- **状态机（State Machine）**：规定允许出现哪些状态，以及状态之间可以怎样转换的模型。例如成功任务不能无原因重新变成运行中。
- **持久化（Persistence）**：把状态保存到进程退出后仍可读取的存储介质，而不是只放在内存中。
- **故障恢复（Failure Recovery）**：进程或节点故障后，根据持久化状态继续处理尚未完成的工作。

### 4.6 失败与重复执行

- **重试（Retry）**：任务失败后，按规则再次执行；
- **超时（Timeout）**：任务超过允许时间仍未结束时，把它视为异常并采取终止、重试或人工处理；
- **取消（Cancellation）**：用户或系统要求不再继续当前工作流；
- **幂等（Idempotency）**：同一个操作执行一次或重复执行多次，最终业务结果相同。

例如“把订单状态设为已完成”容易设计成幂等操作；“给余额增加 100 元”如果没有唯一请求编号，重复执行会增加多次，通常不是幂等操作。可靠平台可以发起重试，但业务任务仍需提供幂等机制或补偿策略。

补偿（Compensation）是用另一个明确操作抵消已经发生的影响，例如奖励发错后创建一条反向记录。补偿不等于删除历史，也不一定能完全恢复外部世界的状态。

## 5. 生活类比

可以把工作流平台想象成餐厅：

- 菜单上的套餐是工作流；
- 洗菜、切菜、烹饪和装盘是任务；
- “切菜前必须洗菜”是依赖；
- 店长是控制面，决定订单何时进入哪个工位；
- 厨师和工位是执行节点；
- 订单小票是持久化状态，厨房短暂停电后仍知道哪些菜没有完成；
- 某道菜重新制作是重试；
- 同一张小票只能出一份菜是幂等要求。

这个类比也有边界：软件任务可能跨机器运行，网络消息可能重复或延迟，外部系统也可能只完成了一半，因此真实实现需要比餐厅小票更严格的状态和唯一标识。

## 6. 最小示例

假设要处理一批新文档：

向量（Vector）是用一组数字表示文本特征的数据结构；索引（Index）是为了更快查找数据而建立的结构。本文只使用它们说明任务关系，不讨论具体算法。

```text
T1 读取文档
  -> T2 清洗内容
      -> T3 生成向量
          -> T4 更新索引
```

### 6.1 输入和输出

| 任务 | 输入 | 输出 | 失败示例 |
|---|---|---|---|
| T1 读取文档 | 文档位置 | 原始文本 | 文件不存在 |
| T2 清洗内容 | 原始文本 | 规范化文本 | 文本格式无法解析 |
| T3 生成向量 | 规范化文本 | 数字向量 | 模型服务超时 |
| T4 更新索引 | 文档编号和向量 | 索引版本 | 存储暂时不可用 |

### 6.2 正常执行

1. 平台保存四个任务和三条依赖；
2. T1 没有前置依赖，因此进入可运行状态；
3. T1 成功后，T2 才能运行；
4. T2、T3、T4 依次成功；
5. 工作流被标记为成功。

### 6.3 失败执行

如果 T3 调用模型时超时：

1. 平台记录 T3 本次尝试失败，而不是忘记它执行过；
2. T4 保持等待，因为依赖尚未成功；
3. 平台根据重试策略决定何时再次执行 T3；
4. T3 重试成功后才允许 T4 运行；
5. 如果达到最大重试次数，工作流进入失败或等待人工处理状态。

## 7. 不使用统一平台时会发生什么

直接串联四个脚本在任务很少时成本最低，但随着数量和风险增加，常见问题包括：

- 每个脚本分别实现日志、重试和超时，规则不一致；
- 进程重启后只知道脚本退出，不知道哪个业务步骤已完成；
- 人工重跑整个脚本，导致已经成功的步骤重复写数据；
- 两台机器同时执行同一批文档；
- T3 失败后 T4 仍被错误启动；
- 用户只能查看散落日志，无法查询统一的工作流状态；
- Agent 获得过多文件、网络或工具权限。

统一平台也有代价：需要维护状态模型、存储、调度和监控。对于一次性、失败后可以直接人工重跑的小脚本，使用完整平台反而会增加复杂度。

## 8. 在本项目中的位置

项目按模块逐步引入复杂度：

可观测性（Observability）是通过日志、指标和调用链理解系统内部运行情况的能力。本地集群资源调度是后续用于验证多个执行环境和资源限制的阶段。

```text
模块 0：定义价值、边界、术语和交接方式
  -> 模块 1：单机可靠工作流内核
  -> 模块 2：自然语言草稿与校验
  -> 模块 3：多节点执行与故障恢复
  -> 模块 4：受限执行环境
  -> 后续模块：可观测性、真实 Agent、案例和本地集群资源调度
```

模块 0 不实现代码。它的作用是让后续实现有稳定语言：当计划写“任务进入运行中状态”或“Mock Agent 返回超时”时，参与者对这些词有相同理解。

学习目标分为三层：

- **了解概念**：能解释术语和最小示例；
- **能够实现**：能在后续模块中用测试实现状态转换和失败处理；
- **能够在面试中解释**：能说明方案取舍、失败模型、验证证据和当前限制。

## 9. 数据流和状态变化

### 9.1 数据流

```text
用户提交工作流定义
  -> 控制面校验任务和依赖
  -> 持久化工作流与任务状态
  -> 调度器选择可运行任务
  -> 执行节点运行普通程序或 Agent
  -> 执行节点上报结果和日志
  -> 控制面更新状态
  -> 后续依赖被解锁，或进入重试/失败/人工处理
```

### 9.2 最小任务状态

```text
等待依赖 -> 可运行 -> 运行中 -> 成功
                    |        -> 失败 -> 等待重试 -> 可运行
                    |        -> 已取消
                    -> 已取消
```

实际实现前需要进一步确认每条状态转换的触发条件。例如任务在“运行中”时收到取消请求，可能先进入“取消中”，等待执行节点确认结束后才进入“已取消”。模块 0 只建立概念，具体状态机属于模块 1 的 TDD 计划。

## 10. 方案选择与替代方案

### 10.1 为什么选择 Go

Go 是一种静态类型、编译型编程语言。静态类型表示许多类型错误可以在运行前检查；编译型表示源代码先转换成可执行程序。

选择原因：

- 当前开发环境已安装 Go，用户已有相关经验；
- 标准库适合网络服务、并发任务和测试；
- 编译后的单个程序便于后续部署控制面；
- 当前目标是学习可靠执行模型，而不是先搭建复杂语言运行环境。

为什么不选择其他语言作为当前控制面实现：

- **Python**：生态丰富、编写原型快，也适合模型和数据处理；但动态类型让部分接口错误到运行时才暴露，控制面长期维护需要额外类型和工程约束。Python 更适合作为任务执行语言或模型实验工具。
- **Node.js**：基于 JavaScript，处理大量输入输出请求方便；但当前团队经验和项目学习主线不以 JavaScript 服务端为中心，引入它不会直接降低模块 1 的正确性风险。
- **Rust**：提供更强的内存安全和底层控制；但学习成本更高，当前单机控制面不需要先承担该成本。进入受限执行节点模块时再单独评审。

选择 Go 的代价是需要编译，部分业务原型代码比 Python 更长。若未来主要工作转为模型实验、数据科学或需要复用大量 Python 库，应把对应任务放在 Python 执行器中，而不必重写整个控制面。

### 10.2 为什么选择本地进程

本地进程是直接在一台开发机器上启动的程序实例。当前先用它验证依赖、状态和恢复逻辑，因为它启动快、调试路径短，不要求安装额外基础设施。

容器（Container）是一种共享宿主机操作系统内核、同时隔离进程、文件和资源的运行环境。容器运行时是负责创建和管理容器的软件。

为什么不选择其他运行环境作为当前起点：

- **Docker Compose**：用于在一台机器上定义和启动多个容器，适合集成多个服务；但模块 1 尚不需要数据库、消息系统和多个服务共同部署。
- **Kubernetes**：一种容器编排平台，用于管理容器化应用的部署、资源和故障恢复；它常简称 K8s，其中数字 8 表示 K 和 s 之间省略的八个字母。它适合多节点与资源调度，但其对象和网络模型会增加排查层级，可能掩盖工作流内核本身的状态错误。
- **虚拟机**：隔离边界通常强于普通进程，但启动、镜像和资源开销更大，不适合模块 1 的快速单元测试。

本地进程不能提供可靠安全隔离，也不能证明多节点故障恢复正确。当进入资源限制、节点选择或容器生命周期验证时，应切换到容器和本地 Kubernetes 集群。

### 10.3 为什么选择 Mock Agent

Mock Agent 能按测试要求稳定返回结果，不消耗模型费用，也不依赖网络，因此适合验证调度器是否正确处理成功、失败、超时和取消。

为什么不选择其他 Agent 实现作为当前起点：

- **真实云模型 API**：能够验证真实响应和供应商限制，但结果可能变化，还会引入费用、网络、速率限制和凭证管理问题。
- **本地模型**：数据可留在本机，也不需要按调用付费；但模型文件、内存和推理资源要求较高，会把模块 1 的重点从可靠执行转移到模型运行环境。
- **固定脚本替代所有 Agent**：最稳定、最便宜，但无法表达 Agent 的非确定输出、工具调用和权限需求；适合作为普通任务测试，不能完全替代后续 Agent 适配验证。

Mock Agent 的代价是不能证明真实模型接入可用。进入 Agent 适配模块后，应保留 Mock 测试，同时增加少量人工触发、设置预算的真实接口测试。

### 10.4 为什么选择接口隔离

接口隔离是让调度器只依赖一组稳定操作，例如“执行任务并返回结果”，而不直接绑定某个模型供应商或数据库客户端。

为什么不选择直接绑定外部依赖：

- **在调度器中直接调用供应商 SDK**：SDK 是 Software Development Kit 的缩写，中文是软件开发工具包。直接调用初期代码少，但更换供应商或离线测试时需要修改调度逻辑。
- **通过全局变量共享外部客户端**：调用方便，但测试之间容易相互影响，也难以为不同任务配置权限和超时。
- **一开始引入消息队列**：消息队列用于异步传递消息，能解耦进程；但模块 1 是单机内核，提前引入会增加消息重复、确认和部署问题。

接口会增加少量类型和适配代码。若未来只有一个永不更换的本地实现，接口价值会降低；但本项目已批准同时支持 Mock、云模型、本地模型和普通程序任务，因此当前需要这个边界。

## 11. 常见错误和失败场景

### 11.1 依赖形成环

A 等 B，B 又等 A，所有任务都无法运行。处理方式是在接受工作流定义时执行环检测，而不是等运行后才发现。

### 11.2 失败后无限重试

如果参数本身错误，重试不会成功，反而持续消耗资源。重试策略需要最大次数、间隔和不可重试错误分类。

### 11.3 重试非幂等操作

执行节点完成写入后，在成功上报前崩溃，控制面可能认为任务失败并重新执行。业务操作必须使用唯一请求编号、幂等写入或补偿策略。

### 11.4 只在内存保存状态

控制面进程重启后失去所有运行信息，无法区分“从未运行”和“已经成功但尚未上报”。模块 1 需要通过存储接口验证恢复逻辑。

### 11.5 把超时等同于任务没有成功

调用方超时只表示没有按时收到结果，远端操作可能已经完成。不能仅凭超时直接重复执行有副作用的操作。

### 11.6 把容器当作绝对安全边界

容器通过操作系统机制隔离进程和资源，但错误配置、操作系统安全漏洞或过宽权限仍可能造成风险。本项目后续只验证受限执行能力，不宣称能安全运行任意恶意代码。

### 11.7 让多 Agent 成为默认方案

多个 Agent 会增加上下文传递、结果合并、修改冲突和模型成本。只有任务能够独立并行，或确实需要不同能力和独立审查时，多 Agent 才可能带来收益。

## 12. 测试、压测、故障实验与验证

测试是用可重复步骤检查实际行为是否符合预期。压测是逐步增加负载，观察延迟、吞吐量和资源使用。延迟（Latency）是完成一次操作所需的时间；吞吐量（Throughput）是单位时间内完成的操作数量。在没有实测数据前，不能写性能数字。

模块 0 只完成文档验证。后续模块应该逐步增加：

| 实验 | 操作 | 期望观察 |
|---|---|---|
| 依赖测试 | 构造 A -> B -> C | A 成功前 B、C 不运行 |
| 环检测 | 构造 A -> B -> A | 工作流在创建时被拒绝 |
| 重试测试 | Mock Agent 前两次失败、第三次成功 | 尝试次数和最终状态正确 |
| 幂等测试 | 对同一任务结果重复提交 | 业务结果只生效一次 |
| 超时测试 | Mock Agent 故意阻塞 | 任务按策略超时，不解锁后续任务 |
| 取消测试 | 任务运行中发起取消 | 不再启动新的后续任务 |
| 恢复实验 | 保存状态后重启控制面 | 已成功任务不被无条件重跑 |
| 离线测试 | 断开外部网络运行测试 | Mock 和核心单元测试仍可运行 |

单元测试（Unit Test）是针对一个较小代码单元进行的自动化测试。模块 1 应先用单元测试覆盖状态转换，再进行进程重启等故障实验。真实模型测试应默认人工触发、低并发并设置预算。

当前尚未得到任务吞吐量、恢复时间或资源开销数据；这些指标必须在实现后记录环境、命令和原始结果。

## 13. 面试追问

### 13.1 为什么不直接使用定时启动工具？

cron 是按时间启动命令的工具，适合简单定时任务；它不原生保存多步骤依赖、每次尝试、统一重试和恢复状态。任务少、失败影响低时 cron 更便宜。

### 13.2 为什么 DAG 不能有环？

有环依赖没有可作为起点的任务，会导致相互等待。循环业务过程应拆成多次工作流运行或由任务内部的明确循环控制。

### 13.3 平台重试能保证只执行一次吗？

不能。网络超时和进程故障可能让平台无法确认远端是否已经成功。实际系统通常追求“至少执行一次并通过幂等去重”，或在受限条件下实现更强语义。

### 13.4 为什么控制面和执行节点要分开？

两者职责和风险不同：控制面维护全局状态，执行节点运行不可信程度更高、资源消耗更大的任务。分开后可以独立扩缩、限制权限和处理节点故障。

### 13.5 为什么不一开始使用 Kubernetes？

模块 1 首先要证明状态和调度逻辑正确。Kubernetes 能解决部署、资源和容器生命周期问题，但不能替代工作流业务状态机；过早引入会增加定位问题的层级。

### 13.6 Mock 测试通过能证明真实 Agent 可用吗？

不能。Mock 只证明平台对预设行为的处理符合预期。真实接口还需要验证鉴权、速率限制、流式响应、输出变化、成本和供应商错误。鉴权（Authentication and Authorization）是确认调用者身份和权限；流式响应（Streaming Response）是服务在结果全部生成前分批返回数据。

## 15. 本章总结与限制

可靠工作流平台通过保存状态、检查依赖、安排执行和处理失败，管理跨多个步骤的后台工作。DAG 描述无环依赖，控制面负责决策，执行节点负责运行；重试解决临时失败，但必须结合幂等、超时和故障恢复。

本项目当前选择 Go、本地进程、Mock Agent 和接口隔离，是为了先在低成本、离线可测试的条件下验证工作流内核。Python、Node.js、Rust、Docker Compose、Kubernetes、真实云模型和本地模型并非永远不使用，而是推迟到它们能够解决当前模块的具体问题时再引入。

本文的限制是尚无业务实现、故障实验和性能数据。下一阶段不能直接依据本文声称系统可靠，而要用模块 1 的 TDD 计划、自动化测试和可复现实验逐条验证状态转换、重试、取消与恢复行为。
