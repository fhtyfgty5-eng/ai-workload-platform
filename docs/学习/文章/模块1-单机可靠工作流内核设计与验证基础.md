# 从 0 构建 AI Workload Platform（三）：单机可靠工作流内核如何设计与验证

## 摘要

我正在从零开发一个新项目：AI Workload Platform。它是一个面向 Agent（能够围绕目标调用模型、工具或外部服务的软件组件）与确定性程序任务（主要按照预先编写的固定规则执行的程序任务）的可靠运行时和调度平台，目标是让由多个步骤组成、可能运行较长时间并且可能中途失败的后台工作，能够被追踪、重试和恢复。

本篇不是在科普一个泛泛的工作流产品，而是学习、实现并验证该项目的第一个核心内核：在一台机器上，不依赖容器（一种隔离程序及其运行依赖的技术）、云服务和真实模型，先把任务定义、DAG（Directed Acyclic Graph，中文为“有向无环图”，用来表示不会形成循环的任务依赖）、状态、重试、超时、取消和重启恢复这些最基础的行为设计清楚，并用自动化测试和性能基线检查这些设计是否成立。

读完本文后，你应该能理解：为什么要区分工作流定义和一次运行，为什么重试不等于可靠，模块 1 为什么选择 Go、模拟执行器和本地 JSON 存储，以及真实测试和性能数据暴露了哪些边界。

## 1. 本章要解决的问题

模块 0 已经定义了工作流、DAG、状态机、重试和恢复等概念，但概念说明只能提出预期行为，不能证明实现遇到并发、超时或持久化失败时仍然正确。模块 1 的任务，就是把这些设计假设变成可运行代码和可重复测试。

假设我们要处理一个数据文件，步骤是：读取文件、清洗内容、调用模型把文本转换为便于检索的数值表示，也就是向量，再更新用于快速查找内容的搜索索引。正常路径并不难写，难的是发生异常时该怎么办：

- 清洗失败时，生成向量能不能开始？
- 模型调用超时时，应该立即失败还是重试？
- 进程在任务成功后、保存状态前崩溃，重启后会不会重复执行？
- 用户取消时，已经在运行的任务和还没开始的任务应该分别如何处理？

如果每个脚本都自己决定这些事，一开始可能很快，但很难保证所有任务的行为一致。模块 1 的目标就是先在单机上把这些边界说清楚、测清楚。

## 2. 前置知识

本文不要求你使用过任何现成的工作流平台，只需理解以下概念：

- **程序**：可以被计算机执行的指令集；
- **进程（Process）**：程序一次正在运行的实例；
- **文件**：保存在磁盘上、进程结束后仍可读取的数据；
- **JSON**：一种用文本表示对象和数组的数据格式，方便程序互相传递；
- **Go**：一种编译型编程语言。程序会先被编译成可执行文件；它随语言提供的基础代码库，也就是标准库，支持同时处理多个任务、取消、文件和测试，适合本模块的目标。

## 3. 一句话理解单机内核

单机可靠工作流内核是：在一个 Go 进程内，使用明确的任务状态、依赖规则和持久化状态，统一决定任务何时执行、失败后是否重试，以及进程重启后如何继续。

这不是一个永远不会失败的系统。“可靠”指的是：失败、超时、取消和崩溃发生时，系统仍然能说清楚发生了什么，不会静默丢失任务，并能按已定策略继续或停止。

## 4. 核心概念

### 4.1 工作流定义和运行实例

**工作流定义（Workflow Definition）** 是“要做什么”的静态说明，包括任务、依赖和重试配置。

**工作流运行实例（Workflow Run）** 是这份说明的一次执行。同一份定义可以执行多次，每次运行都要有自己的标识（ID）和状态。

区分二者很重要：如果把“任务定义”和“任务执行状态”写在同一份数据里，第二次运行很容易误读第一次运行的结果。

### 4.2 TaskRun 和 Attempt

**任务运行实例（Task Run）** 是一次工作流运行中的一个任务。

**执行尝试（Attempt）** 是该任务真正被执行一次的记录。一个 TaskRun 可以有多个 Attempt：第一次失败，第二次重试，它们不应该互相覆盖。

这个分层能回答一个实际问题：“任务现在最终成功了，还是第二次尝试才成功？”

### 4.3 调度器和执行器

**调度器（Scheduler）** 是根据依赖和资源上限决定“现在调度哪些任务”的组件。

**执行器（Executor）** 负责真正调用一个任务。模块 1 使用 Mock Executor（模拟执行器），它不调用真实模型或工具，而是按测试预设返回成功、失败、延迟或超时。这里模拟的是通用任务执行边界，不是真实 Agent。

**并发上限（Concurrency Limit）** 是同一时间允许运行的任务数上限。上限为 `1` 时可用于确定性测试，上限大于 `1` 时才能让 DAG 中无直接依赖的任务同时运行。

### 4.4 状态机

**状态机（State Machine）** 规定一个对象可以处于哪些状态，以及什么事件可以让它进入下一个状态。

例如，任务可以从“等待依赖”到“可执行”，但不应该从“等待依赖”直接跳到“成功”。

### 4.5 持久化和快照

**持久化（Persistence）** 是把数据保存到进程退出后仍可读取的介质，例如本地文件或数据库。

**状态快照（Snapshot）** 是某一时刻的完整状态记录。模块 1 同时保存快照和状态事件：快照用于恢复，状态事件记录每次状态变化，帮助说明运行过程。模块 1 的 FileStore 每次保存完整 JSON 快照，事件也包含在快照中；这适合验证单机语义，但不适合多进程并发写入和复杂查询。

### 4.6 可控时钟

**可控时钟（Controllable Clock）** 是一个可在测试中手动前进时间的接口。如果直接调用系统时钟，测试一个 30 秒超时就可能真等 30 秒；可控时钟可以让测试虚拟时间已经过去。

### 4.7 至少执行一次和幂等

**至少执行一次（At-Least-Once Execution）** 表示任务不会静默丢失，但可能重复执行。例如，执行器已经成功，但进程在保存成功状态前崩溃，恢复后只能重新执行。

**幂等（Idempotency）** 表示同一个操作执行一次或多次，业务结果仍然一致。不能将“任务不重复执行”当作恢复的前提，应该在执行器或业务操作中单独设计。

### 4.8 协作式取消

**协作式取消（Cooperative Cancellation）** 是指调度器发出取消信号，执行器主动检查并停止。它不等于强制杀掉一个不响应的进程。

在 Go 中，执行器通常可以使用 `context.Context`（用于传递取消、超时和请求范围信息的 Go 类型）传递取消和超时信号。但 `context` 只负责传播信号，任务状态、Attempt 结果和恢复规则仍由工作流内核定义。

### 4.9 TaskKey 和内部编译索引

`TaskKey` 是用户在工作流中提供的任务唯一标识，例如 `clean-document`。模块 1 规定它长 1 到 64 个字符，只允许小写英文字母、数字、连字符和下划线。它比自动分配的整数更适合表达依赖和阅读日志：`build-index` 依赖 `clean-document` 比“任务 7 依赖任务 3”更容易理解。

这不意味着调度器要在每次调度时都用字符串查找。工作流提交时，校验器在同一次遍历中建立 `TaskKey -> 数组下标` 的哈希映射索引。**哈希映射（Map）** 是一种按键查找值的数据结构；这里的键是 TaskKey，值是数组下标。然后，校验器把字符串依赖转换为整数邻接表。数组下标只是内部位置，不是第二个任务 ID，也不对用户暴露。

**时间复杂度（Time Complexity）** 用于描述输入规模增大时，算法的操作次数如何增长。大 O 记号关注增长趋势，不表示一个固定的毫秒数。

在 `O(V + E)` 中：

- `V` 是 Vertex（顶点）的数量，在工作流 DAG 中就是任务数；
- `E` 是 Edge（边）的数量，在 DAG 中就是任务之间的依赖关系数。

例如：

```text
A -> B
A -> C
B -> D
C -> D
```

这个 DAG 有 4 个任务，所以 `V = 4`；有 4 条依赖，所以 `E = 4`。

编译工作流时，算法做三类工作：

1. 每个任务遍历一次，校验 TaskKey 并建立索引，成本是 `O(V)`；
2. 每条依赖遍历一次，建立整数邻接表和依赖计数，成本是 `O(E)`；
3. 检测循环依赖时，每个任务和每条依赖最多再被处理一次，成本是 `O(V + E)`。

将这些线性步骤相加后，增长趋势仍然是 `O(V + E)`。它不是 `O(V × E)`，因为算法不会为每个任务重新扫描所有依赖。这里按哈希映射平均一次查找的耗时不会随任务总数线性增加来计算；TaskKey 长度又被限制为最多 64 个字符。运行时使用数组和依赖计数，也不需要反复扫描完整任务列表，实际耗时仍要通过基准测试确认。

### 4.10 依赖列表与未满足依赖计数

`depends_on` 告诉调度器“当前任务必须等哪些任务成功”。这些依赖由工作流作者显式写入 JSON，调度器不会根据任务名称或业务含义自动猜测。

仍以这个 DAG 为例：

```text
A -> B
A -> C
B -> D
C -> D
```

提交工作流时，编译结果可以表示为：

```text
TaskKey -> 数组下标：
A=0, B=1, C=2, D=3

successors（直接下游任务）：
A -> [B, C]
B -> [D]
C -> [D]
D -> []

remainingDeps（尚未成功的依赖数量）：
A=0, B=1, C=1, D=2
```

**邻接表（Adjacency List）** 是按每个任务保存其直接相邻任务的数据结构。这里保存直接下游任务，是因为上游成功后，调度器需要快速知道应检查谁。`remainingDeps` 则记录某次运行中，每个任务还有几个依赖尚未成功。它的初始值等于该任务的**入度（In-degree）**，即指向该任务的依赖边数量；运行后，`remainingDeps` 会随着上游成功而递减，入度本身并不改变。

运行开始时，只有 `remainingDeps == 0` 的 `A` 可以执行。`A` 第一次进入成功状态后，调度器沿着 `A -> [B, C]`，把 `B` 和 `C` 的计数各减为 `0`，二者就可以并发执行。随后 `B` 成功只能把 `D` 从 `2` 减为 `1`；直到 `C` 也成功，`D` 才会变为可执行。

因此，**调度热路径**，也就是运行时被频繁执行的代码路径，不必反复扫描 `D` 的完整依赖列表，只需在上游成功时更新受影响的下游计数，再判断计数是否为 `0`。但完整依赖结构仍会保留在创建后不再修改的编译结果中，用于校验、失败传播和恢复时重算计数。

这里还有三个可靠性边界：

- 只有某个任务**第一次**进入成功状态时，才能递减下游计数；重复收到同一成功结果不能重复递减，否则下游可能被提前解锁；
- 某个依赖最终失败时，下游任务应进入“已跳过”，而不是把失败也当作已满足的依赖；
- 恢复工作流时，应根据完整依赖结构和各任务已保存的成功、失败、取消等最终状态重新计算 `remainingDeps`，而不是完全相信可能在崩溃前只更新了一半的旧计数。

同一份工作流定义的多个 WorkflowRun 可以共享 TaskKey 索引和邻接表，但每次运行都必须有独立的任务状态数组和 `remainingDeps`。共享的是“依赖关系”，不是“执行进度”。

## 5. 从状态变化理解内核

单机内核的一次推进可以直接写成状态和持久化顺序：

```text
等待依赖
  -> 可运行
  -> 保存“运行中”
  -> 调用 Executor
  -> 保存成功、失败或取消结果
  -> 根据已保存结果解锁下游或安排重试
```

这里的顺序决定了可靠性边界：调用 Executor 前必须先保存“运行中”，否则恢复时无法知道是否已经开始；调用成功后必须先保存成功状态，才能解锁下游；保存成功状态失败时，不能继续推进后续任务。进程在外部动作完成但成功状态尚未保存时崩溃，恢复可能再次执行，这就是“至少执行一次”语义需要幂等设计的原因。

## 6. 最小工作流示例

模块 1 的 CLI（Command-Line Interface，命令行界面）从 JSON 文件读取工作流定义。下面是仓库当前可运行的文档处理定义，表示先读取文件，再清洗，最后生成结果：

```json
{
  "id": "document-pipeline",
  "concurrency": 2,
  "tasks": [
    {
      "key": "read",
      "action": "mock-read",
      "retry": {"max_attempts": 2, "interval_ms": 100},
      "timeout_ms": 3000
    },
    {
      "key": "clean",
      "action": "mock-clean",
      "depends_on": ["read"],
      "timeout_ms": 3000
    },
    {
      "key": "summarize",
      "action": "mock-summarize",
      "depends_on": ["clean"],
      "timeout_ms": 5000
    }
  ]
}
```

### 6.1 输入

- 工作流的 `id` 标识工作流定义，任务的 `key` 就是该工作流内唯一的 `TaskKey`；
- `tasks` 是任务列表；
- `depends_on` 表示当前任务依赖哪些任务；
- `concurrency` 是同时允许执行的任务数；
- `max_attempts` 和 `interval_ms` 描述重试策略；
- `timeout_ms` 描述一次执行的最长时间。

### 6.2 执行过程

1. 校验器先检查 TaskKey 和依赖，确认没有环；
2. `read` 没有依赖，进入“可执行”；
3. `read` 成功后，`clean` 被解锁；
4. `clean` 成功后，`summarize` 被解锁；
5. 任意一次尝试失败时，根据 `max_attempts` 决定是否重试；
6. 所有任务成功且状态已保存后，工作流才标记为“成功”。

### 6.3 非法输入

以下工作流不应进入调度：

```json
{
  "id": "invalid",
  "tasks": [
    {"key": "a", "depends_on": ["b"]},
    {"key": "b", "depends_on": ["a"]}
  ]
}
```

`a -> b -> a` 形成依赖环。如果仍然接受，调度器会永远找不到可开始的任务；在提交时拒绝能让错误立即返回。

## 7. 不设计可靠内核会发生什么

直接把三个脚本串起来，只能表达正常路径：

```text
读取 -> 清洗 -> 生成结果
```

但这个脚本很难单独解决：

- 读取成功、清洗失败后，应该不应该继续生成？
- 进程在清洗后崩溃，重启后是否知道读取不用重复？
- 清洗超时时，重试会不会把同一份结果写两遍？
- 取消到底是只停止新任务，还是还要通知正在运行的任务？

可靠内核不是把所有任务都写得更复杂，而是用统一状态和规则管理这些失败路径。

## 8. 在 AI Workload Platform 中的位置

模块 1 是这个新项目已经完成的第一个核心内核，后续模块都会建立在它之上。

这里的**控制面**是接收客户端请求、保存运行状态并管理工作流执行的服务层；**Agent Runtime** 是为 Agent 提供模型、工具、上下文和权限边界的运行时；**Worker** 是实际领取并执行任务的节点；**租约**是带有效期的任务占用权；**Kubernetes** 是用于部署和管理容器化应用的开源平台。

后续模块路线如下：

```text
模块 1：单机内核
  -> 模块 2：控制面 API 与持久化存储
  -> 模块 3：Agent Runtime、模型与工具执行
  -> 模块 4：多 Worker、租约、心跳与故障恢复
  -> 模块 5：可观测性、故障注入与性能验证
  -> 模块 6：受限执行环境与 Kubernetes
  -> 模块 7：真实场景、最小控制台与开源发布
```

如果模块 1 没有明确的状态、重试和恢复语义，后面引入网络控制面、Agent Runtime 或多 Worker 只会把模糊扩大。先实现单机调度，也是为了把核心正确性与数据库、容器和网络问题分开。自然语言生成工作流是模块 3 的必做产品演示，但不是可靠内核的前置条件。

模块 1 完成后，新的限制已经很具体：CLI 只能由本机用户调用；每个 Run 都重写一份完整 JSON 快照；FileStore 不适合多个进程并发写入，也不能高效支持按状态、时间和 Workflow 条件查询；没有常驻服务负责接收其他程序请求并自动恢复未完成的 Run。这些问题已经超出单机内核内部状态机的职责，因此下一步进入模块 2，而不是继续向 Engine 中增加网络或数据库细节。

模块 2 保留本模块已经验证的 Compiler、状态机和调度顺序，在外层增加 HTTP（客户端与服务端交换请求和响应的网络协议）API，并用 OpenAPI（描述接口路径、参数和响应的机器可读规范）固定契约，再用 PostgreSQL（独立运行的关系型数据库）的事务、约束和索引替换网络控制面的文件存储。收益是多个客户端可以通过稳定接口提交和查询，代价是必须新增认证、幂等请求、数据库迁移、并发冲突和断连恢复。FileStore 和本地 CLI 仍作为低依赖测试与演示入口保留，不会因为控制面出现而失效。

## 9. 从提交到恢复的数据流

下面的数据流已经在模块 1 中实现，并由自动化测试覆盖。为了避免并发完成、超时、取消和重试计时器同时修改状态，执行器只把结果发送回 Engine 的事件循环，由事件循环串行更新单个 Run 的快照。

### 9.1 提交时先校验

工作流进入运行前，先检查：

1. TaskKey 是否合法且在当前工作流内唯一；
2. 所有依赖任务是否存在；
3. 是否存在循环依赖；
4. 并发上限、重试次数和超时是否合法。

全部校验通过后，系统才创建运行实例。这样可以把“定义本身无效”和“合法任务执行失败”明确区分开；TaskKey 索引、邻接表和依赖计数的编译过程见 4.9 和 4.10。

### 9.2 状态更新的先后顺序

当前实现中，当任务可以开始时，Engine 先在快照副本中把任务和 Attempt 更新为“执行中”，保存成功后才调用 Mock Executor。任务返回成功后，Engine 先在副本中记录 Attempt 结果、TaskRun 成功和下游依赖计数变化，再原子保存新的完整快照；保存失败时，不提交内存副本，也不启动尚未开始的下游任务。

这样做的原因是：下游任务只能依赖已经被保存的成功状态。如果先解锁、后保存，进程在两步之间崩溃，就可能出现“下游已经开始，上游却仍然是未完成”的矛盾状态。模块 1 还通过故障注入测试证明：开始状态无法保存时不会调用执行器，成功状态无法保存时不会启动后继任务，系统错误会取消同一 Run 中仍在活动的其他 Attempt。

### 9.3 进程重启后恢复

进程重启时，`Resume` 从文件读取最后一份快照：

- 已成功的任务不再调度；
- 根据编译后的完整依赖结构和已保存的任务状态，重新计算未满足依赖计数；
- 保存为“执行中”的 Attempt 无法确认执行器是否已经完成，因此标记为“被中断”；
- 如果还有尝试次数，重新安排该任务；
- 如果重试耗尽，记为失败并向下游传播跳过。

恢复不会直接相信快照里保存的未满足依赖计数，因为崩溃可能发生在一次状态更新尚未完整落盘时。它会校验快照版本、RunID、工作流定义、任务顺序、状态和 Attempt 历史，再根据 DAG 与已经持久化的任务终态重算计数。只有修正后的恢复快照保存成功，Engine 才重新启动执行器。

## 10. 方案选择与替代方案

### 10.1 为什么选择 Go，而不是 Python 或 Rust

模块 1 选择 Go，是因为它的标准库已经提供并发控制、取消信号、`encoding/json` 包（负责 JSON 编解码）、文件操作和测试工具，能够在不引入第三方框架的前提下实现本模块。编译后得到单个可执行文件，也便于后续把同一内核放到本机进程、容器或节点中运行。

Python（一种常用于 AI 和数据处理的编程语言）的生态更丰富，编写原型也通常更快；但模块 1 首先验证的是并发调度、状态恢复和取消语义，若同时引入解释器运行时和大量外部库，会扩大需要排除的变量。Rust（一种强调内存安全和性能控制的编程语言）适合后续受限执行节点等更底层的场景；代价是当前学习和实现复杂度更高，反而会掩盖工作流内核本身的设计问题。

选择 Go 的代价是：它不会自动解决持久化一致性、分布式协调或任务幂等，语言和并发原语只是实现工具。如果后续基准表明核心存储或执行隔离存在更高要求，应分别评估 SQLite、PostgreSQL 等存储方案，以及 Rust 等实现语言。

### 10.2 分层内核与单体调度器

本项目选择分层内核，把校验、状态机、调度器、执行器、存储和时钟分开。这些名词不是为了增加文件数量，而是为了使每个边界可以独立测试。

另一种做法是把所有逻辑放入一个调度器对象。这在很小的原型中代码量较少，但并发、重试和恢复会很快互相影响，不利于测试失败场景。

### 10.3 进程内 Mock Executor 与真实执行

模块 1 使用进程内 Mock Executor。它不创建子进程，而是在同一个 Go 进程中按预定脚本返回结果。这能让测试稳定模拟失败、延迟和取消。它不调用模型、选择工具或执行 Agent 决策，因此未使用 Mock Agent 这个容易造成范围误解的名称。

不选择本地脚本执行，是因为子进程会引入环境变量、进程清理、资源限制和安全风险。这些问题会在受限执行模块单独处理。

### 10.4 本地 JSON 与 YAML、SQLite

模块 1 将 JSON 作为工作流定义和本地快照格式，因为 Go 标准库中的 `encoding/json` 包可以直接处理它。YAML 是另一种更适合人工书写的文本配置格式，但需要额外解析依赖；SQLite 是嵌入应用进程、用表组织关联数据的轻量关系型数据库，更适合查询和事务。事务是“要么全部成功，要么全部失败”的一组数据操作，但使用 SQLite 会引入数据库驱动和新的测试边界。

实际 FileStore 会在状态变化时写入完整快照，因此任务数和事件数增加后，文件读写会成为明显的延迟边界。12.5 节的实测结果验证了这个判断。当运行实例变多、需要并发查询或多进程写入时，本地 JSON 文件不再适合；项目因此在模块 2 转向 PostgreSQL（运行在独立服务中的关系型数据库）和事务存储，但这不否定 FileStore 作为模块 1 单机验证工具的价值。

### 10.5 固定间隔与指数退避、随机抖动

固定间隔指每次重试都等待同样的时间；指数退避则让等待时间逐次增长，例如 `1` 秒、`2` 秒、`4` 秒。随机抖动是在等待时间上加入小范围的随机变化，用于降低大量任务同时重试形成的瞬时压力。

模块 1 选择固定间隔，因为只有单机和 Mock Executor，主要目标是验证重试次数和状态变化。连接大量外部服务时，再评估指数退避和随机抖动。

### 10.6 为什么不用自增整数作任务标识

自增整数适合数据库内部主键，但不适合作为工作流文件中的业务标识。使用 `clean-document` 这样的 TaskKey，用户可以在提交前直接写出依赖，并且在日志中直观识别任务。如果使用 `3` 和 `7`，工作流的任务排序、复制和比较都更容易出现混淆。

另一种常见方案是 UUID（Universally Unique Identifier，通用唯一标识符）。它适合生成跨工作流也很难重复的运行 ID，但字符串较长，不适合让用户频繁手写依赖。TaskKey 只要求在一份工作流定义内唯一，既保留可读性，又能在提交时可靠校验。

这不是用字符串换取性能：4.9 的校验阶段使用 TaskKey 建立一次索引，调度热路径使用数组下标。字符串是对外的可读名称，数组下标是对内的访问优化，二者不是两个业务 ID。

## 11. 常见错误和失败场景

### 11.1 把定义和运行状态混在一起

一个工作流可以多次执行。如果将“清洗任务”的配置和“清洗任务已成功”保存在同一层对象中，重新运行时就会出现状态污染。应该分开 WorkflowDefinition、WorkflowRun 和 TaskRun。

### 11.2 只用一个布尔值表示状态

`is_running` 和 `is_finished` 无法清楚表示“等待重试”、“已跳过”和“被中断”。显式状态机虽然会多几个状态值，但能拒绝不合法的跳转。

### 11.3 只在内存里记录状态

进程退出后内存消失。如果没有快照，重启后无法分辨任务是没开始、正在运行还是已经成功。持久化也不等于不会重复执行；它只是让系统能够知道自己上次停在哪里。

### 11.4 在调用执行器前就标记成功

成功状态必须来自执行器的结果，而且要在状态已经保存后才解锁下游任务。否则进程在执行之前崩溃，系统会得到一个虚假成功。

### 11.5 以为超时一定等于没有执行

超时表示在限定时间内没有收到可确认的结果，不一定代表任务没有产生副作用。**副作用**是任务对文件、数据库或外部服务产生的可观察改变，例如写入一条记录或发送一次请求。强制取消、幂等写入和结果去重是后续执行器需要考虑的问题。

### 11.6 重试所有错误

参数错误、权限错误和依赖不存在时，重试可能只是重复消耗资源。内核需要区分临时执行错误和永久执行错误，而不是把所有错误都简化成“再试一次”。

### 11.7 把文件更新当成原子操作

如果直接覆盖 JSON 文件，进程在写入一半时崩溃，重启时可能无法解析文件。模块 1 的 FileStore 会先在目标目录写临时文件，依次完成写入、文件同步和关闭，再通过 `os.Rename` 替换目标文件并同步目录。**原子替换**指读取方只能看到旧的完整文件或新的完整文件，不会看到只写了一半的内容。临时文件与目标文件位于同一文件系统是重要前提；Go 的 `os.Rename` 不承诺所有操作系统都有相同语义，因此当前只明确支持 macOS 和 Linux。故障注入测试还验证了替换失败时旧快照仍然保留。

## 12. 如何验证

模块 1 完成时，代码库中共有 104 个以 `Test` 开头的自动化测试函数和 9 个 Benchmark 函数。测试数量本身不能证明软件可靠，重要的是这些测试是否覆盖了前文的状态转换、持久化顺序和故障边界。下面只列代表性证据，不把完整测试清单当成正文。

### 12.1 单元测试

- **定义编译：** 非法或重复 TaskKey、缺失依赖、重复依赖、循环依赖、空 Action 和非法重试策略都会被拒绝；10,000 个任务可以编译，10,001 个任务会超过硬上限；
- **数据结构：** TaskKey 到数组下标的映射、下游邻接表和依赖计数能够正确建立，每个 Run 持有独立的运行时计数；
- **状态机：** Workflow、TaskRun 和 Attempt 的合法转换可以执行，越过中间状态或离开终态的非法转换会被拒绝；
- **执行器边界：** Mock Executor 能按工作流、Run 和 TaskKey 隔离脚本进度，并稳定产生成功、临时失败、永久失败、延迟和取消；
- **文件存储：** FileStore 能创建、保存和读取完整快照，拒绝路径穿越和损坏 JSON；并发创建相同 RunID 时只有一个成功，原子替换失败时旧快照仍然有效。

### 12.2 调度与故障测试

调度测试首先验证正常路径：串行 DAG 按依赖顺序执行，互不依赖的任务可以并发执行，同时运行数不会超过工作流定义的并发上限。

更重要的是异常路径：

- 临时失败可以在固定间隔后重试，永久失败不重试；重试耗尽后，下游任务被跳过，独立分支仍可完成；
- Attempt 超时后按策略重试，已经超时的 Attempt 即使稍后返回结果，也不能覆盖新状态；
- 取消会停止运行中的任务、取消尚未开始的任务，并中断等待中的重试计时器；取消与保存结果同时发生时，由单 Run 事件循环收敛为一致状态；
- 任务开始状态保存失败时不调用 Executor，成功状态保存失败时不解锁下游，系统级持久化错误会停止当前 Run 继续推进；
- 恢复测试通过人工构造崩溃前快照，验证运行中的 Attempt 会转为 `interrupted`，成功任务不会重复调度，未保存成功状态的任务可能再次执行；
- 快照中的依赖计数即使被故意改错，恢复仍会根据 DAG 和任务终态重新计算；身份、版本、任务顺序或 Attempt 历史损坏时，系统拒绝执行，而不是猜测修复。

这里要区分“自动化故障测试”和“生产故障演练”：模块 1 使用可控时钟、模拟执行器、模拟持久化失败和人工构造快照来稳定复现边界，没有声称已经在真实多节点生产环境中完成故障演练。

### 12.3 CLI 验收

模块 1 提供了一个三步骤文档处理示例，可以直接运行：

```bash
go run ./cmd/workload local run examples/document-pipeline.json
```

成功时会输出随机生成的 RunID 和最终状态：

```text
run_id=bc7076993d126572b9832e45247a557e status=succeeded
```

再使用实际输出的 RunID 查询持久化结果：

```bash
go run ./cmd/workload local status bc7076993d126572b9832e45247a557e
```

命令行程序通过 `os/signal` 包接收 `Ctrl+C` 产生的中断信号，再将它转换为内核能够处理的取消请求。当前公开命名空间是 `local run/status`；无前缀的 `run/status` 仍保留为模块 1 的兼容入口。CLI 测试验证了运行、查询、非法参数、损坏 JSON、未知 RunID、只读查询不修改快照，以及取消后保存 `canceled` 状态。

按运行 ID 取消和恢复已经是内核接口与自动化测试能力，但模块 1 的 CLI 只有前台 `run` 和只读 `status`，没有通过另一个进程远程执行 `cancel` 或 `resume`。这避免为了两个命令提前引入后台服务和进程间通信。

### 12.4 实际验证命令

```bash
go test ./...
go test -race ./...
go vet ./...
go doc ./workflow
```

这组命令在模块 1 验收时全部通过。`go test` 运行自动化测试；`go test -race` 使用 Go 的竞态检测器检查测试过程中是否出现未同步的并发内存访问；`go vet` 是 Go 自带的静态分析命令，用于发现可疑调用和其他常见问题；`go doc` 检查公开接口能否形成可读文档。它们关注的风险不同，不能互相替代。

所有模块 1 自动化测试都使用 Mock Executor 和本地临时目录，不访问外部网络，不调用真实模型服务，也不执行 Action 字段中的本机命令。

### 12.5 性能基准与规模验证

Go Benchmark 是 Go 标准测试工具提供的可重复性能测量机制。模块 1 于 2026 年 8 月 18 日使用 Go 1.26.2，在一台运行 macOS 26.1、配备 Apple M4、10 个逻辑 CPU 和 32 GiB 内存的开发机上，让每项基准运行约一秒并重复五轮，得到以下均值：

| 基准场景 | 时间均值 | 每次操作分配量 |
| --- | ---: | ---: |
| 编译 10,000 个任务和 9,999 条线性依赖 | 1.841 ms | 约 2.22 MB |
| 创建 1,000 个 Run，共享编译定义 | 1.376 ms | 约 9.27 MB |
| 创建 1,000 个 Run，每次重新编译 | 17.662 ms | 约 31.50 MB |
| 一次成功解锁 9,999 个直接下游 | 0.746 ms | 约 4.76 MB |
| 恢复 10,000 个等待依赖的任务 | 0.117 ms | 约 92 KB |
| 恢复并向 9,999 个后代传播失败 | 0.905 ms | 约 4.93 MB |
| 保存 10,000 个任务和 10,000 条事件的 JSON 快照 | 26.559 ms | 约 14.59 MB |
| 读取同一规模的 JSON 快照 | 29.887 ms | 约 18.93 MB |

这里的“每次操作分配量”表示一次基准操作累计申请的内存，不等于操作结束后的常驻内存。结果支持两个结论：

第一，共享只读编译结果是有效优化。在当前输入下，1,000 个 Run 分别编译比共享定义约慢 12.84 倍，分配量约为 3.40 倍。

第二，FileStore 是当前更明显的延迟边界。即使只有 100 个任务，保存完整快照的均值也约为 9.009 ms，说明文件同步和目录同步存在固定成本；任务和事件增至 10,000 时，完整 JSON 的编码、写入、读取和解码成本进一步增加。这为模块 2 引入事务数据库提供了实际依据。

这些数据仍不是生产性能承诺。1,000 个 Run 基准只比较快照创建和定义共享，没有同时启动 1,000 个执行器；测试只来自一台机器，也没有隔离后台进程、固定 CPU 频率或测量垃圾回收暂停。当前保留首轮基线和瓶颈，但尚未设置持续集成中的绝对性能门槛。

## 13. 进一步思考

实现和测试已经回答了本文设计阶段的一部分问题：

- 调度热路径使用数组下标，TaskKey 继续承担对外可读标识；
- 同一 Run 的状态由事件循环串行提交，执行器和计时器只返回事实事件；
- Engine 只在状态保存成功后启动任务或推进下游，持久化失败会停止当前 Run 继续调度；
- 恢复不相信可能过时的依赖计数，而是根据定义和任务事实重新计算；
- 共享编译结果确实显著降低了创建大量 Run 的时间和内存分配。

模块 1 完成时还留下了以下问题：

1. 真实任务已经写入外部系统时，如何通过幂等键、唯一请求 ID 或结果去重控制至少执行一次带来的重复副作用？
2. 面对外部服务限流和大规模同时失败，何时需要指数退避、随机抖动和全局背压？
3. 扩展到多 Worker 后，如何使用租约、心跳和过期回收避免两个节点长期重复领取同一个任务？
4. PostgreSQL 事务、网络 API 和多进程访问加入后，如何保持模块 1 已经验证的持久化顺序和恢复语义？

其中第 4 个问题已经由模块 2 的事务控制面和停库恢复实验给出第一阶段答案；第 3 个问题也已经由模块 4 的多 Worker 租约、心跳、过期回收和迟到结果实验给出第一阶段答案。前两个问题涉及真实外部副作用和系统级负载控制，仍需随真实执行、分布式调度和性能实验继续收集证据。这样区分可以避免把后来已经回答的问题继续写成当前未知，也不会把后续结果倒写成模块 1 当时已经掌握的结论。

## 14. 总结与限制

模块 1 已经用一个单机 Go 进程实现并验证了可靠工作流的基础边界：

- 工作流定义与一次运行分开；
- 任务必须在依赖成功后才能执行；
- 重试、超时和取消都有明确状态；
- 重启后根据已保存状态恢复，但承认至少执行一次带来的重复可能；
- Engine 在状态保存成功后才执行或推进任务；
- 使用分层接口、Mock Executor、可控时钟和故障注入，使异常路径能够稳定测试；
- 首轮性能数据验证了共享编译结果的收益，也暴露了完整 JSON 快照的成本。

模块 1 完成时的限制也很明确：当时没有 HTTP API、事务数据库、多 Worker 租约、容器隔离、真实 Agent、完整日志指标或生产故障演练；FileStore 不支持多进程并发写入和复杂查询，原子替换只明确支持 macOS 和 Linux；CLI 只提供前台运行和状态查询；性能数据来自单台开发机，不能直接推导生产容量。后续模块已经补上 HTTP 控制面、PostgreSQL、Agent Runtime、多 Worker 租约，以及日志、指标、Trace、告警和故障实验，但并不改变 FileStore、单机 CLI 和本模块性能数据本身的证据边界。

因此，模块 1 的价值不是宣称已经做成成熟平台，而是把后续系统必须继承的状态、执行和恢复语义变成了可运行代码与可复现证据。模块 2 可以更换持久化方式并增加网络控制面，但不应该重新发明另一套调度规则。
