# 学习资料规范

## 1. 目标

学习资料默认读者此前没有使用过工作流、分布式调度、容器、Kubernetes、搜索推荐或 Agent Infra 工具。资料必须先解释问题和术语，再进入架构和代码。

本专栏记录一个正在从零开发的新项目，专栏名称为“从0构建AI Workload Platform工程实践”。`AI Workload Platform` 是项目名称，不是本文要科普的通用行业术语。每篇文章都必须说明本次技术内容在项目中的具体作用。

## 2. 文章分类与结构

### 2.1 项目总览篇

项目总览篇必须在开头明确作者正在从零开发什么产品、产品服务谁、用户如何使用、为什么要做、与成熟产品的关系、待验证的差异化方向、当前阶段和后续路线。项目总览篇可以引用必要技术术语，但不承担完整的技术科普。

### 2.2 技术学习篇

技术学习篇围绕一个技术主题深入讲解。下面各项是内容检查清单，不是必须逐项设置标题的固定模板；应根据主题合并、调整顺序或删除不适用的部分，避免为了形式完整产生重复和无关内容：

1. 本章要解决的问题；
2. 前置知识；
3. 一句话定义；
4. 中英文术语和缩写；
5. 直观但准确的机制解释；
6. 具体场景或最小示例；
7. 不使用该技术时会发生什么；
8. 在本项目中的位置；
9. 数据流或状态变化；
10. 方案选择与替代方案；
11. 常见错误和失败场景；
12. 测试、压测或故障实验；
13. 进一步思考或待验证问题；
14. 本章总结。

技术学习篇必须在开头说明该技术解决项目中的什么具体问题；如果同时需要完整介绍产品，应拆出独立的项目总览篇。

### 2.3 模块实践篇

模块实践篇只记录已经实现并验证的代码、测试、实验结果、失败过程和限制。尚未实现的内容必须标记为设计或假设，不能写成已完成事实。实践篇可以使用不同于技术学习篇的章节结构，但必须解释输入、输出、状态、失败路径和验证证据。

### 2.4 模块递进说明

进入新模块时，需求文档和对应学习文章必须让读者理解该模块为什么此时出现，而不是只罗列新增功能。内容应根据主题自然组织，不强制使用固定标题，但必须回答：

1. 上一模块已经实现并证明了什么；
2. 上一模块仍然解决不了什么具体问题；
3. 为什么该问题需要在当前模块处理；
4. 当前模块新增的能力和技术分别解决什么问题；
5. 为什么没有选择至少两种同类方案；
6. 新技术增加了哪些复杂度、运行成本或故障边界；
7. 当前模块完成后还留下什么问题，以及这些问题为什么交给后续模块。

模块递进描述的是能力和问题之间的因果关系，不应写成“新模块在所有方面都优于旧模块”。旧模块保留的本地入口、测试工具和证据边界仍需准确说明。文章不必重复完整八模块路线，只需讲清与当前主题直接相关的前后关系，并链接或引用项目总览中的整体路线。

## 3. 讲解要求

- 专业名词首次出现时必须解释；
- 英文缩写必须给出英文全称和中文含义；
- 不使用“显然”“很简单”等跳过推理的表述；
- 通俗易懂优先通过直接定义、具体例子、数据流、状态变化和边界说明实现，不用模糊或不准确的日常类比替代技术解释；
- 默认不使用生活类比。只有用户明确需要、类比确实降低理解成本且能清楚说明适用边界时才使用；
- 不为了显得易懂而回避必要的专业名词，正确顺序是先解释名词，再在后文稳定使用；
- 代码必须解释输入、输出、状态和失败路径；
- 资料区分“了解概念”“能够实现”“能够在面试中解释”三个层次；
- AI 生成内容必须通过官方文档、代码实验或测试验证；
- 用户追问产生的结论应增量补充到原资料，避免多个版本互相冲突；
- 不得包含公司保密信息。
- 不得把 Codex 交接、README 阅读顺序、项目状态字段、Git 过程、文件目录约定或文档验收输出写成技术正文；
- 不得伪造读者提问、用户反馈或尚未发生的实验结果；
- “项目总览篇”与“技术学习篇”承担两个独立目标时，必须拆成系列文章，不能为了简短删除必要的知识解释，也不能因为知识详细而隐藏项目定位。

## 4. CSDN 发布要求

每篇学习资料都要同时满足“项目内部学习”和“可直接粘贴到 CSDN”的要求：

- 使用标准 Markdown；
- 标题、摘要、目录、正文、示例、总结结构完整；
- 代码块标注语言；
- 图片或架构图提供文字说明；
- 不依赖仓库内部路径才能理解；
- 不包含公司代码、内部名称、业务数据和密钥；
- 不把 Codex 交接、仓库维护、文件目录或验证脚本输出当作技术正文；
- 文章开头先说明读者能学到什么，结尾说明限制和未解决问题。

文章不能只是 AI 生成的知识摘录。发布证据按照文章类型区分：

- **项目总览篇**：必须包含作者对产品问题、目标用户、使用边界和技术路线的理解；涉及成熟产品时使用官方资料核对；差异化方向必须标记为待验证假设。项目总览篇不强制提供业务代码或实验结果。
- **尚无业务代码的技术学习篇**：必须包含官方资料核对、作者自己的解释与推理、最小示例、方案取舍、可复现的验证计划和明确的当前限制。不得把验证计划写成实际结果，也不得编造实际遇到的问题。
- **已有业务实现的技术学习篇**：除概念和选型说明外，还必须补充覆盖文章结论的代码、测试或故障实验，以及实际发现的问题和限制。
- **模块实践篇**：必须以真实实现、测试命令、原始结果、实际问题和限制为主要证据，不能用概念说明或文档检查代替业务验证。

### 4.1 文章目录与发布状态

- 准备写成博客的学习资料统一放在 `docs/学习/文章/`；
- 文件名保持稳定，不因“草稿”“可发布”“已发布”等状态移动目录，避免相对链接失效和 Git 历史噪声；
- 发布状态、所属模块、CSDN 专栏、最近验证和发布地址统一记录在 `项目状态.md`，不放入可直接复制到 CSDN 的正文；
- “草稿”表示仍缺少当前文章类型要求的证据、用户审核或发布前检查；
- “可发布”表示内容、链接、保密信息、事实准确性和当前文章类型要求的证据均已检查完成，可以直接粘贴到 CSDN；
- “已发布”表示用户已经发布文章，并在文档中记录公开地址；
- “已发布”不表示文章内容被冻结。后续实现、实验或路线变化使原文中的计划、限制或事实过时时，必须复核是否直接更新原文；只有新增内容形成独立主题时才另写文章，不能仅因原文已经发布就默认新增一篇；
- 当文章首次达到“可发布”状态时，Codex 必须主动提醒用户，并提供文章标题、文件路径、验证结果和仍需人工确认的发布信息；标记“可发布”前必须完成技术事实、个人理解、对应文章类型的证据和公开可读性检查。

文章正文必须可以直接复制到 CSDN，不包含上述发布元数据；发布状态和地址只记录在 `项目状态.md`。

### 4.2 发布前编辑审核

文章在标记“可发布”以及提供摘要和标签之前，必须在技术事实审核之外再进行一次独立的编辑审核。编辑审核至少检查：

1. 标题和开头能否让读者立即知道这是在开发什么项目、本篇解决什么问题；
2. 章节顺序是否遵循“问题、定义、机制、项目应用、方案取舍、验证、限制”的理解过程，是否存在跳跃或倒置；
3. 专业名词是否在首次使用前解释，后文用词是否一致；
4. 每一段是否只承担一个主要观点，长句、指代和因果关系是否清楚；
5. 示例是否具体且足以支撑结论，代码前后是否解释输入、输出和观察结果；
6. 是否存在重复解释、过度展开、与主题无关的内容或只有作者自己才理解的上下文；
7. 是否把设计、计划、实际实现、测试结果和限制明确区分；
8. 是否混入审核过程、Git 操作、Codex 行为、虚构读者问题或其他不属于技术正文的内容；
9. 零背景读者能否在不依赖生活类比的情况下沿着定义、例子和数据流理解核心概念；
10. 结尾是否准确总结已证明内容和当前边界，没有突然引入正文未讲解的新观点。

编辑审核发现的问题必须先修正并重新检查，再向用户报告文章路径、主要调整、剩余限制、250 字以内摘要和文章标签。用户完成最终阅读并确认后，文章才能标记为“可发布”。

### 4.3 系列文章的篇数与发布顺序

- 不按模块预设固定文章数量。是否形成文章、合并为一篇或拆成多篇，应根据主题是否独立、篇幅是否适合阅读，以及是否已经具备足够的代码、测试或实验依据决定；
- “设计与概念阶段”和“实现与验证阶段”描述的是学习资料的形成过程，不等于两个阶段必须分别发布一篇文章。设计草稿可以在实现后补充证据并合并发布，也可以在两个主题都足够独立时拆分；
- 已发布文章的原文更新不视为新增系列编号；更新后是否还需要下一篇，仍按主题独立性和新增学习价值判断；
- 已明确列入 `项目状态.md` 的文章按队列顺序审核和发布。后续模块可以继续开发和积累资料，但不能跳过队列中尚未处理的前序文章直接发布；调整或取消队列必须先取得用户确认；
- 不能为了保持编号连续而拼凑内容，也不能为了追求固定篇数把缺少实践证据的草稿标记为“可发布”。

## 5. 技术选型说明要求

凡是资料或代码中引入一个技术，都必须增加“为什么选择它”一节，至少回答：

- 它解决了当前项目中的什么具体问题；
- 为什么当前阶段需要它；
- 为什么没有选择两种以上同类方案；
- 选择它的代价是什么；
- 如果规模或约束变化，什么时候应该换方案。

例如选择 Kubernetes 时，需要对比本地进程、Docker Compose、Kubernetes Job 和其他编排方式，而不是只写“Kubernetes 更适合生产环境”。

## 6. 计划中的主题

- 工作流、任务和 DAG；
- 状态机与持久化；
- 重试、幂等和补偿；
- 调度、队列、优先级和背压；
- 节点注册、心跳和租约；
- 分布式一致性与故障模型；
- RPC 与流式通信；
- 容器、namespace、cgroup 和 seccomp；
- Kubernetes 基础与资源调度；
- 日志、指标和分布式 Trace；
- 倒排索引、向量索引、召回和排序；
- Agent、工具调用、权限与评测；
- 自然语言需求澄清、工作流草稿生成和人工确认。

每个主题只在进入相关模块前展开，避免一次性生成大量未经过实践验证的资料。
