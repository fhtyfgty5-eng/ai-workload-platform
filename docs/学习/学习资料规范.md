# 学习资料规范

## 1. 目标

学习资料默认读者此前没有使用过工作流、分布式调度、容器、Kubernetes、搜索推荐或 Agent Infra 工具。资料必须先解释问题和术语，再进入架构和代码。

本专栏记录一个正在从零开发的新项目，专栏名称为“从0构建AI Workload Platform工程实践”。`AI Workload Platform` 是项目名称，不是本文要科普的通用行业术语。每篇文章都必须说明本次技术内容在项目中的具体作用。

## 2. 文章分类与结构

### 2.1 项目总览篇

项目总览篇必须在开头明确作者正在从零开发什么产品、产品服务谁、用户如何使用、为什么要做、与成熟产品的关系、待验证的差异化方向、当前阶段和后续路线。项目总览篇可以引用必要技术术语，但不承担完整的技术科普。

### 2.2 技术学习篇

技术学习篇围绕一个技术主题深入讲解，采用下面的固定结构：

1. 本章要解决的问题；
2. 前置知识；
3. 一句话定义；
4. 中英文术语和缩写；
5. 生活类比；
6. 最小示例；
7. 不使用该技术时会发生什么；
8. 在本项目中的位置；
9. 数据流或状态变化；
10. 方案选择与替代方案；
11. 常见错误和失败场景；
12. 测试、压测或故障实验；
13. 进一步思考或待验证问题；
14. 本章总结。

技术学习篇必须在开头说明该技术解决项目中的什么具体问题；如果同时需要完整介绍产品，应拆出独立的项目总览篇。

### 2.3 模块实践篇

模块实践篇只记录已经实现并验证的代码、测试、实验结果、失败过程和限制。尚未实现的内容必须标记为设计或假设，不能写成已完成事实。实践篇可以使用不同于技术学习篇的章节结构，但必须解释输入、输出、状态、失败路径和验证证据。

## 3. 讲解要求

- 专业名词首次出现时必须解释；
- 英文缩写必须给出英文全称和中文含义；
- 不使用“显然”“很简单”等跳过推理的表述；
- 代码必须解释输入、输出、状态和失败路径；
- 资料区分“了解概念”“能够实现”“能够在面试中解释”三个层次；
- AI 生成内容必须通过官方文档、代码实验或测试验证；
- 用户追问产生的结论应增量补充到原资料，避免多个版本互相冲突；
- 不得包含公司保密信息。
- 不得把 Codex 交接、README 阅读顺序、项目状态字段、Git 过程、文件目录约定或文档验收输出写成技术正文；
- 不得伪造读者提问、用户反馈或尚未发生的实验结果；
- “项目总览篇”与“技术学习篇”承担两个独立目标时，必须拆成系列文章，不能为了简短删除必要的知识解释，也不能因为知识详细而隐藏项目定位。

## 4. CSDN 发布要求

每篇学习资料都要同时满足“项目内部学习”和“可直接粘贴到 CSDN”的要求：

- 使用标准 Markdown；
- 标题、摘要、目录、正文、示例、总结结构完整；
- 代码块标注语言；
- 图片或架构图提供文字说明；
- 不依赖仓库内部路径才能理解；
- 不包含公司代码、内部名称、业务数据和密钥；
- 不把 Codex 交接、仓库维护、文件目录或验证脚本输出当作技术正文；
- 文章开头先说明读者能学到什么，结尾说明限制和未解决问题。

文章不能只是 AI 生成的知识摘录。发布证据按照文章类型区分：

- **项目总览篇**：必须包含作者对产品问题、目标用户、使用边界和技术路线的理解；涉及成熟产品时使用官方资料核对；差异化方向必须标记为待验证假设。项目总览篇不强制提供业务代码或实验结果。
- **尚无业务代码的技术学习篇**：必须包含官方资料核对、作者自己的解释与推理、最小示例、方案取舍、可复现的验证计划和明确的当前限制。不得把验证计划写成实际结果，也不得编造实际遇到的问题。
- **已有业务实现的技术学习篇**：除概念和选型说明外，还必须补充覆盖文章结论的代码、测试或故障实验，以及实际发现的问题和限制。
- **模块实践篇**：必须以真实实现、测试命令、原始结果、实际问题和限制为主要证据，不能用概念说明或文档检查代替业务验证。

### 4.1 文章目录与发布状态

- 准备写成博客的学习资料统一放在 `docs/学习/文章/`；
- 文件名保持稳定，不因“草稿”“可发布”“已发布”等状态移动目录，避免相对链接失效和 Git 历史噪声；
- 发布状态、所属模块、CSDN 专栏、最近验证和发布地址统一记录在 `项目状态.md`，不放入可直接复制到 CSDN 的正文；
- “草稿”表示仍缺少当前文章类型要求的证据、用户审核或发布前检查；
- “可发布”表示内容、链接、保密信息、事实准确性和当前文章类型要求的证据均已检查完成，可以直接粘贴到 CSDN；
- “已发布”表示用户已经发布文章，并在文档中记录公开地址；
- 当文章首次达到“可发布”状态时，Codex 必须主动提醒用户，并提供文章标题、文件路径、验证结果和仍需人工确认的发布信息；标记“可发布”前必须完成技术事实、个人理解、对应文章类型的证据和公开可读性检查。

文章正文必须可以直接复制到 CSDN，不包含上述发布元数据；发布状态和地址只记录在 `项目状态.md`。

## 5. 技术选型说明要求

凡是资料或代码中引入一个技术，都必须增加“为什么选择它”一节，至少回答：

- 它解决了当前项目中的什么具体问题；
- 为什么当前阶段需要它；
- 为什么没有选择两种以上同类方案；
- 选择它的代价是什么；
- 如果规模或约束变化，什么时候应该换方案。

例如选择 Kubernetes 时，需要对比本地进程、Docker Compose、Kubernetes Job 和其他编排方式，而不是只写“Kubernetes 更适合生产环境”。

## 6. 计划中的主题

- 工作流、任务和 DAG；
- 状态机与持久化；
- 重试、幂等和补偿；
- 调度、队列、优先级和背压；
- 节点注册、心跳和租约；
- 分布式一致性与故障模型；
- RPC 与流式通信；
- 容器、namespace、cgroup 和 seccomp；
- Kubernetes 基础与资源调度；
- 日志、指标和分布式 Trace；
- 倒排索引、向量索引、召回和排序；
- Agent、工具调用、权限与评测；
- 自然语言需求澄清、工作流草稿生成和人工确认。

每个主题只在进入相关模块前展开，避免一次性生成大量未经过实践验证的资料。
