# 学习资料规范

## 1. 目标

学习资料默认读者此前没有使用过工作流、分布式调度、容器、Kubernetes、搜索推荐或 Agent Infra 工具。资料必须先解释问题和术语，再进入架构和代码。

## 2. 每篇资料的固定结构

1. 本章要解决的问题；
2. 前置知识；
3. 一句话定义；
4. 中英文术语和缩写；
5. 生活类比；
6. 最小示例；
7. 不使用该技术时会发生什么；
8. 在本项目中的位置；
9. 数据流或状态变化；
10. 方案选择与替代方案；
11. 常见错误和失败场景；
12. 测试、压测或故障实验；
13. 面试追问；
14. 用户问题与增量修订；
15. 本章总结。

## 3. 讲解要求

- 专业名词首次出现时必须解释；
- 英文缩写必须给出英文全称和中文含义；
- 不使用“显然”“很简单”等跳过推理的表述；
- 代码必须解释输入、输出、状态和失败路径；
- 资料区分“了解概念”“能够实现”“能够在面试中解释”三个层次；
- AI 生成内容必须通过官方文档、代码实验或测试验证；
- 用户追问产生的结论应增量补充到原资料，避免多个版本互相冲突；
- 不得包含公司保密信息。

## 4. CSDN 发布要求

每篇学习资料都要同时满足“项目内部学习”和“可直接粘贴到 CSDN”的要求：

- 使用标准 Markdown；
- 标题、摘要、目录、正文、示例、总结结构完整；
- 代码块标注语言；
- 图片或架构图提供文字说明；
- 不依赖仓库内部相对路径才能理解；
- 不包含公司代码、内部名称、业务数据和密钥；
- 项目内部链接放在文末的“项目实践”部分，不影响文章主体阅读；
- 文章开头先说明读者能学到什么，结尾说明限制和未解决问题。

文章不能只是 AI 生成的知识摘录。发布前必须补充你的理解、实验结果、遇到的问题和方案取舍。

### 4.1 文章目录与发布状态

- 准备写成博客的学习资料统一放在 `docs/学习/文章/`；
- 文件名保持稳定，不因“草稿”“可发布”“已发布”等状态移动目录，避免相对链接失效和 Git 历史噪声；
- 每篇文章开头记录发布状态、所属模块、CSDN 专栏、最近验证和发布地址；
- “草稿”表示仍缺少验证、个人实践或发布前检查；
- “可发布”表示内容、实验、链接、保密信息和事实准确性检查均已完成，可以直接粘贴到 CSDN；
- “已发布”表示用户已经发布文章，并在文档中记录公开地址；
- 当文章首次达到“可发布”状态时，Codex 必须主动提醒用户，并提供文章标题、文件路径、验证结果和仍需人工确认的发布信息。

## 5. 技术选型说明要求

凡是资料或代码中引入一个技术，都必须增加“为什么选择它”一节，至少回答：

- 它解决了当前项目中的什么具体问题；
- 为什么当前阶段需要它；
- 为什么没有选择两种以上同类方案；
- 选择它的代价是什么；
- 如果规模或约束变化，什么时候应该换方案。

例如选择 Kubernetes 时，需要对比本地进程、Docker Compose、Kubernetes Job 和其他编排方式，而不是只写“Kubernetes 更适合生产环境”。

## 6. 计划中的主题

- 工作流、任务和 DAG；
- 状态机与持久化；
- 重试、幂等和补偿；
- 调度、队列、优先级和背压；
- 节点注册、心跳和租约；
- 分布式一致性与故障模型；
- RPC 与流式通信；
- 容器、namespace、cgroup 和 seccomp；
- Kubernetes 基础与资源调度；
- 日志、指标和分布式 Trace；
- 倒排索引、向量索引、召回和排序；
- Agent、工具调用、权限与评测；
- 自然语言需求澄清、工作流草稿生成和人工确认。

每个主题只在进入相关模块前展开，避免一次性生成大量未经过实践验证的资料。
