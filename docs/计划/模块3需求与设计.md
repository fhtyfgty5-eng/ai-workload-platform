# 模块 3：Agent Runtime、模型与工具执行需求与设计

## 1. 文档目的

本文定义模块 3 的实现边界、接口契约、数据结构、权限限制、确认流程、审计边界、测试策略和交付物。模块 3 在模块 1 的可靠工作流内核和模块 2 的控制面之上增加 Agent Runtime（Agent 运行时环境），完成自然语言目标到结构化 Workflow 草稿的最小产品演示。

本文是模块 3 的设计基线。未写入本文或未得到用户明确确认的候选能力，不直接进入实现计划。

## 2. 已确认范围

### 2.1 目标

- 提供统一的 Agent 执行请求、结果和事件边界；
- 提供默认离线可测的 Mock Model（模型模拟器）；
- 提供一个可替换的真实模型适配器，真实调用只由用户人工触发；
- 提供工具注册表和受控工具调用接口；
- 第一版唯一工具是只读工作流目录查询工具；
- 支持自然语言目标生成结构化 Workflow 草稿；
- 在草稿中区分用户事实、Agent 假设和待确认问题；
- 校验依赖、参数、权限、Agent Runtime 预算、任务超时和 Agent Workflow 并发边界；
- 用户确认后才能生成最终 WorkflowDefinition；
- 最终定义继续使用模块 1 的 `workflow.Compile`，再由模块 2 控制面保存；
- 第一版使用 Go 接口和 CLI/JSON 入口，模块 7 再接入 HTTP/控制台；
- 默认自动化测试不访问外部网络，不依赖付费模型 API。

### 2.2 向后兼容的数据扩展

当前模块 1 的 `TaskDefinition` 只有 `Action`，不足以表达自然语言生成的任务输入。模块 3 增加可选的结构化 `Input` 字段，并在 `ExecutionRequest` 中传递该字段：

- 旧的无输入任务保持原有 JSON 和 Go 调用方式不变；
- `Input` 只允许 JSON 对象及其基本值：字符串、数字、布尔值、数组和嵌套对象；
- 不允许函数、脚本、表达式或需要本机执行的对象；
- 调度、状态机、重试、超时、取消和恢复规则不改变；
- FileStore、PostgreSQL 定义 JSON 和定义哈希继续保存完整结构化定义。

### 2.3 明确不做

- 不实现大规模多 Agent 协作；
- 不执行任意 Shell、代码、脚本或本机进程；
- 不读取任意本机文件；
- 不访问外部网络的任意 URL；
- 不实现通用代码沙箱或绝对安全承诺；
- 不让模型直接创建 Workflow、启动 Run 或修改数据库；
- 不在模块 3 首版实现 HTTP 控制台；
- 不把任意供应商 SDK 类型暴露到平台公开接口；
- 不把 API Key、密码、完整 Authorization 头或未经脱敏的敏感模型上下文写入日志、测试夹具或 Git；
- 不对真实模型响应时间、费用或可用性作平台性能承诺；
- 不为了模块 3 提前引入 Redis、Kafka、gRPC、API Gateway 等未出现实际需求的组件。

## 3. 总体架构

```text
用户自然语言目标
        |
        v
   Agent Runtime
    /        \
   v          v
Model       Tool Registry
Adapter     (只读目录工具)
    \        /
     v      v
       Workflow Draft
              |
              v
       Draft Validator
              |
              v
       CLI 展示并确认
              |
              v
      workflow.Compile
              |
              v
      模块 2 控制面提交
```

组件职责：

- **Agent Runtime**：管理一次 Agent 生成会话的上下文、工具调用、预算、超时、取消、草稿状态和审计事件；不负责 DAG 调度。
- **Model Adapter**：把平台统一请求转换为具体模型协议，再把模型响应转换为平台结构化结果；不创建 Workflow 或 Run。
- **Tool Registry**：只暴露显式注册的工具，检查工具名称、输入、调用次数和超时。
- **Workflow Catalog Tool**：返回已注册任务模板、Action、参数定义、权限要求和任务超时上限；不修改数据。
- **Workflow Draft**：保存用户目标、候选定义、事实、假设、待确认问题和校验结果，是人工审核对象。
- **Draft Validator**：执行结构、目录参数、权限、任务超时和 Agent Workflow 并发校验，并最终调用模块 1 的 `workflow.Compile`。
- **模块 2 控制面**：只接收经过用户确认且已经编译通过的结构化定义，负责版本化保存和后续运行。

普通程序任务和 Agent 任务仍然共用模块 1 的工作流状态、重试、超时、取消和恢复语义。Agent Runtime 只产生任务定义和 Agent 执行边界，不把 Agent 分支揉入调度器。

## 4. 数据模型

### 4.1 WorkflowDefinition 扩展

沿用模块 1 的定义模型，并为 `TaskDefinition` 增加：

```text
Input map[string]any `json:"input,omitempty"`
```

`Input` 是任务执行输入。它通过 `ExecutionRequest` 传给具体 Executor；普通 Mock Executor 可以忽略它，目录中需要参数的任务模板必须明确声明并校验它。

### 4.2 Workflow Draft

```text
WorkflowDraft
- draft_id
- goal
- definition
- facts[]
- assumptions[]
- questions[]
- validation
- tool_calls[]
- status
- content_hash
- created_at
- confirmed_at
```

字段语义：

- `facts` 是从用户输入中直接得到的陈述，不表示平台已经从外部系统验证；
- `assumptions` 是模型为补全目标而推断的内容，必须单独展示；
- `questions` 是影响任务、依赖、参数、权限、任务超时或并发的未决问题；存在未解决问题时不能确认；
- `validation` 保存错误码、警告和校验阶段；
- `tool_calls` 保存工具名称、参数摘要、允许/拒绝结果和耗时，不保存敏感完整内容；
- `content_hash` 是审核字段规范化 JSON 的哈希，审核字段包括目标、定义、事实、假设、问题、校验结果、工具调用记录和状态，用于确认时检测草稿是否被修改。

草稿状态：

```text
generated -> validated -> needs_confirmation -> confirmed
                                      \-> rejected
```

模型响应结构错误、工具拒绝、校验失败或用户取消都不能进入 `confirmed`。

### 4.3 任务模板

工作流目录中的任务模板至少包含：

- 稳定模板标识；
- 可用 `Action`；
- 输入字段及类型、必填项、可选项和枚举值；
- 所需权限；
- 模块 3 可执行校验的任务超时上限；
- 是否允许 Agent 使用。

第一版使用项目内静态注册表，不读取任意本机目录。CPU、内存和临时存储尚未进入 `TaskDefinition`，因此模块 3 不声称已经校验或隔离这些资源；它们在模块 6 的真实执行环境中统一设计。未来若目录改为数据库或远程服务，仍通过同一只读工具接口接入。

## 5. 核心接口

### 5.1 Model Adapter

平台只依赖统一接口，具体供应商协议隐藏在适配器内部：

```text
Generate(context.Context, ModelRequest) (ModelResponse, error)
```

`ModelRequest` 包含用户目标、允许的工具清单、按轮次排列的工具调用与结果历史、剩余调用预算和响应大小限制；超时与取消信号由 `context.Context` 传递。`ModelResponse` 只接受结构化 JSON 及必要的模型调用元数据。

实现顺序：

1. `MockModel`：固定输入、固定工具结果和固定输出，保证离线测试可复现；
2. 一个可替换的真实模型适配器：人工显式启用，凭证只从环境变量或本地未提交配置读取；
3. 真实适配器的供应商类型不穿透到 Runtime、CLI 或公开 SDK。

### 5.2 Tool Registry

工具统一使用：

```text
Invoke(context.Context, ToolRequest) (ToolResponse, error)
```

Runtime 在调用前检查工具是否注册、参数是否符合工具输入定义、调用次数是否超限以及当前 Agent 是否拥有权限。工具只能返回数据，不能直接改变草稿、Workflow、Run 或文件。

第一版 `WorkflowCatalogTool` 只读查询任务模板。它不执行 Shell、不读取任意文件、不访问网络、不写数据库。

### 5.3 Draft Service

CLI 和未来 HTTP 控制台都通过同一服务层使用以下操作：

```text
GenerateDraft(ctx, goal) -> WorkflowDraft
ValidateDraft(ctx, draft) -> WorkflowDraft
ConfirmDraft(ctx, draft, contentHash) -> WorkflowDefinition
```

`ConfirmDraft` 必须同时满足：草稿状态允许确认、内容哈希匹配、没有未解决问题、校验无错误、所有任务模板仍然可用。它只返回最终结构化定义，不自动启动 Run。

## 6. 生成、校验和提交流程

```text
workload agent draft <goal>
  -> Mock/真实 Model 生成草稿
  -> 必要时查询只读任务目录
  -> 保存或输出 WorkflowDraft

workload agent validate <draft-file>
  -> 结构校验
  -> 目录和参数校验
  -> 权限、任务超时与 Agent Workflow 并发校验
  -> workflow.Compile

workload agent confirm <draft-file> --hash <content-hash>
  -> 检查草稿未被修改
  -> 检查问题已处理
  -> 输出最终 WorkflowDefinition JSON

go run ./cmd/workload workflow create <definition-file> \
  --idempotency-key <key>
  -> 模块 2 控制面保存不可变 Workflow 版本
```

`agent confirm` 默认不提交控制面，也不启动 Run。提交仍使用已有控制面 CLI，便于用户在演示中清楚看到 Agent 建议、用户确认和可靠执行之间的边界。模块 7 再把这几个步骤组合成控制台交互。

## 7. 错误、重试、取消与预算

稳定错误码至少包括：

- `model_timeout`、`model_unavailable`、`model_invalid_response`；
- `tool_not_allowed`、`tool_invalid_input`、`tool_timeout`；
- `budget_exceeded`、`draft_invalid`、`approval_required`、`draft_changed`、`canceled`。

只有模型服务不可用等传输类错误允许一次有界重试。工具拒绝、参数错误、预算超限和草稿校验失败不重试。Runtime 的重试不改变模块 1 的 Attempt 语义。

第一版限制：

- 单次生成的模型调用轮数；
- 单次生成的工具调用次数；
- 工具和模型响应字节数；
- Runtime 总超时；
- 草稿任务数量；
- 每个任务的模板超时上限；
- Agent 生成的 Workflow 并发不得超过任务数，并且最高为 32。

所有模型和工具调用响应 `context.Context` 的取消和截止时间。用户取消后不得继续发起新的模型或工具调用。

## 8. 审计与敏感信息

至少记录以下结构化审计事件：

- 草稿生成开始、成功和失败；
- 模型适配器标识、结果分类和预算消耗；
- 工具调用、参数校验、允许或拒绝原因；
- 草稿校验结果；
- 用户确认；
- 草稿内容哈希；
- 超时、取消和预算耗尽。

模块 3 没有独立的“拒绝草稿”命令，用户可以不执行确认或直接废弃本地草稿文件；它也不把确认和控制面提交合并成一个操作。最终 Workflow ID 和版本继续由模块 2 控制面日志和数据库记录，避免 Agent 审计声称自己完成了未执行的提交。

日志和审计只保存必要元数据。API Key、密码、完整 Authorization 请求头、未脱敏敏感目标和完整工具结果不得写入日志、示例或 Git。真实模型适配器只从环境变量或本地未提交文件读取配置。

## 9. 测试与验收

### 9.1 自动化测试

默认测试不访问外部网络，至少覆盖：

- Mock Model 的确定性输出；
- 非法 JSON、未知字段、超大响应和供应商错误；
- 工具注册、允许调用、未知工具、非法参数、超时和预算耗尽；
- 事实、假设和待确认问题的结构化标记；
- 缺少参数、未知 Action、依赖环、任务数量、任务超时和 Agent Workflow 并发限制；
- Runtime 超时、取消和有界重试；
- 草稿哈希变化后的确认拒绝；
- 未解决问题不能确认；
- 确认后的定义能够通过模块 1 编译器；
- CLI 成功输出、稳定错误码和非零退出码；
- 真实模型适配器默认不会被调用。

### 9.2 人工演示

使用不包含公司信息的固定目标：

> 先读取文档，再清洗内容，最后生成摘要；清洗依赖读取，摘要依赖清洗。

演示展示自然语言输入、结构化草稿、事实/假设/待确认问题、目录工具记录、校验结果、用户确认、最终定义以及现有控制面创建的不可变版本。

### 9.3 性能和限制

只测平台自身开销：Mock Model 生成、工具调用、草稿校验、编译和取消收敛。真实模型延迟、费用和供应商限流不作为平台性能承诺。10,000 任务的编译基线继续由模块 1 维护，模块 3 只验证草稿转换不会绕过该上限。

## 11. 验收标准

模块 3 只有同时满足以下条件才算完成：

1. Mock Model、只读目录工具、草稿生成、校验和用户确认均有自动化测试；
2. 默认测试不需要网络、API Key 或付费模型；
3. 至少一个真实模型适配器可由用户人工显式触发，且凭证不进入代码、日志和提交；
4. 未注册工具、越权参数、未解决问题、校验失败和草稿篡改都不能进入确认或提交；
5. 确认后的定义仍由模块 1 编译器校验，并能通过模块 2 创建不可变 Workflow 版本；
6. 取消、超时、预算耗尽和模型错误均有稳定错误码、测试或可复现实验；
7. CLI 演示能完整展示“自然语言 -> 草稿 -> 校验 -> 确认 -> Workflow 版本”；
8. 学习资料面向零背景读者解释 Agent、模型适配器、工具调用、事务边界和审批，并说明技术选型、未选择同类方案的原因与限制；
9. 开源检查不包含公司信息、密钥、外部私有数据或本机绝对路径。

## 12. 变更控制

以下能力不自动进入模块 3：多 Agent 编排、任意代码沙箱、外部知识库、远程文件工具、自动启动 Run、HTTP 控制台和新的基础设施组件。若后续需要，必须说明新增问题、收益、成本、受影响接口和验收方式，并更新架构决策记录、路线图和实现计划。

## 13. TDD 实现计划

### 13.1 全局约束

- 默认自动化测试必须离线运行，不读取真实 API Key，不访问付费模型。
- 真实模型适配器只允许用户人工显式触发，凭证来自环境变量或本地未提交配置。
- 第一版唯一工具是只读工作流目录查询；禁止任意 Shell、任意本机文件、任意外部 URL 和数据库写入。
- Agent 不能直接创建 Workflow、启动 Run 或修改持久化状态；确认后的定义必须走模块 2 既有入口。
- `TaskDefinition.Input` 是向后兼容的可选 JSON 对象；不改变 DAG、状态机、重试、超时、取消和恢复语义。
- 默认限制为：单次 Runtime 最多 4 轮模型调用、最多 8 次工具调用、单次模型/工具响应最多 64 KiB、Runtime 总超时 30 秒；限制必须可配置并覆盖测试。
- 代码标识符保持英文；公开类型和关键不变量使用符合 Go 工程习惯的中文注释。
- 每个任务完成后运行对应测试、`gofmt`、`go test`；全部任务完成后再运行全量验证并暂停模块级人工审核。
- 文章和实验文档只能描述已经实现、测试或人工验证的事实，不把计划写成完成结果。

- `agent/budget.go`：模型轮数、工具次数、响应大小和 Runtime 截止时间。
- `agent/audit.go`：审计事件类型、记录接口和敏感字段脱敏。
- `agent/tool.go`：`Tool`、`ToolRegistry`、工具请求/响应和权限检查。
- `agent/catalog/catalog.go`：静态任务模板目录与只读查询工具。
- `agent/draft.go`：`WorkflowDraft`、事实、假设、问题和状态。
- `agent/validator.go`：草稿结构、目录、参数、权限、任务超时、Agent Workflow 并发和 Compile 校验。
