# 模块 7：真实场景、最小控制台与开源发布需求与设计

## 1. 文档目的

本文定义模块 7 的需求边界、浏览器控制台设计、Draft API、真实公开场景、测试策略、部署方式、CI/CD 和开源治理。

模块 7 是当前路线的最后一个建设模块。它不重新设计工作流内核、控制面、Worker、观测或受限执行环境，而是把前六个模块已经验证的能力组织成一条新用户可以安装、理解、操作和演示的产品流程。

模块 7 建立在以下能力之上：

- 模块 1：工作流定义、DAG（Directed Acyclic Graph，有向无环图）调度、状态机、重试、超时、取消和恢复；
- 模块 2：版本化 HTTP 控制面、PostgreSQL 事务持久化、幂等提交和查询；
- 模块 3：Agent Runtime、Mock Model、工具权限、草稿校验、内容哈希和人工确认；
- 模块 4：独立 Worker、Dispatch、租约、心跳、回收和故障接管；
- 模块 5：结构化日志、Prometheus 指标、Trace、告警、故障注入和性能证据；
- 模块 6：固定 Action、受限 Docker/Kubernetes 执行器和本地部署清单。

## 2. 为什么现在进入模块 7

模块 6 之后，平台已经具有较完整的后端执行链，但新用户仍需要通过多个终端、CLI 命令和 JSON 文件理解各阶段，存在以下缺口：

- 自然语言草稿、校验、确认和可靠执行没有统一的浏览器入口；
- 工作流、Run、Task、Attempt、Worker 和事件事实分散在多个 API 与终端输出中；
- 现有能力缺少一个不包含公司信息的公开场景来证明产品价值；
- 新电脑的安装、前后端启动、测试和演示流程还没有 CI/CD 与开源治理作为自动门禁。

因此模块 7 的目标是提供一个轻量但真实的客户端和一条端到端演示路径，而不是堆叠一个与后端无关的静态页面。

## 3. 术语

### 3.1 Web 控制台

Web 控制台是运行在浏览器中的操作界面。它负责收集用户输入、调用 HTTP API 并展示服务端返回的事实；它不是新的业务服务，也不直接连接 PostgreSQL。

### 3.2 Draft API

Draft API 是面向 Agent 工作流草稿的 HTTP 接口。草稿是模型根据自然语言目标生成、但尚未成为业务事实的结构化建议。草稿必须经过服务端校验和用户确认，才能提交为不可变 Workflow 版本。

### 3.3 sessionStorage

`sessionStorage` 是浏览器按标签页保存的临时键值存储。模块 7 使用它保存用户当前输入的控制面地址、Token 和尚未提交的草稿；关闭标签页后数据清除，不把凭据写入 URL、源码或构建产物。

### 3.4 Vite

Vite 是前端开发服务器和构建工具。开发时它提供快速热更新和 API 代理；发布时它把 React 与 TypeScript 代码构建为可由静态文件服务器提供的资源。

### 3.5 CI/CD

CI（Continuous Integration，持续集成）是在代码变更后自动运行格式化检查、测试和构建。CD（Continuous Delivery/Deployment，持续交付/部署）是把通过检查的构建产物以可重复方式交付。模块 7 只要求 GitHub Actions 完成检查和构建，不自动发布生产服务。

## 4. 目标与非目标

### 4.1 目标

模块 7 必须完成：

1. 在现有 Go 控制面中增加最小 Draft API，复用模块 3 的 Agent Service、目录、校验器和 Mock Model；
2. 使用 React、TypeScript 和 Vite 在独立 `web/` 目录构建轻量控制台；
3. 通过浏览器完成“输入自然语言、生成草稿、查看校验结果、人工确认、创建 Workflow、启动 Run、查看执行和观测”的闭环；
4. 复用现有 Workflow、Run、Task、Event、Worker、Cancel 和 Metrics API，不让前端复制状态机或调度逻辑；
5. 使用公开且不包含公司信息的文档处理场景，展示普通程序任务与 Agent 草稿之间的协作边界；
6. 补齐前端测试、后端接口测试、生产构建、本地开发文档和浏览器手动验收路径；
7. 增加 GitHub Actions、许可证、贡献指南、安全策略、行为准则、变更记录和发布前检查。

### 4.2 非目标

模块 7 不承诺：

- 任意拖拽流程设计器、复杂图编辑器或低代码编排平台；
- 完整的用户注册、登录、OAuth/OIDC、多租户或细粒度权限后台；
- 让浏览器直接访问 PostgreSQL、Docker Engine 或 Kubernetes API；
- 在前端重新实现 DAG 校验、状态转换、重试、取消、租约或恢复；
- 默认调用付费模型或把模型 API Key 发送到浏览器；
- WebSocket、SSE、实时日志检索、完整日志后台或生产级监控产品；
- 移动端、小程序、复杂商业报表和未经证据支持的企业级功能；
- 自动发布 GitHub Release、部署云环境或修改用户的 Docker/kind 环境。

## 5. 产品主线与验收场景

### 5.1 推荐演示场景

场景使用固定文档处理目标：

> 先读取 `article.md`，再清洗内容，最后生成摘要。

默认使用 Mock Model。Mock Model 是用固定响应模拟模型协议的本地实现，不代表真实模型的理解质量，也不访问外部网络。该场景的浏览器流转为：

```text
用户输入自然语言目标
  -> 控制面生成 WorkflowDraft
  -> 控制台展示事实、假设、问题和工具调用摘要
  -> 控制面执行校验
  -> 用户确认 content_hash 对应的草稿
  -> 控制面创建不可变 Workflow v1
  -> 控制面启动 Run
  -> Worker 领取并执行任务
  -> 控制台轮询 Run、Task、Attempt 和 Event
  -> 展示成功、失败、取消或恢复接管结果
```

模型建议不是执行事实。只有确认后的 `WorkflowDefinition`、数据库中的 Run/Task/Attempt/Event 和 Worker 返回的结构化结果才能驱动后续页面。

### 5.2 公开场景边界

场景只能使用仓库示例文件、固定 Action 和 Mock Model，不包含公司代码、业务数据、个人路径、Token 或第三方 API Key。真实模型适配器仍由服务端配置显式启用，浏览器不能提交模型地址、模型名或密钥。

## 6. 总体架构

```text
浏览器 Web 控制台（React + TypeScript）
              |
              | HTTP/JSON + Bearer Token
              v
Go 控制面 API
  |-- Agent Service / Draft API
  |-- Workflow 与 Run Application Service
  |-- PostgreSQL Repository
  |-- Worker / Dispatch API
  `-- Metrics
              |
              v
独立 Worker -> Mock 或受限 Docker/Kubernetes 执行器
```

控制台是现有控制面的客户端，不新增第二套 Go 服务端。开发环境由 Vite 代理 `/api`、`/health` 和 `/metrics` 到 `WORKLOAD_SERVER_URL`；演示或发布时使用构建后的静态文件。优先采用同源部署，以减少跨域配置和凭据暴露面。

## 7. 认证与安全边界

### 7.1 Token 输入

当前控制面使用配置式 viewer/operator Bearer Token，没有用户登录接口。控制台提供本地 Token 输入页：用户选择角色并输入 `.env.local` 中对应 Token。

- viewer Token 只能查询 Workflow、Run、Task、Event、Worker 和 Metrics；
- operator Token 才能生成/校验/确认草稿、创建 Workflow、启动 Run 和取消 Run；
- Token 只保存在当前标签页的 `sessionStorage`；
- Token 不写入 URL、localStorage、源码、`.env` 前端变量、日志或错误消息；
- 退出控制台时清除会话 Token；
- API 返回 401/403 时显示重新认证或权限不足，不自动猜测或替换 Token。

这是本地演示认证，不等同于生产级用户身份系统。后续若引入 OAuth/OIDC，必须单独评审并更新 ADR、接口和安全边界。

### 7.2 服务端约束

Draft API 继续使用控制面统一的 request ID、错误结构、就绪检查、Body 限制和 Bearer 认证。前端提交的草稿内容必须由服务端重新计算哈希并执行完整校验；不能信任前端传回的 `status`、`validation` 或 `content_hash`。

草稿不写入 PostgreSQL。浏览器在当前标签页的 `sessionStorage` 中暂存完整草稿，服务端每次校验和确认都重新检查；只有确认后的 Workflow、Run 和执行事件成为持久化业务事实。刷新页面或控制面重启后，浏览器可以重新提交同一草稿进行校验；关闭标签页后草稿清除。服务端不依据内存记录信任旧草稿。

## 8. Draft API 设计

### 8.1 创建草稿

`POST /api/v1/agent/drafts`

请求：

```json
{"goal":"先读取 article.md，再清洗内容，最后生成摘要"}
```

要求 operator Token。服务端使用默认 Mock Model 或服务端明确配置的合法模型适配器调用 Agent Service，返回完整 `agent.WorkflowDraft`，包括 `draft_id`、结构化定义、事实、假设、问题、工具调用摘要、状态和 `content_hash`。创建草稿不创建 Workflow、Run 或数据库业务事实。

### 8.2 校验草稿

`POST /api/v1/agent/drafts/{draft-id}/validate`

请求携带完整草稿：

```json
{"draft": {"draft_id":"draft_xxx", "goal":"...", "definition": {}}}
```

服务端检查路径中的 ID 与草稿 `draft_id` 一致，然后调用既有 Draft Validator 和 `workflow.Compile`。返回刷新后的完整草稿：存在错误时状态保持可修正状态；无错误时状态进入 `needs_confirmation`，并返回新的哈希。校验不写入 PostgreSQL。

### 8.3 确认草稿

`POST /api/v1/agent/drafts/{draft-id}/confirm`

请求携带完整草稿和用户看到的哈希：

```json
{"draft": {"draft_id":"draft_xxx", "status":"needs_confirmation", "content_hash":"..."}, "content_hash":"..."}
```

服务端重新计算哈希、重新校验所有问题和结构，并拒绝以下情况：草稿 ID 不一致、哈希不一致、存在未解决问题、校验错误、状态不允许确认或定义无法编译。成功时返回编译后的 `WorkflowDefinition`，但不自动创建 Workflow 或启动 Run；前端随后使用既有 Workflow API 和新的幂等 Key 完成持久化。

### 8.4 错误分类

Draft API 复用模块 3 的错误码并映射到统一错误信封，至少包括：`draft_invalid`、`draft_changed`、`approval_required`、`model_timeout`、`model_unavailable`、`tool_denied`、`tool_timeout`、`canceled` 和 `internal_error`。错误消息不得包含 API Key、完整输入文件内容或内部堆栈。

## 9. 控制台页面与交互

### 9.1 页面结构

采用带侧边导航的单页应用（SPA，Single-Page Application，页面切换不重新加载整个文档），页面数量保持最小：

1. **Overview**：最近 Run、按状态统计、在线 Worker、队列和 Metrics 摘要；
2. **Workflows**：Workflow 列表、最新版本、版本定义和任务依赖；
3. **Create**：自然语言目标输入和草稿生成；
4. **Draft Review**：定义任务表、依赖、事实、假设、待确认问题、错误/警告和确认操作；
5. **Run Detail**：Run 状态、Task/Attempt、事件时间线、取消按钮和轮询状态；
6. **Workers**：Worker 状态、执行器能力、并发上限和活动租约；
7. **Observability**：低基数 Metrics 摘要、指标原文入口和事件查询入口。

页面必须提供明确的加载、空数据、网络失败、401、403、404、409、服务未就绪和成功状态。状态颜色不能作为唯一信息，必须同时显示文本。

### 9.2 页面数据来源

| 页面 | 主要 API | 允许的写操作 |
| --- | --- | --- |
| Overview | `/api/v1/runs`、`/api/v1/workers`、`/metrics` | 无 |
| Workflows | `/api/v1/workflows`、`/api/v1/workflows/{id}`、版本 API | 创建版本 |
| Create/Draft Review | Draft API | 生成、校验、确认 |
| Run Detail | Run、Task、Event API | 取消 Run |
| Workers | `/api/v1/workers`、`/api/v1/workers/{id}` | 无 |
| Observability | `/metrics`、Run Event API | 无 |

前端不直接读取数据库，不使用 Worker 注册、领取、心跳、完成或 drain 接口。Worker 协议只供独立 Worker 进程使用。

### 9.3 轮询

第一版使用固定间隔的有限轮询刷新 Run、Task 和 Worker。每次请求使用可取消的 `AbortController`；组件卸载或切换页面时取消请求和定时器。前端只展示服务端状态，不根据本地时间自行把 `pending` 推断为 `running`，也不自行执行重试和恢复。

不提前引入 WebSocket 或 SSE。只有轮询在真实演示中被证明无法满足体验时，才单独评估服务端推送。

## 10. 前端技术选型

### 10.1 选择 React、TypeScript 和 Vite

- React 提供成熟的组件模型，适合把草稿、运行状态、表格和时间线拆成可测试的界面单元；
- TypeScript 在编译期检查 API 响应和组件数据结构，减少状态字段拼写和空值处理错误；
- Vite 提供轻量开发服务器和静态构建，能与现有 Go 控制面保持单独部署边界。

### 10.2 不选择的方案

- 不选择 Go HTML 模板：可以快速生成页面，但不能充分证明现代前后端整合能力，交互状态也更难拆分测试；
- 不选择 Next.js：Go 控制面已经是唯一服务端事实源，增加第二套服务端会模糊认证、部署和状态边界；
- 不引入 Redux、TanStack Query 或大型 UI 框架：当前页面状态和请求数量有限，额外缓存层会增加学习与调试成本；
- 不引入图编辑器：第一版只展示依赖表和结构化定义，不允许用户任意编辑 DAG；
- 图标使用 `lucide-react`，不手写重复 SVG；控制按钮使用熟悉的图标和悬停提示，文字按钮只用于明确的业务命令。

## 11. 后端接口与代码边界

Draft API 适配器放在控制面 HTTP 边界附近，依赖 `agent.Service` 的公开方法，不把 Agent 内部实现复制到 HTTP Handler。建议保持以下接口方向：

```go
type DraftService interface {
    GenerateDraft(context.Context, string) (agent.WorkflowDraft, error)
    ValidateDraft(context.Context, agent.WorkflowDraft) (agent.WorkflowDraft, error)
    ConfirmDraft(context.Context, agent.WorkflowDraft, string) (workflow.WorkflowDefinition, error)
}
```

HTTP Handler 只负责路径、角色、JSON、Body 限制、错误映射和响应编码；草稿生命周期、哈希、目录权限和编译仍由 Agent Service 负责。控制面启动时默认注入 Mock Model；真实 HTTP Model 只在服务端配置完整且显式启用时创建。

模块 7不改变既有 CLI、SDK、WorkflowService、RunService、Worker API 或数据库表结构。若实现过程中发现必须改变公开接口、认证、数据模型或模型配置，必须先更新本设计和 ADR 再继续。

## 12. 测试策略

### 12.1 后端

- Draft API 的生成、校验、确认成功路径；
- viewer 拒绝 Draft 写操作，operator 可以执行；
- 路径 Draft ID 与 Body ID 不一致；
- 修改定义、事实、假设、问题或校验结果后哈希被拒绝；
- 未校验、未解决问题、校验错误和模型错误的状态映射；
- Draft API 不创建数据库 Workflow/Run；
- OpenAPI 路径、方法、请求体、响应体和错误码契约；
- 全仓 `go test ./...`、`go test -race ./...`、`go vet ./...` 和文档验证。

### 12.2 前端

使用 Vitest、React Testing Library 和 JSDOM（模拟浏览器 DOM 的测试环境）覆盖：

- Token 输入、sessionStorage 保存、退出清除和角色边界；
- API 客户端的 JSON、Bearer Token、幂等 Key、分页和错误信封；
- 草稿生成、校验警告、哈希确认和篡改错误；
- Workflow 创建、Run 启动、轮询、取消、完成、失败和网络中断；
- Task/Attempt/Event、Worker 和 Metrics 展示；
- 加载、空状态、401/403/404/409/503 和响应字段缺失；
- `npm run build` 生产构建。

### 12.3 浏览器验收

在本地 PostgreSQL、控制面和至少一个 Worker 已启动的环境中，人工完成一条闭环：

1. 输入自然语言目标并生成草稿；
2. 查看事实、假设、校验结果和任务依赖；
3. 确认草稿并创建 Workflow v1；
4. 启动 Run 并看到 Task/Attempt 逐步完成；
5. 查看事件和 Metrics 摘要；
6. 对运行中的 Run 执行取消，或通过 Worker 强杀实验看到 `interrupted` 后由新 Worker 接管并成功；
7. 刷新页面后重新从 API 恢复状态，不依赖前端内存。

## 13. 本地开发与部署

### 13.1 开发模式

`web/` 提供 `.env.example` 或 Vite 配置中的 API 代理目标，但不放 Token。开发步骤为：

1. 按现有部署手册启动 PostgreSQL、迁移、控制面和 Worker；
2. 在 `web/` 安装锁定版本依赖；
3. 设置仅包含 API Base URL 的本地前端配置；
4. 启动 Vite 开发服务器；
5. 在浏览器输入本机 viewer/operator Token。

### 13.2 演示/发布模式

`npm run build` 生成 `web/dist` 静态文件。第一版推荐由反向代理或静态文件服务器提供，并把 `/api`、`/health` 和 `/metrics` 转发到 Go 控制面；也可以在 Go 控制面中增加可选的静态文件托管，但不得把前端构建产物和服务端业务逻辑混在同一个新服务中。

控制面仍是唯一业务事实源。浏览器部署变化不能改变数据库、Worker、租约和恢复语义。

### 13.3 换电脑要求

本地开发与配置手册需要新增：Node.js 版本要求、npm 依赖安装、前端启动、生产构建、浏览器 Token 输入、Vite 代理和常见前端故障排查。Token、数据库数据、Docker 镜像、kind 集群和 `web/node_modules` 不通过 Git 同步；新电脑按手册重新生成 Token、安装依赖和构建。

## 14. CI/CD 与开源治理

### 14.1 GitHub Actions

至少配置以下检查：

- Go 格式化差异、全仓测试、竞态测试和 `go vet`；
- 文档链接、必需文件、冲突标记和 Markdown 检查；
- Kubernetes 清单静态检查；
- Node.js 锁定版本、`npm ci`、前端测试和生产构建；
- 敏感信息扫描和依赖许可证检查；
- 仅在代码、文档或工作流相关路径变化时触发对应任务，并保留一个全量门禁任务。

CI 不访问付费模型、不依赖本机 Docker Desktop、不把真实 Token 写入日志，也不把性能基线误设为绝对容量门禁。

### 14.2 开源文件

补齐并维护：

### 15.3 完成标准

模块 7 只有同时满足以下条件才算完成：

1. 新电脑能够按部署手册启动后端、前端和示例；
2. 浏览器能够完成草稿生成、服务端校验、人工确认、Workflow 创建和 Run 启动；
3. 浏览器能够查询 Run、Task、Attempt、Event、Worker 和 Metrics，并执行取消；
4. Worker 强杀或控制面恢复证据能够在页面中看到对应结果，且不由前端伪造；
5. CLI、SDK 和既有 HTTP API 继续通过原有测试；
6. Go、前端、文档、Kubernetes 和敏感信息检查全部通过；
7. 公开材料明确说明 Mock Model、容器安全边界、轮询限制、单协调者和未完成实验，不把计划写成已验证能力。
