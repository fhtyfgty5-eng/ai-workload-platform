# 模块 4：多 Worker、租约、心跳与故障恢复需求与设计

## 1. 文档目的

本文定义模块 4 的需求边界、架构、状态模型、持久化结构、Worker 协议、故障语义、安全限制、测试策略和交付物。模块 4 在已有可靠工作流内核、控制面和 Agent Runtime 之上，将任务执行从控制面进程内部拆分到多个独立 Worker 进程。

本文是模块 4 的设计基线。详细实施步骤、测试顺序和精确文件改动在本文审核通过后另行编写；本文确认前不修改业务代码。

## 2. 为什么现在进入模块 4

### 2.1 前三个模块已经证明了什么

- 模块 1 已经验证 DAG（Directed Acyclic Graph，有向无环图）、状态机、依赖解锁、重试、超时、取消和单进程恢复语义；
- 模块 2 已经建立 HTTP/OpenAPI 控制面、PostgreSQL 事务持久化、幂等提交、认证和单协调者恢复；
- 模块 3 已经建立 Agent Runtime、模型适配、工具权限、自然语言工作流草稿、校验和人工确认边界。

这些能力解决了“任务如何定义、状态如何保存、客户端如何提交、Agent 如何受控生成工作流”的问题，但任务最终仍由控制面进程中的 Mock Executor 执行。

### 2.2 上一阶段仍解决不了什么

当前单进程执行模型无法回答以下问题：

- 如何增加执行节点而不复制整个控制面；
- 两个 Worker 同时看到同一任务时，谁有权执行；
- Worker 进程崩溃或网络中断后，任务何时可以重新分配；
- 旧 Worker 恢复后提交迟到结果时，如何阻止它覆盖新 Attempt；
- Worker 没有空闲容量时，如何让任务可靠等待而不是无限启动 goroutine；
- 如何在保留至少执行一次语义的同时，明确重复副作用的责任边界。

因此，模块 4 不是为了增加“分布式”名词，而是把已经验证的单进程状态语义扩展到真实的进程间执行所有权和故障窗口。

### 2.3 本模块完成后仍留下什么

模块 4 只建立可解释的多 Worker 调度与恢复语义。完整指标、分布式调用链、系统容量结论和故障注入平台留到模块 5；真实进程或容器执行、CPU/内存/网络限制和 Kubernetes 留到模块 6；完整控制台和开源发布体验留到模块 7。

## 3. 术语

- **Worker（执行节点）**：从控制面领取任务并调用本地已注册 Executor 的独立进程。
- **任务分发记录（Dispatch）**：持久化保存“某个任务正在等待 Worker 或已经分配”的数据库记录。
- **租约（Lease）**：带失效时间的任务执行权。Worker 只有在租约仍有效时才能续约或提交结果。
- **心跳（Heartbeat）**：Worker 周期性向控制面报告存活状态，并请求续期自己仍在执行的租约。
- **隔离令牌（Fencing Token）**：每次合法领取生成的随机令牌。控制面只接受当前租约令牌，旧 Worker 的迟到写入会被拒绝。
- **背压（Backpressure）**：执行能力不足时限制继续分发，让任务保持在持久化等待状态，而不是无限占用内存或启动执行。
- **优雅退出（Graceful Shutdown）**：Worker 停止领取新任务，等待已有任务完成或到达退出期限后再结束进程。
- **数据库时钟（Database Clock）**：租约的签发、续期、失效和 Attempt 截止时间统一以 PostgreSQL 时间为准，避免不同机器本地时间偏差改变所有权判断。

## 4. 目标与非目标

### 4.1 目标

- 支持至少两个独立 Worker 进程并发领取和执行任务；
- Worker 注册时声明支持的执行器类型和最大并发容量；
- 使用持久化任务分发记录，不依赖控制面内存队列保存唯一任务事实；
- 使用租约、心跳和隔离令牌管理临时执行所有权；
- Worker 失联后自动回收租约，并按现有重试策略重新分配；
- 拒绝过期租约、错误 Worker 会话和旧 Attempt 的迟到结果；
- 区分排队等待、实际执行、执行超时和 Worker 中断；
- 保留 Workflow `Concurrency`，并增加 Worker 容量和全局分发上限；
- 提供稳定的 Worker HTTP/OpenAPI 契约、Worker 客户端和独立进程入口；
- 使用安全 Mock Executor 完成多进程自动化测试和人工故障演示；
- 记录多 Worker 领取、续租、完成和故障恢复的性能基线与限制。

### 4.2 明确不做

- 不实现多个控制面实例同时协调同一数据库；
- 不实现跨区域调度、自动扩缩容、任务抢占或复杂优先级；
- 不实现多租户权重、配额计费或公平调度算法；
- 不引入 Kafka、Redis、NATS 或其他独立消息队列；
- 不改用 gRPC 或双向流式连接；
- 不依赖 Kubernetes 完成 Worker 调度；
- 不执行任意 Shell、脚本、本机程序、容器或生产 Agent 任务；
- 不承诺恰好执行一次，不把租约描述为消除重复副作用的机制；
- 不在本模块引入 mTLS（Mutual TLS，双向传输层安全认证）、OAuth/OIDC 或完整机器身份平台；
- 不将本机基准结果写成生产吞吐、可用性或容量承诺。

## 5. 方案比较与选择

### 5.1 方案一：PostgreSQL 持久化分发队列与 HTTP 拉取

Worker 主动通过 HTTP 从控制面领取任务。控制面使用 PostgreSQL 事务、行锁和 `SKIP LOCKED` 完成并发领取，任务状态、Attempt、租约和结果提交共享同一个事实存储。

优点：

- 直接复用模块 2 已验证的 PostgreSQL 和 HTTP/OpenAPI 边界；
- 可以在同一数据库事务中提交工作流状态与租约事实；
- 故障实验只涉及控制面、Worker 和一个数据库，问题来源更容易隔离；
- 不需要解决数据库与消息队列之间的双写一致性。

代价：

- Worker 需要轮询，空闲时会产生额外请求；
- PostgreSQL 同时承担业务状态和任务分发压力；
- 达到高吞吐或跨区域需求后，可能需要通知层、Outbox 或消息队列。

本模块选择该方案。

### 5.2 方案二：控制面主动推送

控制面维护 Worker 地址并主动发送任务。它需要处理 Worker 网络可达性、连接重建、推送超时和控制面内存连接状态。Worker 可能位于 NAT、防火墙或动态地址之后，推送会扩大当前网络边界，因此不选择。

### 5.3 方案三：消息队列

Kafka、Redis Streams、NATS JetStream 等系统可以提高异步分发能力，但会增加消息确认、数据库状态、重复投递和事务提交之间的一致性问题。当前尚无基准证明 PostgreSQL 已成为瓶颈，因此不为了覆盖技术栈提前引入。

### 5.4 为什么使用拉取而不是 gRPC 流

HTTP 拉取与现有认证、错误结构、OpenAPI 和测试工具一致。Worker 根据自身空闲槽位请求任务，天然表达容量。gRPC 流更适合持续高频双向通信，但需要新增协议、连接生命周期和代理配置；只有 HTTP 轮询数据证明成为瓶颈时才重新评估。

## 6. 总体架构

```text
CLI / SDK / 控制台
        |
        v
控制面 HTTP API
        |
        +-> Workflow / Run API
        |
        +-> Worker 注册、领取、心跳、结果 API
        |
        v
PostgreSQL
  |-> Workflow / Run / TaskRun / Attempt
  |-> Worker Session
  `-> Task Dispatch / Lease
        ^
        |
多个 workload-worker 进程
        |
        `-> 已注册的安全 Mock Executor
```

模块 4 保留一个控制面协调者。现有 PostgreSQL Advisory Lock 继续阻止第二个协调者同时启动；多个 Worker 不持有该全局锁，也不直接访问数据库，只通过控制面 API 操作。

## 7. 组件职责

### 7.1 Dispatch Coordinator

分发协调器负责：

- 扫描可执行的 `ready` 任务；
- 只为存在兼容活动 Worker 的任务创建分发记录；
- 在 Workflow 并发、Worker 能力和全局队列上限内推进 `ready -> queued`；
- 将到期的 `waiting_retry` 任务重新变为可分发；
- 回收过期租约或达到 Attempt 截止时间的任务；
- 标记心跳超时的 Worker；
- 在事务失败时保持原状态并等待下一轮扫描。

周期扫描负责恢复遗漏，Run 创建、Worker 注册、结果提交和租约回收也可以发送进程内唤醒信号以减少等待。唤醒信号只是性能优化，PostgreSQL 中的状态才是事实。

### 7.2 Worker API

Worker API 负责注册、签发会话、领取任务、心跳续租、结果提交和优雅退出。它不信任 Worker 提供的时间、Attempt 编号、任务定义或状态转换，只接受稳定标识和受限结果，再从数据库事实中校验。

### 7.3 workload-worker

独立 Worker 进程负责：

- 使用引导 Token 注册并保存仅存在于进程内存的会话令牌；
- 根据本机空闲槽位领取兼容任务；
- 为每个租约创建可取消的执行 Context；
- 周期性发送心跳并续租；
- 在收到撤销、租约安全期限到达或进程关闭时取消本地执行；
- 对同一结果使用相同请求重试提交；
- 进入 draining 后停止领取新任务。

模块 4 的 Worker 只注册 `mock` 执行器。`Action` 仍是不透明动作名称，不解释为命令或代码。

### 7.4 工作流状态核心

分布式路径和现有本地 Engine 必须共享状态转换和依赖传播规则，不能在 Worker API 中复制另一套成功、失败、重试、取消和后代跳过逻辑。实施阶段应提取可独立测试的纯状态转换边界，再由本地 Engine 和 PostgreSQL 分发事务分别调用。

## 8. 工作流定义和状态扩展

### 8.1 执行器类型

`TaskDefinition` 增加可选字段：

```text
ExecutorKind string `json:"executor,omitempty"`
```

规则：

- 省略时归一为 `mock`，保持现有定义兼容；
- 当前只允许 `mock`；
- Worker 只领取自己声明支持的执行器类型；
- 未来 `agent` 或 `container` 必须在对应模块实现并批准后才加入允许值；
- `ExecutorKind` 决定由哪类执行器处理，`Action` 决定该执行器内部执行哪个受支持动作。

### 8.2 Task 状态

新增 `queued`：

```text
waiting_dependencies -> ready -> queued -> running -> succeeded
                                      |          |-> waiting_retry -> ready
                                      |          |-> failed
                                      |          |-> canceled
                                      |          `-> interrupted / timed_out 后重试或失败
                                      `-> canceled
```

`queued` 表示已存在持久化分发记录，但尚未被 Worker 领取。排队时间不计入 Attempt 执行超时，也不消耗最大尝试次数。

本地 Engine 仍允许 `ready -> running`，因为本地执行没有网络分发阶段。分布式控制面路径必须经过 `queued`。

### 8.3 Attempt 状态

- Worker 成功领取后才创建 `running` Attempt；
- Worker 主动返回成功、临时失败或永久失败时，按现有规则收敛；
- 租约在任务截止时间前失效时，Attempt 进入 `interrupted`；
- 到达任务截止时间时，Attempt 进入 `timed_out`；
- Run 取消时，活动 Attempt 进入 `canceled`；
- `interrupted` 和 `timed_out` 都消耗一次 Attempt，再根据 `MaxAttempts` 决定重试或失败。

## 9. 持久化模型

### 9.1 Worker Session

Worker 会话至少保存：

- `worker_id`：服务端生成的随机标识；
- `display_name`：用于本地演示和诊断，不作为权限身份；
- `executor_kinds`：支持的执行器类型集合；
- `max_concurrency`：Worker 最大并发槽位；
- `status`：`active`、`draining`、`offline` 或 `stopped`；
- `session_token_hash`：会话令牌摘要，不保存明文；
- `registered_at`、`last_heartbeat_at`、`stopped_at`；
- `protocol_version`：Worker 与服务端协议版本。

Worker 每次进程启动都创建新会话，不复用旧进程的 WorkerID。旧会话及其租约按超时规则回收，避免同名进程互相覆盖。

### 9.2 Task Dispatch

任务分发记录至少保存：

- `dispatch_id`；
- `run_id`、`task_key`、`task_index`；
- `executor_kind`、`action` 和结构化 `input_json`；
- `status`：`pending`、`leased`、`completed`、`expired` 或 `canceled`；
- `available_at`、`created_at`、`claimed_at`、`completed_at`；
- `worker_id`；
- `lease_token_hash` 和 `lease_expires_at`；
- `attempt_number` 和 `attempt_deadline`；
- 已接受结果的规范化哈希，用于结果提交幂等与冲突检查。

约束：

- 同一 `(run_id, task_key)` 最多存在一个 `pending` 或 `leased` 分发记录；
- Worker 不能自行指定 Attempt 编号；
- `action` 和 `input_json` 来自已经版本化和校验的工作流定义；
- 租约明文令牌不写入数据库、日志或查询 API；
- Attempt 保存 `worker_id` 和 `dispatch_id`，用于解释执行历史。

### 9.3 索引

至少需要：

- 按 `status、available_at、created_at、dispatch_id` 查询可领取记录；
- 按 `lease_expires_at` 查询待回收租约；
- 按 `worker_id、status` 查询活动租约；
- 按 `last_heartbeat_at` 查询失联 Worker；
- 同一任务活动分发记录的部分唯一索引；
- Worker 会话令牌摘要的唯一约束。

实际索引必须用查询计划和基准验证，不以索引数量代替性能证据。

## 10. Worker HTTP 契约

### 10.1 注册

```text
POST /api/v1/workers/register
```

请求包含显示名称、协议版本、执行器类型和最大并发数。注册使用配置式 Worker 引导 Token。响应返回 WorkerID、只显示一次的会话令牌、心跳间隔、租约时长和协议版本。

### 10.2 心跳与续租

```text
POST /api/v1/workers/{worker-id}/heartbeat
```

请求携带当前仍在本机执行的租约 ID 和令牌。服务端使用数据库时间续期合法租约，响应逐项返回 `renewed`、`revoked` 或 `unknown`。续期后的租约不能超过 Attempt 截止时间。

### 10.3 领取任务

```text
POST /api/v1/workers/{worker-id}/claims
```

请求只声明空闲槽位数量。服务端从会话中读取执行器能力和最大容量，返回不超过实际空闲容量的任务。领取事务使用 `FOR UPDATE SKIP LOCKED`，并原子完成：

1. 锁定一个兼容的 `pending` 分发记录；
2. 复核 Run 未取消且当前运行 Attempt 未超过 Workflow 并发；
3. 创建下一编号的 `running` Attempt；
4. 将 Task 从 `queued` 更新为 `running`；
5. 生成租约令牌并写入摘要、到期时间和 Attempt 截止时间；
6. 递增 Run revision 并写入状态事件；
7. 提交后返回执行请求和租约明文令牌。

任一步失败都回滚，Worker 不会收到没有持久化的任务。

### 10.4 提交结果

```text
POST /api/v1/workers/{worker-id}/leases/{dispatch-id}/complete
```

结果只接受 `success`、`temporary_failure` 和 `permanent_failure`，并限制输出与错误字段大小。服务端校验 Worker 会话、租约令牌、租约状态、租约到期时间、Attempt 截止时间和当前 Attempt 身份。

- 首次合法提交在一个事务中更新分发记录、Attempt、Task、Run、下游依赖和状态事件；
- 相同租约重复提交相同规范化结果，返回首次接受结果；
- 相同租约提交不同结果，返回 `result_conflict`；
- 过期、撤销或不匹配的租约返回 `lease_lost`，不得修改工作流状态。

### 10.5 优雅退出

```text
POST /api/v1/workers/{worker-id}/drain
```

进入 `draining` 后不能领取新任务，但允许续租和提交已有任务。活动租约全部完成后，Worker 标记为 `stopped` 并退出；超过本地退出期限时停止进程，未完成租约由控制面按到期规则回收。

### 10.6 查询

viewer 和 operator 可以分页查询 Worker 摘要与单个 Worker 状态，但查询响应不返回会话令牌、租约令牌或完整敏感输入。完整诊断视图和指标留到模块 5。

## 11. 调度、公平性和背压

### 11.1 三层并发限制

- Workflow `Concurrency` 限制单个 Run 同时处于 `queued` 或 `running` 的任务数；
- Worker `max_concurrency` 限制单个 Worker 的活动租约数；
- 控制面全局分发上限限制数据库中 `pending + leased` 的记录总数。

分发上限到达时，任务保持 `ready`，不会失败、丢失或消耗 Attempt。容量释放后，扫描器继续推进。

### 11.2 基础公平性

分发协调器每轮最多为一个 Run 推进一个任务，Run 内按稳定 `task_index` 顺序。跨轮选择使用 PostgreSQL 中已经持久化的 Dispatch 历史：从未分发的 Run 优先，其余按最近一次 Dispatch 创建时间从早到晚排列；进程重启后不依赖内存游标也能继续轮换。领取端按 `available_at、created_at、dispatch_id` 处理兼容任务。

这只提供可解释的跨轮基础公平性，避免全局容量很小时同一个旧大 Run 连续占用每一轮；它不等同于租户权重、优先级或严格公平调度。

### 11.3 能力匹配

只有存在 `active` 且有空闲容量的兼容 Worker 时，协调器才把 Ready 任务推进为 Queued。Worker 失联后，尚未领取且已经没有兼容节点的分发记录会安全退回 Ready，等待新 Worker 注册。

## 12. 租约和时间边界

### 12.1 默认时序

初始推荐配置：

- Worker 心跳间隔：5 秒；
- 租约有效期：15 秒；
- 租约回收扫描间隔：1 秒；
- Worker 离线判定：连续超过 3 个心跳周期；
- Worker 空闲轮询使用有上限的指数退避和随机抖动。

这些是本地开发默认值，不是生产固定值。配置校验必须保证租约有效期明显大于心跳间隔，避免一次普通延迟立即触发回收。

### 12.2 续租

每次成功心跳都基于数据库当前时间重新计算租约到期时间，但不能超过 `attempt_deadline`。Worker 只根据服务端响应确认续租成功，不能因本机已发送请求就假设所有权延长。

### 12.3 Worker 本地安全期限

Worker 保存最近一次成功续租返回的剩余有效时长，并使用单调计时器在到期前留出安全余量停止本地执行。该行为降低数据库或网络断开后旧 Worker 长时间继续产生副作用的风险，但最终结果是否接受仍由服务端数据库时间决定。

## 13. 故障语义

### 13.1 Worker 崩溃

心跳停止后租约到期。协调器将未达到任务截止时间的 Attempt 标记为 `interrupted`；有剩余尝试次数时进入 `waiting_retry`，否则 Task 失败并传播到后代。任务不会因为 Worker 消失而静默停留在 running。

### 13.2 网络分区或数据库不可用

Worker 无法续租时必须在本地安全期限前取消执行。即使外部动作已经完成，结果也可能无法提交；后续重试可能重复产生副作用，因此本模块仍是至少执行一次语义。

### 13.3 控制面重启

Worker 会话、分发记录和租约保存在 PostgreSQL。控制面在租约尚未过期时重启，Worker 可以使用原会话继续心跳并提交结果；超过租约期限后按过期规则处理。进程内唤醒信号丢失不会导致任务丢失，周期扫描会从数据库事实继续。

### 13.4 迟到结果

服务端在处理结果的事务中再次检查数据库时间和当前租约。旧 Worker 即使比回收扫描更早到达，只要租约已经过期，也不能提交成功。新 Attempt 创建后，旧 Attempt 的令牌和编号都无法匹配当前事实。

### 13.5 结果响应丢失

数据库可能已经接受结果，但 Worker 没收到 HTTP 响应。Worker 使用同一租约和相同结果重试，服务端根据结果哈希返回幂等成功；不同结果被拒绝。

### 13.6 Run 取消

取消请求先持久化。协调器撤销 pending/leased 分发记录，取消未开始任务，并把活动 Attempt 收敛到 canceled。Worker 通过心跳收到撤销并取消本地 Context；取消后到达的结果返回 `lease_lost`。

### 13.7 重复副作用

租约只能决定平台接受哪个结果，不能撤销旧 Worker 已经写入外部系统的操作。真实 Executor 必须根据业务选择：

- 使用稳定的 `(run_id, task_key)` 作为业务幂等键；
- 在目标系统建立唯一约束或结果去重；
- 对无法幂等的操作设计补偿或人工处理；
- 不把随机 Attempt 编号当作跨重试保持不变的业务幂等键。

## 14. 认证与安全边界

- 新增独立 `WORKLOAD_WORKER_BOOTSTRAP_TOKEN`，不得与 viewer/operator Token 相同；
- 注册成功后签发随机 Worker 会话令牌，数据库只保存安全哈希；
- Worker 会话令牌只存在于 Worker 内存，不写日志、文件或命令输出；
- Worker API 请求体、结果体、能力数量和并发数都有上限；
- WorkerID、DispatchID 和租约令牌均由服务端生成；
- 远程部署必须使用 TLS，当前明文 HTTP 仅允许本机开发和测试；
- 共享引导 Token 不等同于生产机器身份，后续可按实际部署评估 mTLS 或 OIDC；
- Mock Worker 不执行 Action，不读取任意文件，不访问任意 URL，也不获得数据库凭证。

## 15. 错误契约

Worker API 继续使用模块 2 的统一错误结构和 request ID。新增稳定错误码至少包括：

- `worker_session_invalid`：WorkerID、会话令牌或协议版本不匹配；
- `worker_draining`：draining Worker 请求领取新任务；
- `worker_capacity_exceeded`：请求槽位超过注册容量或已有活动租约；
- `no_compatible_task`：当前没有可领取的兼容任务；
- `lease_lost`：租约过期、撤销、Worker 不匹配或已经被回收；
- `result_conflict`：同一租约重复提交了不同结果；
- `worker_protocol_unsupported`：Worker 协议版本不受支持。

`no_compatible_task` 属于正常空闲结果，不记录为服务端错误，也不触发紧密重试。

## 18. 测试策略

### 18.1 纯状态测试

- Ready、Queued、Running、WaitingRetry 和终态转换；
- queued 不创建 Attempt、不启动任务超时；
- 领取后创建连续 Attempt；
- 成功解锁下游、临时失败重试、永久失败传播；
- interrupted、timed_out、canceled 的次数与终态规则；
- 本地 Engine 原有 `ready -> running` 行为不回归。

### 18.2 PostgreSQL 事务测试

- 多个并发 Worker 不能合法领取同一分发记录；
- `SKIP LOCKED` 不因一个慢事务阻塞其他可领取任务；
- Worker 能力、容量和 Workflow 并发限制；
- 租约续期使用数据库时间且不超过 Attempt 截止时间；
- 过期结果、错误令牌、错误 Worker 和错误 Attempt 被拒绝；
- 相同结果重复提交幂等，不同结果冲突；
- 领取、完成、回收和取消的任一步失败都完整回滚；
- Run revision 与事件序号在并发结果下保持连续；
- 迁移升级、重复迁移和未知迁移版本保护。

### 18.3 Worker 单元测试

- 注册、领取、空闲退避、随机抖动、并发槽位和优雅退出；
- 心跳续租、撤销处理和本地安全期限；
- 结果提交网络失败后使用相同请求重试；
- 日志不包含引导 Token、会话令牌、租约令牌或敏感输入；
- 协议版本和服务端错误分类。

### 18.4 多进程端到端测试

- 一个控制面、两个 Worker 执行并行 DAG；
- 强制终止持有租约的 Worker，另一个 Worker 完成重试；
- 旧租约迟到结果不能覆盖新 Attempt；
- 控制面在有效租约期间重启，Worker 继续提交结果；
- 运行中取消能撤销租约并收敛 Run；
- Worker 优雅退出不领取新任务；
- 没有兼容 Worker 时任务保持等待，兼容 Worker 注册后继续；
- 数据库连接中断时 Worker 在本地安全期限前停止执行。

### 18.5 人工演示

模块验收至少演示：

1. 启动 PostgreSQL 和控制面；
2. 启动两个不同名称的 Worker；
3. 提交包含并行任务的 Workflow 和 Run；
4. 在任务运行中强制终止一个 Worker；
5. 查看租约过期、Attempt 1 interrupted、Attempt 2 被另一 Worker 领取；
6. 确认 Run 最终成功；
7. 使用伪造或旧令牌提交结果并观察 `lease_lost`。

该演示会并入项目最新完整演示，不要求按模块逐个展示。
