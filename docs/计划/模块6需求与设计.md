# 模块 6：受限执行环境与 Kubernetes 需求与设计

## 1. 文档目的

本文定义模块 6 的需求边界、术语、技术选型、执行器接口、安全限制、资源限制、Docker 与 Kubernetes 运行路径、故障实验、测试策略和交付物。

模块 6 建立在前五个模块已经验证的能力之上：

- 模块 1：工作流定义、DAG 调度、状态机、重试、超时、取消和恢复；
- 模块 2：控制面、PostgreSQL 事务持久化、幂等提交和恢复协调；
- 模块 3：Agent Runtime、工具权限、预算、审计和自然语言工作流草稿；
- 模块 4：独立 Worker、Dispatch、租约、心跳、回收、迟到结果拒绝和分布式取消；
- 模块 5：结构化日志、指标、Trace、告警、故障注入和性能验证。

模块 6 新增的是“任务在什么受限环境中执行”，不是重新设计工作流状态机，也不是把容器宣传为绝对安全沙箱。

## 2. 为什么现在进入模块 6

模块 5 已经能够回答任务在哪里、为什么失败、恢复是否完成以及当前观测开销如何，但 Worker 仍然只执行安全的 Mock Action。这个边界留下了几个无法通过 Mock 证明的问题：

- 任务是否真的受到 CPU、内存、临时存储和执行时间限制；
- 任务是否能够读取宿主机文件、访问外部网络或尝试提权；
- 容器或 Pod 被停止、删除或所在 Worker 失联后，租约和恢复语义是否仍然正确；
- 任务执行环境的错误如何映射为已有的超时、取消、临时失败和永久失败；
- 本地 Docker 运行与 Kubernetes 编排之间是否能共享同一套可靠执行契约。

因此模块 6 的目标是：在明确的安全边界内运行少量受控任务，并用可复现实验验证资源限制、权限拒绝、容器故障和 Pod 故障不会绕过既有工作流事实。

## 3. 术语

### 3.1 容器

容器是由操作系统和容器运行时提供的进程隔离与资源控制环境。它通常共享宿主机内核，不等于独立虚拟机，也不能自动保证能够安全运行任意恶意代码。

### 3.2 Docker Engine API

Docker Engine API 是 Docker 提供的 HTTP API，允许程序创建、启动、停止、读取日志和删除容器。模块 6 使用 API 管理容器生命周期，不把用户输入拼接成宿主机 Shell 命令。

### 3.3 Kubernetes、Pod 与 Job

Kubernetes 是用于部署和管理容器化应用的开源编排平台。Pod 是运行一个或多个紧密相关容器的最小调度单元。Job 表示一个应完成的批处理任务，Kubernetes 会根据 Job 配置创建 Pod 并记录完成或失败结果。

Kubernetes 负责调度和维持 Pod 生命周期，但不会替平台判断某个 Attempt 的租约是否有效，也不会替代工作流状态机。

### 3.4 kind

kind（Kubernetes IN Docker）是使用 Docker 容器运行本地 Kubernetes 节点的工具。它适合在 Mac mini M4 上创建可重复的开发和实验集群。本项目只把 kind 用于本地验证，不把它当作生产集群方案。

### 3.5 Action 注册表

Action 注册表是平台维护的有限映射，把公开的动作名称映射到预先批准的执行描述。它不是任意命令执行入口。

## 4. 目标与非目标

### 4.1 目标

模块 6 必须完成：

1. 在现有 Worker 执行协议中增加受控 container 执行器类型，同时保留 mock 执行器；
2. 使用 Action 注册表把有限动作映射到固定镜像、固定入口和固定参数规则；
3. 通过 Docker Engine API 创建短生命周期、非特权、资源受限的本地容器；
4. 通过 Kubernetes API 创建受限 Job/Pod，验证本地集群中的任务执行和恢复；
5. 将容器退出、超时、取消、资源超限和运行时错误映射到已有结构化执行结果；
6. 复现 Worker 被杀、容器被停止、Pod 被删除、租约过期和迟到结果拒绝等故障；
7. 继续使用模块 5 的日志、指标、Trace、告警和故障实验边界；
8. 更新本地开发与配置手册，使另一台 Mac mini M4 能按文档准备 Docker、kubectl、kind 和本地集群；
9. 形成模块 6 验证报告、学习文章和可运行演示。

### 4.2 非目标

模块 6 不承诺：

- 安全运行任意恶意代码或提供多租户级别的绝对隔离；
- 自研容器运行时、Kubernetes、虚拟机或微虚拟机；
- 在线构建用户镜像或允许工作流任意指定镜像；
- 允许任务访问 Docker Socket、宿主机目录或宿主机网络；
- GPU 调度、跨区域集群、生产级 Kubernetes 高可用或大规模容量；
- Helm、Service Mesh、Operator、Prometheus Operator、完整监控后台；
- 模型训练、推理优化或新增 Agent 编排框架；
- Web 控制台。轻量 Web 控制台仍属于模块 7。

## 5. 总体架构

    用户 / CLI / SDK
            |
            v
    控制面 API -> PostgreSQL 工作流事实、Dispatch、租约和 Attempt
            |
            v
    独立 Worker
      |-- mock executor       -> 安全模拟结果
      |-- container executor  -> Docker Engine API -> 受限容器
      '-- kube executor       -> Kubernetes API -> Job -> Pod -> 受限容器
            |
            '-- Complete / Heartbeat / 日志、指标、Trace、告警

Docker 和 Kubernetes 是两条底层运行路径，但必须共享以下上层契约：

- 任务输入由 Action 注册表提供，不由请求直接决定镜像和命令；
- 执行器接受 Context，用于超时、取消和 Worker 失联后的本地停止；
- 执行器返回有限的 ExecutionResponse，由工作流内核决定重试、失败传播和终态；
- Worker 仍然只在租约有效时提交结果；
- 观测数据不能替代 PostgreSQL 和状态机中的业务事实。

## 6. 执行器接口与任务描述

### 6.1 执行器类型

在 workflow.ExecutorKind 中增加 container：

- mock：已有安全模拟执行器；
- container：通过 Docker 或 Kubernetes 运行注册动作。

ExecutorKind 只描述执行器类别，不携带镜像、Shell 或运行时参数。编译器仍然拒绝未知执行器类型。

### 6.2 任务定义边界

任务定义继续使用结构化字段：

    {
      "key": "normalize",
      "executor": "container",
      "action": "document.normalize",
      "input": {
        "source": "sample.txt"
      },
      "timeout_ms": 30000
    }

其中：

- key 是工作流内任务的正式标识；
- executor 选择 mock 或 container；
- action 是注册表中的动作名称，不是 Shell 命令、文件路径、URL 或镜像名；
- input 是注册动作允许的结构化输入；
- timeout_ms 仍然限制单次 Attempt，而不是整个 Workflow。

### 6.3 Action 注册表

注册表中的执行描述至少包含：

- ActionName；
- Image；
- ImageDigest 或固定版本；
- Entrypoint；
- 参数映射规则；
- 输入 Schema；
- CPU、Memory、EphemeralStorage 限制；
- NetworkMode 或 NetworkPolicy 选择；
- 输出大小上限。

第一版注册表只允许仓库内固定的公开示例动作，例如：

- document.normalize：读取任务临时目录中的示例文本，输出规范化文本；
- document.summarize：对固定示例输入执行确定性摘要，不调用外部模型；
- resource.cpu-burn：仅在测试和性能实验中使用，验证 CPU 限制，不作为默认演示动作。

注册表的动作描述不能来自用户请求、环境变量或未校验的远程配置。动作不存在、输入不符合 Schema、镜像不在允许集合或资源参数超出平台上限时，任务在启动容器前返回永久失败。

### 6.4 接口边界

现有 Executor 接口保持不变：

    type Executor interface {
        Execute(context.Context, ExecutionRequest) ExecutionResponse
    }

容器执行器内部另行抽象运行时客户端，便于测试替换：

    type RuntimeClient interface {
        Create(context.Context, ContainerSpec) (ContainerHandle, error)
        Start(context.Context, ContainerHandle) error
        Wait(context.Context, ContainerHandle) (ExitStatus, error)
        Stop(context.Context, ContainerHandle) error
        Remove(context.Context, ContainerHandle) error
        Logs(context.Context, ContainerHandle, int64) (LogOutput, error)
    }

Kubernetes 执行器使用同等职责的 Job/Pod 客户端接口，不让工作流内核依赖 Docker 或 Kubernetes SDK。

## 7. Docker 本地执行设计

### 7.1 生命周期

一次本地容器 Attempt 的基本顺序：

    校验 Action 注册表
      -> 生成 ContainerSpec
      -> Create
      -> Start
      -> 等待退出、Context 取消或 Attempt 截止时间
      -> 读取受限日志和退出状态
      -> Stop（必要时）
      -> Remove
      -> 映射 ExecutionResponse

容器句柄、名称和日志不能作为业务事实。Worker 重启后，控制面只依据 Attempt、Dispatch 和租约状态恢复，不依据本地容器名称猜测任务状态。

### 7.2 默认容器限制

第一版本地容器至少设置：

- 非 root 用户；
- 只读根文件系统；
- 仅提供受限临时目录；
- 禁止特权模式；
- 删除全部可删除 Linux capabilities；
- no-new-privileges；
- 不挂载宿主机目录；
- 不挂载 Docker Socket；
- 默认无外部网络；
- CPU、内存、临时存储和进程数上限；
- 标准输出和错误输出大小上限；
- 由 Context 和 Attempt 截止时间共同控制的执行期限。

这些限制是模块 6 的可验证配置，不等于完整的恶意代码防护。所有被拒绝的能力都要有测试或实验记录，不能只在 YAML 或 Go 结构体中声明。

### 7.3 错误映射

| 容器现象 | 执行结果 | 默认处理 |
| --- | --- | --- |
| 退出码为 0 | success | 保存输出并解锁下游 |
| 注册动作输入非法 | permanent_failure | 不启动容器 |
| 容器启动失败 | temporary_failure 或 permanent_failure | 按错误码和重试策略处理 |
| Attempt 截止时间到达 | temporary_failure，错误码 timeout | 取消容器并按策略重试 |
| Context 被取消 | canceled | 不把取消当作业务失败 |
| 内存超限被终止 | temporary_failure，错误码 oom_killed | 保存证据并按策略处理 |
| 输出超过上限 | permanent_failure，错误码 output_limit_exceeded | 截断读取并拒绝过大结果 |
| 外部网络访问失败 | 由动作契约决定；默认 permanent_failure | 记录网络限制证据 |
| Worker 进程退出 | 不由执行器直接决定 | 租约过期后由控制面恢复 |

最终是否重试、是否跳过后代和 Workflow 是否终止，仍由已有工作流状态机决定。

## 8. Kubernetes 执行与本地部署

### 8.1 运行模式

模块 6 验证两种运行模式：

- 本地模式：Worker -> Docker Engine API -> 容器；
- Kubernetes 模式：Worker -> Kubernetes API -> Job -> Pod -> 容器。

两种模式不在同一次 Attempt 中同时使用。由 Worker 配置选择运行时，任务定义只能选择已经批准的 container 执行器，不得从请求中切换到任意集群或 Namespace。

### 8.2 Job/Pod 约束

Kubernetes Job/Pod 至少设置：

- resources.requests 和 resources.limits；
- activeDeadlineSeconds；
- backoffLimit: 0，避免 Kubernetes 自己重复执行而绕过平台 Attempt 语义；
- 非 root securityContext；
- readOnlyRootFilesystem: true；
- allowPrivilegeEscalation: false；
- privileged: false；
- 不自动挂载 ServiceAccount Token；
- 临时存储限制；
- 默认拒绝外部网络的 NetworkPolicy；
- 固定 Namespace、标签和 OwnerReference，便于回收和实验清理。

Kubernetes Pod 的重启或 Job 的重新创建不能直接推进 Workflow 状态。只有 Worker 在当前租约有效时提交 Complete，控制面事务才可以接受结果。

### 8.3 kind 本地集群

本地 Kubernetes 使用 kind，原因是：

- 它基于 Docker Desktop，适合当前 Mac mini M4 环境；
- 可以通过命令创建、删除和重建集群；
- 可以把本机构建镜像加载到集群，避免依赖公开镜像仓库；
- 适合开源仓库提供可复现的开发和故障实验步骤。

不选择 minikube，是因为本项目已经使用 Docker Desktop，kind 的 Docker 节点模型和脚本化集群生命周期更直接；不选择 k3d，是因为当前验收重点是 Kubernetes API、Job/Pod 生命周期和 NetworkPolicy，而不是再引入另一套轻量发行版差异。最终若目标环境限制发生变化，再单独评审替代方案。

### 8.4 Kubernetes 清单

设计阶段曾考虑把控制面和 Worker 一并部署到集群。实际验收选择了更小且可验证的边界：控制面和 Worker 仍作为本机 Go 进程运行，Kubernetes Worker 通过 kubeconfig 调用集群 API，仓库在 `deploy/k8s/` 提供：

- Namespace；
- 默认拒绝外部网络的 NetworkPolicy；
- 用于固定动作验证的受限 Job 清单。

没有交付未接线的控制面或 Worker Deployment、ConfigMap 和 Secret 模板，避免让使用者误以为当前仓库支持完整集群部署。现有清单不能包含真实凭据、公司信息、本机绝对路径或未审计的外部镜像地址。

## 9. 安全威胁模型

### 9.1 保护对象

模块 6 保护：

- 控制面主机文件和 Docker Socket；
- Worker 会话令牌、租约令牌和数据库凭据；
- 其他任务的输入、输出和临时文件；
- PostgreSQL、控制面 API 和 Kubernetes API；
- 工作流状态、Attempt 结果和观测数据。

### 9.2 主要威胁

需要通过拒绝测试或配置检查验证：

- Action 注入 Shell、URL、宿主机路径或任意镜像；
- 容器尝试读取宿主机文件或访问 Docker Socket；
- 容器尝试以 root 或特权能力运行；
- 容器通过网络访问未批准的外部地址；
- 容器产生无限日志或占满临时存储；
- Worker 因失联重试后，旧容器迟到结果覆盖新 Attempt；
- Kubernetes 自动重试与平台 Attempt 重试叠加，造成重复执行；
- 部署清单把 Token、Secret 或本机路径提交到公开仓库。

### 9.3 边界声明

模块 6 的安全结论只适用于已批准动作、固定镜像、受控输入和当前本地环境。它不等于通用代码沙箱，也不保证对抗恶意内核漏洞、容器逃逸或供应链攻击。面向不可信用户代码的生产方案需要独立威胁模型、镜像供应链、微虚拟机或专用沙箱，并不属于本项目当前承诺。

## 10. 故障与恢复实验

每个实验必须记录环境、注入步骤、预期结果、实际结果、日志/指标/Trace 入口和限制。

### 10.1 Docker 实验

1. 合法注册动作成功执行；
2. 未知 Action 在创建容器前被拒绝；
3. 试图把 sh -c、URL 或宿主机路径作为 Action 时被拒绝；
4. 容器访问外部网络失败；
5. 容器读取未挂载宿主机文件失败；
6. 容器超时被停止并产生结构化 timeout 结果；
7. 容器内存超限被识别为 oom_killed；
8. 输出超过上限被截断并返回 output_limit_exceeded；
9. Worker 被强杀后，租约过期，后续 Worker 接管并完成新 Attempt；
10. 旧容器完成后提交迟到结果，被控制面拒绝。

### 10.2 Kubernetes 实验

1. kind 集群启动后，控制面和 Worker 能按文档运行；
2. 合法 Job/Pod 执行成功并回传结构化结果；
3. Worker Pod 被删除后，任务在租约过期后重新分配；
4. 执行 Job/Pod 被删除后，Attempt 根据平台状态恢复；
5. Pod 重启或 Kubernetes Job 失败不会绕过租约校验；
6. CPU、内存、临时存储和执行时间限制能够复现；
7. NetworkPolicy 拒绝默认外部网络访问；
8. 部署清单中的安全上下文和凭据边界通过静态检查。

## 11. 测试策略

### 11.1 单元测试

- Action 注册表的未知动作、输入 Schema、镜像白名单和资源上限；
- Docker ContainerSpec 和 Kubernetes PodSpec 的安全默认值；
- 退出码、超时、取消、OOM、输出超限到 ExecutionResponse 的映射；
- Context 取消时停止并清理容器或 Job；
- Worker 租约失效时不提交结果；
- Kubernetes 标签、Namespace、OwnerReference 和清理策略。

### 11.2 运行时客户端测试

Docker Engine API 和 Kubernetes API 都必须通过接口注入 Fake/Stub 测试。默认单元测试不依赖 Docker Desktop、kind、外部镜像仓库或真实 Kubernetes 集群。

### 11.3 集成测试

在明确环境前置条件后，增加可选择运行的集成测试：

- Docker Desktop 可用时执行真实容器成功、超时、网络和资源限制测试；
- kind 集群可用时执行 Job/Pod 成功、删除、重启和 NetworkPolicy 测试；
- PostgreSQL、控制面、Worker 和容器运行时组合验证租约恢复与迟到结果拒绝。

测试必须输出清晰的跳过原因，不能把缺少本地 Docker 或 kind 误报为代码通过。

### 11.4 全量质量门禁

模块 6 完成前必须重新运行：

    go test ./... -count=1
    go test -race ./... -count=1
    go vet ./...
    go doc ./workflow
    bash scripts/test-verify-docs.sh
    bash scripts/verify-docs.sh
    git diff --check

并新增 Docker 受限执行、kind 集群部署和清理、Kubernetes 故障实验、清单安全检查脚本，以及验证报告中的原始输出和环境说明。

## 12. 观测与业务事实边界

模块 6 继续遵守模块 5 的观测边界：

- PostgreSQL 中的 Workflow、Run、Task、Attempt、Dispatch 和租约仍是事实源；
- 容器 ID、Pod 名称、Job 名称和节点名称是诊断关联字段，不是业务状态；
- Docker/Kubernetes API 错误不能直接覆盖平台状态，必须经过执行器结果和租约事务处理；
- 日志、指标和 Trace 不写入 Token、密码、完整输入、模型提示词或敏感结果；
- 容器运行时的清理失败必须进入可观测错误路径，但不能伪造任务成功；
- 资源实验的本机结果不能写成生产容量或 SLA 承诺。

## 13. 技术选型与未选择方案

### 13.1 Docker Engine API

选择 Docker Engine API，是因为它能以结构化方式控制容器生命周期、资源限制、日志和取消，并能被接口替换后进行单元测试。

未选择直接执行宿主机 Shell，是因为它会把 Action 输入变成任意本机命令执行边界；未选择在 Worker 中长期维护容器进程，是因为容器生命周期和资源回收需要由运行时明确管理。

### 13.2 Kubernetes API

选择 Kubernetes API，是因为任务 Job/Pod 的创建、状态读取、删除和标签管理需要稳定的程序接口；kubectl 适合人工操作，不适合作为业务执行器。

未选择让 Kubernetes 自己负责任务重试，是因为它的重试语义会与平台 Attempt、租约和幂等边界叠加；第一版使用 backoffLimit: 0，由平台统一决定重试。

### 13.3 kind

选择 kind，是因为它与 Docker Desktop 兼容、可脚本化、可加载本地镜像，适合 Mac mini M4 的开源演示。

未选择 minikube 或 k3d，是因为当前更关注 Kubernetes 原生 Job/Pod API、NetworkPolicy 和故障生命周期，不需要再引入另一个本地发行版的独有抽象。

### 13.4 不引入 Rust

模块 6 暂不引入 Rust。当前主要风险是执行器协议、资源限制、权限配置、容器生命周期和 Kubernetes 恢复语义，Go 已经足够验证这些边界。Rust 只有在后续明确需要低层隔离组件时再单独评审。

## 15. 验收标准

模块 6 只有同时满足以下条件才算完成：

1. mock 执行器和模块 1 至模块 5 的现有演示继续可用；
2. 合法注册动作能够在 Docker 受限容器中成功执行；
3. 未知 Action、Shell 注入、宿主机路径、任意镜像和未批准网络访问被拒绝；
4. CPU、内存、临时存储、输出和执行时间限制至少各有一项可复现实验；
5. Docker 容器停止、Worker 强杀、租约过期和迟到结果路径通过自动化或人工实验验证；
6. kind 集群可以按文档创建、部署、运行和清理；
7. Kubernetes Job/Pod 的成功、删除、重启、资源限制和 NetworkPolicy 路径有证据；
8. Kubernetes 不会通过自身重试绕过平台 Attempt 语义；
9. 日志、指标、Trace 和告警能够关联容器/Pod 诊断信息，但不取代数据库事实；
10. 全量 Go、竞态、静态、文档和清单安全检查通过；
11. 新电脑手册能够让另一台 Mac mini M4 在不使用公司信息和真实密钥的前提下完成本地演示；
12. 模块 6 学习文章只写已实现代码和已完成实验，并解释术语、技术选型、未选择方案和安全限制。

## 16. 模块递进与下一步

模块 5 解决了“如何观察和验证分布式执行”，模块 6 继续解决“任务实际在哪个受限环境运行以及资源和权限边界是否有效”。模块 6 不替代模块 5，而是复用其日志、指标、Trace、告警和故障实验方法。

模块 6 完成后，项目仍缺少面向新用户的可视化产品入口。模块 7 将在不重复实现后端事实和调度逻辑的前提下，增加轻量 Web 控制台、真实公开场景、CI/CD 和开源发布治理。
