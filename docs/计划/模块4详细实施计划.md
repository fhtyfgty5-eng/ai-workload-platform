# 模块 4：多 Worker、租约、心跳与故障恢复详细实施计划

> 本计划在《模块 4 需求与设计》审核通过后执行。实施时必须使用 `test-driven-development`，每个任务先看到预期失败，再写最小实现；模块结束前必须使用 `verification-before-completion`。用户要求整个模块完成后统一人工审核，因此任务之间只执行自动质量门禁，不逐任务请求人工确认，也不由 Codex 执行 Git 提交。

**目标：** 把控制面中的进程内 Mock 执行拆分为多个独立 Worker，通过 PostgreSQL 持久化分发、HTTP 拉取、租约、心跳和隔离令牌，在 Worker 崩溃、网络中断和迟到结果下保持可解释的至少执行一次语义。

**架构：** 现有单机 Engine、FileStore 和 `workload local` 保持可用。网络控制面改由 Dispatch Coordinator 扫描 PostgreSQL 中的 Run 状态并创建持久化 Dispatch；Worker 只通过 HTTP 注册、领取、续租和提交结果，不直接访问数据库。工作流状态变化先由 `workflow` 包中的共享纯状态函数生成候选快照，再由 PostgreSQL 事务使用 revision、事件序号和租约事实一起提交。

**技术栈：** Go 1.26、Go 标准库 HTTP/Context/Crypto、PostgreSQL 16、pgx v5、OpenAPI 3.1、Docker Compose、现有 Mock Executor。

## 1. 全局约束

- 只实现一个控制面协调者和多个 Worker；现有 PostgreSQL Advisory Lock 继续阻止第二个协调者启动。
- Worker 通过 HTTP 主动拉取，PostgreSQL 是任务分发和运行状态的唯一事实来源；不引入 Kafka、Redis、NATS、gRPC 或 Kubernetes。
- 模块 4 只执行安全 Mock 动作，不把 `Action` 解释为 Shell、脚本、文件路径、URL 或任意程序。
- `TaskDefinition.executor` 省略时归一为 `mock`；当前只接受 `mock`。
- 分布式路径必须经过 `ready -> queued -> running`；本地 Engine 继续允许 `ready -> running`。
- `queued` 不创建 Attempt、不开始任务超时、不消耗最大尝试次数。
- Worker 成功领取时才创建 Attempt；租约失效和任务超时都消耗一次 Attempt。
- 租约和心跳只能控制平台接受哪个结果，不能保证外部副作用只发生一次；模块保持至少执行一次语义。
- WorkerID、会话令牌、DispatchID 和租约令牌由服务端使用加密安全随机数生成；数据库只保存令牌 SHA-256 摘要。
- Worker 不接收数据库凭据；引导令牌、会话令牌、租约令牌和完整敏感输入不得进入日志、持久化演示文件或查询 API。
- 默认心跳 5 秒、租约 15 秒、回收扫描 1 秒；租约时长必须明显大于心跳间隔。
- 所有时间所有权判断使用 PostgreSQL 当前时间；Worker 本地只用单调计时器提前停止，不自行判定服务端租约有效。
- 现有 Workflow/Run API、幂等语义、模块 1 本地 CLI 和模块 3 Agent 草稿流程保持兼容。
- 模块完成后统一人工审核；用户审核通过后手动执行 Git 提交。


控制面创建 Run 的事务提交后调用 `Wake`，取消请求持久化后调用 `Cancel`。现有单机 Engine 通过小型适配器满足该接口；Dispatch Coordinator 直接实现该接口。

```go
// internal/workerprotocol/types.go
const ProtocolVersion = 1

type RegisterRequest struct {
    DisplayName    string                  `json:"display_name"`
    ProtocolVersion int                   `json:"protocol_version"`
    ExecutorKinds []workflow.ExecutorKind `json:"executor_kinds"`
    MaxConcurrency int                    `json:"max_concurrency"`
}

type LeaseRef struct {
    DispatchID string `json:"dispatch_id"`
    LeaseToken string `json:"lease_token"`
}

type CompleteRequest struct {
    LeaseToken string                   `json:"lease_token"`
    Result     workflow.ExecutionResponse `json:"result"`
}
```

`RegisterResponse` 返回 WorkerID、一次性会话令牌、心跳间隔、租约时长和协议版本；`ClaimResponse` 返回任务定义所需字段、Attempt 编号、Attempt 截止时间和租约令牌；`HeartbeatResponse` 对每个租约返回 `renewed`、`revoked` 或 `unknown`，并返回服务端计算的剩余租约时间。

## 6. 实施暂停条件

以下情况不是普通实现细节，出现时必须暂停并由用户确认：

1. PostgreSQL 事务无法在可接受复杂度内同时保证租约事实和 Run 状态提交，需要引入消息队列或 Outbox；
2. 需要改变现有 Workflow/Run 公开 API、幂等语义或模块 1 本地 Engine 行为；
3. 需要执行真实 Shell、文件、网络、模型或容器任务；
4. 需要引入新的第三方运行时依赖、gRPC、Redis、Kafka、Kubernetes、OAuth/OIDC 或 mTLS；
5. 真实基准显示初始范围无法达到可用演示效果，需要调整 Worker 数量、Dispatch 上限或数据库模型；
6. 安全边界要求把会话令牌写入文件，或需要在日志和查询 API 暴露敏感输入；
7. 模块范围无法在一个可统一审核的交付中保持清晰，需要拆分新的独立模块。
