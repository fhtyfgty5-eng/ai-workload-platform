# 模块 1：单机可靠工作流内核需求与设计

## 1. 文档目的

本文档记录模块 1 已经用户确认的需求边界和设计方向，作为后续学习资料和 TDD 详细计划的输入。

本文档不是实施计划，不包含已实现声明，也不表示模块 1 业务代码已开始。

## 2. 模块目标

不依赖容器、云服务、真实模型或外部网络，用 Go 实现一个可在单机上验证的可靠工作流内核，覆盖：

- 工作流和任务定义；
- DAG 依赖校验与调度；
- 显式状态机；
- 有上限的并发执行；
- 失败重试、任务超时和工作流取消；
- 本地持久化和进程重启恢复；
- 可重复运行的自动化测试与最小 CLI 演示；
- 面向单个工作流最多 10,000 个任务、单机最多 1,000 个活跃运行实例的性能验证目标。

## 3. 范围边界

### 3.1 已批准范围

- 交付形式是 Go 内核库加最小 CLI 和示例；
- 执行器只提供进程内 Mock Executor（模拟执行器），按测试预设返回结果；
- 工作流在内核中使用 Go 结构体表示，CLI 从 JSON 文件读取定义；
- 任务使用用户可读的 `TaskKey` 作为唯一正式标识，调度器使用编译阶段派生的数组下标访问运行时状态；
- 使用可配置的并发上限；
- 每个任务可配置最大尝试次数、固定重试间隔和单次执行超时；
- 取消采用协作式取消；
- 持久化采用内存状态加本地 JSON 文件；
- 保存当前状态快照、执行尝试历史和状态变更事件；
- 自动化测试是验收主体，CLI 是最小手工演示入口。

### 3.2 非目标

- 不执行真实模型、本机命令、脚本、容器或远程任务；
- 不引入 HTTP API、Web 界面、多进程 Worker 或多节点调度；
- 不引入 SQLite、PostgreSQL、Redis、消息队列或 Kubernetes；
- 不实现指数退避、随机抖动、熔断或分布式限流；
- 不实现完整日志、指标、调用链和任务产物管理；
- 不实现完整事件溯源，不声称“恰好执行一次”；
- 不在任务执行代码的中断位置继续运行；
- 不在模块 1 实现人工审批、失败后手工继续或部分失败容忍策略。

## 4. 核心概念和数据模型

### 4.1 工作流定义

`WorkflowDefinition` 是可重复使用的静态定义，包含任务、依赖、执行参数、重试和超时配置。一次运行创建后，该运行使用的定义不再修改。

### 4.2 工作流运行实例

`WorkflowRun` 表示工作流的一次实际执行。同一个定义可以创建多次运行，每次运行拥有独立的运行 ID、状态、开始时间和结束时间。

### 4.3 任务运行实例

`TaskRun` 表示某次工作流运行中的一个任务，记录依赖、当前状态、尝试次数和最终结果。

### 4.4 执行尝试

`Attempt` 表示任务的一次具体执行。任务重试时创建新的 Attempt，不覆盖前一次记录。

### 4.5 TaskKey 与编译后工作流

`TaskKey` 是任务在 WorkflowDefinition 中的唯一正式标识，由工作流定义提供。它必须在当前工作流内唯一，长度为 1 到 64 个字符，只允许小写英文字母、数字、连字符和下划线。

工作流提交时，校验和编译过程在同一次任务遍历中建立 `TaskKey -> 数组下标` 的映射，再把字符串依赖转换为整数邻接表和未满足依赖计数。该下标只是内部数组位置，不是第二个任务 ID，不对 CLI 和用户暴露。

编译结果是不可变的，包含任务数组、TaskKey 索引和 DAG 邻接表。同一份 WorkflowDefinition 创建的多个 WorkflowRun 共享该编译结果，每个运行实例只维护自己的任务状态、依赖计数、Attempt 和结果。

### 4.6 依赖结构与运行时计数

工作流定义中的 `depends_on` 是依赖关系的唯一来源，调度器不推断隐式业务依赖。编译结果同时保存每个任务的直接下游任务和完整依赖关系；每个 WorkflowRun 根据该结构创建独立的未满足依赖计数。

调度器只在上游任务第一次进入成功状态时递减其直接下游任务的计数，计数减为零后才能将下游任务转为“可执行”。重复的成功结果不得重复递减。依赖任务最终失败时，下游进入“已跳过”，不能通过递减计数变为可执行。

恢复时根据不可变依赖结构和已经持久化的任务状态重新计算未满足依赖计数，不把旧计数作为唯一事实来源。同一份编译结果可以由多个 WorkflowRun 共享，但任务状态和依赖计数不能跨运行实例共享。

## 5. 状态机

### 5.1 工作流状态

- 等待运行；
- 运行中；
- 成功；
- 失败；
- 已取消。

### 5.2 任务状态

- 等待依赖；
- 可执行；
- 执行中；
- 等待重试；
- 成功；
- 失败；
- 已取消；
- 已跳过。

### 5.3 执行尝试结果

- 执行中；
- 成功；
- 失败；
- 超时；
- 已取消；
- 被中断。

超时和进程重启中断是某次 Attempt 的结果。如果仍有重试次数，TaskRun 进入“等待重试”；重试耗尽后，TaskRun 进入最终“失败”。

重启前正在执行的 Attempt 记为“被中断”，并计入已经发生的一次尝试。

### 5.4 失败和取消传播

- 任务最终失败后，依赖它的下游任务标记为“已跳过”；
- 已跳过状态继续向更下游传播；
- 任一任务最终失败时，工作流最终失败；
- 取消工作流时，未开始任务标记为“已取消”，运行中任务通过取消信号协作停止；
- 已成功任务保持成功，取消不触发重试。

## 6. 组件与接口职责

### 6.1 Validator/Compiler

在创建运行实例前校验并编译工作流定义：

- TaskKey 格式是否合法、在工作流内是否唯一；
- 依赖的任务是否存在；
- 依赖图是否有环；
- 重试、超时和并发配置是否合法；
- 在唯一性校验的同一次遍历中建立 TaskKey 索引，并将依赖编译为整数邻接表。

校验失败时直接拒绝提交，不创建 WorkflowRun。校验、依赖编译和环检测的总时间复杂度应保持为 `O(V + E)`，其中 `V` 是任务数，`E` 是依赖数。

### 6.2 StateMachine

定义工作流、任务和 Attempt 的合法状态转换，任何未定义跳转都返回错误。

### 6.3 Scheduler

负责：

- 识别依赖已满足的任务；
- 管理并发槽位；
- 建立 Attempt 并调用 Executor；
- 处理成功、临时失败、永久失败、超时、取消和中断结果；
- 触发重试、失败传播和工作流终态判定；
- 在重启时恢复未完成工作流。

调度器统一修改内存中的工作流状态。Mock Executor 可并发执行，但执行结果交回调度器后按顺序更新状态和持久化，避免并发改写同一份状态。

调度热路径使用数组下标访问任务状态、依赖计数和邻接表，不在每次调度时重复扫描任务列表或重新解析字符串依赖。

### 6.4 Executor

接收任务定义、超时和取消信号，返回结构化结果。模块 1 只提供 Mock Executor 实现，用于稳定模拟成功、临时失败、永久失败、延迟、超时和取消。它不调用模型或工具，也不代表后续模块的真实 Agent Runtime。

### 6.5 Store

提供创建、读取和保存工作流运行状态的抽象。文件实现使用“每个运行实例一个 JSON 文件”，同时保存快照、Attempt 历史、状态事件和最小结果元数据。

每次保存先在目标文件所在目录写临时文件，再在支持的平台和同一文件系统内原子替换目标文件，避免崩溃后只留下部分 JSON 内容。Go 的 `os.Rename` 不保证所有操作系统都具有相同的原子行为，因此实现与测试必须明确支持平台和该边界。

### 6.6 Clock

提供当前时间和等待能力。测试可替换为可控时钟，不需要真实等待重试间隔或超时。

### 6.7 CLI

CLI 只调用内核公开接口，不直接修改存储文件或内部状态。模块 1 不启动后台服务，`run` 命令在当前终端前台执行，用户按 `Ctrl+C` 时触发内核的协作式取消。独立命令只读取持久化状态，最小命令范围为：

```text
workload run <workflow.json>
workload status <run-id>
```

## 7. 执行数据流

1. CLI 或 Go 调用提交 WorkflowDefinition；
2. Validator/Compiler 完成全部校验，建立 TaskKey 索引并编译 DAG；
3. 创建 WorkflowRun 和按编译下标排列的 TaskRun 状态，并持久化初始状态；
4. Scheduler 识别可执行任务，并在并发上限内创建 Attempt；
5. 在调用 Executor 之前，先持久化“执行中”状态；
6. Executor 在任务级超时和取消信号下执行 Mock Executor；
7. 执行结果交回 Scheduler，先写入 Attempt，再更新 TaskRun 和 WorkflowRun；
8. 状态保存成功后，才解锁下游任务或安排重试；
9. 工作流进入终态后停止调度。

## 8. 重试、超时与取消

### 8.1 重试

- 重试策略由最大尝试次数和固定重试间隔组成；
- 临时执行错误、超时和进程中断可重试；
- 永久执行错误和用户取消不重试；
- 模块 1 不使用指数退避或随机抖动。

### 8.2 超时

每次 Attempt 使用任务的单次超时限制。超时后发出取消信号，Attempt 记为“超时”，然后按重试策略决定后续状态。

### 8.3 取消

取消是协作式的：Scheduler 发出取消信号，Mock Executor 检查信号并主动停止。模块 1 不承诺强制终止一个不响应取消的执行器。

## 9. 持久化与恢复语义

恢复指恢复工作流状态和调度过程，不是从任务代码中断的某一行继续执行。

重启时：

- 已成功任务不重复执行；
- 等待依赖和可执行任务继续调度；
- 执行中 Attempt 标记为“被中断”；
- 被中断任务按剩余尝试次数决定重试或最终失败；
- 已取消、已跳过和最终失败任务不自动恢复。

模块 1 提供“至少执行一次”语义：任务不会因为崩溃被静默丢失，但可能重复执行。如果任务已执行成功，进程却在保存成功状态之前崩溃，重启后会再次执行该任务。

因此未来的真实执行器必须通过幂等操作、唯一请求 ID 或结果去重控制重复副作用。模块 1 的 Mock Executor 不产生真实外部副作用。

## 10. 错误分类

- 定义错误：提交时直接拒绝；
- 临时执行错误：按任务策略重试；
- 永久执行错误：任务立即最终失败；
- 系统错误：如文件写入失败或非法状态转换，停止继续调度并向调用方返回错误；
- 超时和进程中断：作为可重试的 Attempt 结果；
- 用户取消：进入取消终态，不重试。

## 11. 结果保存范围

模块 1 只保存：

- 成功或失败结果；
- 结构化错误原因；
- 开始和结束时间；
- 尝试次数；
- Mock Executor 返回的简短结果。

不保存完整文本日志、标准输出、大文件或任务产物。

## 12. 测试与验收设计

### 12.1 单元测试

- 非法或重复 TaskKey、缺失依赖、循环依赖和非法配置被拒绝；
- TaskKey 索引、整数邻接表和依赖计数编译正确；
- 上游任务第一次成功时正确递减直接下游计数，重复成功结果不重复递减；
- 合法状态转换通过，非法转换被拒绝；
- 任务只在依赖成功后变为可执行；
- 重试次数、固定间隔和耗尽逻辑正确；
- 超时和取消产生正确的 Attempt 结果；
- 并发任务数不超过配置上限；
- 文件存储能够完成快照写入、读取和事件保存；
- 文件替换在声明支持的平台上通过崩溃边界测试，并明确不保证的平台行为。

### 12.2 调度器集成测试

- 简单串行工作流成功；
- 无直接依赖的任务可并发执行；
- 临时失败后重试并最终成功；
- 重试耗尽后下游任务跳过；
- 超时后按策略重试；
- 取消后运行中任务停止，未开始任务取消；
- 进程重启后执行中任务记为中断并按策略恢复；
- 恢复时根据完整依赖结构和任务状态重算未满足依赖计数；
- 持久化失败后不继续调度新任务。

### 12.3 CLI 验收

使用本地 JSON 示例完成：

```text
提交工作流 -> 获取运行 ID
查询运行状态 -> 查看任务和工作流状态
前台执行时按 Ctrl+C -> 查看取消结果
```

按运行 ID 取消仍然是内核接口和自动化测试的能力，但不在模块 1 中通过另一次 CLI 调用远程操作前台运行。这避免为了一个命令提前引入后台服务和进程间通信。

### 12.4 预期验证命令

```bash
go test ./...
go vet ./...
```

所有自动化测试必须使用 Mock Executor 和本地临时目录，不访问外部网络，不使用真实模型 API。

### 12.5 性能基准与规模验证

使用 Go Benchmark 单独测量：

- 10,000 个任务的 TaskKey 唯一性校验和索引建立；
- 10,000 个任务及其依赖的 DAG 编译和环检测；
- 调度器处理可执行任务、完成事件和依赖解锁的速率；
- 1,000 个活跃 WorkflowRun 共享编译后定义时的内存占用；
- 相同运行规模下，共享同一编译结果与分别持有不同编译结果的内存对照；
- JSON 快照在不同任务数和事件数下的写入、读取和恢复成本。

目标规模是模块 1 的必测场景，不是尚未经过实验的性能承诺。完成首轮基准测试后，必须记录本机环境、输入规模、原始结果和主要瓶颈，再与用户确认可接受的延迟、吞吐和内存验收阈值。

## 13. 关键取舍

### 13.1 为什么选择分层内核

分层内核让校验、状态转换、调度、执行、存储和时间控制可以独立测试和替换。未选择单体调度器，因为并发、重试和恢复逻辑会快速相互耦合；未选择完整事件溯源，因为当前没有需求支撑它的额外复杂度。

### 13.2 为什么选择 JSON 文件

Go 标准库可以直接编解码 JSON，不需要数据库或第三方解析库。未选择 YAML，因为它需要额外依赖；未选择 SQLite，因为模块 1 的单进程验证尚不需要完整查询和事务能力。

### 13.3 为什么选择 Mock Executor

Mock Executor 能稳定产生成功、失败、延迟、超时和取消结果，不产生 API 费用或网络波动。未选择 Mock Agent 作为名称，是因为模块 1 验证的是与执行对象无关的可靠内核，模拟行为不包含模型、工具或 Agent 决策。未选择真实模型，因为它的输出、延迟和限流会干扰内核正确性测试；未选择本机命令执行，因为会提前引入进程、环境和安全管理。
