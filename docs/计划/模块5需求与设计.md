# 模块 5：可观测性、故障注入与性能验证需求与设计

## 1. 文档目的

本文定义模块 5 的需求边界、术语、技术选型、组件职责、接口、数据流、告警语义、故障实验、性能验证方法和交付物。

模块 5 建立在模块 4 已验证的多 Worker、任务租约、心跳、回收、迟到结果拒绝和分布式取消之上。它要增加的是“能够解释和度量已经存在的执行语义”，不能借机重写模块 4 的状态机、租约所有权或数据库事实。

本文确认前不修改模块 5 业务代码。本文确认后，另行编写测试驱动的实施任务；模块完成后再统一进行代码、实验、文档和学习文章审核。

## 2. 为什么现在进入模块 5

### 2.1 模块 4 已经证明了什么

- 多个独立 Worker 可以从控制面领取并执行任务；
- PostgreSQL 持久化了 Dispatch、租约、Attempt 和结果；
- Worker 失联后可以回收租约并重新分配；
- 迟到结果、错误会话和重复完成会被拒绝；
- 背压、跨 Run 基础公平性和分布式取消已有自动化验证；
- 控制面重启、Worker 强杀和 Worker 后注册恢复已经有故障证据；
- 1、4、16 Worker 的吞吐基线已经记录。

### 2.2 仍然缺少什么

当前系统主要依靠日志和数据库查询判断执行过程，维护者仍需要人工拼接多个来源才能回答：

- 一个任务当前在哪个阶段，是等待依赖、排队、执行、重试还是租约回收；
- 某次失败来自应用结果、超时、Worker 失联、数据库错误还是权限拒绝；
- 一个 HTTP 请求、Dispatch、Worker Attempt 和最终状态是否属于同一条执行链；
- 队列持续堆积、Worker 全部离线或连接池耗尽是否已经达到需要处理的程度；
- 故障期间吞吐下降多少，恢复后是否回到稳定状态；
- 当前观测数据本身是否因为高基数标签、阻塞导出或敏感信息泄露而引入新问题。

### 2.3 模块 5 完成后仍然留下什么

模块 5 不运行任意代码，不提供完整 Web 监控台，不部署 Jaeger、Tempo 或 Grafana，也不把本地实验结果写成生产容量承诺。真实资源限制、容器执行和 Kubernetes 故障留到模块 6；面向新用户的控制台、CI/CD 和开源治理留到模块 7。

## 3. 术语

- **可观测性（Observability）**：通过日志、指标和调用链，根据系统外部输出推断系统内部状态的能力。日志适合回答“发生了什么”，指标适合回答“发生了多少”，调用链适合回答“一次请求经过了哪些组件”。
- **结构化日志**：每条日志都由固定字段组成的键值记录，而不是只能靠人阅读的一段自由文本。
- **指标（Metric）**：随时间变化的可聚合数值，例如队列深度、请求耗时或在线 Worker 数量。
- **标签（Label）**：指标旁边用于分组的有限取值字段。高基数值（可能出现大量不同值的字段）会使指标存储和查询成本急剧增加，因此不能把 run_id、task_key 或 worker_id 作为指标标签。
- **调用链（Trace）**：一次请求或任务执行跨越多个组件时，由多个 Span（跨度）组成的时间线。Span 记录单个组件的开始时间、结束时间、状态和有限属性。
- **告警（Alert）**：指标、状态或错误满足规则后主动产生的通知。告警有触发、持续、抑制和恢复四个阶段。
- **故障注入（Fault Injection）**：在受控测试环境中主动加入延迟、错误、进程退出或资源限制，以验证系统在故障下的实际行为。
- **低基数**：取值集合较小且稳定，例如 HTTP 方法、路由模板、错误码或执行器类型；它不等于“字段长度短”。

## 4. 目标与非目标

### 4.1 目标

1. 统一控制面、Coordinator、Worker 和 PostgreSQL 相关日志字段。
2. 提供低基数 Prometheus 指标和 HTTP /metrics 读取入口。
3. 使用 OpenTelemetry 串联单次 Worker Claim、Heartbeat、Complete 请求的客户端、控制面 HTTP 和 Worker API Span；异步 Dispatch 创建使用日志和指标关联，不伪造跨异步边界的父子关系。
4. 提供本地 HTTP Webhook 告警出口，验证触发、抑制、恢复和重复通知控制。
5. 提供不进入生产业务路由的可编程故障注入接口和可复现实验脚本。
6. 复测单 Run、多 Run、1/4/16 Worker 的吞吐、延迟、队列深度和资源使用。
7. 证明观测能力不会改变模块 4 的状态转换、租约所有权、结果幂等和恢复结论。
8. 让学习资料能解释技术选型、观测数据边界、故障实验方法和性能数据限制。

### 4.2 非目标

- 不开发完整 Web 监控后台或长期日志存储系统；
- 不部署或维护 Jaeger、Tempo、Grafana、Alertmanager 等完整观测平台；
- 不接入真实邮件、短信、企业 IM 或外部告警 SaaS；
- 不引入 Kafka、Redis、NATS 或其他消息队列；
- 不把每个 Run、Task、Attempt 或 Worker 的 ID 写入指标标签；
- 不开放任意 HTTP 故障注入接口；
- 不允许故障注入绕过认证、权限和正常状态校验；
- 不保证恰好执行一次，不把观测数据当作业务事实来源；
- 不设置没有实验依据的绝对吞吐、延迟或容量门禁。

## 5. 技术选型与替代方案

### 5.1 结构化日志：Go log/slog

继续使用 Go 标准库 log/slog，统一 JSON 日志作为机器读取格式，同时保留文本格式用于本地阅读。现有请求日志已经使用 slog，模块 5 只抽取公共字段和上下文注入能力，不再引入第二套日志 API。

没有选择 Zap 或 Zerolog，是因为当前日志量尚未证明标准库成为瓶颈；引入更高性能日志库会增加 API 学习和迁移成本。若后续基准证明日志编码是主要瓶颈，再单独评审替代方案。

### 5.2 指标：Prometheus exposition format 与官方 Go Client

使用 Prometheus 指标模型：Counter（只增不减的计数器）、Gauge（可上下变化的当前值）和 Histogram（按区间统计耗时或大小）。使用官方 client_golang 注册器和直方图实现，提供只读 /metrics 文本出口。

没有选择 StatsD，是因为本模块需要低基数标签、直方图分桶和测试中直接读取指标；没有选择自研指标格式，是因为 Prometheus 文本格式已有明确契约并可被后续监控工具读取。模块 5 不部署 Prometheus 服务本身。

### 5.3 调用链：OpenTelemetry Go SDK

使用 OpenTelemetry（开放遥测标准）API 和 SDK。默认关闭外部导出；本地演示使用 stdout exporter（把 Span 打印到标准输出），自动化测试为采样 Provider 注册内存 SpanRecorder，验证父子关系、状态和属性。HTTP 上下文通过标准传播器传递，Worker 请求带上上游 trace context。

没有选择厂商专用 SDK，是为了保留后续切换 Jaeger、Tempo 或其他后端的能力；没有现在部署完整追踪平台，是因为模块 5 的验收重点是跨组件关联是否正确，不是搭建一套长期运行的观测基础设施。

### 5.4 告警：进程内规则评估与本地 HTTP Webhook

告警规则由应用内的有限状态评估器计算，通知通过可替换的 AlertSink 接口发送到本地 HTTP Webhook。Webhook 接收器只用于测试和人工演示，不承担持久化、认证中心或生产通知职责。

没有选择 Alertmanager，是因为当前尚未部署 Prometheus 服务，直接引入会把规则、路由、抑制和通知拆到另一套未验证基础设施；接口边界保留后续替换空间。

### 5.5 故障注入：构造函数注入与实验夹具

故障注入通过 Repository、Worker Client、Clock、Coordinator 和连接池构造函数接收的测试接口完成。实验配置只在测试进程和显式实验命令中存在，不增加生产 HTTP 路由，不读取真实凭据，不修改业务定义。

没有选择向运行中的服务开放任意故障 API，是为了避免开源项目被误用为远程破坏入口；没有选择直接修改 PostgreSQL 数据文件，是因为那无法稳定表达网络延迟、请求错误和并发竞争。

## 6. 总体架构

```text
CLI / SDK / Worker
        |
        v
控制面 HTTP API -----> Trace Propagator
        |
        +-> Workflow / Dispatch / Worker Service
        |       |
        |       +-> Structured Logger
        |       +-> Metrics Registry
        |       +-> Tracer
        |       `-> Alert Evaluator -> AlertSink -> 本地 Webhook
        |
        v
PostgreSQL Repository

Worker Runtime ---- HTTP Claim / Heartbeat / Complete ---- 控制面
       |                         |
       +-> Logger / Metrics / Tracer
       `-> Fault Plan（仅测试夹具）
```

可观测性组件是横向能力，不拥有 Workflow、Task 或 Dispatch 的最终状态。状态和事件仍以 PostgreSQL 与既有状态核心为事实来源；日志、指标、调用链和告警只能记录、聚合或通知，不能自行推进任务状态。

### 6.1 组件职责

#### internal/observability

负责创建并组合 Logger、Metrics、Tracer、HTTP middleware 和观测上下文。该包不依赖 PostgreSQL 具体实现，不读取业务数据库，不生成业务 ID。

#### internal/alerting

负责告警规则的输入快照、状态机、去重键、恢复条件和 AlertSink。它只消费低基数聚合数据，不保存完整 Run 或 Task 结果。

#### internal/faultinject

负责故障计划、延迟、错误和取消点。默认计划为空，生产构造路径不从 HTTP 请求接收故障参数。

#### 现有控制面、Coordinator 和 Worker

在关键操作边界创建 Span、记录统一日志字段、更新指标并把 context.Context 传递给下游。它们继续调用模块 4 已存在的状态和 Repository 接口。

## 7. 统一日志契约

### 7.1 必填字段

以下字段在对应操作可获得时必须出现；未知字段使用空值或省略，不能伪造：

| 字段 | 含义 | 是否允许高基数 |
| --- | --- | --- |
| request_id | 一次 HTTP 请求的稳定标识 | 日志允许，指标禁止 |
| run_id | 工作流运行实例标识 | 日志允许，指标禁止 |
| task_key | 工作流内任务标识 | 日志允许，指标禁止 |
| attempt | 当前第几次执行尝试 | 日志允许，指标禁止 |
| worker_id | 执行该 Attempt 的 Worker 标识 | 日志允许，指标禁止 |
| dispatch_id | 任务分发记录标识 | 日志允许，指标禁止 |
| operation | 有限操作名，如 claim、heartbeat、complete | 只能使用枚举 |
| duration_ms | 操作耗时，统一使用毫秒数值 | 不作为标签 |
| error_code | 平台错误码；成功时可省略 | 只能使用有限错误码 |
| trace_id、span_id | 调用链关联标识 | 日志允许，指标禁止 |

duration 在用户可读文章中可以作为概念名称，但程序日志统一使用 duration_ms，避免同一字段在不同组件使用不同单位。

### 7.2 日志级别和敏感信息

- INFO：Run、Dispatch、Worker 会话和恢复的生命周期事件；
- WARN：租约回收、迟到结果拒绝、短暂数据库错误和告警触发；
- ERROR：操作最终失败、告警发送失败和协调器无法继续工作；
- DEBUG：轮询、空领取和详细故障注入信息。

日志不得写入 Bearer Token、Worker Session Token、租约令牌、模型 API Key、完整任务输入、模型提示词或可能包含个人数据的结果。错误内容要保留可诊断信息，但必须经过长度限制和敏感字段过滤。

## 8. 指标契约

### 8.1 指标名称与标签

指标使用 workload_ 前缀。标签只使用有限集合：operation、status、error_code、executor_kind、method、route、outcome。禁止使用 run_id、task_key、attempt、worker_id、dispatch_id、原始 URL 或用户输入。

至少提供以下指标：

| 指标 | 类型 | 说明 | 标签 |
| --- | --- | --- | --- |
| workload_workers | Gauge | 当前在线或活动 Worker 数量 | status |
| workload_active_leases | Gauge | 当前活动租约数量 | 无 |
| workload_queue_depth | Gauge | 当前可领取和排队 Dispatch 数量 | status |
| workload_operation_duration_seconds | Histogram | Claim、Heartbeat、Complete 等耗时 | operation、outcome |
| workload_lease_reclaim_duration_seconds | Histogram | 租约回收耗时 | outcome |
| workload_http_requests_total | Counter | HTTP 请求数量 | method、route、status |
| workload_http_request_duration_seconds | Histogram | HTTP 请求耗时 | method、route |
| workload_db_pool_connections | Gauge | 连接池总数、使用数和空闲数 | state |
| workload_db_pool_wait_seconds_total | Counter | 等待连接池的累计时间，只累加 pgx 快照增量 | 无 |
| workload_alerts_total | Counter | 告警触发、恢复和通知结果 | rule、operation、outcome |

模块 5 不提供 Run、Task、Attempt 和 Dispatch 的生命周期 Counter。它们的状态转换在 PostgreSQL 事务内完成，如果在事务外根据 API 返回值再次推测并计数，进程崩溃或请求重放时可能与数据库事实不一致。单对象状态以查询 API、事件和 Trace 诊断；如果后续需要严格累计值，应从已提交事件或事务内 outbox（与业务事务一起写入的待发布事件表）派生，而不是先发布一个不可靠的计数器。

指标注册器支持测试隔离，不能因为测试重复初始化而 panic。/metrics 只读，不修改数据库，也不包含请求体、Token 或业务结果。

### 8.2 观测失败的边界

指标更新、日志编码和 Span 导出失败不得改变任务状态保存、租约续期或结果提交。`off` 模式不采样；`stdout` 使用容量 256 的 Batch Span Processor（批量 Span 处理器），业务 goroutine 只把已结束 Span 放入有界队列，慢 Writer 不直接阻塞 `Span.End`。队列满时 OpenTelemetry 允许丢弃观测数据；本模块没有提供“调用链零丢失”承诺。

## 9. 调用链契约

### 9.1 Span 层级

当前可以验证的是“一次 Worker HTTP 请求”的跨进程父子关系。例如一次 Complete 请求：

```text
worker.complete                         [Worker Client]
  `- POST /workers/{id}/.../complete    [控制面 HTTP]
      `- worker.complete                 [控制面 Worker API]
```

Claim 和 Heartbeat 使用相同的 W3C 上下文传播规则。Run 创建、Coordinator 异步扫描和稍后的 Worker 领取之间没有持续持有同一个 Context，因此不会自动属于同一个 Trace。跨异步边界使用 Run ID、Task Key、Worker ID 和 Dispatch ID 日志关联；未来若要形成整条 Run Trace，必须先设计 Trace Context 的持久化、过期和访问控制，不能只在内存中保存。

### 9.2 Span 属性

Span 可以记录 operation、executor_kind、route、status、error_code 和协议版本。run_id、task_key、worker_id 和 dispatch_id 只作为日志或测试断言中的属性，不写入公开指标；调用链后端如果未来启用，也必须配置采样和访问控制。

### 9.3 上下文传播

HTTP 服务端从请求头提取 W3C Trace Context；Worker Client 在 Claim、Heartbeat、Complete 请求头中注入当前 Span 上下文。缺少上游上下文时创建新的根 Span，不把客户端伪造的 request_id 当作 trace 身份。请求 ID 仍由控制面生成或校验，并在日志中保留。

## 10. 告警规则与状态机

### 10.1 规则

规则评估周期默认为 1 秒，连续满足条件才触发，避免单次抖动造成通知：

| 规则 | 触发条件 | 默认持续时间 | 恢复条件 |
| --- | --- | --- | --- |
| queue_backlog | queue_depth > 0 且没有可用槽位 | 10 秒 | 队列深度为 0 或出现可用槽位并持续 5 秒 |
| workers_offline | 队列深度大于 0 且在线 Worker 数为 0 | 5 秒 | 至少一个 Worker 在线并持续 5 秒 |
| lease_reclaim_errors | 租约回收操作错误计数在窗口内大于 0 | 1 个评估周期 | 连续一个窗口没有错误 |
| complete_error_rate | Complete 错误率超过 5%，且样本数至少 20 | 30 秒 | 错误率低于 1% 且样本数满足条件 |
| db_pool_near_exhaustion | 使用连接数 / 最大连接数 >= 80% | 10 秒 | 比例低于 70% 并持续 10 秒 |

阈值属于本地实验默认值，不是生产 SLO（Service Level Objective，服务等级目标）。每次实验必须记录是否使用默认值以及修改原因。

### 10.2 去重、抑制和恢复

- 告警唯一键为 rule，不带 Run、Task 或 Worker ID，避免同一系统问题产生大量通知；
- pending -> firing 只发送一次触发通知；
- firing 持续期间不重复发送，除非规则配置显式要求重新通知；
- firing -> resolved 发送一次恢复通知并清理活动状态；
- Webhook 失败只记录通知失败指标，不改变告警状态；下一评估周期可以有限重试，重试次数和间隔有上限；
- 规则输入缺失时标记为 unknown 并记录错误，不把未知误判为恢复。

### 10.3 Webhook 负载

本地 Webhook 只接收以下有限字段：alert_name、status、summary、starts_at、ends_at、rule_version 和有限标签。不得发送 Token、请求体、完整错误堆栈或业务输入。通知超时默认 1 秒，不能阻塞 Coordinator 主循环。

## 11. 故障注入与实验设计

### 11.1 注入边界

故障计划只能由测试夹具或显式实验进程创建，注入点通过接口传递：

- PostgreSQL 操作前后：返回一次性错误、短暂错误或固定延迟；
- Worker Client Claim、Heartbeat、Complete：返回网络错误、HTTP 5xx、超时或连接中断；
- Worker Runtime：在领取后强制取消、延迟结果或退出进程；
- Coordinator：模拟 Advisory Lock 检查失败或调度扫描延迟；
- 连接池：限制最大连接数并阻塞获取连接；
- Clock：在测试中推进租约时间和告警评估时间。

每个注入点都必须能关闭，测试结束后不能污染其他用例。生产构造函数不读取 WORKLOAD_FAULT_* 环境变量，也不在公开 API 中接受故障参数。

### 11.2 必做实验

每个实验报告必须包含环境、输入、注入步骤、预期状态、实际日志/指标/调用链证据、恢复时间和限制：

1. PostgreSQL 短暂不可用：请求失败后恢复，Run/Dispatch 不产生非法终态。
2. Claim 延迟：队列保持可解释，Worker 不重复领取同一 Dispatch。
3. Complete 延迟或错误：租约和结果幂等语义保持，迟到结果不会覆盖新 Attempt。
4. Heartbeat 网络错误：Worker 取消本地执行，租约过期后由控制面回收。
5. Worker 强杀：新 Worker 接管，Attempt 状态与模块 4 规则一致。
6. Coordinator 锁检查失败：协调器停止推进而不伪造完成，恢复后继续扫描。
7. 租约过期：回收耗时、回收计数和重试结果可以从指标与日志关联。
8. 数据库连接池耗尽：请求产生明确错误，恢复后连接池和告警自动收敛。

实验不修改业务数据以制造“看起来成功”的结果；使用专用 Workflow ID、临时数据库或测试事务隔离。

## 12. 性能验证设计

### 12.1 规模与对照组

- 单 Run：1,000 个可执行任务，使用模块 4 已验证的 Mock Executor；
- 多 Run：至少 8 个并行 Run，每个 125 个任务，观察跨 Run 队列公平性；
- Worker：1、4、16 三组；
- 轮次：预热 1 轮，正式 5 轮；
- 对照：关闭 Tracing、仅日志、日志加指标、日志加指标加 Tracing 四种观测配置；
- 数据库：Docker Compose 提供的 PostgreSQL 16，记录 CPU、内存、连接池和版本；
- 机器：记录操作系统、CPU、内存、Go 版本、Docker 和 PostgreSQL 版本。

### 12.2 记录指标

正式矩阵每轮记录总耗时、任务吞吐、Claim/Heartbeat/Complete P50/P95/P99、空领取次数、`B/op` 和 `allocs/op`。其中 `B/op` 与 `allocs/op` 是 Go Benchmark 统计的累计分配量和分配次数，不是进程常驻内存。

早期设计曾计划同时记录队列最大深度、租约回收耗时、在线 Worker 数、数据库连接池峰值、进程 CPU、goroutine 数和观测丢弃计数。最终基准直接调用 Repository，以保持 24 组输入一致，没有引入会额外查询数据库的采样器；OpenTelemetry BatchSpanProcessor 也不公开队列丢弃总数。因此这些字段没有进入正式矩阵，不能从现有结果反推。队列、连接池和租约的当前值由 `/metrics` 与故障实验验证，进程资源和导出丢弃量需要后续单独设计采集方法后重新取证。

### 12.3 结论边界

报告只描述本机配置、输入规模和五轮数据，不外推为生产容量或 SLA。当前矩阵比较日志编码、进程内指标更新和 Span 创建、排队、批处理开销，不包含生产 HTTP 中间件、Coordinator 聚合查询、Webhook、网络导出或长期存储成本；不能把混合差值解释成任一组件的独立开销。

## 13. 安全与开源边界

- /metrics 不需要把业务 Token 写入响应；是否要求 viewer 权限沿用控制面现有认证策略，并在 API 文档中明确；
- Webhook URL 只来自本地配置，不写入日志和实验报告；
- Trace、日志和告警默认脱敏，限制单条消息长度；
- 故障注入包不被生产入口导入，不在公开 API 中注册路由；
- 文档只使用公开场景、示例 ID 和虚构错误，不写公司名称、内部 URL、个人路径或真实凭据；
- 依赖增加前执行许可证和供应链检查，记录版本和用途；
- 观测数据不能替代审计事件，也不能绕过既有权限判断。

## 15. 测试与验收矩阵

### 15.1 单元测试

- 日志字段存在、错误字段统一、Token/输入脱敏和长度限制；
- 指标重复注册、指标标签白名单、/metrics 文本格式和无高基数标签；
- Span 父子关系、错误状态、上下文提取和注入；
- 告警触发、持续、去重、恢复、未知输入和 Webhook 超时；
- 故障计划的一次性错误、延迟、取消、关闭和并发隔离。

### 15.2 集成与端到端测试

- HTTP 启动 Run 后，日志、Trace 和指标能关联到 Dispatch、Claim、Complete；
- Worker 强杀、租约过期和数据库短暂失败后，既有状态转换和恢复结果不改变；
- 告警在队列堆积、Worker 全离线和连接池耗尽时触发，恢复后只发送一次 resolved；
- /metrics 和 Webhook 故障不会阻塞状态保存或租约续期；
- 观测配置关闭时，核心业务行为和现有接口兼容。

### 15.3 自动化门禁

模块级完成前必须重新运行：

```bash
go test ./... -count=1
go test -race ./... -count=1
go vet ./...
go doc ./workflow
bash scripts/test-verify-docs.sh

```

真实 PostgreSQL、多进程故障实验和性能基准必须单独记录命令、环境和原始输出。任何实验失败都要先说明真实结果，不能用“日志看起来正常”替代断言。

## 16. 实施顺序

实施仍采用 TDD（Test-Driven Development，测试驱动开发）：先写能复现需求的失败测试，再写最小实现，最后重构和回归。建议拆为以下可独立验证的任务：

1. 观测配置、日志上下文和脱敏；
2. 指标注册器、低基数标签和 /metrics；
3. OpenTelemetry HTTP 与 Worker 上下文传播；
4. Coordinator、Repository、Worker 的统一操作日志和指标；
5. 告警规则、状态机、去重和本地 Webhook；
6. 构造函数级故障注入夹具和单元测试；
7. PostgreSQL、Claim/Complete/Heartbeat、Worker 强杀和锁失效实验；
8. 连接池耗尽、恢复收敛和告警端到端实验；
9. 1/4/16 Worker 观测开关对照基准与资源报告；
10. README、换电脑手册、验证报告和模块 5 学习文章的跨模块复核。

每个任务由自动质量门禁验证；所有任务完成后才进行一次模块级人工审核。任务之间不改变模块 4 的公开状态、租约协议或 Worker 认证边界，除非先更新本文并获得用户确认。

## 17. 模块 5 验收标准

模块 5 只有同时满足以下条件才算完成：

1. 关键日志包含统一字段并通过脱敏测试；
2. /metrics 输出可被 Prometheus 读取，标签无 Run、Task、Attempt、Worker 或 Dispatch ID；
3. 同一次 Claim、Heartbeat 或 Complete 请求的 Worker Client、控制面 HTTP 与 Worker API Span 能通过 W3C Trace Context 关联；异步边界限制已明确记录；
4. 至少五类告警场景完成触发、抑制和恢复验证；
5. 八类故障实验均有可复现命令、状态证据、指标/日志/Trace 证据和限制说明；
6. 1/4/16 Worker、单 Run/多 Run 和四种观测配置基准完成五轮并保留原始结果；
7. 观测组件故障不会改变模块 4 已验证的状态机、租约和结果幂等语义；
8. 全仓测试、竞态检测、静态检查、文档验证和差异检查通过；
9. 本地开发与配置手册能在目标 Mac mini M4 上完成观测和故障演示；
10. 模块 5 学习文章完成模块 0 至模块 5 的术语、递进关系、技术选型和限制复核，并经用户阅读确认后再发布。

## 18. 已知限制

- 本模块的指标和告警只在单控制面、PostgreSQL 和本地多 Worker 范围内验证；
- stdout 或内存 Trace exporter 不能代表生产采集链路的可靠性；
- 进程内告警评估器在控制面完全停止期间不能发送通知，模块 6/7 再评估外部告警组件；
- 指标低基数设计牺牲了按单个 Run 直接聚合的便利，单 Run 诊断必须使用日志、Trace 或数据库查询；
- 故障注入只能覆盖已经设计的注入点，不能证明所有网络、操作系统和数据库故障组合都已覆盖；
- 五轮本机基准用于比较本项目配置变化，不等于云环境或生产环境容量。
