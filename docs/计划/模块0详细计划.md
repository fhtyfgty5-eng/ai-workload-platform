# 模块 0：项目定义与交接基线详细计划

## 1. 计划目的

本计划把[项目路线图](项目路线图.md)中模块 0 的概要要求拆成可以阅读、检查和审核的文档交付物。

模块 0 只负责回答三个问题：

1. 项目要解决什么问题，服务哪些用户；
2. 系统边界、主要组件和技术学习顺序是什么；
3. 新窗口如何根据仓库事实恢复上下文，并判断能否进入模块 1。

本模块不实现工作流引擎、调度器、执行节点或 Agent 适配器。

## 2. 问题背景

一个后台工作经常由多个有先后关系的步骤组成，可能运行几分钟到几小时，也可能在中途失败。只使用脚本、定时器和人工操作时，团队很难准确知道步骤执行到哪里、失败后能否安全恢复，以及多个机器是否会重复执行同一个任务。

本项目要学习并验证一种统一的工作流执行方式：保存任务状态，检查步骤依赖，分配执行机会，处理重试、超时、取消和恢复，并记录执行过程。这里的“工作流”是由多个任务及其依赖关系组成的可执行过程；“编排”是根据依赖和策略安排这些任务何时运行。

## 3. 模块目标

- 让项目价值、目标用户、适用场景和非目标清晰可解释；
- 固化已批准的高层架构和技术学习边界；
- 建立面向零背景读者的术语与技术选型说明；
- 建立新窗口启动、状态交接和文档验证约定；
- 为模块 1 的详细 TDD 计划提供稳定前置条件。

## 4. 已批准范围

模块 0 继承以下已批准内容，不在本计划中重新决策：

- 面向 AI 与数据任务的可靠工作流编排与执行平台；
- 工作流定义、任务依赖、状态持久化、失败处理和执行审计是项目主线；
- 普通程序任务、单 Agent 和多 Agent 都是合法执行方式，多个 Agent 不是默认选项；
- 自然语言只生成需要校验和用户确认的工作流草稿，不能绕过依赖、参数、权限和资源校验；
- 控制面建议使用 Go；执行节点、容器、Kubernetes、真实模型接口和搜索/推荐案例按路线图后续模块推进。

## 5. 非目标

- 不实现任何业务代码或可运行的工作流内核；
- 不安装或接入 PostgreSQL、Redis、Kafka、容器运行时、Kubernetes 或真实模型 API；
- 不实现数据库、消息队列、容器运行时或 Kubernetes 本身；
- 不承诺亿级生产规模、商业化结果、任意恶意代码安全执行或完全替代程序员；
- 不把候选想法直接加入正式功能，不修改 `docs/决策/ADR-0001-项目范围.md`。

## 6. 交付物

### 6.1 项目定义文档

- `README.md`：项目入口、安全边界和核心文档顺序；
- `项目状态.md`：当前阶段、已完成、正在进行、下一步、测试状态和最近交接；
- `docs/产品/产品说明.md`：产品价值、目标用户、适用边界和待验证假设；
- `docs/架构/架构基线.md`：控制面、执行节点、Agent 适配层、状态与事件、可观测性和 Kubernetes 使用边界；
- `docs/决策/ADR-0001-项目范围.md`：项目主线、取舍和未选择方案。

### 6.2 模块 0 专属资料

- 本文件：模块目标、范围、学习内容、验收和验证；
- `docs/学习/文章/模块0-工作流-DAG-状态机与可靠执行基础.md`：面向零背景读者的术语、最小示例、选型比较、失败场景和限制；发布状态统一记录在 `项目状态.md`。
- `scripts/verify-docs.sh`：本地文档基线验证入口；
- `scripts/test-verify-docs.sh`：验证入口的临时目录回归测试。

## 7. 学习资料要求

模块 0 的学习资料必须遵守[学习资料规范](../学习/学习资料规范.md)：

- 先解释问题，再介绍术语和架构；
- 首次出现专业名词时给出英文全称、中文含义和生活类比；
- 解释工作流、任务、依赖、DAG（Directed Acyclic Graph，有向无环图）、Agent、Mock Agent、控制面、执行节点、持久化、重试、幂等和故障恢复；
- 对 Go、本地进程、Mock Agent 和接口隔离说明选择原因，并至少对比两种替代方案；
- 代码示例若出现，必须解释输入、输出、状态和失败路径；
- 区分“了解概念”“能够实现”“能够在面试中解释”三个层次；
- 明确当前文档没有生产规模实验数据，不能把设计假设写成性能结论。

## 8. 文档验证契约

验证命令不依赖外部网络、模型 API 或第三方包：

```bash
bash scripts/test-verify-docs.sh
bash scripts/verify-docs.sh
git diff --check
```

验证结果要求：

- 回归测试覆盖成功基线、缺失必需文件、坏的本地 Markdown 链接和冲突标记；
- `verify-docs.sh` 成功时返回退出码 `0`，失败时返回非零并指出失败文件；
- `git diff --check` 没有空白错误；
- 验证脚本只读检查仓库，不创建、删除或修改项目文件。

在验证脚本完成前，当前已知的手工检查是：README 与启动协议的核心文档引用顺序检查通过，`git diff --check` 通过；这不等同于业务测试通过。

## 9. 验收标准

模块 0 只有在以下条件全部满足且用户明确确认后才算完成：

1. 用户能够用自己的语言说明项目解决的问题、适用场景和不适用场景；
2. README 与启动协议使用一致的阅读顺序；
3. 状态文件能够反映当前 Git 分支、最近提交、未完成工作、验证结果和下一步；
4. 模块 0 详细计划和术语导览能够被没有相关背景的读者独立阅读；
5. 技术选型资料解释了选择原因、至少两种替代方案、代价和更换条件；
6. 文档验证脚本及其回归测试通过；
7. 工作区没有业务代码、外部服务接入或未经批准的范围变化；
8. 用户批准模块 1 的范围，之后才允许编写模块 1 的详细 TDD 计划。

## 10. 待确认问题

- 用户是否认可当前产品主线和非目标；
- 用户是否认可 Go、Mock Agent、本地进程优先的学习顺序；
- 用户是否批准进入模块 1 的单机可靠工作流内核计划。

在这些问题获得确认前，不进入业务实现，也不提交 Git。
