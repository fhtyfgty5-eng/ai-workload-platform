# 模块 2：控制面 API 与持久化存储需求与设计

## 1. 文档目的

本文定义模块 2 的实现边界、接口契约、数据模型、事务语义、恢复方式、测试策略和交付物。模块 2 的目标是将模块 1 的单机可靠工作流内核封装为可被客户端稳定调用的控制面服务，并使用 PostgreSQL 保存工作流定义、运行状态和执行历史。

本文是模块 2 的设计基线。未写入本文或未得到用户明确确认的候选能力，不直接进入实现计划。

## 2. 已确认范围

### 2.1 目标

- 提供版本化 HTTP/REST API 和 OpenAPI 3.1 契约；
- 将工作流定义和运行实例作为两个独立资源；
- 创建工作流时原子地创建第一个不可变版本；
- 创建新版本时调用模块 1 的 `Compile` 校验；
- 异步启动 Run，使用 `Idempotency-Key` 防止网络重试造成重复运行；
- 使用 PostgreSQL 关系表保存 Run、TaskRun、Attempt 和状态事件；
- 通过增量持久化边界复用单套模块 1 Engine；
- 支持查询 Run 摘要、任务详情和事件；Run 可按 Workflow 和状态组合过滤，列表使用键集游标分页；
- 支持取消、服务重启自动恢复和基础身份权限校验；
- 提供配置、迁移、结构化日志、健康检查、Go SDK、最小客户端 CLI 和接口测试；
- 提供可复现的本地开发环境和换电脑检查清单。

### 2.2 明确不做

- 不实现多控制面实例高可用；
- 不实现模块 4 的多 Worker、任务租约和心跳；
- 不执行任意本机 Shell 命令；
- 不调用真实模型，不实现 Agent Runtime；
- 不在第一阶段同时维护 PostgreSQL 和 MySQL 两套存储实现；
- 不提前加入 Redis、Kafka、gRPC、API Gateway 或复杂可观测性平台；
- 不把 Docker Compose 提供的数据库容器描述为任务容器化或安全沙箱；
- 不实现登录、用户注册、OAuth/OIDC 或 Token 签发系统；
- 不提供“自动运行最新版”的隐式版本选择；
- 不保存编译后的内部数组索引作为数据库协议。

## 3. 核心资源模型

### 3.1 Workflow 与版本

Workflow 表示一个逻辑工作流，例如 `document-pipeline`。Workflow 不直接承载可执行任务内容；任务内容属于不可变的版本。

首次创建：

```http
POST /api/v1/workflows
```

该请求在一个事务中完成：

1. 调用模块 1 的 `Compile` 校验完整定义；
2. 创建逻辑 Workflow；
3. 创建 `version=1`；
4. 保存完整定义 JSON、摘要和创建者信息；
5. 保存幂等记录。

后续修改：

```http
POST /api/v1/workflows/{workflow-id}/versions
```

每次修改创建新版本。版本不能原地修改，Run 必须固定关联具体版本。

创建新版本时锁定对应 Workflow 行，在事务中递增 `latest_version` 并插入新版本，避免并发请求生成相同版本号。

### 3.2 Run

Run 是某个确定 Workflow 版本的一次运行实例。启动时 URL 必须明确指定版本：

```http
POST /api/v1/workflows/{workflow-id}/versions/{version}/runs
```

启动请求在数据库事务中先创建 `pending` Run、初始 TaskRun、幂等记录，然后立即返回 `202 Accepted` 和 RunID。后台 Engine 在 HTTP 请求结束后继续执行。

服务进程在数据库提交成功、后台调度尚未开始之间崩溃时，重启恢复会扫描数据库中的非终态 Run 并继续执行。若服务从未重启，该 Run 会保持 `pending`，不会凭空执行。

## 4. 总体架构

```text
HTTP 客户端 / Go SDK / 最小 CLI
               |
               v
        HTTP 路由与中间件
   鉴权、请求 ID、日志、错误转换
               |
               v
          应用服务层
  WorkflowService / RunService
       |                 |
       v                 v
模块 1 Compiler      模块 1 Engine
       |                 |
       v                 v
定义缓存          增量持久化边界
       \                 /
        v               v
         PostgreSQL Repository
```

组件职责：

- **HTTP 层**：解析请求、限制请求体大小、校验 Bearer Token、生成 request ID、转换业务错误。不直接写 SQL，不包含 DAG 调度规则。
- **WorkflowService**：创建 Workflow 和不可变版本，调用 `Compile`，事务提交成功后缓存编译结果。
- **RunService**：处理幂等启动、查询、分页和取消；后台运行不依赖客户端连接。
- **Engine**：继续负责 DAG 调度、状态机、重试、超时、取消和恢复，通过增量变更集保存状态。
- **Repository**：负责 SQL、事务、约束和查询，不决定任务状态转换规则。
- **恢复协调器**：服务启动并取得 PostgreSQL Advisory Lock 后扫描非终态 Run，调用 Engine 恢复。
- **Mock Executor**：提供确定性执行结果和测试故障注入，不执行本机命令或真实模型。
- **Go SDK**：封装 HTTP 调用，供 CLI 和其他 Go 客户端复用。

模块 2 保留单套 Engine。持久化层增加增量变更边界：Engine 每次状态变化生成受影响的 Run、TaskRun、Attempt 和 StateEvent 变更；FileStore 和 PostgreSQL 分别实现对应适配器。禁止为控制面重新实现第二套调度器。

## 5. HTTP API 契约

所有业务接口使用 `/api/v1` 版本前缀。

| 方法与路径 | 权限 | 作用 |
|---|---|---|
| `POST /api/v1/workflows` | operator | 创建 Workflow 和 version=1 |
| `GET /api/v1/workflows` | viewer | 分页查询 Workflow |
| `GET /api/v1/workflows/{id}` | viewer | 查询 Workflow 摘要 |
| `POST /api/v1/workflows/{id}/versions` | operator | 创建不可变新版本 |
| `GET /api/v1/workflows/{id}/versions` | viewer | 分页查询版本 |
| `GET /api/v1/workflows/{id}/versions/{version}` | viewer | 查询完整定义 |
| `POST /api/v1/workflows/{id}/versions/{version}/runs` | operator | 异步启动指定版本 |
| `GET /api/v1/runs` | viewer | 按条件分页查询 Run |
| `GET /api/v1/runs/{run-id}` | viewer | 查询 Run 摘要 |
| `GET /api/v1/runs/{run-id}/tasks` | viewer | 分页查询任务状态 |
| `GET /api/v1/runs/{run-id}/tasks/{task-key}` | viewer | 查询任务和 Attempt |
| `GET /api/v1/runs/{run-id}/events` | viewer | 分页查询状态事件 |
| `POST /api/v1/runs/{run-id}/cancel` | operator | 请求取消 Run |

健康检查：

```http
GET /health/live
GET /health/ready
```

`live` 只表示进程存活；`ready` 只有在数据库连接、迁移版本、Advisory Lock 和全部非终态 Run 已交给后台监督恢复后才成功。它不等待这些 Run 全部到达终态。

`GET /api/v1/runs` 支持可选的 `workflow_id` 和 `status` 组合过滤。Workflow、Version、Run、Task 和 Event 列表使用不透明的键集游标：游标记录上一页末尾的稳定排序键，而不是“跳过多少行”。Run 游标还绑定当前过滤条件，不能换一组过滤条件继续使用。

### 5.1 认证和权限

客户端通过请求头提交 Token：

```http
Authorization: Bearer <token>
```

服务端从环境变量或部署 Secret 读取合法 Token，并将其映射到 `viewer` 或 `operator` 角色。配置式 Bearer Token 不表示服务端凭空授予权限；请求中的 Token 必须与服务端配置匹配。

- 缺少 Token 或 Token 不正确：`401 Unauthorized`；
- Token 正确但角色不足：`403 Forbidden`；
- 健康检查不要求业务 Token；
- Token、密码和 Authorization 请求头不得写入日志、代码或 Git。

模块 2 不实现登录、注册、Token 签发和 OAuth/OIDC；多用户身份系统按需在后续评审。

### 5.2 幂等

创建 Workflow 版本和启动 Run 必须提供 `Idempotency-Key`。相同调用者、相同操作和相同 Key 的相同请求返回第一次创建的资源；相同 Key 对应不同请求内容时返回 `409 Conflict`。取消操作由 RunID 定位，重复取消保持幂等，不额外要求 Key。

统一错误结构：

```json
{
  "error": {
    "code": "workflow_definition_invalid",
    "message": "workflow contains a dependency cycle",
    "request_id": "req_...",
    "details": {}
  }
}
```

`code` 用于程序判断，`message` 用于人阅读，`request_id` 用于关联日志。数据库错误和内部堆栈不能直接返回给客户端。

## 6. 数据模型

### 6.1 工作流定义

```text
workflows
- id
- latest_version
- created_at
- created_by

workflow_versions
- workflow_id
- version
- definition_schema_version
- definition_json
- definition_hash
- created_at
- created_by
```

工作流定义保存为经过 `Compile` 校验的完整 JSON。`definition_schema_version` 用于识别未来格式变化；`definition_hash` 用于一致性检查，不替代幂等 Key。

### 6.2 运行状态

```text
workflow_runs
- run_id
- workflow_id
- workflow_version
- status
- revision
- last_event_sequence
- cancel_requested_at
- created_at
- started_at
- finished_at
- created_by

task_runs
- run_id
- task_key
- task_index
- status
- remaining_dependencies
- ready_at
- finished_at

attempts
- run_id
- task_key
- attempt_number
- status
- started_at
- finished_at
- output
- error_code
- error_message

state_events
- run_id
- sequence
- entity_type
- entity_key
- from_status
- to_status
- reason
- occurred_at
```

Run、TaskRun、Attempt 和事件使用关系表。查询接口按需要组合这些数据，不再每次状态变化重写完整 JSON 快照。

`revision` 在 Run 创建时为 0，此后每次成功状态提交严格加 1，用于乐观并发控制：更新必须携带预期版本，数据库只允许当前版本匹配时写入。`last_event_sequence` 用于事务内分配连续事件序号。时间统一存储 UTC，API 使用 RFC 3339。

表之间使用外键；状态字段使用检查约束；针对外键、状态、创建时间、`ReadyAt` 和事件序号建立必要索引，不为所有字段盲目建索引。

### 6.3 幂等记录

```text
idempotency_records
- principal_id
- operation
- idempotency_key
- request_hash
- resource_type
- resource_id
- resource_version
- created_at
```

`principal_id + operation + idempotency_key` 建立唯一约束。业务对象和幂等记录在同一事务中创建，避免业务对象已经创建但幂等记录丢失。

## 7. 事务、并发和恢复

Engine 为一次状态变化生成候选状态和增量变更集。Repository 在一个 PostgreSQL 事务中：

1. 使用预期 `revision` 更新 WorkflowRun；
2. 更新受影响的 TaskRun；
3. 新增或更新 Attempt；
4. 追加 StateEvent；
5. 分配连续事件序号并提交。

只有事务成功后，Engine 才接受新的内存状态、启动后续任务或解锁下游任务。事务失败时放弃候选状态。

取消请求先持久化 `cancel_requested_at`，再通知进程内 Engine。取消与执行完成竞争时，依靠 revision 和终态判断收敛；取消已经提交但通知 Engine 前服务崩溃时，重启恢复会继续处理取消请求。

数据库故障时：

- 不启动新的 Attempt；
- 不解锁下游任务；
- 中断当前执行器，但不把基础设施中断写成用户取消；
- 保留最后一次成功提交的状态；
- `ready` 变为失败；
- 停止 HTTP 服务并让原进程以错误退出；
- 数据库恢复后由新进程重新检查迁移、取得锁、扫描事实状态，并按至少执行一次语义恢复。

原进程不自动重连或重新取得 Advisory Lock，因为断连后它无法证明期间没有其他进程取得协调权。约束冲突、非法状态和数据损坏同样不能盲目重试。

服务启动顺序：

```text
读取并校验配置
连接 PostgreSQL
检查迁移版本
取得 Advisory Lock
扫描并加载 pending/running/waiting_retry 等非终态 Run
把非终态 Run 异步交给受监督的恢复执行
ready=true
接收业务流量
```

Advisory Lock 是 PostgreSQL 提供的应用级协调锁。模块 2 用它保证同一数据库同时只有一个控制面实例作为执行协调者；第二个实例启动失败，数据库连接断开时锁自动释放。它不是多 Worker 租约，也不提供高可用。

## 8. 配置、迁移和换电脑

### 8.1 本地数据库

仓库提供 `compose.yaml`，只负责启动开发环境中的 PostgreSQL。Go 控制面和工作流任务仍在本机运行：

```text
Go 控制面：本机运行
PostgreSQL：Docker Compose 容器
工作流任务：Mock Executor
```

也允许通过 `DATABASE_URL` 连接已经安装在本机或其他机器上的 PostgreSQL。Docker Compose 不代表任务容器化或安全沙箱。

### 8.2 配置与密钥

提交 `.env.example`，真实 `.env` 加入 `.gitignore`。核心配置包括：

```text
DATABASE_URL
WORKLOAD_HTTP_ADDR
WORKLOAD_VIEWER_TOKEN
WORKLOAD_OPERATOR_TOKEN
WORKLOAD_LOG_LEVEL
WORKLOAD_LOG_FORMAT
```

Token 和数据库密码没有不安全默认值；缺失或格式错误时启动失败。生产环境通过环境变量或部署 Secret 注入。

### 8.3 数据库迁移

迁移是随代码版本管理的 SQL 文件，用于可重复创建或修改表结构。迁移文件提交到 Git，数据库内容不提交。

提供显式迁移命令：启动 PostgreSQL、执行 `migrate up`、启动控制面。控制面启动时检查迁移版本，不默认修改生产数据库；版本不匹配时保持 `ready=false` 并提示执行迁移。

### 8.4 换电脑检查清单

README 提供最短启动步骤，`docs/部署/本地开发与配置.md` 提供完整说明：

1. 安装指定版本的 Go 和 Docker；
2. 克隆仓库；
3. 从 `.env.example` 创建本地配置；
4. 在新电脑重新生成 Token；
5. 启动 PostgreSQL；
6. 执行数据库迁移；
7. 启动服务并检查 `live`、`ready`；
8. 运行接口测试或演示工作流。

工作流定义、迁移脚本和代码来自 Git；Token、数据库密码、数据库内容、日志、临时数据和本机数据目录不来自 Git。需要保留个人测试数据时使用 PostgreSQL 备份与恢复工具，不复制公司数据、内部配置或密钥。

## 9. 服务、SDK 和 CLI

建议提供两个可执行程序：

```text
workload-server
负责迁移检查、启动 HTTP 控制面和后台恢复

workload
作为客户端调用控制面，同时保留模块 1 本地模式
```

命令结构：

```bash
workload local run examples/document-pipeline.json
workload local status <run-id>
workload workflow create <definition.json>
workload workflow add-version <workflow-id> <definition.json>
workload run start <workflow-id> --version 2 --idempotency-key <key>
workload run status <run-id>
workload run cancel <run-id>
```

现有本地能力移动到 `local` 命名空间，避免与 HTTP 控制面模式混淆。

SDK（Software Development Kit，软件开发工具包）是供其他 Go 程序调用控制面的客户端库。它封装 HTTP、Bearer Token、幂等 Key、JSON、错误和分页；CLI 复用 SDK，不重复实现 HTTP 请求。SDK 不执行工作流，也不是另一个服务。

SDK 第一阶段手写，不提交大量自动生成代码。OpenAPI 负责契约描述和一致性测试；未来有多语言客户端需求时，再评估生成客户端。

SDK 不默认自动重试写请求。调用方需要重试时必须复用同一个幂等 Key，避免隐藏网络故障或产生不可预期的业务操作。

## 10. 测试和可观测性

### 10.1 测试分层

- **单元测试**：请求解析、严格 JSON、认证、权限、错误、游标、幂等判断、服务层规则和 Engine 行为；
- **Repository 集成测试**：真实 PostgreSQL 迁移、约束、事务、并发版本、幂等、revision、Advisory Lock 和恢复；
- **HTTP 接口测试**：真实 Handler、OpenAPI 路径、状态码、错误结构、鉴权、分页、取消和数据库故障；
- **端到端测试**：创建 v1、启动 Run、查询、重复请求、创建 v2、取消、重启和自动恢复。

默认执行器为 Mock Executor，测试不依赖真实模型、外部网络或本机命令。

### 10.2 可观测性

模块 2 实现最小可观测能力：

- 结构化 JSON 日志；
- 每个 HTTP 请求的 `request_id`；
- 日志包含 WorkflowID、Version、RunID、TaskKey、AttemptNumber 和错误码；
- 隐藏 Token、数据库密码和 Authorization 请求头；
- `live`、`ready` 健康检查；

请求数、错误数、运行终态数量、恢复数量、Prometheus、OpenTelemetry、完整调用链和指标面板统一属于模块 5，不在模块 2 提前增加没有明确消费方的计数接口。

### 11.1 交付物

- 控制面 Go 服务；
- PostgreSQL Repository、迁移和集成测试；
- 版本化 HTTP/REST API；
- OpenAPI 契约；
- Go SDK 和最小客户端 CLI；
- Mock Executor 控制面接入；
- 配置、健康检查、结构化日志和恢复协调器；
- 按设计与概念、实现与验证两个阶段积累的模块 2 学习资料；
- `docs/部署/本地开发与配置.md`；
- 模块 2 验证报告。

### 11.2 验收标准

- 客户端通过版本化 HTTP API 创建工作流版本；
- 创建和新版本提交经过模块 1 `Compile` 校验；
- Run 异步启动且必须幂等；
- Run、TaskRun、Attempt 和事件使用 PostgreSQL 关系表保存；
- 重复请求不会创建重复版本或重复 Run；
- `viewer/operator` 权限有效；
- 取消请求可恢复；
- 控制面重启后自动恢复非终态 Run；
- 数据库或 Advisory Lock 运行期失效时，原进程停止接收流量并安全退出，重启后再恢复非终态 Run；
- 第二个控制面实例无法取得 Advisory Lock；
- Workflow、Version、Run、Task 和事件列表支持键集游标分页，Run 支持 Workflow 与状态过滤；
- OpenAPI 3.1、README、换电脑文档和测试齐全；
- `go test ./...`、`go test -race ./...`、`go vet ./...`、数据库集成测试和文档验证通过；
- 性能结论来自模块 2 的实际实验，不把模块 1 基线直接当作模块 2 性能承诺。

## 12. 文档与开源边界

模块 2 的学习笔记面向没有相关背景的读者，首次出现的 HTTP、REST、OpenAPI、事务、索引、幂等、乐观并发控制、数据库迁移、Advisory Lock、SDK 等术语必须解释，并说明为什么选择 PostgreSQL、为什么不同时维护 MySQL、为什么 Docker Compose 只负责开发数据库。

可直接发布博客的技术学习文章统一放在 `docs/学习/文章/`，发布前仍需经过内容审核、事实验证和用户确认。设计文档、部署文档、OpenAPI 文件和实验报告不自动视为博客文章。

“设计与概念、实现与验证”是学习资料的形成阶段，不预设模块 2 必须发布两篇文章。模块验收时根据主题是否独立、篇幅和真实实现证据决定合并为一篇、拆分为多篇或暂不发布；发布顺序还必须服从 `项目状态.md` 中已经确认的文章队列。

仓库不得包含 Token、密码、公司代码、业务数据、内部配置或其他保密信息。模块 2 的未来能力、性能目标和产品优势在证据产生前必须标为计划或待验证假设。
