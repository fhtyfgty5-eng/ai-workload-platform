# 项目路线图

## 1. 路线目标

项目按模块 0 至模块 7 共 8 个模块推进，逐步构建一个面向 Agent 与确定性程序任务的可靠运行时和调度平台。

模块数量只是交付边界，不是产品价值。每个模块都必须产生可以运行、测试和解释的增量，不能仅完成文档或接入一个新技术名词。

## 2. 执行原则

- 每个模块先确认需求边界，再补充必要的学习资料和实施计划；
- 行为变更默认使用测试驱动开发，即先写失败测试，再实现最小代码使测试通过；
- 每个子模块完成后暂停，等待用户人工审核；
- 未获得用户批准，不进入下一子模块或下一模块；
- 每个模块至少提供可运行入口、自动化测试、失败场景、性能或资源证据、架构取舍和 README 示例；
- 概念学习篇可以在实现前编写，模块实践篇只能基于已经发生的代码、测试和实验；
- 性能验证从模块 1 开始持续执行，不等到后期统一补做；
- 默认测试不访问外部网络，不依赖付费模型 API；
- 不自动提交 Git，不自动创建 Pull Request，不自动公开仓库。
- 传统后端公共能力作为横向底座按模块补齐，不为了覆盖技术名词提前堆叠组件。

## 3. 模块路线

### 模块 0：项目定义与文档基线

**目标：** 明确产品问题、目标用户、范围、架构、术语、学习资料规范和低成本验证方式。

**状态：** 已完成。

**关键交付物：**

- 产品说明、架构基线和范围决策；
- 学习资料规范和项目路线图；
- 新窗口交接协议和文档验证工具；
- 项目总览与可靠执行基础文章。

**验收证据：** 用户能够说明项目解决的问题；核心文档和链接通过自动检查；模块 1 范围获得批准。

### 模块 1：单机可靠工作流内核

**目标：** 不依赖容器、网络服务和真实模型，实现任务定义、DAG 编译、状态转换、依赖解锁、重试、超时、取消和进程重启恢复。

**关键交付物：**

- Go 内核公开接口和命令行入口；
- Mock Executor 和文件持久化实现；
- 状态机、调度器、存储和恢复测试；
- 10,000 个任务、1,000 个活跃运行实例等目标规模的基准结果。

**验收证据：** 示例工作流可在本机运行；失败、超时、取消和重启场景可自动复现；基准测试记录环境、输入和原始结果。

### 模块 2：控制面 API 与持久化存储

**目标：** 将单机内核封装为可被客户端稳定调用的控制面服务，并使用事务型数据库保存定义、运行状态和执行历史。

**关键交付物：**

- 创建工作流、启动运行、查询状态和取消运行的版本化 HTTP/REST/OpenAPI API；
- PostgreSQL 第一实现、数据库迁移、事务与索引验证和幂等提交；
- 基础身份与权限校验、配置管理、结构化日志、健康检查和接口测试；
- Go SDK 或最小客户端；
- 并发请求、事务失败、服务重启和数据迁移测试。

**验收证据：** 客户端不直接访问内部存储；重复请求不会意外创建多次运行；控制面重启后可从数据库恢复。

PostgreSQL 是模块 2 的第一实现，不代表拒绝 MySQL。两者都属于可行的事务型关系数据库；具体比较、保持 SQL 可移植性的边界和不同时实现两套数据库的原因，记录在架构基线中。

### 模块 3：Agent Runtime、模型与工具执行

**目标：** 在可靠工作流内核之上建立 Agent 的执行边界，同时保持普通程序任务是一等能力，并完成自然语言到结构化工作流草稿的最小产品演示。

**关键交付物：**

- 统一的 Agent 执行请求、结果和事件协议；
- Mock 模型、至少一个合法模型适配器和工具调用接口；
- 上下文、预算、超时、取消、人工审批和审计边界；
- 自然语言目标到结构化工作流草稿的转换；
- 用户事实、Agent 假设和待确认问题的标记；
- 依赖、参数、权限和资源校验，以及用户修改和确认流程；
- 单 Agent 流程示例；多 Agent 协作只有在真实场景证明职责隔离或并行协作有明确收益后再单独评审。

**验收证据：** 默认自动化测试只使用 Mock Model（模拟模型，用固定结果模拟模型响应）；真实模型测试低并发、人工触发且有预算限制；自然语言草稿经过校验和用户确认后才能提交；工具权限、用户拒绝、模型超时和校验失败路径可复现。

自然语言生成工作流草稿是本模块的必做最小演示能力，但不是模块 1 或模块 2 的前置条件。模块 7 负责把这条流程接入控制台并完善用户体验，不重复实现内核校验。

### 模块 4：多 Worker、租约、心跳与故障恢复

**目标：** 支持多个执行节点并发领取任务，并在节点失联、重复上报和网络超时下维持可解释的执行语义。

**关键交付物：**

- Worker 注册、能力描述、心跳和优雅退出；
- 任务租约、续约、过期回收和重新分配；
- 并发限制、基础公平性和背压；
- 多进程故障测试。

租约是带有效期的任务占用权。Worker 只有在租约有效时才能代表当前执行者更新任务结果，从而降低失联节点和新节点同时提交结果的冲突风险。

**验收证据：** 杀死 Worker 后任务不会静默丢失；过期结果不会覆盖新结果；重复执行边界和幂等要求有明确记录。

### 模块 5：可观测性、故障注入与性能验证

**目标：** 让维护者能够回答任务在哪里、为什么失败、恢复是否成功以及系统容量边界在哪里。

**关键交付物：**

- 结构化日志、指标和分布式调用链；
- 运行、任务、Attempt 和 Worker 的诊断视图；
- 告警规则和至少一个可验证的通知出口；
- 可重复的存储失败、进程退出、网络延迟和租约过期实验；
- 持续基准、资源使用和性能回归报告。

告警是系统在指标、状态或错误满足预设条件时主动产生的通知。模块 5 只验证告警规则、抑制重复通知和一个本地或测试通知出口，不自研完整短信、邮件或即时通信平台。

**验收证据：** 每个故障实验有注入步骤、预期行为和实际结果；关键执行链可以关联；告警能在满足条件时触发、恢复后关闭且不会无限重复；性能结论来自可复现数据。

### 模块 6：受限执行环境与 Kubernetes

**目标：** 在明确的安全边界内运行任务，并验证控制面和 Worker 在本地 Kubernetes 集群中的部署与恢复。

**关键交付物：**

- 基于 Docker/Compose 的可复现本地运行环境和合法容器运行时执行器；
- CPU、内存、临时存储、超时和网络访问限制；
- 本地 Kubernetes 部署清单；
- Pod 重启、节点不可用和资源耗尽实验；
- 威胁模型与安全限制说明。

**验收证据：** 资源限制和权限拒绝可以复现；Pod 或节点故障不会绕过工作流恢复规则；文档不把容器描述为绝对安全沙箱。

是否引入 Rust 必须在本模块开始前单独评审，不是既定要求。

### 模块 7：真实场景、最小控制台与开源发布

**目标：** 用真实但不包含公司信息的公开场景验证产品价值，并让新用户能够独立安装、运行和理解项目。

**关键交付物：**

- 至少一个同时体现 Agent 与确定性任务的端到端场景；
- 一个用于查看运行、任务、日志和人工审批的最小控制台；
- 稳定的 API/SDK、快速开始、示例和升级说明；
- GitHub Actions 等 CI/CD 检查，覆盖格式化、自动化测试、文档验证和发布前检查；
- 许可证、贡献指南、安全策略、行为准则和变更记录；
- 发布前安全、依赖许可证、性能和故障报告。

**验收证据：** 新环境可以按照 README 完成部署和示例；公开内容不包含密钥、公司代码、业务数据或本机路径；项目优势和限制均由真实实验支撑。

## 4. 跨模块持续要求

以下工作不会推迟到某个后期模块才开始：

- **性能：** 模块 1 建立基线，此后重要路径变更都运行相关基准；
- **安全：** 从输入校验和敏感信息检查开始，模块 3 增加工具权限，模块 6 完成系统化威胁模型；
- **可观测性：** 前期保留最小结构化事件，模块 5 建成完整日志、指标和调用链；
- **开源：** 从现在起避免本机绝对路径和内部信息，模块 7 完成发布治理与公开检查；
- **学习资料：** 只在进入相关模块前展开，首次出现的专业名词必须解释，技术选型必须说明未选择同类方案的原因。
- **公共后端底座：** 模块 2 补齐 HTTP/REST/OpenAPI、SQL 事务、索引、迁移、幂等、配置、日志、健康检查和接口测试；模块 6 先完成 Docker/Compose，再进入 Kubernetes。
- **条件引入：** Redis、Kafka、对象存储、OAuth/OIDC、gRPC、Elasticsearch 和 API Gateway 只有在真实需求、故障实验或部署边界出现后才单独评审。

## 5. 变更控制

新增模块或改变模块顺序前，必须回答：

1. 它解决哪个已经出现的问题；
2. 为什么不能放入现有模块；
3. 对当前接口、测试、学习资料和完成时间有什么影响；
4. 哪些已有内容会被替代；
5. 如何通过代码或实验验收。

范围变化获得用户批准后，先增加或更新 ADR，再修改路线图和实施计划。
